## 2020/21 · Q3(d) [25 marks] and 2021/22 · Q2(b) [25 marks]
> **Questions:** Discuss the time components involved in accessing a disk block? (2020/21) · Explain the terms *seek time*, *rotational delay*, and *transfer time*. (2021/22)

### Expected answer
To read or write a block given its address, the time is
$$\text{block access time} = s + rd + btt$$
1. **Seek time ($s$):** the time for the **actuator to move the read/write head** to the correct **track (cylinder)**. Mechanical; depends on the distance moved; typically 5–10 ms (desktops) or 3–8 ms (servers). Manufacturers quote an average.
2. **Rotational delay / latency ($rd$):** once on the track, the time waiting for the **required block to rotate under the head**. On average **half a revolution**: $rd = \tfrac12 \times \tfrac{60{,}000}{p}$ ms for $p$ rpm (e.g. 7,200 rpm → 4.17 ms). Inversely proportional to rotation speed.
3. **Block transfer time ($btt$):** time for the block's data to pass under the head and be transferred: $btt = B/tr$, where $tr$ (bytes/ms) = track size ÷ revolution time. Usually much smaller than $s$ and $rd$.
(Optionally: controller/command overhead; when reading consecutive blocks, the **bulk transfer rate** $btr = \frac{B}{B+G}tr$ accounts for interblock gaps.)

**Point to stress:** $s$ and $rd$ dominate, so reading **consecutive blocks** on the same track/cylinder (paying $s + rd$ once: $s + rd + k \cdot btt$) is far cheaper than $k$ random blocks ($k(s + rd + btt)$).

### Key points to include
Definition of each term, cause (arm movement / rotation / data passing head), typical magnitude, formula, total access time, consecutive vs random.

### How to approach
Three labelled paragraphs + the formula + one numeric illustration (e.g. 2400 rpm → rd = 12.5 ms).

## 2022/23 · Q1(a) [25 marks] and 2023/24 · Q1(a) [25 marks]
> **Questions:** Explain the key factors that influence disk performance, providing real-world examples where they may impact the overall system performance. (2022/23) · Explain how disk-related factors can cause slow query responses even when CPU and memory are sufficient. (2023/24)

### Expected answer
**Factors**
| Factor | Effect | Real-world impact |
|---|---|---|
| Seek time | arm movement on every random access | OLTP systems (banking, ticket booking) doing many random lookups become I/O-bound |
| Rotational speed (rpm) | lower rpm → higher $rd$, lower $tr$ | a 5,400 rpm disk ($rd$ 5.6 ms) vs 15,000 rpm ($rd$ 2 ms) |
| Transfer rate and block size | small blocks → more requests; low $tr$ → slow scans | report queries scanning whole tables |
| Data placement / fragmentation | scattered blocks pay $s + rd$ each time | a fragmented table makes a full scan 30× slower (Tutorial 1: 3.2 s vs 109 s) |
| Access pattern (random vs sequential) | random I/O ~10–40 ms per block vs ~1 ms sequential | non-clustered index range scans |
| Buffering / caching | too few buffers → repeated reads | buffer pool smaller than working set |
| Concurrency / queueing | many requests on one disk | month-end batch jobs slow everyone |
| RAID level / redundancy | parity writes slower | write-heavy logs on RAID 5 |
| Interblock gaps | reduce useful bandwidth | |

**Why queries are slow with sufficient CPU and memory (2023/24):** the query is **I/O-bound**. The CPU waits idle while the disk performs mechanical seeks and rotations (milliseconds each, about a million times slower than memory). Typical causes: full table scans because of missing indexes; non-clustered index access causing **random I/O per row**; **fragmented/non-contiguous** files; data not in the buffer pool; contention from many concurrent requests; RAID parity overhead. **Remedies:** suitable (clustered) indexes, contiguous allocation and clustering, larger blocks/prefetching, **double buffering** and caching, SSDs, RAID 0/10 striping, query optimization.

### Key points to include
At least 4–5 factors, each with **mechanism + example**; explicitly say "I/O-bound, CPU idle waiting for disk" for 2023/24; finish with remedies.

### How to approach
A table or a list of factors with examples. Use numbers from the formulas to show scale.

## 2022/23 · Q1(c) [25 marks]
> **Question:** A system is using a hard disk with: rotational speed of 7200 RPM, average seek time of 8 ms and average disk latency of 4.17 ms (calculated from the RPM). Calculate the average time required to complete a disk operation that involves both seeking and latency.

### Expected answer
1. Check latency: one revolution $= 60{,}000/7200 = 8.33$ ms → average latency $= 8.33/2 = 4.17$ ms ✓.
2. Average time (seek + latency):
$$t = s + rd = 8 + 4.17 = \mathbf{12.17\ ms}$$
(If a transfer time were given, it would be added: $s + rd + btt$.)

### Key points to include
Formula, the rpm → latency derivation, units, final answer.

## 2023/24 · Q1(c) [25 marks]
> **Question:** 7200 RPM; average seek time 9 ms; average rotational latency half of a full rotation; data transfer rate 120 MB/s; block size to be read 64 KB. Assuming command processing overlaps with seek time, calculate the average time to complete a single disk read operation, given that data transfer starts only after seek and rotational latency.

### Expected answer
1. **Seek:** $s = 9$ ms (command processing overlaps with it, so it adds nothing).
2. **Rotational latency:** one revolution $= 60{,}000/7200 = 8.33$ ms → $rd = 8.33/2 = \mathbf{4.17\ ms}$.
3. **Transfer time:** $btt = \dfrac{64\ \text{KB}}{120\ \text{MB/s}}$.
   - With 64 KB = 65,536 bytes and 120 MB/s = 120,000,000 bytes/s: $65{,}536/120{,}000{,}000\ \text{s} = 0.000546\ \text{s} = \mathbf{0.55\ ms}$.
   - (Same base for both, $64/(120 \times 1024)$ s = 0.52 ms; decimal KB, 0.53 ms.)
4. **Total** (transfer starts only after seek and latency, so the three add):
$$t = 9 + 4.17 + 0.55 \approx \mathbf{13.7\ ms}$$

### Key points to include
State the unit convention; show $rd$ derivation; explain why command overhead is not added (overlap); sum the three parts.

### How to approach
Write the formula $t = s + rd + btt$ first, compute each term on its own line, then add. ~5 lines.
