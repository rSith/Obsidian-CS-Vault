# PP 01.4 · Records (Fixed/Variable, Spanned/Unspanned) and File Calculations

> [!info] [[PP 01 - Data Storage and File Organization|PP 01 index]] · Lessons: [[01.05 Records, Blocking and File Allocation]], [[01.12 Worked File and Disk Calculations]] · Tutorial: [[TUT 1 - Disk and File Calculations]]

## 2020/21 · Q3(a) [25 marks]
> **Question:** Differentiate between fixed length records and variable length records in a file.

### Expected answer
- **Fixed-length records:** every record in the file has **exactly the same size** (e.g. EMPLOYEE record of 71 bytes in the lecture). Each field has a fixed length and a **fixed position (offset)** within the record, so programs can locate any field directly, and record *i* is at a computable position. May **waste space** when values are shorter than the reserved length or optional fields are empty. Blocking factor $bfr = \lfloor B/R\rfloor$ exactly.
- **Variable-length records:** records in the file have **different sizes**. Reasons: (1) **variable-length fields** (e.g. Name), (2) **repeating fields/groups** (several phone numbers), (3) **optional fields**, (4) **mixed files** containing different record types (e.g. STUDENT followed by its GRADE_REPORT records). To parse them, the system needs **separator characters** or **length fields** (or ⟨field name, value⟩ pairs). They use space efficiently but are harder to locate, update in place (a longer value may not fit) and block ($bfr$ is an average).

| | Fixed | Variable |
|---|---|---|
| Size | same | differs |
| Field location | fixed offsets | separators / length prefixes |
| Space | may be wasted | efficient |
| Access/update | simple, in place | complex, records may move |

### Key points to include
Definitions, the four reasons, how fields are located, pros/cons; a small diagram of each record layout earns marks.

## 2020/21 · Q3(b) [25 marks]
> **Question:** What do you mean by spanned and unspanned organization of records?

### Expected answer
Records must be stored in **blocks** (the unit of transfer). **Blocking factor** $bfr = \lfloor B/R \rfloor$.
- **Unspanned:** records are **not allowed to cross block boundaries**; each record lies entirely within one block. The leftover space $B - bfr \cdot R$ per block is **wasted**. Used with **fixed-length records when $B > R$**, because each record starts at a known position in the block, making processing simple.
- **Spanned:** to use that leftover space, **part of a record is stored at the end of one block and the rest in another block**; a **pointer** at the end of the first block points to the block holding the remainder (if it is not the next consecutive block). **Required when a record is larger than a block**; useful for variable-length records with a large average size. $bfr$ then means the average number of records per block.
```text
Unspanned: | R1 | R2 | R3 | (unused) |   | R4 | R5 | R6 | (unused) |
Spanned:   | R1 | R2 | R3 | R4(part)→ |   |(rest)R4 | R5 | R6 | R7(part)→|
```
Number of blocks in both cases: $b = \lceil r/bfr \rceil$.

### Key points to include
Definitions, the pointer, when each is used/required, wasted-space formula, diagram.

## 2021/22 · Q6(a)–(e) [5 × 20 marks] (= Tutorial 1 Q2)
> **Question:** A file has r = 20,000 STUDENT records of fixed length. Fields: Name (30), Ssn (9), Address (40), PHONE (10), Birthdate (8), Sex (1), Major_dept_code (4), Minor_dept_code (4), Class_code (4, integer), Degree_program (3). An additional byte is used as a deletion marker. Disk: B = 512 bytes; G = 128 bytes; 20 blocks per track; 400 tracks per surface; 15 double-sided disks.
> (a) record size R; (b) bfr and b (unspanned); (c) average linear search time, contiguous + double buffering; (d) average linear search time, not contiguous; (e) binary search time on Ssn.

> [!warning] Assumption needed
> The paper gives no rpm or seek time. State: "assume 2400 rpm and average seek time 30 ms (the disk of Tutorial 1)". Then $rd = 12.5$ ms, $tr = 12{,}800/25 = 512$ bytes/ms, $btt = 1$ ms, $btr = \frac{512}{640}\times512 = 409.6$ bytes/ms.

### Expected answer
**(a)** $R = 30+9+40+10+8+1+4+4+4+3+1 = \mathbf{114}$ bytes.

**(b)** $bfr = \lfloor 512/114 \rfloor = \mathbf{4}$ records/block; $b = \lceil 20{,}000/4 \rceil = \mathbf{5{,}000}$ blocks.

**(c)** Average linear search reads $b/2 = 2{,}500$ blocks; contiguous + double buffering → one seek and one rotational delay:
$$s + rd + 2500 \times \frac{B}{btr} = 30 + 12.5 + 2500 \times 1.25 = \mathbf{3{,}167.5\ ms}$$
(or $30 + 12.5 + 2500 \times 1 = 2{,}542.5$ ms using $btt$)

**(d)** Not contiguous → each block is a random access:
$$2500 \times (30 + 12.5 + 1) = 2500 \times 43.5 = \mathbf{108{,}750\ ms} \approx 108.75\ \text{s}$$

**(e)** Binary search: $\lceil \log_2 5000 \rceil = 13$ block accesses, each random:
$$13 \times 43.5 = \mathbf{565.5\ ms}$$

### Key points to include
Formula before each number; deletion-marker byte; floor/ceiling; "average = b/2"; why contiguous+double buffering pays $s + rd$ once; random access cost per binary-search probe.

### How to approach
Present as a calculation table; carry the disk parameters at the top. All five parts take about one page.
