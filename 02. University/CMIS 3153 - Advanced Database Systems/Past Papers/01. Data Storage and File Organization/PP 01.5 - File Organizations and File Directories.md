## 2022/23 · Q1(d) [25 marks] and 2023/24 · Q1(d) [25 marks]
> **Questions:** A company is maintaining an employee database that stores employee records consisting of the fields Employee ID, Name, Department, and Salary. The company expects frequent updates to the records based on employee promotions and department changes. Discuss the pros and cons of using sequential file organization versus indexed file organization for this database. (2022/23) · Discuss the suitability of sequential versus indexed file organization for frequently updated records. (2023/24)

### Expected answer
**Sequential (sorted/ordered) file organization:** records are stored **physically in order** of a key (e.g. Employee ID).
- **Pros:** reading all records in key order needs no sorting (good for payroll runs and reports); next record usually in the same block; **binary search** on the key ($\log_2 b$ block accesses); **range queries** on the key are efficient (records contiguous); no index storage.
- **Cons:** **insertion is expensive**: find the position and shift on average **half the records** (half the blocks read and rewritten); deletion leaves gaps (deletion markers + periodic **reorganization**); **modifying the ordering field moves the record**; searches on **non-ordering fields** (Department, Name) need a **linear search** ($b/2$ blocks); usually requires an **overflow file** merged periodically.

**Indexed file organization:** a data file plus one or more **indexes** (ideally a **dynamic B+-tree**) on the key, and possibly secondary indexes (e.g. Department).
- **Pros:** fast direct access by key (index height + 1 I/O, ~3–4); **secondary indexes** give fast access by Department/Name; **B+-trees absorb inserts and deletes locally** (split/merge) without reorganizing the file; range queries via linked leaves; scales to large files.
- **Cons:** **index maintenance overhead** on every insert/delete and on updates of indexed fields (e.g. a department change updates the Department index); extra **storage**; ordered full scans are slower if the index is non-clustered; more complex.

**Applying to the scenario:** promotions change **Salary**, transfers change **Department**, both **non-key** fields; staff join and leave. With a sequential file each update needs a search (binary only on Employee ID; linear otherwise), and inserts/deletes need shifting or overflow handling. With an indexed organization the record is found via the index and updated **in place** (if fixed-length), and only the affected index entries change.

**Conclusion:** for **frequently updated** records and random lookups, **indexed organization (B+-tree on Employee ID, plus a secondary index on Department if queried)** is more suitable. Sequential organization fits **batch-oriented** processing in key order with infrequent, batched updates.

### Key points to include
Define both; pros/cons table; link to scenario (salary/department = non-key updates; inserts/deletes); dynamic index; conclusion with justification.

### How to approach
Two-column pros/cons table + a scenario paragraph + a clear recommendation. Mention **overflow file / reorganization** and **index maintenance** as the key costs.

## 2022/23 · Q7(d) [short note, 25 marks]
> **Question:** The Role of File Directories in file organization.

> [!warning] No dedicated lecture section

The answer combines lecture material on **file headers/descriptors** (L1 §5.3.5), **file organization vs access method** (§6), the **bucket table in the file header** for hashing (§7.3) and the **directory of extendible hashing** (§7.3.1.2), with the general textbook meaning of a directory. This information could not be fully verified from the available course materials.

### Expected answer
A **file directory** (catalogue) is the structure the operating system/DBMS keeps that **maps each file's name to the information needed to find and use the file**, chiefly its **file header (file descriptor)**.

**What it/the header records**
- the file name, type, size, owner/permissions, creation date (directory entry);
- the **disk addresses of the file's blocks**: first/last block (for heap inserts), linked block pointers, extents, or an index of blocks (indexed allocation);
- **record format**: field lengths and order (fixed-length), field type codes, separators and record type codes (variable-length);
- organization-specific data, e.g. the **bucket-number → block-address table** of a hashed file.

**Role in file organization**
1. **Locating files and blocks:** programs use the directory/header to find where the blocks are, whatever the allocation method (contiguous, linked, clustered, indexed).
2. **Interpreting records:** the format description lets programs parse records in buffers.
3. **Supporting access methods:** Open reads the header; Insert in a heap uses the last-block address; hashing maps bucket numbers to blocks; indexes are themselves located via the directory.
4. **Dynamic organizations:** in **extendible hashing**, a **directory** of $2^d$ bucket pointers (global depth $d$) lets the file grow by splitting buckets and doubling the directory, without rehashing everything.
5. **Space management:** free blocks/free-space information.
6. **Security and sharing:** permissions; in distributed systems a **distributed directory/catalog** tracks where fragments and replicas live ([[05.03 Transparency, Autonomy and Reliability]]).
Without directories/headers, the only way to find a record would be a **linear search** of every block.
