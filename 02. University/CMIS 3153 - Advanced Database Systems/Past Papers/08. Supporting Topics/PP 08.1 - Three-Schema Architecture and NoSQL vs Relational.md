## 2021/22 · Q4(a) [25 marks]
> **Question:** Describe the three-schema architecture for database management systems and explain how it supports different forms of data independence.

### Expected answer
The **three-schema (ANSI/SPARC) architecture** separates user applications from the physical database by describing the database at three levels:
```text
External level:   [view 1]  [view 2]  …  [view n]      ← user/application views
                       └── external/conceptual mappings ──┘
Conceptual level:        [ conceptual schema ]          ← whole DB: entities, types, relationships, constraints
                              │ conceptual/internal mapping
Internal level:          [ internal schema ]            ← storage structures, file organizations, indexes
                              │
                       stored database on disk
```
1. **Internal level:** the **internal schema** describes the **physical storage**: record formats, file organizations (heap, sorted, hashed), indexes, blocking, access paths.
2. **Conceptual level:** the **conceptual schema** describes the **structure of the whole database for all users**: entities/relations, attributes, data types, relationships, constraints, operations; hides storage details.
3. **External (view) level:** **external schemas (user views)** describe the part of the database each user group needs and hide the rest (e.g. a view of only Name and GPA for the exam office).
The DBMS uses **mappings** between levels to transform requests and results.

**Data independence** = the capacity to change the schema at one level **without changing the schema at the next higher level** (only the mapping changes):
- **Logical data independence:** change the **conceptual schema** (add a column or table, split a table, add constraints) without changing **external schemas** or application programs; the external/conceptual mapping is updated (e.g. view definitions). Harder to achieve.
- **Physical data independence:** change the **internal schema** (add/drop an index, change file organization, move files, change block size or storage device) without changing the **conceptual schema** and therefore without changing applications; only the conceptual/internal mapping changes. Easier and very common (e.g. the optimizer starts using a new index transparently).

**How the architecture supports it:** because each level is defined separately and connected only by mappings, changes are **absorbed by the mappings**; applications written against external schemas are insulated. Cost: mapping overhead at run time.

## 2022/23 · Q7(b) [short note, 25 marks]
> **Question:** NoSQL vs. Relational Databases: when to choose one over the other.

### Expected answer
**Relational databases:** data in **tables** with a **fixed schema**, relationships via keys/foreign keys, **SQL** queries with joins, **ACID** transactions and strong consistency; mature tools (MySQL, PostgreSQL, Oracle). Scale mainly **vertically** (bigger server); horizontal scaling (sharding) is harder.
**NoSQL databases:** non-relational stores designed for **horizontal scaling**, **flexible schemas** and very large, fast-changing data: **key-value** (Redis, DynamoDB), **document** (MongoDB, Couchbase), **wide-column** (Cassandra, HBase), **graph** (Neo4j). Often favour **availability and partition tolerance** with **eventual consistency** (BASE), built-in replication and sharding; limited joins; product-specific query APIs.

| Criterion | Relational | NoSQL |
|---|---|---|
| Schema | fixed, structured | flexible / schema-less |
| Consistency | strong ACID | often eventual (tunable) |
| Scaling | vertical (mainly) | horizontal across commodity nodes |
| Queries | complex SQL, joins, ad-hoc reporting | simple key/document access; limited joins |
| Typical CAP choice | consistency | availability (AP) or CP depending on product |
| Best for | transactions, integrity | big data, high throughput, varied data |

**Choose relational when:** data is structured with important relationships; **transactions and consistency** are critical (banking, payments, inventory, student records, ERP); complex queries/reports and joins are needed; schema is stable.
**Choose NoSQL when:** massive volume/traffic needing **horizontal scaling** (social media, IoT, logs, clickstreams); **semi-structured or evolving** data (JSON product catalogues, user profiles); **high availability and low latency** matter more than immediate consistency (lecture: eventual consistency acceptable for social media/e-commerce); simple access patterns or graph traversals.
**Often both (polyglot persistence):** e.g. orders and payments in an RDBMS, catalogue in a document store, sessions in a key-value store, recommendations in a graph DB (lecture L5 §2: combining relational for structured data with NoSQL for unstructured data).
