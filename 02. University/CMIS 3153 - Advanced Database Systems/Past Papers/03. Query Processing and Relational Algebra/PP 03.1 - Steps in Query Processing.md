# PP 03.1 · Steps in Evaluating an SQL Query

## 2020/21 · Q1(c) [30 marks] · 2022/23 · Q4(a) [25 marks] · 2023/24 · Q4(a) [25 marks]
> **Questions:** A user just connected to a database server and submitted a SQL query in the form of a string. Give the important steps involved in evaluating that SQL query **and the order in which they are performed**. (2020/21) · … Give **four** important steps involved in evaluating that query. (2022/23, 2023/24)

### Expected answer
```text
SQL string ─► [1 Parse & translate] ─► RA expression / query tree
                                              │
                         catalog statistics ─►[2 Optimize]
                                              │
                                     [3 Generate execution plan]
                                              │
                    data ─────────────► [4 Evaluate / execute] ─► result to user
```
1. **Parsing and translation**
   - **Scanning (lexical analysis):** the string is split into **tokens** (keywords such as SELECT/FROM/WHERE, relation and attribute names, operators, constants).
   - **Parsing (syntax analysis):** tokens are checked against SQL grammar; a **parse tree** is built. Syntax errors stop processing.
   - **Validation / semantic analysis:** relation and attribute names are checked against the **catalog** (they must exist), data types checked, privileges verified.
   - **Translation** into an internal form: a **relational-algebra expression / query tree**.
2. **Query optimization:** the optimizer generates **equivalent RA expressions** (heuristic rewriting such as pushing selections down, replacing × + σ by ⋈, reordering joins) and alternative **access paths/algorithms** (index vs table scan, hash vs nested-loop join), estimates each one's cost from **catalog statistics** (number of tuples, blocks, distinct values, selectivity, indexes), and selects the **cheapest plan**.
3. **Execution-plan (code) generation:** the chosen plan is turned into a **physical query plan**: an ordered tree of operators annotated with algorithms and access methods (possibly compiled code), deciding pipelining/materialization.
4. **Query evaluation (execution):** the **query-execution engine** runs the plan: reads blocks (scans/indexes), applies filters, joins, aggregates, sorts; then **returns the result** to the user/application.

For "the order": **parse → validate/translate → optimize → generate plan → execute → return results**; optimization always precedes execution and is the only step that chooses *how* the query runs.

### Key points to include
Tokens, parse tree, catalog check, RA/query tree, optimizer with statistics, execution plan, evaluation engine, results; the diagram.

### How to approach
Numbered steps, each with *what happens* and *its output*, plus the diagram. For 30 marks add examples (a syntax error caught by the parser; a missing column caught by validation; an index chosen by the optimizer).

## 2023/24 · Q5(a) [20 marks]
> **Question:** Explain the process of query processing in database management systems, detailing its stages, techniques, and how they contribute to efficient query execution.

### Expected answer
**Stages** (as above, with lecture names): (1) **parsing**, (2) **semantic analysis**, (3) **query optimization**, (4) **execution-plan generation**, (5) **query execution**, (6) **result presentation**.

**Techniques and their contribution to efficiency**
| Stage | Technique | Contribution |
|---|---|---|
| Parsing / translation | parse tree → relational algebra / query tree | a formal structure that can be rewritten safely (equivalence rules) |
| Optimization (logical) | **heuristics**: predicate push-down, projection push-down, (σ, ×) → ⋈, most restrictive joins first | shrinks intermediate results early; avoids Cartesian products |
| Optimization (cost-based) | **cost models** with selectivity/cardinality estimates, histograms; join ordering (dynamic programming) | picks the cheapest access paths and join order |
| Plan generation | access paths (**index scan** vs table scan), **join algorithms** (nested loop, index nested loop, hash, sort-merge), sort methods | reduces disk I/O and CPU |
| Execution | **pipelining** (tuples flow between operators without temporary tables), parallel execution, buffering/caching | less memory and I/O, faster first results |

Conclusion: correct result with **minimum resource usage** (CPU, memory, I/O), the stated goal of query processing.

### How to approach
List stages briefly, then spend most of the answer on techniques → efficiency (table form is ideal).
