# PP 03.2 · Translating SQL into Relational Algebra (2020/21 Q1(a)(b))

> [!info] [[PP 03 - Query Processing and Relational Algebra|PP 03 index]] · Lessons: [[03.03 Set Operations and Joins]] (γ), [[03.04 Writing Relational Algebra Queries]] (SQL → RA), [[04.06 Heuristic Optimization and Transformation Rules]] · Priority 🟡

Tables: $R(a, b, c)$, $S(d, e, f)$, $T(g, h, i)$; γ = grouping/aggregation.

---

## 2020/21 · Q1(a) [40 marks]
> **Question:** For the SQL query
> ```sql
> SELECT R.b FROM R, S, T
> WHERE R.a = S.d AND S.e = T.g AND T.h > 21 AND S.f < 50
> GROUP BY R.b
> HAVING count(*) > 2
> ```
> indicate whether each RA expression is a correct translation:
> (i) $\pi_{R.b}(\sigma_{TOTAL>2}(\gamma_{R.b,\,count(*)\to TOTAL}(\sigma_{T.h>21 \wedge S.f<50}(R \bowtie_{R.a=S.d}(S \bowtie_{S.e=T.g} T)))))$
> (ii) $\pi_{R.b}(\sigma_{TOTAL>2}(\sigma_{T.h>21 \wedge S.f<50}(\gamma_{R.b,\,count(*)\to TOTAL}(R \bowtie_{R.a=S.d}(S \bowtie_{S.e=T.g} T)))))$

### Expected answer
SQL's logical order: **FROM** (joins) → **WHERE** (row filter) → **GROUP BY** (γ) → **HAVING** (filter on groups) → **SELECT** (π).

**(i) Correct.**
- The joins $S \bowtie_{S.e=T.g} T$ and $R \bowtie_{R.a=S.d}(\dots)$ implement the FROM clause with the join conditions of WHERE.
- $\sigma_{T.h>21 \wedge S.f<50}$ applies the remaining WHERE conditions to individual rows **before grouping**.
- $\gamma_{R.b,\ count(*) \to TOTAL}$ groups by R.b and counts rows per group (GROUP BY).
- $\sigma_{TOTAL>2}$ is the HAVING clause; $\pi_{R.b}$ is the SELECT list.
Every clause is applied in the correct order.

**(ii) Incorrect.**
- The selection on `T.h > 21 AND S.f < 50` is placed **after** γ. The output of γ contains only **R.b and TOTAL**, so **T.h and S.f no longer exist**: the selection is not even well-formed.
- Semantically, the counts would include rows that should have been **filtered out before grouping**, so TOTAL (and the HAVING test) would be wrong. A selection on non-grouping attributes **cannot be moved past γ** (it is not one of the valid transformation rules).

### Key points to include
SQL clause order; WHERE before γ, HAVING after γ; attributes available after γ; therefore (i) correct, (ii) incorrect with reason.

## 2020/21 · Q1(b) [30 marks]
> **Question:** For the SQL query
> ```sql
> SELECT R.b FROM R, S
> WHERE R.a = S.d
>   AND R.b NOT IN (SELECT R2.b FROM R AS R2, T WHERE R2.b = T.g)
> ```
> show an equivalent RA expression (same format as (a)) or draw it as an expression tree / logical query plan.

### Expected answer
- Outer part: the b-values of R rows that join with S: $\pi_{R.b}(R \bowtie_{R.a = S.d} S)$.
- Subquery: the b-values of R (renamed R2) that match some T.g: $\pi_{R2.b}(\rho_{R2}(R) \bowtie_{R2.b = T.g} T)$.
- `NOT IN` = keep outer values **not** in the subquery result → **set difference**:
$$
\pi_{R.b}\big(R \bowtie_{R.a = S.d} S\big)\ -\ \pi_{R2.b}\big(\rho_{R2}(R) \bowtie_{R2.b = T.g} T\big)
$$
Expression tree:
```text
                      −
              ╱               ╲
         π_{R.b}             π_{R2.b}
            │                    │
     ⋈_{R.a = S.d}         ⋈_{R2.b = T.g}
       ╱       ╲             ╱         ╲
      R         S        ρ_{R2}(R)       T
```
Note: the difference is taken on the **projected b-values**, which is valid because only R.b is returned (both operands are union-compatible: one attribute b). Under SQL bag semantics duplicates of b from the outer query would be kept; in set-based RA they collapse.
Alternative form with an **anti-join**: $\pi_{R.b}\big((R \bowtie_{R.a=S.d} S) \mathbin{\overline{\ltimes}}_{R.b = T.g} T\big)$ (rows with no matching T.g), which is equivalent here.

### How to approach
Translate the subquery separately → translate the outer query → combine with "−" for NOT IN → draw the tree.
