## 2020/21 · Q4(b) [30 marks] and 2021/22 · Q4(d) [25 marks]
> **Question:** While in relational databases Primary Keys are used for identification, object-oriented and object-relational systems use Object Identities (OIDs). Discuss (two main) differences between the two concepts.

### Expected answer
**Primary key:** one or more attributes whose **values** uniquely identify a row in a table; chosen by the designer; every row must have a unique PK value, which **determines the row's identity**.
**OID:** a **system-generated** identifier that every object receives on creation; the object's identity **exists independently of its attribute values** (identity by existence); in SQL: `REF IS oid SYSTEM GENERATED` (or DERIVED).

**Main differences**
1. **Value-based vs value-independent identity.** A PK is made of **attribute values**; if the values change (e.g. a corrected ID number) the identity changes and every foreign key referencing it must change. An OID is **independent of all attribute values** and **immutable**: an object keeps the same OID even if every attribute changes; two objects with **identical values are still different** objects (identity ≠ equality).
2. **Who creates/sees it.** PKs are **defined and supplied by users**, are **visible** and meaningful (Reg_No, NIC). OIDs are **generated and managed by the system**, usually **hidden** from users, carry no business meaning and are **never reused**.
3. **Scope.** A PK is unique **within one table**; an OID is unique **across the whole database/system**.
4. **Referencing mechanism.** PKs are referenced by **foreign keys** (copies of the value), followed by **joins**, which are non-directional. OIDs are referenced by **reference attributes (pointers)** (`REF(type) SCOPE table`), followed by **dereferencing** (`->`), which is direct navigation.
5. **Necessity.** Relational tables must declare a PK to identify rows; objects always have an OID automatically.

*Example:* two `Employee` objects both named "Kamal Perera", born the same day: relationally they need a distinguishing key value; as objects they are distinct by their OIDs.

### How to approach
Define both → give the two strongest differences (value-based vs immutable system identity; FK join vs reference pointer) in detail → (for 25–30 marks) add scope/visibility/example.

## 2020/21 · Q4(a) [30 marks]
> **Question:** Discuss the differences of 'Object Tables' compared to 'Relational Tables' in an Object Relational database.

### Expected answer
- A **relational table** is defined by listing its columns: `CREATE TABLE Dept (dno INT PRIMARY KEY, dname VARCHAR(20))`; its rows are tuples of (mostly atomic) values identified by primary keys.
- An **object (typed) table** is defined **from a user-defined type**: `CREATE TABLE Company OF Comp_type (REF IS comp_id SYSTEM GENERATED, PRIMARY KEY(comp_name))`; each row is an **object (instance) of that type**.

| Aspect | Relational table | Object table |
|---|---|---|
| Structure | explicit column list | taken from a **UDT** (`OF type`) |
| Rows | tuples | **objects** of the type |
| Identity | primary key values | **OID** (`REF IS … SYSTEM GENERATED/DERIVED`) + optional PK |
| Referenced by | foreign keys (joins) | **REF attributes** with `SCOPE`, dereferenced by `->` |
| Column types | atomic/built-in | can hold UDTs, row types, arrays, nested tables, references |
| Behaviour | none in the table | **methods** of the type apply to rows |
| Inheritance | none | **type/table hierarchies** (`UNDER`); subtable rows appear in supertable queries |
| Reuse / evolution | each table separate | one type → several tables; change the type to change all |

> [!warning] Only touched on in the lecture
> The lecture shows `CREATE TABLE … OF type` and `REF IS` (slides 43–44) but does not list these differences explicitly; points on methods/inheritance/substitutability come from SQL:2003 / textbook.

## 2020/21 · Q4(c) [40 marks]
> **Question:** A database created with an SQL:2003-compliant DBMS:
> ```sql
> CREATE TYPE aType AS (x INTEGER, y INTEGER) NOT FINAL;
> CREATE TYPE bType UNDER aType AS (z INTEGER) FINAL;
> CREATE TABLE aTable OF aType;
> CREATE TABLE bTable OF bType UNDER aTable;
> INSERT INTO aTable VALUES (1, 2);
> INSERT INTO aTable VALUES (3, 4);
> INSERT INTO bTable VALUES (5, 6, 7);
> ```
> Discuss the results (how many columns, how many rows) of (i) `SELECT * FROM aTable;` (ii) `SELECT * FROM bTable;`

### Expected answer
**Interpretation of the definitions**
- `aType` has attributes x, y and is **NOT FINAL** (it may have subtypes).
- `bType` is a **subtype** of aType (`UNDER`): it **inherits x, y** and adds z; **FINAL** (no further subtypes).
- `aTable` is a typed table of aType; `bTable` is a typed table of bType declared **UNDER aTable** → a **table hierarchy**: bTable is a **subtable** of aTable.
- In SQL:2003, every row of a subtable is **also a row of its supertable** (**substitutability**: every bType object *is an* aType object).

**(i) `SELECT * FROM aTable;`** → **2 columns (x, y)** and **3 rows**:
| x | y |
|---|---|
| 1 | 2 |
| 3 | 4 |
| 5 | 6 |
The bTable row (5, 6, 7) appears **projected onto aTable's columns**; z is not shown.

**(ii) `SELECT * FROM bTable;`** → **3 columns (x, y, z)** and **1 row**:
| x | y | z |
|---|---|---|
| 5 | 6 | 7 |
Rows inserted directly into aTable are not bType objects, so they are not in bTable.

**Additional points:** `SELECT * FROM ONLY (aTable)` returns just the 2 rows inserted directly into aTable; inserting (5, 6, 7) into bTable makes the row visible in both tables but it is stored once; no OID column appears because no `REF IS` clause was declared.

> [!warning] Partly beyond the lecture
> The slides cover `UNDER` for types only; table hierarchies, substitutability and `ONLY` are standard SQL:2003 behaviour (textbook). This information could not be fully verified from the available course materials.

Explain what each statement creates (types, subtype, typed tables, subtable) → state the substitutability rule → give each result as a small table with column and row counts → mention `ONLY`.
