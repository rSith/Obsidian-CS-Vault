## 2021/22 · Q4(b) [30 marks]
> **Question:** Discuss the differences between relational, object-oriented and object-relational data models. Your answer should cover differences in data representation, data definition languages, data manipulation, and data access/query languages.

### Expected answer
| Aspect | Relational | Object-oriented | Object-relational |
|---|---|---|---|
| **Data representation** | flat **tables** (relations) of rows with **atomic** values; relationships through **foreign keys**; identity by **primary key** values; normalization | **objects** = state (attributes, relationships) + **behaviour** (methods); **classes**, **inheritance**, **encapsulation**, complex/nested and collection-valued attributes; relationships as **object references**; identity by **OID** | relational tables **extended** with **user-defined types**, **row and array types**, nested tables/varrays, **REF types** and **OIDs**, **typed tables**, **type/table inheritance** (`UNDER`), methods |
| **Data definition language** | SQL DDL: `CREATE TABLE`, constraints (PK, FK, CHECK) | class definitions in an OO language or **ODL** (ODMG Object Definition Language) | SQL:1999/2003 DDL: `CREATE TYPE … AS (…) [NOT] FINAL`, `METHOD …`, `CREATE TABLE … OF type`, `REF IS … SYSTEM GENERATED`, `UNDER` |
| **Data manipulation** | set-oriented SQL `INSERT/UPDATE/DELETE` on rows | via **methods** of objects in the host language; **navigational** (follow references); persistence of program objects | SQL DML on tables and typed tables; method invocation; constructor functions; dot notation for components; `->` dereferencing |
| **Query / access language** | **SQL**: declarative, based on relational algebra; powerful joins, optimizable | **OQL** (Object Query Language) or navigation through object graphs in program code | **SQL with object extensions** (SQL3): path expressions, functions on UDTs, collections, `ONLY` for hierarchies |
| Strengths | mature, simple, scalable (> 10¹⁰ records), standard | natural fit for complex data and OO programs | keeps SQL/relational strengths + richer modelling |
| Weaknesses | impedance mismatch; weak complex types | small market (< 5%), weaker querying/optimization, scale ~10⁷ | complexity; vendor-specific features |

### How to approach
Use the four aspects named in the question as the rows of a comparison table; add a final row of strengths/weaknesses; close with "ORDB = relational base + OO features, still SQL".

## 2021/22 · Q4(c) [20 marks]
> **Question:** Superficially the object-oriented and relational data models are similar but in reality they are functionally very different. Discuss whether: (i) a Class in a UML class diagram is equivalent to an Entity Type in a relational model; (ii) a Class in a UML class diagram is equivalent to a Relation/Table in a relational model.

### Expected answer
**(i) Class vs entity type: similar, but not equivalent.**
- *Similar:* both describe a set of things with common **attributes** (Student class ↔ STUDENT entity type); associations ↔ relationship types; EER specialization ↔ class inheritance.
- *Different:* a class also has **operations (methods)** and **encapsulation** (behaviour), which an entity type lacks; objects have **identity independent of attribute values (OID)** whereas entities are distinguished by a **key attribute**; classes support **inheritance with polymorphism** and attributes that are **objects or collections**; UML associations can be **directional** (navigability). So an entity type captures only the **structural** part of a class.

**(ii) Class vs relation/table: not equivalent.**
- A table is a **flat set of tuples** with **atomic** values and a **primary key**; a class may have **complex, multi-valued, nested** attributes, **methods**, **inheritance** and **references** to other objects.
- Mapping a class usually needs **several tables** (multi-valued attributes and many-to-many associations → separate tables; inheritance → table per class or per hierarchy); methods are not stored (or become stored procedures).
- **Associations** in OO are **directional** references (`Customer` has `Set<Order>`, `Order` has `Customer`), whereas relational **foreign keys are non-directional** (join either way) (lecture slides 19–20).
- ORM frameworks map class → table, instance → row, attribute → column (slides 9–10, 17), showing a **correspondence after flattening**, not equivalence.
**Conclusion:** both statements are **false** in the strict sense: a UML class is a richer construct than either an entity type or a table.

## 2022/23 · Q7(a) [short note, 25 marks] and 2023/24 · Q7(a) [25 marks]
> **Questions:** Object-Relational Databases to bridge the gap between Object-Oriented Programming and Relational Databases. (2022/23) · Explain the key features of object-relational databases. How do they extend traditional relational databases to support complex data types and object-oriented concepts? (2023/24)

### Expected answer
**The gap (impedance mismatch).** OO programs model data as **objects** with identity, nested structures, collections, inheritance, references and methods; relational DBs store **flat tables** of atomic values linked by foreign keys and queried by set-based SQL. Converting between them is the **object-relational impedance mismatch**. Pure **OODBMSs** never became popular (immature vs RDBMS, scale 10⁷ vs > 10¹⁰ records, < 5% market, encapsulation hinders querying/indexing/transactions).

**ORDBMS idea.** An **object-relational database** **extends the relational model with object-oriented features**: data stays in tables and is accessed with **SQL**, while the database can act as an **object store**. Most commercial RDBMSs offer these extensions (SQL3/SQL-99, SQL:2003).

**Key features and how they extend the relational model**
| Feature | Extension |
|---|---|
| **User-defined types (object types/ADTs)** | composite types with attributes (e.g. `Addr_type(street, city, zip)`, `Point(x, y)`) used as column types or table types |
| **Complex data types / type constructors** | **row** types, **array** types (`VARCHAR(20) ARRAY[10]`), **nested tables**, **varrays**, JSON/XML columns → non-flat data without splitting into many tables |
| **Methods / functions** | behaviour declared with the type (`METHOD apt_no() RETURNS CHAR(8)`), stored procedures → encapsulated business logic |
| **Inheritance** | `CREATE TYPE Manager_type UNDER Emp_type …`; typed-table hierarchies; PostgreSQL table inheritance (Vehicle → Car, Truck) |
| **Object identity and references** | `CREATE TABLE … OF type (REF IS id SYSTEM GENERATED)`; `REF(type) SCOPE (table)` attributes; `->` dereferencing → OO-style pointers |
| **Object views** | present existing relational data as objects without changing storage |
| **Encapsulation via views and triggers; polymorphism via joins; triggers/rules** | approximate OO encapsulation, polymorphism and event-driven behaviour (lecture slides 37–40) |

**Complementary ORM frameworks** (Hibernate/JPA, EclipseLink, Entity Framework, SQLAlchemy, Django ORM) map classes ↔ tables, objects ↔ rows, attributes ↔ columns, generate SQL for CRUD, manage sessions and lazy loading, giving developers transparent persistence.

**Benefits:** keep relational strengths (SQL, ACID, optimization, scalability, maturity) while modelling complex real-world data closer to OO code; code reuse via inheritance; fewer joins for nested data.
**Limitations:** more complex design and querying; vendor-specific syntax; optimizers handle complex types less well.

### How to approach
Short note: problem → ORDB definition → feature list with one-line examples (code snippets welcome) → ORM as complement → benefits/limits. For 2023/24 emphasise the **"how they extend"** column.
