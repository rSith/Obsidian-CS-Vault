# PP 07.1 · OLTP vs OLAP

> [!info] [[PP 07 - Data Warehousing and OLAP|PP 07 index]] · Lesson: [[07.02 OLTP vs OLAP]] · Priority 🟡

---

## 2023/24 · Q7(b) [25 marks]
> **Question:** Define OLTP systems and explain their key characteristics. How do they differ from OLAP systems in terms of workload, data access patterns, and performance requirements?

### Expected answer
**Definition.** **OLTP (Online Transaction Processing)** systems are the **operational, transactional databases** that run an organisation's **day-to-day business**: they process large numbers of short **transactions** that **insert, update and delete** a few records each, plus simple queries (e.g. sales at a checkout, student registrations, bank account updates, airline bookings).

**Key characteristics**
- **Current, detailed, operational** data; **frequently updated**; short-term.
- **Many concurrent users** issuing **short, simple, predefined** transactions touching **few rows**.
- **Normalised** relational schema (avoid redundancy and update anomalies).
- Strong **ACID** guarantees, concurrency control and recovery; **high availability**.
- Optimised for **fast response (milliseconds) and high throughput** (transactions per second).
- Data usually from **one application**; relatively smaller size.

**OLAP (Online Analytical Processing)** analyses complex data in a **data warehouse** for **decision support**: summarising, aggregating and exploring large volumes of **historical, integrated** data (roll-up, drill-down, slice and dice, pivot).

**Differences**
| Aspect | OLTP | OLAP |
|---|---|---|
| **Workload** | very many short **read-write transactions** (INSERT/UPDATE/DELETE + simple SELECTs); continuous | relatively few **long, complex, ad-hoc read-only queries**; data loaded in **periodic batches** (ETL refresh) |
| **Data access patterns** | **random access to a few rows by key**, usually via **indexes** (point queries); current data | **large scans over millions of rows**, **aggregations** (SUM, AVG, COUNT), GROUP BY, multi-dimensional joins of fact and dimension tables (star schema); historical data |
| **Performance requirements** | **low latency per transaction**, high **throughput**, strict **consistency** and concurrency, **availability** | acceptable seconds–minutes per query; **fast aggregation/scan performance** and consistent reporting; optimised for **retrieval**, not updates |
| Data | current, detailed, normalised | historical, summarised, integrated from many sources, denormalised (cubes, star/snowflake) |
| Updates | frequent, real time | periodic, non-volatile |
| Users | clerks, customers, applications | managers, analysts, executives |
| Size | GB | TB–PB |
| System | operational database | data warehouse / OLAP server |

**Why separate them:** heavy analytical queries on the OLTP system would slow transactions (lock and I/O contention), and OLTP data is not structured for trend analysis; a warehouse separates the two workloads.

### Key points to include
Definition + examples; 4–6 characteristics; a table covering at least **workload, access pattern, performance** (the three named aspects); one line on why they are separated.

### How to approach
Definition → bullet characteristics → three-row (or longer) comparison table → concluding sentence.
