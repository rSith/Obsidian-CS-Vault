## 2022/23 · Q4(b) [25 marks] and 2023/24 · Q4(b) [25 marks]
> **Question:** Explain the difference between logical and physical query optimization, including examples of each.

### Expected answer
**Logical query optimization** works on the **logical query plan**: an abstract relational-algebra representation (query tree) that says **what** operations are needed (σ, π, ⋈, γ, sort) **without** saying how they are implemented; it is **independent of indexes, storage and hardware**. Optimization = **rewriting** the RA expression into an equivalent, cheaper one using transformation rules/heuristics:
- **predicate push-down** (apply selections early), **projection push-down**, **join reordering**, replacing σ over × by ⋈, removing redundant operations.
*Example:* $\pi_{name}(\sigma_{dept\_name='Sales'}(Emp \bowtie Dept))$ → $\pi_{name}(Emp \bowtie \sigma_{dept\_name='Sales'}(Dept))$: the filter is applied before the join, so the join processes far fewer rows.

**Physical query optimization** turns the logical plan into a **physical plan** that says **how** each operation runs: **access paths** (full table scan vs index scan), **join algorithms** (nested loop, index nested loop, hash join, sort-merge), **sort methods** (in-memory vs external merge sort), pipelining, parallelism. Choices are made by **cost estimation** using statistics (I/O, CPU, memory).
*Example (lecture):* `SELECT first_name, last_name FROM employees WHERE department = 'Sales' ORDER BY first_name;` → logical: filter → project → sort; physical: **index scan on department** (if an index exists) instead of a full scan; **in-memory sort** if the result is small, else **external merge sort**; if joins existed, **hash join** vs **nested loops**.

| | Logical | Physical |
|---|---|---|
| Question | what to do | how to do it |
| Representation | RA expression / query tree | operator tree with algorithms and access paths |
| Depends on indexes / storage? | no | yes |
| Technique | equivalence rules, heuristics | cost models, statistics |
| Example | push σ below ⋈ | index scan; hash join |

### How to approach
Define each (what vs how) → one example each → comparison table.

## 2021/22 · Q7(a) [20 marks]
> **Question:** Explain the THREE key steps of Query Optimisation using a diagram.

### Expected answer
```text
 SQL query ──► (1) Parser & translator ──► relational-algebra expression / initial query tree
                                                   │
                     statistics about data ──► (2) Optimizer ──► execution plan
                                                   │
                         data ───────────► (3) Evaluation engine ──► query output
```
1. **Parsing and translation:** the query is scanned and parsed, names validated against the catalog, and translated into an internal **relational-algebra** form (initial query tree).
2. **Optimization:** equivalent expressions and alternative algorithms/access paths are generated (heuristic rewriting + cost estimation using **catalog statistics**); the plan with the **lowest estimated cost** is chosen as the **execution plan**.
3. **Evaluation:** the **query-execution engine** executes the plan and returns the result.

## 2021/22 · Q7(b) [20 marks] and 2022/23 · Q5(b) [20 marks]
> **Questions:** Describe Cost-based and Rule-based query optimisation techniques. (2021/22) · Discuss the concepts of cost-based optimization and heuristic-based optimization. What is the fundamental difference between these approaches? (2022/23)

### Expected answer
**Cost-based optimization (CBO):** the DBMS **generates several alternative execution plans** (e.g. different join orders, access paths, join algorithms), **estimates the cost** of each with a **cost model** (CPU, disk I/O, memory, network) based on **statistics** (table cardinalities, **selectivity** of conditions, histograms, available indexes, index levels), and **chooses the plan with the lowest estimated cost**.
Steps: plan generation → cost estimation → plan selection.
+ accurate, adapts to data and hardware; − optimization can be expensive for complex queries (large search space); depends on accurate, up-to-date statistics; estimates may be wrong.

**Rule-based / heuristic optimization (RBO):** applies a fixed set of **transformation rules** believed to improve almost any query, without computing costs:
- push selections and projections down; perform the most restrictive selections/joins first; replace Cartesian product + selection by a join; avoid sorting; constant folding.
+ fast and simple, low optimization overhead; − static, **ignores the actual data distribution**, so it can produce suboptimal plans (e.g. using an index on a predicate that matches 80% of the rows).

**Fundamental difference:** **heuristic optimization decides by general rules about the form of the query; cost-based optimization decides by numerical cost estimates computed from statistics about the actual data.** Heuristics do not compare alternatives quantitatively; CBO does.

**In practice:** a **hybrid**: heuristics first (to simplify and prune the search space), then cost-based choice among the remaining plans.

| | Heuristic / rule-based | Cost-based |
|---|---|---|
| Basis | fixed rules | estimated cost |
| Statistics | not used | essential |
| Plans compared | one transformed plan | many alternatives |
| Optimization time | low | higher |
| Plan quality | usually good, not guaranteed | usually better (if statistics are good) |

### How to approach
Define both with steps/examples → pros and cons → the one-sentence fundamental difference → hybrid remark.
