## 2021/22 · Q7(c) [60 marks]
> **Question:** Consider the initial query tree on EMPLOYEE, WORKS_ON and PROJECT:
> $\pi_{Lname}\big(\sigma_{Pname='Aquarius' \wedge Pnumber=Pno \wedge Essn=Ssn \wedge Bdate>'1957-12-31'}((EMPLOYEE \times WORKS\_ON) \times PROJECT)\big)$
> Sample data: EMPLOYEE(SSN, Lname, Bdate): (12329, Rogers, 1957-12-31), (13453, Ahmed, 1978-03-04), (15463, Bohm, 1956-06-03); WORKS_ON(ESSN, Pnumber, HrsWorked): (12329, 49, 450), (13453, 43, 200), (15463, 46, 19); PROJECT(Pno, Pname, Pstartdate): (43, Aquarius, 2021-02-03), (44, Markets, 2020-12-11), (46, Hospitality, 2020-12-24).
> (i) Express the equivalent SQL statement. (ii) Explain why the query tree is inefficient. (iii) Describe how the tree could be transformed to run efficiently.

### Expected answer
**(i) SQL**
```sql
SELECT Lname
FROM   EMPLOYEE, WORKS_ON, PROJECT
WHERE  Pname = 'Aquarius' AND Pnumber = Pno AND Essn = Ssn
  AND  Bdate > '1957-12-31';
```
(Last names of employees born after 1957 who work on the Aquarius project; with the sample data the answer is **Ahmed**.)

**(ii) Why inefficient**
- It is the **canonical tree**: it first forms the **Cartesian product of all three relations**. Even with the tiny sample this is 3 × 3 × 3 = 27 tuples; with realistic sizes (e.g. 1,000 × 10,000 × 100) it is 10⁹ tuples, almost all useless.
- **All selection conditions are applied only at the end**, after the huge intermediate result has been built, although only **one PROJECT tuple** (Aquarius) and only employees born after 1957 are needed.
- **All attributes** are carried through every step though only Lname and the join attributes are needed.
- Join conditions are expressed as a selection over ×, so no efficient join algorithm can be used.
→ enormous intermediate results: high I/O, memory and CPU cost.

**(iii) Transformations (heuristic rules)**
1. **Break up the conjunctive selection** into a cascade of single selections (rule: cascade of σ).
2. **Push selections down:** $\sigma_{Bdate>'1957-12-31'}$ onto EMPLOYEE, $\sigma_{Pname='Aquarius'}$ onto PROJECT; place the join conditions directly above the × they relate (rules: commute σ with ×).
3. **Apply the most restrictive selection first / reorder leaves:** σ on PROJECT returns **one tuple** (Pname is unique), so join PROJECT with WORKS_ON first, then with EMPLOYEE (rules: commutativity/associativity of ×), avoiding a product of EMPLOYEE × PROJECT, which has no join condition.
4. **Replace × + join condition with ⋈:** $\sigma_{Pnumber=Pno}(\cdot \times \cdot) \to \bowtie_{Pnumber=Pno}$, $\sigma_{Essn=Ssn}(\cdot \times \cdot) \to \bowtie_{Essn=Ssn}$.
5. **Push projections down:** keep only Pno from PROJECT, Essn and Pnumber from WORKS_ON, Ssn and Lname from EMPLOYEE, Essn after the first join.
```text
Final tree
π_{Lname}
   │
⋈_{Essn=Ssn}
 ╱                         ╲
π_{Essn}                    π_{Ssn, Lname}
   │                             │
⋈_{Pnumber=Pno}              σ_{Bdate>'1957-12-31'}
 ╱            ╲                  │
π_{Pno}        π_{Essn, Pnumber} EMPLOYEE
   │               │
σ_{Pname='Aquarius'} WORKS_ON
   │
PROJECT
```
With the data: Aquarius → Pno 43 → WORKS_ON (13453, 43) → EMPLOYEE 13453 Ahmed (born 1978) → **Ahmed**. Intermediate results contain 1 tuple at every step instead of 27.

### How to approach
(i) Read the tree bottom-up → SQL. (ii) Name the problems: Cartesian products, late selection, unnecessary attributes. (iii) Show **each transformation step with the rule used** and draw the final tree (drawing 2–3 intermediate trees earns more marks).

## 2023/24 · Q5(c) [20 + 20 + 20 marks]
> **Question:**
> ```sql
> SELECT E.Name, D.Dept_Name
> FROM Employee E, Department D, Works W
> WHERE E.Emp_ID = W.Emp_ID AND W.Dept_ID = D.Dept_ID
>   AND D.Location = 'Colombo' AND E.Salary > 80000;
> ```
> (i) Draw the initial query tree. (ii) Using heuristic optimization rules, convert it into an optimized tree. (iii) Explain how the optimized tree improves efficiency.

### Expected answer
**(i) Initial (canonical) tree**
```text
π_{E.Name, D.Dept_Name}
   │
σ_{E.Emp_ID=W.Emp_ID ∧ W.Dept_ID=D.Dept_ID ∧ D.Location='Colombo' ∧ E.Salary>80000}
   │
   ×
 ╱   ╲
×     W
╱ ╲
E   D
```
**(ii) Optimized tree**
Steps: cascade the σ → push `E.Salary > 80000` onto E and `D.Location='Colombo'` onto D → reorder leaves so each × has a join condition (E–W–D; E and D share no condition) → convert σ+× into ⋈ → push projections down.
```text
                  π_{E.Name, D.Dept_Name}
                           │
                 ⋈_{W.Dept_ID = D.Dept_ID}
               ╱                         ╲
     π_{E.Name, W.Dept_ID}          π_{D.Dept_ID, D.Dept_Name}
             │                               │
     ⋈_{E.Emp_ID = W.Emp_ID}         σ_{D.Location='Colombo'}
       ╱                ╲                    │
π_{Emp_ID, Name}    π_{Emp_ID, Dept_ID}      D
       │                 │
σ_{E.Salary>80000}       W
       │
       E
```
(Equally valid: start with $\sigma_{Location='Colombo'}(D) \bowtie W$ if Colombo departments are more selective than high salaries.)

**(iii) Why it is more efficient**
1. **No Cartesian products**: the initial tree materializes |E| × |D| × |W| tuples; the optimized tree joins only matching tuples.
2. **Selections first** (predicate push-down): only employees earning > 80,000 and only Colombo departments reach the joins → much smaller intermediate results.
3. **Projections early**: narrower tuples → more per block → fewer disk I/Os, less memory.
4. **Join order follows the join conditions** with reduced inputs first (most restrictive first).
5. Smaller inputs enable efficient **join algorithms** (in-memory hash join, index nested loop) and **pipelining**; overall lower I/O, CPU and memory cost; same result.

### How to approach
Draw the canonical tree exactly (× of all relations, one σ, one π) → list the heuristic steps with rule names → draw the optimized tree → 4–5 numbered efficiency reasons.
