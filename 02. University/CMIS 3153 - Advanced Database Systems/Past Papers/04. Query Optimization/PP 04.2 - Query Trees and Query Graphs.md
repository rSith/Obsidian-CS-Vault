## 2022/23 · Q5(c) [20 marks] and 2023/24 · Q5(b) [20 marks]
> **Questions:** Compare and contrast query trees with query graphs. (2022/23) · Compare query graphs with query trees, highlighting how query graphs assist in join ordering and query optimization. (2023/24)

### Expected answer
**Query tree:** a tree representing a **relational-algebra expression**: **leaves = input relations**, **internal nodes = RA operators** (σ, π, ⋈, ×, γ, sort), **root = final result**; edges show data flow; executed **bottom-up**, so it fixes an **order of operations**.
**Query graph:** represents a **relational-calculus** query: **nodes = relations** (and **constant** nodes), **edges = join conditions** (between relations) and **selection conditions** (relation–constant); retrieved attributes are listed beside the relations. It shows **what is connected**, but **no order** of execution.

| | Query tree | Query graph |
|---|---|---|
| Represents | RA expression | relational calculus / connections |
| Structure | hierarchical tree | general graph (may contain cycles) |
| Order of operations | specified | not specified (neutral) |
| Per query | many equivalent trees | **exactly one** graph |
| Used for | heuristic rewriting, cost-based plan choice, **execution** | visualizing relations and conditions; **which joins are possible** |
| Preferred by optimizers | **yes**: the plan must state an order | aid only |
| Similarities | both are internal representations produced after parsing; both show relations and join/selection conditions; both used in optimization |

**How query graphs help join ordering (2023/24):**
- Edges show **which relations share a join condition**; joining relations **not connected** by an edge would create a **Cartesian product**, so the optimizer only considers orders that follow edges (avoids ×).
- The graph's **shape** (chain, star, cycle) limits and structures the set of sensible join orders (e.g. dynamic programming over connected subgraphs).
- **Selection edges to constants** reveal which relations are most reduced (e.g. `Pname = 'Aquarius'` → 1 tuple), which should be joined **first**.
- Being order-neutral, the graph lets the optimizer explore orders freely; the chosen order is then expressed as a **query tree**.

*Example (lecture Stafford query):* graph P —(P.Dnum = D.Dnumber)— D —(D.Mgr_ssn = E.Ssn)— E, with P —(P.Plocation = 'Stafford')— constant. The chain shows P must be joined to D before E (no edge P–E), and the constant suggests starting from P.

## 2022/23 · Q5(d) [20 + 10 + 10 marks] (= lecture L4 practice Q2)
> **Question:** `SELECT e.name, d.department_name FROM employees e INNER JOIN departments d ON e.department_id = d.department_id WHERE e.salary > 50000;`
> (i) Construct a query tree for this query. (ii) Show the join as a separate node and explain how the filter condition salary > 50000 is applied before or after the join. (iii) Indicate the expected order of operations for the query.

### Expected answer
**(i) Query tree** (initial form, then optimized):
```text
Initial (direct translation)                 Optimized (filter pushed down)
π_{e.name, d.department_name}                π_{e.name, d.department_name}
          │                                              │
σ_{e.salary > 50000}                        ⋈_{e.department_id = d.department_id}
          │                                     ╱                     ╲
⋈_{e.department_id = d.department_id}   σ_{e.salary > 50000}       departments d
     ╱                ╲                          │
employees e      departments d               employees e
```
**(ii)** The join is the separate node $\bowtie_{e.department\_id = d.department\_id}$ with the two tables as children. The filter `salary > 50000` refers **only to employees**, so by the transformation rule *commuting σ with ⋈* ($\sigma_c(E \bowtie D) = \sigma_c(E) \bowtie D$ when $c$ uses only E's attributes) it can be applied **before the join** (**predicate push-down**). Both placements give the **same result**; applying it **before** is better because fewer employee rows enter the join (smaller intermediate result, less I/O and CPU). Applying it after means joining every employee first, then discarding low earners.
**(iii) Order of operations (optimized):**
1. Scan **employees** (or use an index on salary if selective).
2. Apply **σ salary > 50000**.
3. Scan **departments**.
4. **Join** on department_id (e.g. hash join, or index nested loop using an index on departments.department_id).
5. **Project** e.name, d.department_name; return the result.

## 2020/21 · Q2(a) [40 marks]
> **Question:** Tables $R(a,b,c)$, $S(d,e,f)$, $T(g,h)$, $U(i,j,k)$.
> `SELECT R.b, avg(U.k) AS avg FROM R, S, T, U WHERE R.a = S.d AND S.e = T.g AND T.h = U.i AND U.j = 5 AND (R.c + S.f) < 10 GROUP BY R.b`
> Draw a logical plan for the query. Any correct plan is accepted (no need to worry about efficiency).

### Expected answer
```text
                     π_{R.b, avg}
                          │
              γ_{R.b, AVG(U.k) → avg}
                          │
                    ⋈_{T.h = U.i}
                  ╱              ╲
            ⋈_{S.e = T.g}       σ_{U.j = 5}
           ╱           ╲           │
   σ_{R.c + S.f < 10}    T          U
          │
     ⋈_{R.a = S.d}
      ╱        ╲
     R          S
```
Simplest fully correct alternative (canonical): $\pi_{R.b,avg}\big(\gamma_{R.b,\ AVG(U.k)\to avg}(\sigma_{R.a=S.d \wedge S.e=T.g \wedge T.h=U.i \wedge U.j=5 \wedge R.c+S.f<10}(R \times S \times T \times U))\big)$.
Notes: the condition $R.c + S.f < 10$ involves R **and** S, so it can only be applied after R ⋈ S; grouping γ comes **after** all WHERE conditions; π at the top.

### How to approach
Draw leaves → joins following the join conditions → selections at the right places → γ → π. Label every node.
