## 2020/21 · Q2(b) [60 marks]
> **Question:** Consider two physical query plans. Give two reasons (with explanation) why plan B may be faster than plan A.
> **Plan A:** π_{A.d,B.d} (on the fly) ← σ_{B.c<2000} (on the fly) ← ⋈_{A.b=B.b} (**index nested loop**), outer input σ_{a>10}(A) using a **B+-tree index on A.a**, inner B via a **B+-tree index on B.b**.
> **Plan B:** π_{A.d,B.d} (on the fly) ← ⋈_{A.b=B.b} (**hash join**), inputs σ_{a>10}(A) (**file scan**) and σ_{B.c<2000}(B) (**file scan**).

### Expected answer
**Reason 1: The range index scan on A.a can cost more than a file scan.**
`a > 10` is a **range predicate that may qualify a large fraction of A**. If the B+-tree on A.a is **unclustered**, each qualifying tuple requires a separate **random page access** (potentially one I/O per tuple, often re-reading the same pages). A **file scan** reads every page of A **once, sequentially**. When selectivity is low (many matches), the sequential scan is cheaper (Tutorial 4: above ~10% selectivity a full scan wins; 300,000 random reads vs a scan).

**Reason 2: Index nested-loop join probes the B.b index once per outer tuple; a hash join reads each input once.**
For **every** qualifying A tuple, Plan A traverses the B+-tree on B.b (2–4 I/Os) and fetches matching B tuples by **random I/O** (and B.b's index may be unclustered). With many outer tuples, this is thousands–millions of random I/Os. **Hash join** builds a hash table on one (filtered) input and probes it with the other, reading each relation **about once** (≈ 3(M + N) I/Os with partitioning), mostly **sequentially**; ideal for large inputs and equality joins.

**Reason 3 (also acceptable): selection placement.** Plan B applies $\sigma_{B.c<2000}$ **before** the join (predicate push-down), so fewer B tuples are hashed and probed. Plan A applies it **after** the join (on the fly), so the join works on **all** matching B tuples, many of which are discarded afterwards; the join output is larger.

(Plan A could win only if `a > 10` were very selective and the indexes clustered.)

### How to approach
Pick two reasons; for each: what Plan A does → why it is expensive (random I/O, per-tuple probes, late filtering) → what Plan B does instead → why cheaper. Mention selectivity and clustered/unclustered.

## 2022/23 · Q5(a) [20 marks] and 2023/24 · Q2(a) [25 marks]
> **Questions:** Briefly explain the role of indexing in query optimization. (2022/23) · Discuss how indexing influences query optimization and system performance in relational databases. (2023/24)

### Expected answer
**Role in optimization**
- Indexes are **access paths**: for each relation the optimizer chooses between a **full table scan** and an **index scan** by estimating cost from **selectivity** ($\text{matching}/\text{total}$) and catalog statistics (index levels, distinct values, clustering).
- **Selective predicates** (equality on keys, small ranges): index lookup ≈ height + 1 I/Os vs $b$ blocks for a scan (Tutorial 4 Ex 2: 4 I/Os vs 50,000).
- **Joins:** an index on the inner relation's join column enables **index nested-loop joins**; sorted indexes enable **merge joins**.
- **Avoiding sorts:** reading a B+-tree in order satisfies ORDER BY, GROUP BY, MIN/MAX.
- **Covering indexes** answer queries without touching the table (Tutorial 4 Ex 7: 5–6 vs 503 I/Os).
- **Unique indexes** tell the optimizer a predicate returns ≤ 1 row → good choice for join order.
- The optimizer **will not use an index** when selectivity is poor (e.g. `status='pending'` = 25% of rows → full scan; bitmap index better for low cardinality) or when a non-clustered index would cause too many random I/Os.

**Influence on system performance**
- (+) Faster queries, lower I/O and CPU per query → better response time and throughput, more concurrent users, less contention.
- (−) **Write overhead**: each INSERT/UPDATE/DELETE maintains every index (splits/merges); **storage**; too many indexes enlarge the optimizer's search space and maintenance; stale statistics → bad plans.
- **Guidelines:** index columns used in WHERE/JOIN/ORDER BY with good selectivity; clustered index on the main range column; composite/covering indexes for frequent queries; drop unused indexes; keep statistics current; verify with EXPLAIN.

### How to approach
Two halves: (1) how the optimizer uses indexes (access paths, selectivity, joins, sorting, covering); (2) system-wide effects (read gains vs write/storage costs). One numeric example strengthens it.

## 2020/21 · Q7(a) [20 marks]
> **Question:** Discuss the reasons for poor performance of queries and possible remedies.

> [!note] No dedicated lecture section
> Built from L4 §1.2 (cost factors), L4 essay questions (indexing, execution plans, joins vs subqueries, data distribution, refactoring, caching) and L1 (disk I/O).

### Expected answer
| Reason | Remedy |
|---|---|
| **Missing/unsuitable indexes** → full scans | create indexes on filter/join columns; composite or covering indexes |
| **Non-selective use of non-clustered indexes** → random I/O | clustered index for range-heavy columns; let optimizer choose scans |
| **Poorly written SQL**: `SELECT *`, functions on indexed columns, unnecessary DISTINCT/ORDER BY, correlated subqueries, redundant joins | **query refactoring**: select only needed columns; rewrite subqueries as joins; make predicates sargable |
| **Missing join conditions / Cartesian products; bad join order** | correct conditions; heuristic + cost-based optimization |
| **Outdated statistics / skewed data** → wrong estimates | update statistics; histograms; partitioning |
| **Large intermediate results; memory spills (external sort)** | push σ/π down; pipelining; more memory |
| **Disk I/O bottlenecks**: fragmentation, scattered blocks, slow disks | contiguous allocation, reorganization, buffering/caching, SSD, RAID striping |
| **Too many indexes slowing writes** | drop unused indexes |
| **Concurrency: locking, long transactions** | shorter transactions, proper isolation levels |
| **Repeated identical queries** | query/result caching |
| **Network cost in distributed systems** | data localization, semijoins, replication |
Diagnostic tool: inspect the **execution plan** (EXPLAIN) to find full scans, expensive joins and sorts.

### How to approach
Reason → remedy pairs (table), 6–8 rows; finish with "use EXPLAIN to diagnose".
