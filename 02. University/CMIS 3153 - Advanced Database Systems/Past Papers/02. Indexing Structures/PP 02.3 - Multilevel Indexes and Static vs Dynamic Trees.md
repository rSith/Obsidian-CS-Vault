# PP 02.3 · Multilevel Indexes; Static vs Dynamic Tree Indexes

> [!info] [[PP 02 - Indexing Structures|PP 02 index]] · Lesson: [[02.06 Multilevel Indexes]]

---

## 2021/22 · Q1(d) [25 marks]
> **Question:** How does the multilevel indexing structure improve the efficiency of searching an index file?

### Expected answer
- A single-level ordered index of $b_1$ blocks is searched by **binary search**: $\lceil \log_2 b_1 \rceil$ block accesses, halving the search space at each step.
- A **multilevel index** treats the first-level index as an ordered file and builds a **sparse primary index on it** (second level), then an index on that, and so on, until the **top level fits in one block**.
- Each index block holds **fo** entries (the **fan-out** = index blocking factor $bfr_i$), so each level divides the search space by **fo** (typically 50–300) instead of 2.
- A search reads **one block per level** + one data block: $t + 1$ accesses with
$$t = \lceil \log_{fo} r_1 \rceil$$
- **Example (lecture):** dense secondary index with $r_1 = 30{,}000$ entries, $fo = 68$, $b_1 = 442$ blocks: binary search = 9 + 1 = **10** accesses. Multilevel: level 2 = ⌈442/68⌉ = 7 blocks, level 3 = 1 block → $t = 3$ → **4** accesses.
- Further, a **dynamic** multilevel index (B/B+-tree) leaves free space and splits/merges nodes so that insertions and deletions don't require reorganizing ordered index files.

### How to approach
Explain binary search cost → the idea of an index on the index → fan-out → formula → lecture example → mention B+-trees as the dynamic version.

## 2023/24 · Q3(b) [25 marks]
> **Question:** Discuss the circumstances under which a static tree index might be preferred over a dynamic tree index.

### Expected answer
- **Static tree index (ISAM-style):** the non-leaf levels are built once and **never change**; new entries go to **overflow pages** chained from the leaf pages; periodic rebuild.
- **Dynamic tree index (B+-tree):** nodes **split and merge** on every insert/delete; the tree stays balanced.

**A static index is preferred when:**
1. The data is **static or read-mostly**: archives, historical/reporting tables, data warehouses, reference/lookup tables loaded in bulk. Few inserts → no overflow chains → no balance problems.
2. **Updates are rare or come in periodic batches**: rebuild the index after each batch load.
3. **High concurrency of readers**: because index pages above the leaves never change, **no locking of non-leaf pages** is required; dynamic trees must lock nodes during splits/merges, which limits concurrency.
4. Space efficiency matters: a static index can be **packed 100% full** (dynamic nodes are typically ~67% full), so fewer pages and sometimes one level fewer → faster searches.
5. The key distribution is **known and stable**, so the static structure suits it; simplicity and **predictable** behaviour.

**When not:** frequent inserts concentrated in some key ranges create **long overflow chains**, making search cost grow → dynamic B+-trees are better for volatile OLTP data.

### How to approach
Define both → list 3–5 circumstances with reasons (read-mostly, batch updates, concurrency, space) → one sentence on when dynamic wins.
