# PP 02.2 · Clustered vs Unclustered Indexes, and Choosing Indexes

> [!info] [[PP 02 - Indexing Structures|PP 02 index]] · Lesson: [[02.05 Clustered vs Non-Clustered Indexes and Index Selection]] · Tutorial: [[TUT 4 - Selectivity and Index Cost]]

---

## 2020/21 · Q6(b) [30 marks] and 2022/23 · Q2(b) [25 marks]
> **Questions:** Briefly explain what clustered and unclustered indexes are. (2020/21) · Explain clustered indexing and non-clustered indexing, highlighting the key differences between them and providing examples where one might be preferred over the other. (2022/23)

### Expected answer
- **Clustered index:** the **data rows are stored physically in the same order as the index key** (the index determines the row order). Only **one** per table. Matching rows for a range are **contiguous**.
- **Unclustered (non-clustered) index:** a **separate structure** holding keys and **pointers (row IDs)** to rows stored elsewhere in some other order. **Many** per table. Matching rows may be **scattered** across blocks.

| Difference | Clustered | Non-clustered |
|---|---|---|
| Row order | = index order | independent |
| Per table | one | many |
| Range query I/O | sequential, few pages | up to one random I/O per row |
| Point lookup | fast | fast + one pointer hop |
| Insert/update cost | higher (keep physical order; page splits; row moves if key changes) | lower on the table, but each index updated |
| Extra storage | no extra copy of rows | separate structure |

**When to prefer which**
- **Clustered** on columns used for **range queries / sorting / grouping**: e.g. `Order_Date` for "orders last month", `Salary` for "salary between 40k and 60k", primary key IDs that are scanned in order. Tutorial 4: 300,000 rows (6%) in a date range → clustered range scan used; non-clustered → 300,000 random reads → full scan preferred.
- **Non-clustered** on **selective lookup** columns: e.g. `Email`, `Customer_ID` (foreign key for joins), `Reg_No` when the table is clustered on something else; and as **covering indexes** for frequent queries.

## 2023/24 · Q2(b) [25 marks]
> **Question:** Discuss which indexing approach best supports frequent range and exact-match queries in a database table, with reference to clustered and non-clustered indexes.

### Expected answer
- A **B+-tree** index supports **both**: exact match = one root-to-leaf traversal (≈ 3–4 I/Os); range = find the first key then follow the **linked leaves**. A hash index supports only exact match.
- Make the B+-tree **clustered** on the column with the **heaviest range workload**, because ranges benefit most from physical order: matching rows are read sequentially (e.g. 50,000 rows = 250 pages clustered vs up to 50,000 random reads non-clustered, Tutorial 4 Exercise 3). Only one clustered index is possible, so choose it carefully (stable, frequently ranged, ideally ever-increasing to avoid mid-table inserts).
- Use **non-clustered** B+-tree (or **hash**) indexes for **exact-match** columns with **high selectivity** (few rows per value), where scattered rows cost little; consider **covering** composite indexes for frequent queries.
- Note the cost: more indexes = more maintenance on writes.
**Conclusion:** clustered B+-tree on the main range column + non-clustered (B+-tree/hash) indexes for selective exact-match columns.

## 2020/21 · Q5(b) [30 marks]
> **Question:** Discuss what you would consider in choosing each of the following index types in creating an index on a relation: (i) the choice of primary index; (ii) hash versus tree indexes.

### Expected answer
**(i) Choice of primary (clustered) index**: only one is possible, so consider:
1. Which attribute is most used for **range queries, ORDER BY, GROUP BY**, or sequential processing → physical order helps most.
2. Whether the attribute is **unique** (primary index) or not (clustering index).
3. **Update frequency** of the attribute: avoid volatile attributes (changing them moves rows).
4. **Insert pattern**: monotonically increasing keys append at the end; random keys cause splits/reorganization.
5. Use in **joins** (merge joins on sorted data).
6. The **relative frequency/importance** of queries vs updates in the workload.

**(ii) Hash vs tree indexes**
- **Hash:** best for **equality** (`=`) only; ~1 I/O; no ranges, no ordering, no prefix searches; sensitive to skew; static hashing needs rehashing as data grows.
- **Tree (B+-tree):** supports **equality and ranges**, ordered scans, MIN/MAX, prefix; balanced and dynamic; cost height + 1.
- **Decide by the query types on the attribute:** equality-only → hash; any ranges/ordering → B+-tree; also consider data growth and skew.

## 2020/21 · Q6(c) [45 marks]
> **Question:** Relation $R(a, b, c, d, e)$ with at least 1000 distinct values for each attribute. Workloads A and B independently: **A.** 100,000 queries `select * from R where b < ?`; **B.** 10,000 queries `select * from R where c = ?`. If possible to speed it up significantly by adding up to two indexes, specify for each index: (i) search key, (ii) clustered or unclustered, (iii) hash or B+-tree. If an index would not make a significant difference, say so. Justify.

### Expected answer
**Workload A: range queries on b**
- (i) Search key: **b**.
- (ii) **Clustered**: a range `b < ?` can return a large fraction of R; with clustering the qualifying tuples are on consecutive pages (sequential I/O). An unclustered index could need one random I/O per tuple and might be no better than a scan for large ranges.
- (iii) **B+-tree**: hash indexes cannot evaluate `<`.
- Significant speed-up: yes, compared with scanning all of R for each of the 100,000 queries.

**Workload B: equality queries on c**
- (i) Search key: **c**.
- (ii) **Unclustered is sufficient**: with ≥ 1000 distinct values each query returns about ≤ 0.1% of R, so following a few pointers is cheap. (Because the workloads are independent, a clustered index on c would also be acceptable; if both workloads ran on the same table, the single clustered index should go to **b**.)
- (iii) **Hash index**: pure equality; ~1 bucket access. (A B+-tree would also work, slightly more I/O.)
- Significant speed-up: yes, versus a full scan per query.

**Summary**
| Workload | Key | Clustered? | Structure |
|---|---|---|---|
| A (`b < ?`) | b | clustered | B+-tree |
| B (`c = ?`) | c | unclustered | hash |

### How to approach
Answer the three sub-items for each workload in a table, then justify each choice in 1–2 sentences, mentioning range vs equality and selectivity.
