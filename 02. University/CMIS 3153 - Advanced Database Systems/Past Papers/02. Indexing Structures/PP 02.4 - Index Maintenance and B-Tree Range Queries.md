## 2022/23 · Q2(c)(i) [25 marks] · 2023/24 · Q2(c)(i) [25 marks] · 2022/23 · Q7(e) [short note, 25 marks]
> **Questions:**
> - Large table **Students(Student_ID, Name, Age, GPA)**, frequently queried for students with a GPA higher than a threshold. (i) Discuss the impact of index creation and maintenance on performance, particularly with respect to insertions, deletions, and updates. (2022/23)
> - Retail table **Orders(Order_ID, Customer_ID, Order_Date, Total_Amount, Order_Status)**, frequently queried for orders with Total_Amount above a value, while new orders are continuously inserted and existing ones updated or cancelled. (i) Discuss how creating and maintaining indexes affects performance during insert, delete, and update operations. (2023/24)
> - Short note: Impact of indexing on Insert, Update, and Delete operations. (2022/23 Q7(e))

### Expected answer
**Benefit side:** an index on GPA / Total_Amount turns the frequent range query from a full table scan into an index search (a few I/Os) plus reading only matching rows. Updates/deletes **with a WHERE clause** also find their rows faster.

**Cost side: every index is a second copy of (part of) the data that must be kept consistent.**
| Operation | Effect on indexes |
|---|---|
| **INSERT** | an entry must be added to **every** index on the table in sorted position; in a B+-tree the leaf may **overflow and split**, splits may propagate up; for a **clustered** index the row must be placed in key order (page splits, row movement). Cost grows with the **number of indexes**. |
| **DELETE** | the entry is removed from every index; nodes may **underflow → redistribute or merge**; sorted structures leave gaps (deletion markers, later reorganization). |
| **UPDATE of an indexed column** | = **delete old entry + insert new entry** in that index (e.g. a GPA change, a Total_Amount correction); if the column is the **clustered key**, the **row physically moves** and secondary indexes pointing to its location may need updating. |
| **UPDATE of a non-indexed column** | indexes unaffected (if the row stays in place), e.g. Order_Status change when no index on Order_Status. |
| **Index creation** | scans and sorts the whole table; locks/resources while building. |
| **Other costs** | extra **disk space**; **locking/contention** on hot index pages (e.g. ever-increasing Order_IDs at the right edge); **fragmentation** over time → rebuilds; more work for the optimizer. |

**Scenario-specific points**
- *Students:* GPA changes each semester → each change updates the GPA index; new intakes insert into all indexes; graduates are deleted (merges). Keep **Student_ID as the clustered/primary index** and GPA as a **non-clustered B+-tree**; bulk GPA updates can be followed by an index rebuild.
- *Orders:* continuous inserts → keep the clustered key **ever-increasing** (Order_ID/Order_Date) so inserts append without splits in the middle; a **non-clustered B+-tree on Total_Amount** serves the range query; **cancellations** (Order_Status updates) do not touch the Total_Amount index; avoid indexing low-cardinality, frequently-changing columns like Order_Status in an OLTP table.

**Guidelines:** index only columns that queries actually filter/join/sort on; avoid redundant indexes (lecture lab: drop unused indexes); choose a stable clustered key; batch updates; monitor with EXPLAIN; balance read speed vs write overhead.

### How to approach
Start with the benefit (1–2 lines), then go **operation by operation** (insert, delete, update) explaining splits/merges and clustered moves, then **other costs**, then **apply to the table in the question**, then guidelines.

## 2022/23 · Q2(c)(ii) [25 marks] and 2023/24 · Q2(c)(ii) [25 marks]
> **Questions:** Explain how B-tree indexing could be used to speed up these GPA-based queries. Describe the structure of a B-tree index and its operations. (2022/23) · Explain the structure and key operations of a B-tree index and discuss how a B-tree index on the Total_Amount field improves the efficiency of range queries. (2023/24)

### Expected answer
**Structure**
- A **balanced search tree** in which every node is a **disk block** containing many **sorted keys** and pointers; **all leaves are at the same depth**.
- Order $p$: a node has at most $p$ child pointers and $p-1$ keys; every node except the root is at least **half full** ($\ge \lceil p/2 \rceil$ children); root has ≥ 2 children.
- In a B-tree each key appears **once** with a **data pointer**; in a **B+-tree** (used by DBMSs) **all keys with data pointers are in the leaves**, internal nodes hold only separator keys, and **leaves are linked** in key order.
```text
                 [ 3.0 | 3.5 ]
          ┌────────┼─────────┐
   [2.1 2.5 2.8] [3.0 3.2 3.4] [3.5 3.7 3.9 4.0]   ← linked leaves (B+-tree)
```

**Operations**
- **Search:** start at the root, compare the key with the node's keys, follow the matching child pointer, repeat to a leaf. Cost = **height** (e.g. 3–4 I/Os for millions of rows): $O(\log_p N)$.
- **Insert:** find the leaf; insert in sorted position; if the node overflows, **split** it and **push the middle key up**; splits may propagate; a root split creates a new root (height + 1). Tree stays balanced.
- **Delete:** remove the key (internal keys replaced by predecessor/successor in a B-tree); if a node **underflows**, **borrow** from a sibling (redistribute) or **merge** with it (pulling down the separator); may propagate; root may disappear (height − 1).

**Speeding up the range query** (`GPA > 3.5` / `Total_Amount > 10000`)
1. `CREATE INDEX idx_gpa ON Students(GPA);` (or `ON Orders(Total_Amount)`).
2. **Search** the tree for the first key > threshold: ~3–4 block reads instead of scanning all blocks.
3. **Scan forward** in key order: in a B+-tree simply follow the **linked leaves** (in a plain B-tree, an in-order traversal) collecting all qualifying entries.
4. Fetch the rows via their pointers: cheap when few rows qualify or the index is **clustered**; if a very large fraction qualifies with a non-clustered index, the optimizer may still prefer a full scan.
5. Because the tree **stays balanced** during the frequent inserts/updates/deletes, the search cost remains logarithmic and predictable.

**Comparison:** without index → read all $b$ blocks; with index → height + leaf blocks covering the range + matching rows.

### How to approach
Diagram → structure bullets → three operations → step-by-step range query → one sentence on clustered vs non-clustered effect.
