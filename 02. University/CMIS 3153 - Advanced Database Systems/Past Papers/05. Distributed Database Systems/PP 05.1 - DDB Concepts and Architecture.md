# PP 05.1 · Distributed Database Concepts, Benefits and Architecture

> [!info] [[PP 05 - Distributed Database Systems|PP 05 index]] · Lessons: [[05.01 DDB Concepts and Architecture]], [[05.03 Transparency, Autonomy and Reliability]]

---

## 2022/23 · Q6(a) [25 marks] and 2023/24 · Q7(c) [20 marks]
> **Questions:** Explain the concept of a distributed database, and how it differs from a centralized database. (2022/23) · Define a distributed database system and explain its key characteristics and architecture. How does it differ from a centralized database system in terms of data storage, processing, and transparency? (2023/24)

### Expected answer
**Definition.** A **distributed database (DDB)** is a **collection of multiple, logically related databases distributed over a computer network**. A **distributed DBMS (DDBMS)** is the software that **manages the DDB and makes the distribution transparent** to users. It consists of **loosely coupled sites (nodes)** that share no physical components; a transaction may access data at one or several sites and is executed by them in a unified way.

**Key characteristics**
- Data spread over **multiple sites** connected by a **network**; each site has its own DBMS, processors and storage.
- **Logically one database**: a **global schema** over all sites.
- **Fragmentation** (horizontal/vertical) and **replication** of data.
- **Transparency**: location, naming, fragmentation and replication transparency; design and execution transparency.
- **Autonomy** of sites (design, communication, execution).
- **Distributed query processing and distributed transactions** (2PC), **reliability and availability** through replication and fault isolation.

**Architecture (diagram):** users → global schema / global query processor / global transaction manager / distributed catalog → sites, each with a local DBMS, local schema and local data (fragments/replicas) → communication network. (See [[05.01 DDB Concepts and Architecture]] §3.)

**Distributed vs centralized**
| Aspect | Centralized | Distributed |
|---|---|---|
| **Data storage** | all data at **one site** | data **fragmented and/or replicated** over several sites, placed near its users |
| **Processing** | one DBMS executes every query | queries **decomposed** into sub-queries at several sites, executed **in parallel**, results **merged**; communication cost matters |
| **Transparency** | only logical/physical data independence | must also provide **distribution transparency**: users don't see location, fragments, copies |
| Reliability | single point of failure | failure isolated to a site; replicas keep data available |
| Scalability | vertical | horizontal (add sites) |
| Transactions | local concurrency control/recovery | distributed locking, deadlock detection, **2PC** |
| Complexity | simpler | complex design (fragmentation, allocation, catalog, consistency) |

### How to approach
Definition (both DDB and DDBMS) → characteristics → diagram → comparison table organized by the three named aspects (storage, processing, transparency).

## 2021/22 · Q3(a) [25 marks]
> **Question:** With the aid of a diagram, explain the Distributed Database architecture.

> [!warning] Partly beyond the lecture
> The lecture shows only the "distributed database environment" (Figure 1) and homogeneous/heterogeneous figures. The layered schema architecture is textbook material (Elmasri & Navathe). This information could not be fully verified from the available course materials.

### Expected answer
```text
                         Global users / applications
                                   │
      ┌──────────── Global conceptual schema (one logical DB) ─────────────┐
      │  Fragmentation schema → Allocation schema                           │
      │  DDBMS: global query processor · global transaction manager ·      │
      │         replication manager · distributed catalog (directory)      │
      └────────────────────────────────────────────────────────────────────┘
           │                          │                          │
   ┌───────▼────────┐        ┌────────▼───────┐         ┌────────▼───────┐
   │ Site 1         │        │ Site 2         │         │ Site 3         │
   │ local schema   │        │ local schema   │         │ local schema   │
   │ local DBMS     │        │ local DBMS     │         │ local DBMS     │
   │ local data     │        │ local data     │         │ local data     │
   └───────┬────────┘        └────────┬───────┘         └────────┬───────┘
           └──────────────── communication network ──────────────┘
```
- **Sites (nodes):** independent computers, each with its own local DBMS and database storing **fragments/replicas**; loosely coupled, no shared memory or disks.
- **Communication network:** LAN/WAN connecting the sites; transfers queries, data and results.
- **Global conceptual schema:** the single logical description users see.
- **Fragmentation schema:** how global relations are split into fragments (σ for horizontal, π for vertical).
- **Allocation schema:** which site(s) store each fragment (replication).
- **Local schemas:** how each site stores its part.
- **DDBMS components** (at each site): global query processing/optimization (decomposition, localization), distributed **transaction management** (concurrency control, 2PC, recovery), **replication** management, the **distributed catalog/directory**.
- Styles: **client–server**, **peer-to-peer/collaborating servers**, **federated/multidatabase** (heterogeneous).
The architecture gives **distribution transparency**: users query the global schema; the DDBMS maps queries to fragments and sites.

## 2023/24 · Q6(a) [25 marks]
> **Question:** A multinational company with branches in Colombo, London and Singapore plans to integrate their local customer order databases into a distributed database system to enhance availability, performance, and global data access. Identify the features that make this setup a distributed database system, and explain the benefits the company can expect.

### Expected answer
**Features that make it a DDB**
1. **Multiple sites**: the Colombo, London and Singapore servers each keep their own database (local DBMS, storage).
2. **Connected by a network** (WAN between continents).
3. **Logically related data integrated under one global schema**: customer orders from all branches form **one logical database**.
4. **A DDBMS** coordinating the sites and providing **transparency**: a user in London can query all orders without knowing where they are stored.
5. **Fragmentation/replication** of the orders data across branches; **distributed queries and transactions** span sites.
6. **Local autonomy**: each branch can keep processing local orders.

**Expected benefits**
| Benefit | For this company |
|---|---|
| **High availability / reliability** | if the Singapore server or link fails, Colombo and London continue; replicated data still accessible; no single point of failure |
| **Performance** | each branch accesses its own orders **locally** (low latency); global reports run **in parallel** at three sites; load balanced |
| **Global data access** | head office sees all orders as one database (location transparency) |
| **Scalability** | add new branches/sites (horizontal scaling) without replacing hardware |
| **Disaster recovery** | copies in other countries survive a local disaster |
| **Local autonomy and compliance** | data can stay in its region (data-protection laws); local management |
| **Cost** | commodity servers instead of one huge central server |
| **Easier application development/expansion** | transparency hides distribution from applications |

### How to approach
Two lists tied to the scenario: features (what makes it distributed) → benefits (what the company gains). Always mention the city names.
