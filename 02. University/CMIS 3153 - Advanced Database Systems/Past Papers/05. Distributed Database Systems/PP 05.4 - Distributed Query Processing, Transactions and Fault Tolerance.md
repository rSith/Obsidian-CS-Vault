# PP 05.4 · Distributed Query Processing, Transaction Management and Fault Tolerance

> [!info] [[PP 05 - Distributed Database Systems|PP 05 index]] · Lessons: [[05.06 Distributed Query Processing and Semijoin]], [[05.07 Distributed Concurrency Control and Recovery]]

---

## 2023/24 · Q6(c) [25 marks]
> **Question:** Customer order reports frequently involve queries that access data from multiple locations (Colombo, London, Singapore). Explain how distributed query processing and optimization would be performed, and discuss the main challenges involved.

### Expected answer
**How it is performed (lecture stages)**
1. **Query mapping:** the report query (e.g. monthly sales per product across all branches) is written against the **global schema** and translated into an algebraic query on **global relations**: normalized, checked for semantic errors, simplified (as in a centralized DBMS).
2. **Localization:** using fragmentation/replication information, global relations are replaced by their **fragments**: `Orders` → `Orders_Colombo ∪ Orders_London ∪ Orders_Singapore`; replicated tables (Products) are read from the nearest copy.
3. **Global query optimization:** choose the strategy with the lowest cost, where **communication cost usually dominates** (WAN). Techniques:
   - push **selections/projections** to each site (only this month, only needed columns);
   - **partial aggregation** at each site (local SUM/COUNT per product), shipping only small summaries;
   - **ship the smaller relation** to the site of the larger one (lecture example: shipping DEPARTMENT, 3,500 bytes, instead of EMPLOYEE, 1,000,000 bytes);
   - **semijoins**: send only join-column values to the remote site to filter tuples before shipping them back (lecture: 4,800 vs 1,000,000 bytes for Q′).
4. **Local query optimization** at each branch (indexes, local join algorithms).
5. **Join processing** (query-to-data / data-to-query / hybrid), **aggregation**, and **result merging** at the result site (union of partial results, combine sums/counts).

**Main challenges**
- **High communication cost and latency** over intercontinental links.
- **Cost estimation** is harder: statistics of remote fragments may be stale; network speed varies.
- **Large search space** of strategies (where to execute each operation, join order, semijoins).
- **Replica selection and consistency** (avoid stale copies).
- **Site/link failures** during execution; partial results.
- **Load imbalance / data skew** between branches; **heterogeneity** (different DBMSs/schemas); **security** of data in transit; currency/time-zone differences in reports.

## 2023/24 · Q7(d)(ii) [15 marks]
> **Question:** (New York, London, Singapore) Explain how query processing and transaction management would be handled to ensure consistency and efficiency across the sites.

### Expected answer
**Query processing (efficiency)**
- Global queries decomposed and **localized** to branch fragments; selections/aggregations pushed to sites; small replicated tables read locally; semijoins and "ship the smaller relation" to minimize transfer; parallel execution and merging at the result site.
- Most day-to-day queries are **local** to one branch's fragment → no network cost.

**Transaction management (consistency)**
- Local transactions (orders of the local branch) committed locally.
- **Distributed transactions** (e.g. an order using stock from another branch) coordinated by the originating site with **two-phase commit**: *prepare* (all participants vote) → *commit/abort* (only if all vote yes), so all sites commit or none; **three-phase commit** avoids blocking if the coordinator fails.
- **Concurrency control:** distributed two-phase locking using a **primary-copy** scheme (locks on the primary copy of each replicated item) or **voting/quorum**; **distributed deadlock detection**/time-outs.
- **Replica consistency:** synchronous updates for critical data (stock, payments); asynchronous propagation for catalogue data.
- **Recovery:** logs and checkpoints at each site; coordinator **election** or backup site if the coordinator fails; recovering sites catch up before rejoining.

## 2022/23 · Q7(f) [short note, 25 marks]
> **Question:** Fault tolerance in Distributed Databases.

### Expected answer
**Fault tolerance** is the ability of a distributed database to **continue operating correctly despite failures** of sites, disks or communication links. Concepts: a **fault** causes an **error** (bad state) which may cause a **failure** (deviation from specified behaviour); **reliability** = probability the system is up at a point in time; **availability** = probability it is continuously available over an interval.

**Types of failures in DDBs:** site (node) crashes, disk failures, **communication link failures**, **network partitioning**, failures during **distributed commit**.

**Mechanisms**
1. **Replication / redundancy**: copies of data at several sites; if one fails, others serve requests.
2. **No single point of failure / fault isolation**: failures confined to their site; other sites continue.
3. **Primary site with backup site**, **primary copy**, and **coordinator election** when a coordinator fails.
4. **Voting (quorum)**: a majority of copies can still grant locks/serve data when some are unreachable.
5. **Distributed commit protocols**: **2PC** (all-or-nothing commit), **3PC** (non-blocking if the coordinator crashes).
6. **Logging and checkpointing** to recover each site to a consistent state; recovering sites are brought **up to date** before rejoining.
7. **Handling partitions**: CAP trade-off: stay consistent (CP) or available (AP, eventual consistency).
8. **Geographic distribution and disaster recovery**: copies in different regions survive site-wide disasters.
9. Within a site: **RAID** and backups.

**Importance:** high availability for 24/7 global services; protection against data loss; but replication and coordination add **update cost and complexity**.

### How to approach
Define → list failure types → mechanisms (with lecture terms) → trade-offs/importance.
