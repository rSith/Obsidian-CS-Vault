# PP 05.3 · CAP Theorem and DDB Properties Applied to Scenarios

> [!info] [[PP 05 - Distributed Database Systems|PP 05 index]] · Lessons: [[05.02 CAP Theorem]], [[05.03 Transparency, Autonomy and Reliability]]

## 2022/23 · Q6(b) [25 marks]
> **Question:** Discuss the CAP Theorem (Consistency, Availability, Partition Tolerance) and how it applies to distributed databases.

### Expected answer
**CAP theorem (Brewer's theorem):** a distributed data store can guarantee **at most two** of:
- **Consistency (C):** every read returns the **most recent write**; all nodes see the same data at the same time.
- **Availability (A):** **every request receives a response** (read or write), even if some nodes are down, though the data may not be the latest.
- **Partition tolerance (P):** the system **continues to operate** when the network splits and some nodes cannot communicate.

**Key insight:** network partitions are unavoidable in real distributed systems, so **P must be provided**; therefore **during a partition** a system must choose between **C** (reject or delay some requests to avoid inconsistency) and **A** (answer every request, possibly with stale data). Without partitions both C and A are possible.

**Types**
- **CP:** consistency + partition tolerance; may refuse requests during partitions: **HBase, ZooKeeper** (lecture).
- **AP:** availability + partition tolerance; temporary inconsistency, **eventual consistency**: **Cassandra, Couchbase** (lecture).
- **CA:** consistency + availability without partition tolerance: **only theoretical** for distributed systems (a single-site DB).

**How it applies to DDB design**
- Arises from **replication**: copies at several sites must be synchronized over the network.
- Designers choose per type of data: banking/inventory → CP; social media feeds, carts, catalogues → AP with eventual consistency.
- Implemented via synchronous vs asynchronous replication, quorum/voting, distributed commit (2PC), conflict resolution.
- Explains the variety of database models (NoSQL systems tuned for C or A).
*Example:* two bank branches, link broken: refuse withdrawals (CP) or allow them on possibly stale balances (AP).

## 2022/23 · Q6(c)(i) [25 marks]
> **Question:** You are designing a distributed database to support a multinational logistics company that manages warehouses, shipping routes and inventory across geographic regions; large transactional volume, high availability, consistency across sites. Explain how the core properties of distributed databases impact the design and operation of such a system.

### Expected answer
| Property | Impact on design and operation |
|---|---|
| **Distribution (location/naming) transparency** | dispatchers anywhere query `Inventory`, `Shipments`, `Routes` without knowing which regional server holds them; data can be relocated without changing applications; requires a **global catalog** with unique names |
| **Fragmentation transparency** | inventory and shipment tables **horizontally fragmented by region/warehouse** for local speed; global queries ("total stock of item X worldwide") see one table → DDBMS must localize and merge fragment queries |
| **Replication transparency** | routes, product master data and warehouse lists **replicated** to all regions for fast reads; the DDBMS keeps copies consistent (synchronous for critical data) |
| **Autonomy** | each regional warehouse system keeps receiving, picking and shipping when links to other regions fail; local maintenance; but global coordination rules must be agreed |
| **Reliability and availability** | failure of one warehouse server doesn't stop others; replicas and backup sites keep data accessible 24/7; isolation of faults |
| **Distributed transaction management** | inter-warehouse transfers update two sites **atomically (2PC)** so stock is never lost or double-counted; distributed concurrency control prevents two regions from allocating the same stock |
| **Distributed query processing** | global reports executed in parallel at regional sites with partial aggregation; communication cost minimized |
| **Scalability** | new regions/warehouses added as new sites |
| **Consistency vs availability (CAP)** | decides which data must be strongly consistent (stock levels) vs available (tracking) |

### How to approach
Name each core property → state its consequence for **this** logistics system (warehouses, routes, inventory) → a design decision it implies.

## 2022/23 · Q6(c)(ii) [25 marks]
> **Question:** For this logistics system, which properties of the CAP Theorem would be prioritized, and why?

### Expected answer
- **Partition tolerance is mandatory**: regional data centres are linked over WANs; partitions will happen; the system must keep operating.
- **Consistency for transactional core data → CP**: inventory levels, stock allocation, order and shipment status changes, billing. Inconsistent stock across sites leads to **over-selling, double allocation of the same pallet/truck, failed deliveries and financial loss**; the requirement explicitly asks for **consistency across sites**. During a partition, conflicting cross-region updates are blocked/queued rather than accepted inconsistently.
- **Availability for read-heavy, tolerant data → AP**: shipment tracking, vehicle locations, dashboards, route suggestions. Customers and drivers must always get an answer; seconds of staleness are acceptable (**eventual consistency**).
- **Design to reduce the impact:** fragment data so most transactions are **local to one region** (each region remains available for its own data even during a partition while remaining consistent), replicate read-only reference data, use synchronous replication within a region and asynchronous across regions for non-critical data.
**Conclusion:** **CP** for the transactional inventory/order core (with P), **AP** for tracking/analytics: a balanced design matching the stated needs for consistency *and* high availability.

## 2023/24 · Q6(d) [25 marks]
> **Question:** Using the CAP theorem, analyse the trade-offs the company (Colombo, London, Singapore customer orders) must consider when designing this distributed database system.

### Expected answer
1. **Partitions are inevitable** between Colombo, London and Singapore (intercontinental WAN) → **P required**; the real choice is **C vs A during partitions**.
2. **Choosing consistency (CP):** order placement/stock/payment data stay correct everywhere; but during an outage a branch may **reject or delay** orders that need other sites' data → lost sales, unhappy customers.
3. **Choosing availability (AP):** every branch keeps accepting orders during outages; replicas may diverge (e.g. the last unit sold twice, duplicate customer updates) → need **reconciliation**, conflict resolution, refunds/back-orders after the partition heals.
4. **Latency trade-off even without partitions:** strong consistency across continents needs **synchronous** coordination (2PC/quorums) adding ~150–300 ms round trips per write; asynchronous replication is fast but temporarily inconsistent.
5. **Data-specific decisions:**
   | Data | Choice | Reason |
   |---|---|---|
   | stock levels, payments, order confirmation | **CP** | correctness and money |
   | product catalogue, prices | AP (replicated everywhere) | read-mostly; brief staleness acceptable |
   | order history/reporting | AP / eventual | analytics tolerate delay |
6. **Mitigation:** horizontal fragmentation by branch so most orders are **local** (no cross-site coordination needed), quorum reads/writes for shared data, clear conflict-resolution rules, monitoring of partition events.

### How to approach
Explain C/A/P briefly → state P is mandatory → analyse "if CP …" and "if AP …" consequences **for this company** → recommend a per-data-type mix.
