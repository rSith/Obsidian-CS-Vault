# 06.01 · Relational vs Object-Oriented (vs Object-Relational) Data Models

> [!info] [[06.00 Object-Relational Databases|Lesson 6]] · ORDBMS slides 1–8, 9–10, 17–20, 49–50 · Priority 🟡 Medium
> **Asked as:**
> - "Discuss the differences between relational, object-oriented and object-relational data models … data representation, data definition languages, data manipulation, and data access/query languages." (2021/22 Q4(b), 30 marks)
> - "Superficially the object-oriented and relational data models are similar but functionally very different. Discuss whether (i) a Class in a UML class diagram is equivalent to an Entity Type in a relational model; (ii) a Class is equivalent to a Relation/Table." (2021/22 Q4(c), 20 marks)
> - Lecture discussion: "Explain the reasons object-oriented DBMSs never became very popular"; "OODBMS vs RDBMS".

## 1. Relational databases: recap (slides 1–2)
A relational database has **three parts**:
1. a **data model**: data in **tables** with a variable number of **rows**, each with a **fixed number of columns**;
2. a high-level way to express **operations**: getting a subset of rows, a subset of columns, or combining tables (relational algebra / SQL);
3. **design principles**: **normalization** (functional dependencies) to reduce redundancy, increase integrity, minimize complexity.

### Issues with relational databases (slide 3)
- Tables are **flat**: no good support for **nested structures** such as sets and arrays.
- Weak support for **complex data types** (graphics, multimedia, objects).
- Do **not take advantage of object-oriented** software-engineering approaches (encapsulation, inheritance).

## 2. Object-oriented databases: recap (slide 4)
- An **OODB adds DBMS functionality** (persistence, transactions, queries) **to an OO programming language**.
- It stores an object's **state** (attributes + relationships/links to other objects and their values) and exhibits its **behaviour** through **operations** (methods) that examine or change the state.
- An object's behaviour depends on its state and the operation requested (a **service**).

> [!tip] Analogy
> **Relational:** facts written into a ledger, one line per fact. **Object-oriented:** small robots, each holding its own data and knowing how to do things (methods), and pointing at other robots.

## 3. Why OODBMSs never became popular (slides 5–6)
- RDBMSs had been around **20+ years**; OODBMSs were new and lacked the **efficiencies of well-entrenched** relational systems.
- **Scale:** RDBMSs handle more than $10^{10}$ records, OODBMSs about $10^7$ (lecture figures).
- OODBs are good for **complex descriptions** (e.g. a plant schematic); RDBs suit simple, **flat** data, which is most business data.
- **Market:** RDBMSs > 90%, OODBMSs < 5%.
- Most commercial RDBMSs added an **"object-relational" extension** instead.
- DB features such as **querying, indexing and transactions** depend on **static, visible data**; objects **hide data behind behaviour** (encapsulation), which gets in the way of queries, indexes and transactions ("try indexing a true method").
- Keeping objects connected to a database leaves **~80% of the work** to the developer or an ORM; people felt the remaining 20% benefit wasn't worth leaving the relational/SQL standard.

## 4. Comparison of the three models (2021/22 Q4(b))
| Aspect | Relational | Object-oriented | Object-relational |
|---|---|---|---|
| **Data representation** | flat **tables** of rows/columns; atomic values (1NF); relationships by **foreign keys** | **objects** with state + behaviour; classes, **inheritance**, **encapsulation**; nested/complex structures; relationships by **object references** | tables **plus** user-defined (structured) types, **row and array** types, nested tables, **references (REF)**, typed tables, **type/table inheritance** |
| **Identity** | **primary key value** (user-visible, value-based) | **OID**: system-generated, immutable, independent of values | both: PK and optional **REF IS … SYSTEM GENERATED** OIDs |
| **Data definition (DDL)** | SQL `CREATE TABLE`, constraints | class definitions in an OO language / ODL (ODMG) | SQL:1999/2003 DDL extended: `CREATE TYPE … AS`, `UNDER`, `NOT FINAL`, `CREATE TABLE … OF type`, `REF`, `METHOD` |
| **Data manipulation (DML)** | set-oriented SQL `INSERT/UPDATE/DELETE` | through **methods** of objects in the host language; navigational (follow references) | SQL DML on typed tables + method invocation, dot notation, `->` dereferencing |
| **Query / access language** | **SQL** (declarative, based on relational algebra) | **OQL** (Object Query Language) or navigation in program code | **SQL with object extensions** (SQL3/SQL-99): path expressions, functions on UDTs, `ONLY`, collections |
| Behaviour | outside the DB (apps) or stored procedures | methods are part of the class | methods declared in UDTs; stored procedures/functions |
| Strengths | mature, scalable, simple, standard | complex data, close match to OO code | keeps SQL/relational strengths + object modelling |
| Weaknesses | impedance mismatch; weak complex types | small market, weaker query/optimization, scalability | more complex; vendor differences |

## 5. Is a UML class an entity type or a table? (2021/22 Q4(c))
**(i) UML class vs entity type**
- **Similar:** both describe a **set of things with common attributes** (Student class ≈ STUDENT entity type); class associations ≈ relationship types.
- **But not equivalent:** a class also has **operations (methods)** and **encapsulation**; objects have **identity independent of attribute values** (OID), whereas entities are identified by a **key attribute**; classes support **inheritance/polymorphism** (EER specialization is only partly comparable); attributes may be **multi-valued/complex** objects; associations are **directional** references.
- So a UML class is a **richer** concept: an entity type covers its **structural** part only.

**(ii) UML class vs relation/table**
- A table is a **flat** set of rows with **atomic** values and a **primary key**; a class may have **complex, multi-valued, nested** attributes, **methods**, **inheritance** and **references**.
- Mapping a class usually needs **several tables**: multi-valued attributes and many-to-many associations become separate tables; inheritance becomes one table per class or one table per hierarchy; methods are not stored at all (or become stored procedures).
- Associations in OO are **directional** (a `Customer` has `Set<Order>`, an `Order` has a `Customer`), while foreign keys are **non-directional** (join either way) (slides 19–20).
- An ORM maps **class → table, instance → row, attribute → column** (slides 9–10, 17), which shows they *correspond*, but only **after** the class is flattened. **Conclusion: not equivalent.**
