# 06.05 · Object Identity (OID) vs Primary Key, and Object Tables vs Relational Tables

> [!info] [[06.00 Object-Relational Databases|Lesson 6]] · ORDBMS slides 16, 33, 43–44, 50 · Priority 🔴 High (**asked twice**)
> **Asked as:**
> - "While in relational databases Primary Keys are used for identification, object-oriented and object-relational systems use Object Identities (OIDs). Discuss two main differences between the two concepts." (2020/21 Q4(b), 30 marks)
> - "… Discuss the differences between the two concepts." (2021/22 Q4(d), 25 marks)
> - "Discuss the differences of 'Object Tables' compared to 'Relational Tables' in an Object Relational database." (2020/21 Q4(a), 30 marks)

## 1. Two ways to say "this one"
- **Primary key (relational):** every row must have a **unique primary-key value**, and that **value determines the row's identity** (slide 16).
- **Object identity / OID (object world):** each object has its **own identity simply because it exists** (its "location"), **independent of the values of any of its attributes** (slide 16). In ORDBs the system can generate an OID per row (`REF IS … SYSTEM GENERATED`; PostgreSQL row OIDs, slide 33).

> [!tip] Analogy: twins
> Identical twins can have the same height, hair and clothes (same attribute values) but they are still **two different people**: that is **object identity**. A **primary key** is like identifying people **only by their National ID number**: if you change the number, the database thinks it is a different person; if two records had the same number, they would be "the same person".

## 2. OID vs primary key: differences
| Aspect | Primary key | Object identifier (OID) |
|---|---|---|
| **Basis of identity** | **value-based**: identity = the value of chosen attribute(s) | **existence-based**: independent of attribute values |
| **Who creates it** | **user/designer** chooses and supplies values | **system-generated** (or derived) automatically |
| **Changeability** | values can be **updated** (e.g. a changed email used as key); updates must cascade to foreign keys | **immutable** for the object's whole lifetime, even if every attribute changes |
| **Visibility / meaning** | **visible**, meaningful to users (Reg_No, Ssn) | usually **hidden/internal**, no business meaning |
| **Uniqueness scope** | unique **within one table** | unique **system-wide** (across the database) |
| **Equal attribute values** | two rows with the same key value are the same row (not allowed) | two objects with identical attribute values are still **different objects** (identity ≠ equality) |
| **Referencing** | through **foreign keys** (copy the key value; join to follow) | through **references/pointers** (`REF`, `->` dereferencing); direct navigation |
| **Reuse** | a deleted key value may be reused | an OID is never reused |
| **Requirement** | every table must have a PK | every object has an OID automatically |

**"Two main differences"** (2020/21 Q4(b)), the strongest pair:
1. **Value-based vs value-independent:** a PK is made of attribute values chosen by the designer and can change if values change; an OID is system-generated, independent of attribute values, and **immutable**.
2. **How relationships are made:** PKs are referenced by **foreign keys** (value copies, followed by joins, unique per table); OIDs are referenced by **references/pointers** (followed by dereferencing, unique across the whole system).

## 3. Object tables vs relational tables (2020/21 Q4(a))
An **object (typed) table** is created **from a user-defined type**: `CREATE TABLE Company OF Comp_type (REF IS comp_id SYSTEM GENERATED, …)`. A **relational table** is created with an explicit column list.

| Aspect | Relational table | Object (typed) table |
|---|---|---|
| Definition | `CREATE TABLE T (col1 type, col2 type, …)` | `CREATE TABLE T OF some_type` (structure comes from a UDT) |
| Rows are | tuples of values | **objects (instances) of the type** |
| Identity | primary key values | **OID** (`REF IS … SYSTEM GENERATED / DERIVED`), plus optional PK |
| Can be referenced by | foreign keys | **REF attributes** with `SCOPE`, dereferenced with `->` |
| Column types | usually atomic/built-in | can include UDTs, row types, arrays, nested tables, references |
| Behaviour | none (separate procedures) | **methods** declared in the type apply to every row |
| Inheritance | none (standard SQL) | **type and table hierarchies** with `UNDER`; subtable rows appear in supertable queries |
| Reuse | each table defined separately | one type can define many tables; types reused as column types |
| Schema change | `ALTER TABLE` | change the type (affects all tables of that type) |
