# 06.04 · Object-Relational Features in SQL (SQL3 / SQL-99 / SQL:2003)

> [!info] [[06.00 Object-Relational Databases|Lesson 6]] · ORDBMS slides 29–48 · Priority 🔴 High
> **Asked as:** 2020/21 Q4(c) (40 marks): `CREATE TYPE aType … NOT FINAL; CREATE TYPE bType UNDER aType … FINAL; CREATE TABLE aTable OF aType; CREATE TABLE bTable OF bType UNDER aTable;` inserts, then the results (columns, rows) of `SELECT * FROM aTable` and `SELECT * FROM bTable` · 2023/24 Q7(a) key features.

## 1. Background (slide 29–30)
SQL is a relational language. **SQL3** (from 1989/1992 work) added object-oriented features; a subset was approved as **SQL-99**; **SQL:2003** continued it. SQL-99 provides:
1. **Type constructors** to specify complex objects (row type, array type).
2. A mechanism for **object identity** (reference types).
3. **Encapsulation of operations** (UDTs that declare methods).
4. **Inheritance** (`UNDER`: specialization/generalization).

> [!tip] Analogy
> `CREATE TYPE` is like designing a **form template** (fields + rules). `CREATE TABLE … OF type` is a **filing cabinet that only accepts that form**, and stamps each form with a permanent serial number (OID). `UNDER` creates a **more detailed form** that has all the old fields plus extra ones.

## 2. Type constructors: row and array (slides 41–42)
**Row type** (a structured UDT, like a tuple/record):
```sql
CREATE TYPE Addr_type AS (
    street VARCHAR(45),
    city   VARCHAR(25),
    zip    CHAR(5)
);
```
*Explanation:* defines a reusable composite type; a column `address Addr_type` stores all three parts as one value.

General syntax: `CREATE TYPE row_type_name AS [ROW] (<component declarations>);`

**Array type** (a collection-valued attribute):
```sql
CREATE TYPE Comp_type AS (
    comp_name VARCHAR(20),
    location  VARCHAR(20) ARRAY[10]
);
```
*Explanation:* each company can have up to 10 locations stored in one attribute. (The slide prints `VARCHAR (2).`, a typo for `VARCHAR(20),`.)

**Dot notation** refers to components: `comp1.comp_name` is the `comp_name` part of `comp1` (of type `Comp_type`).

## 3. Object identifiers using references (slides 43–44)
A UDT can be the **row type of a table** (a **typed table / object table**), with a system-managed object identifier:
```sql
CREATE TABLE Company OF Comp_type (
    REF IS comp_id SYSTEM GENERATED,
    PRIMARY KEY (comp_name)
);
```
*Explanation:* every row of `Company` is an object of `Comp_type`; `comp_id` is its **OID**, generated by the system. A primary key can still be declared.

Syntax: `REF IS <oid_attribute> <value_generation_method>` where the method is **SYSTEM GENERATED** or **DERIVED** (derived from the primary key).

**Attributes as references:**
```sql
CREATE TYPE Employment_type AS (
    employee REF(Emp_type)  SCOPE (Employee),
    company  REF(Comp_type) SCOPE (Company)
);
```
*Explanation:* `employee` and `company` hold **references (pointers) to rows** of the Employee and Company tables. `SCOPE` says which table the reference points into. Follow a reference with `->`: `e.company->comp_name` gives the name of the referenced company.

## 4. Encapsulation of operations (slides 45–46)
A UDT can declare **methods** as well as attributes, similar to a class:
```sql
CREATE TYPE Addr_type AS (
    street VARCHAR(45),
    city   VARCHAR(25),
    zip    CHAR(5)
)
METHOD apt_no() RETURNS CHAR(8);
```
General form: `CREATE TYPE <type-name> ( attributes; declarations of EQUAL and LESS THAN methods; other methods )`, with `METHOD <name>(<arg-list>) RETURNS <type>;`. The method body is defined separately (`CREATE METHOD …`).

## 5. Inheritance with UNDER (slide 47)
```sql
CREATE TYPE Manager_type UNDER Emp_type
    AS (dept_managed CHAR(20));
```
*Explanation:* `Manager_type` **inherits all attributes and methods** of `Emp_type` and adds `dept_managed`.
- **NOT FINAL:** the type may have subtypes (required for a supertype).
- **FINAL:** no further subtypes may be created.
- **Table inheritance:** `CREATE TABLE Manager OF Manager_type UNDER Employee;` makes Manager a **subtable** of Employee.

## 6. Other features (slide 48)
`WITH RECURSIVE` for recursive queries; **roles** for authorization (roles can change); **trigger granularity**: row-level and statement-level triggers; programming-language facilities (SQL/PSM).

## 7. Worked exam question: 2020/21 Q4(c)
```sql
CREATE TYPE aType AS (x INTEGER, y INTEGER) NOT FINAL;
CREATE TYPE bType UNDER aType AS (z INTEGER) FINAL;
CREATE TABLE aTable OF aType;
CREATE TABLE bTable OF bType UNDER aTable;
INSERT INTO aTable VALUES (1, 2);
INSERT INTO aTable VALUES (3, 4);
INSERT INTO bTable VALUES (5, 6, 7);
```
- `bType` has attributes **x, y** (inherited) and **z**. `bTable` is a **subtable** of `aTable`.
- In an SQL:2003 **table hierarchy**, every row of a subtable is **also a row of its supertable** (**substitutability**: a `bType` object *is an* `aType` object).

**(i) `SELECT * FROM aTable;`** → **2 columns (x, y)**, **3 rows**: (1, 2), (3, 4) and (5, 6). The subtable row appears, **projected onto the supertable's columns** (z is not shown).
**(ii) `SELECT * FROM bTable;`** → **3 columns (x, y, z)**, **1 row**: (5, 6, 7). Supertable rows are not subtable rows.

To exclude subtable rows: `SELECT * FROM ONLY (aTable);` → 2 rows (1, 2), (3, 4).
(Depending on the product, `SELECT *` on a typed table can also expose the self-referencing OID column if one was declared with `REF IS`; none was declared here.)

> [!warning] Partly beyond the lecture
> The slides introduce `UNDER` for types but do **not** explain table hierarchies, substitutability or `ONLY`. The answer above follows the SQL:2003 standard behaviour (and Elmasri & Navathe). This information could not be fully verified from the available course materials.
