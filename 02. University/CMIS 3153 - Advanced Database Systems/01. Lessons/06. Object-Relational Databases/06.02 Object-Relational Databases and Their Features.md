# 06.02 · Object-Relational Databases and Their Main Features

> [!info] [[06.00 Object-Relational Databases|Lesson 6]] · ORDBMS slides 7–8, 11–12, 31–40, 49 · Priority 🔴 High
> **Asked as:**
> - "Short note: Object-Relational Databases to bridge the gap between Object-Oriented Programming and Relational Databases" (2022/23 Q7(a), 25 marks)
> - "Explain the key features of object-relational databases. How do they extend traditional relational databases to support complex data types and object-oriented concepts?" (2023/24 Q7(a), 25 marks)

## 1. What is an ORDBMS? (slides 7–8)
An **Object-Relational Database (ORDB)** **extends the relational data model** to fix its weaknesses by **adding features of object-oriented systems**.
- It is **based on the relational database**: data is stored in tables and accessed with a query language like **SQL**.
- It also shows **object-oriented characteristics**, treating the relational database as an **object store**.
- It is "a relational model that allows users to integrate object-oriented features into it": a combination of RDBMS and OODBMS ideas.
- Most commercial RDBMSs (Oracle, PostgreSQL, IBM Db2) ship such extensions.

> [!tip] Analogy
> A family car (relational: reliable, everyone knows how to drive it) fitted with a roof box, tow bar and child seats (object features). You still drive it the same way (SQL), but it now carries odd-shaped luggage (complex types).

## 2. The gap it bridges (impedance mismatch)
OO programs use classes, nested objects, collections, inheritance, references and methods; relational DBs use flat tables, atomic values, foreign keys and set-based SQL. Translating between them is the **object-relational impedance mismatch** ([[06.03 Object-Relational Mapping]]). An ORDB narrows the gap **inside the database**; ORM frameworks narrow it **in the application**.

## 3. Main features of an ORDBMS (slides 11–12)
| Feature | What it means | Example |
|---|---|---|
| **Object types / UDTs** | user-defined (abstract) data types, referred to as object types | `Addr_type(street, city, zip)` |
| **Complex data types** | new types combining existing ones; structured, nested values | an `address` column of type `Addr_type` |
| **Functions / methods** | behaviour defined for each object type (data access methods) | `METHOD apt_no() RETURNS CHAR(8)` |
| **Inheritance** | types/tables acquire properties of other types and add their own | `Manager_type UNDER Emp_type` |
| **Nested tables** | a collection of rows stored **inside** another table's column | an order row containing its order lines |
| **Varrays** | variable-size **arrays** of homogeneous elements stored as one value | up to 10 phone numbers |
| **Object views** | present existing **relational tables as objects** without changing storage | an object view over legacy EMP and DEPT tables |

## 4. SQL object-relational features (slides 29–40) and how they extend RDBs
SQL3 (1999, SQL-99) added OO features; SQL:2003 extended them.
| Feature | How it extends the relational model | Benefit (lecture) |
|---|---|---|
| **User-defined types (UDTs)** | composite types with attributes (and methods), like classes | model real-world objects directly (e.g. `Point(x, y)`) |
| **Table inheritance** | a table inherits columns from another (e.g. Car, Truck under Vehicle in PostgreSQL) | model hierarchies, reuse fields, reduce redundancy |
| **Object identifiers (OIDs)** | system-generated unique row identifiers usable as references | relationships between objects like OO references |
| **Complex data types: arrays, JSON, XML** | structured/hierarchical data in one column (PostgreSQL JSON/JSONB, MySQL JSON) | flexible modelling without flattening into many tables |
| **Methods / functions / stored procedures** | behaviour attached to types/tables (e.g. distance between two `Point`s) | encapsulate business logic in the DB, reuse |
| **Encapsulation via views and triggers** | views expose a "public" read-only state; triggers enforce rules on change | separation of concerns; hide implementation |
| **Relationships via foreign keys** | object associations represented by FK → PK (Customer–Orders) | referential integrity |
| **Polymorphism via joins** | query parent and child tables (Vehicle, Car, Truck) as one type | treat subclasses uniformly |
| **Triggers and rules** | automatic actions on events (e.g. update a timestamp on change) | event-like behaviour, consistency |
SQL-99 mechanisms (slide 30): **type constructors** (row, array) for complex objects; **reference types** for object identity; **UDTs with operations** for encapsulation; **UNDER** for inheritance. Details and syntax: [[06.04 SQL Object-Relational Features]].

## 5. Advantages and disadvantages
**Advantages:** keeps relational strengths (SQL, transactions, optimization, scalability, maturity) while adding rich types; reduces impedance mismatch; code reuse via inheritance and methods; better modelling of complex domains (multimedia, GIS, engineering).
**Disadvantages:** more complex to design and use; features and syntax **differ between vendors**; complex types can be harder to query and optimize; many developers prefer ORMs + plain tables.

## 6. Model answer outline for the short note (2022/23 Q7(a))
1. The problem: OOP vs relational (flat tables, atomic values, no inheritance, no methods) → **impedance mismatch**; OODBMSs didn't succeed.
2. The ORDB idea: relational base + OO features; still SQL.
3. Features bridging the gap: UDTs/complex types, row/array types, REF/OIDs, methods, inheritance (`UNDER`), nested tables/varrays, object views.
4. Complementary ORM frameworks (Hibernate, JPA, Entity Framework, SQLAlchemy, Django ORM) mapping classes ↔ tables.
5. Benefits and limitations; conclusion.
