# 06.03 · Object-Relational Mapping (ORM)

> [!info] [[06.00 Object-Relational Databases|Lesson 6]] · ORDBMS slides 9–10, 13–28, 50 · Priority 🟡 Medium (supports 2022/23 Q7(a); lecture discussion questions)

## 1. What is ORM?
**Object-relational mapping** is a **programming technique** that lets developers work with the database **using objects in their programming language, without writing raw SQL**. It **converts data between the incompatible type systems** of OO languages and relational databases, and defines the **structural relationships** between the two representations.

> [!tip] Analogy: a translator at a meeting
> The programmer speaks "objects", the database speaks "tables and SQL". The ORM is an interpreter sitting between them, translating `customer.save()` into `INSERT INTO customer …` and turning result rows back into objects.

## 2. The basic mapping (slides 9–10, 17–18)
| OO world | Relational world |
|---|---|
| **class** | **table** |
| **object (instance)** | **row** |
| **attribute / field** | **column** |
| object identity (`user.id`) | **primary key** column |
| **method** call (`find`, `save`) | **SQL query** (SELECT, INSERT, UPDATE, DELETE) |
| association (reference, collection) | **foreign key** |

### Relationships (slides 18–20)
- ORM frameworks map **one-to-one, one-to-many, many-to-many** relationships (FKs, join tables) to **associations between objects**.
- **Relational associations are not directional:** with joins it is as easy to find a customer's orders as an order's customer.
- **OO associations are directional:** `Customer` holds `Set<Order> orders`; `Order` holds `Customer customer`. Each direction must be declared.
```java
public class Customer {
    private Set<Order> orders;   // one-to-many: navigate customer → orders
}
public class Order {
    private Customer customer;   // many-to-one: navigate order → customer
}
```
*Explanation:* in the database, both directions come from one foreign key `Order.customer_id`; in Java two fields express the two directions.

**Many-to-one vs one-to-many (discussion Q d):** the same relationship seen from opposite ends: *many* Orders → *one* Customer (many-to-one, a single reference in Order) vs *one* Customer → *many* Orders (one-to-many, a collection in Customer).

## 3. Frameworks and what they provide (slides 13–16, 23–24, 27–28)
- **Transparent persistence:** hides the storage technology; persistent classes **do not know they are persistent**; objects are created, loaded and deleted by the framework.
- **Declarative mapping schema:** a description (annotations/XML) of how domain classes relate to tables.
- **Identity:** every row needs a **unique primary key**; every object has **identity by existence** (memory location), not by attribute values ([[06.05 Object Identity vs Primary Key]]).
- Examples: **Hibernate**, **OpenJPA**, **EclipseLink** (JPA implementations, Java), **Entity Framework** (C#), **SQLAlchemy** (Python), **Django ORM** (Python); Oracle.

## 4. How ORM works internally (slides 21–22)
- **CRUD via objects:**
  - **Create:** instantiate an object and save it → ORM generates `INSERT`.
  - **Read:** `find()`, `get()`, `query()` → ORM runs `SELECT` and converts rows to objects.
  - **Update:** change attributes and save → ORM generates `UPDATE`.
  - **Delete:** remove the object → ORM generates `DELETE`.
- **Session / unit of work:** the session tracks changes to objects and emits the needed SQL when it is **committed**.
- **Mapper:** translates objects ↔ rows automatically.
- **Lazy loading:** related data (e.g. a customer's orders) is loaded **only when first accessed**.

### Lazy vs eager loading (discussion Q e)
| | Lazy loading | Eager loading |
|---|---|---|
| When related data is loaded | on first access | immediately with the parent (join/extra query) |
| + | fewer data loaded if not needed; fast initial load | no extra round trips later; avoids the "N+1 queries" problem |
| − | many small queries if you loop over children (N+1) | may load lots of unused data |

## 5. ORM techniques (slides 25–28)
| Technique | Idea | Examples |
|---|---|---|
| **1. Call-level APIs** | the program passes a **hand-written SQL string** to a driver; results come back as rows of untyped columns | **JDBC** (Java), **ODBC**, **ADO.NET** |
| **2. SQL query mapping frameworks** | declare links between classes and SQL queries; hide the call-level API but **developers still write SQL**; do not generate SQL | **iBATIS / iBATIS.NET** (MyBatis) |
| **3. Proprietary approaches** | data access integrated directly into the language | Microsoft **LINQ** |
| **4. Full ORM frameworks** | **declarative mapping** classes ↔ tables; **generate SQL**; hide the DB structure and query language; transparent persistence | **JPA** with **Hibernate**, **EclipseLink**, **OpenJPA** |

## 6. Advantages of ORM (slide 23)
Simplifies DB interaction (high-level OO code instead of SQL); **productivity**; **portability** across DBMSs; **maintainability** (separates DB logic from business logic).

## 7. Object-relational impedance mismatch (discussion question)
The **impedance mismatch** is the set of conceptual and technical difficulties when objects in OO programs must be stored in relational tables. Contributing factors:
1. **Identity:** object identity (by existence) vs primary-key value.
2. **Structure/granularity:** nested objects and collections vs flat rows of atomic values.
3. **Inheritance and polymorphism:** not native in the relational model.
4. **Associations:** directional references vs non-directional foreign keys; many-to-many needs a join table.
5. **Encapsulation:** private state + methods vs public columns queried by SQL.
6. **Data access style:** navigating object graphs vs set-based declarative queries.
7. **Type systems:** language types vs SQL types (strings, dates, nulls).
8. **Transactions/lifecycle:** objects in memory vs persistent rows.

### Entity class vs value type (discussion Q b)
- **Entity class:** objects with their **own identity** and lifecycle, stored in their own table with a PK (e.g. `Customer`).
- **Value type:** objects **without independent identity**, owned by an entity and stored as columns of the owner's row (e.g. an `Address` embedded in `Customer`); two equal values are interchangeable.
