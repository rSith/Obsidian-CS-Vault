# 03.05 · Why Relational Algebra: SQL, Database Design and Integrity

> [!info] [[03.00 Query Processing and Relational Algebra|Lesson 3]] · Lecture L3 §3.2–§3.5, Exercise 5 · [[TUT 3 - Relational Model and Relational Algebra|Tutorial 3 Q1–Q3]] · Priority 🟡 Medium
> **Asked as:** "If sID is a key for the Suppliers relation, could it be a key for the Catalog relation? Discuss." (2021/22 Q5(a), 20 marks)

## 1. Relational model basics (Tutorial 3 Q1–Q2)
- A **relation** is a **table**: a **set of tuples** (rows), each tuple having one value per **attribute** (column) drawn from that attribute's **domain**.
- **Two properties of its elements (tuples):**
  1. **Tuples are distinct**: a relation is a set, so no two rows are identical (there is always a key).
  2. **Values are atomic**: each attribute value is a single, indivisible value (first normal form).
  (Also: tuple order and attribute order carry no meaning.)
- **Relation schema** vs **relation (instance)**:

| | Relation schema | Relation (instance / state) |
|---|---|---|
| What | the **structure**: name, attributes, domains, keys, e.g. `EMPLOYEE(Ssn, Name, Salary)` | the **actual set of tuples** stored at a given moment |
| Changes? | rarely (design time) | constantly (inserts, deletes, updates) |
| Analogy | the column headings of a form | the filled-in forms |

The tutorial notation $N_1(\{A, B\}, \{A\})$ means schema $N_1$ with attributes $\{A, B\}$ and key $\{A\}$.

## 2. Keys and foreign keys
- **Superkey:** set of attributes whose values are unique for every tuple. **Key (candidate key):** a minimal superkey. **Primary key:** the chosen key.
- **Foreign key / inclusion dependency:** $Catalog[sID] \subseteq Suppliers[sID]$ means every sID in Catalog must exist in Suppliers (**referential integrity**).

### Referential integrity in RA (Tutorial 3 Q3)
$N_1[B] \subseteq N_2[B]$ is expressed as:
$$
\pi_B(r_1) \subseteq \pi_B(r_2) \qquad\text{equivalently}\qquad \pi_B(r_1) - \pi_B(r_2) = \emptyset
$$
Every B-value used in $r_1$ must appear among the B-values of $r_2$.

### Could sID (key of Suppliers) be a key of Catalog? (2021/22 Q5(a))
`Suppliers(sID, sName, address)`, `Parts(pID, pName, colour)`, `Catalog(sID, pID, price)`, with $Catalog[sID] \subseteq Suppliers[sID]$ and $Catalog[pID] \subseteq Parts[pID]$.
- In **Suppliers**, sID is a key: one row per supplier.
- In **Catalog**, sID is a **foreign key**. One supplier usually supplies **many parts**, so the same sID appears in **many** Catalog rows: e.g. (s1, p1, 10), (s1, p2, 15). sID alone is **not unique** → **not a key**.
- The key of Catalog is the **combination (sID, pID)**: a supplier lists a given part once, with one price.
- sID could be a key of Catalog **only if** a business rule said every supplier supplies **at most one part**: being a key in one relation says nothing about uniqueness in another.

## 3. Why relational algebra? (lecture §3.2)
| Reason | Meaning |
|---|---|
| Foundation of query languages | SQL is built on RA; σ ↔ WHERE etc. |
| Formal query representation | precise, unambiguous meaning |
| Set-based operations | works on whole relations → declarative; optimizable |
| **Optimization** | equivalent RA expressions can be swapped to find a cheaper one |
| Simplicity and composability | small set of operators, freely combined |
| Abstraction | think about *what* data, not storage |
| **Data independence** | queries don't depend on physical storage (logical data independence) |
| Mathematical rigor | correctness can be proved |
| Database theory | basis of normal forms, dependency theory, design |

## 4. RA and SQL (lecture §3.3)
| SQL | Relational algebra |
|---|---|
| SELECT (column list) | π projection |
| WHERE | σ selection |
| JOIN | ⋈ join |
| UNION | ∪ union |
| GROUP BY + aggregates | γ (extended RA) |

Knowing RA improves SQL comprehension: you can predict how the engine evaluates and optimizes a query.

## 5. RA and database design (lecture §3.4, Exercise 5)
- **Normalization** decomposes a relation into smaller ones using **projection**: $R \to \pi_{X}(R), \pi_{Y}(R)$.
- A decomposition is **lossless** if joining the pieces gives back exactly the original: $\pi_X(R) \bowtie \pi_Y(R) = R$.

> [!example] Normalization with RA
> `EMP_DEPT(EmpID, Name, DeptID, DeptName)` repeats DeptName for every employee (redundancy, update anomalies), because DeptID → DeptName.
> Decompose: $EMP = \pi_{EmpID, Name, DeptID}(EMP\_DEPT)$ and $DEPT = \pi_{DeptID, DeptName}(EMP\_DEPT)$.
> Since DeptID is a key of DEPT, $EMP \bowtie DEPT = EMP\_DEPT$: **lossless**. This moves the design from 2NF/3NF violations to 3NF.

- **Integrity constraints** (keys, foreign keys) can be stated with RA (as above: $\pi_B(r_1) - \pi_B(r_2) = \emptyset$).

## 6. RA and query optimization (lecture §3.5)
- **Reorder operations:** apply σ before π and before joins to shrink intermediate results.
- **Predicate push-down:** move filter conditions close to the base tables.
- **Join reordering:** choose the join sequence (and join algorithm) with the lowest estimated cost.
- **Cost-based optimization:** cost models evaluate alternative RA expressions.
- **Transformation rules:** equivalences used to rewrite expressions ([[04.06 Heuristic Optimization and Transformation Rules]]).

> [!warning] Incorrect rule printed in the lecture (L3 §3.5)
> The lecture gives "commutativity of join and union: $(A \bowtie B) \cup C = (A \cup C) \bowtie (B \cup C)$". **This is not a valid equivalence** (the two sides generally don't even have the same columns). Valid rules include: ⋈ and ∪ are each **commutative and associative**; σ commutes with ∪; π commutes with ∪; and join **distributes over union**: $A \bowtie (B \cup C) = (A \bowtie B) \cup (A \bowtie C)$. Do not quote the lecture's version.
