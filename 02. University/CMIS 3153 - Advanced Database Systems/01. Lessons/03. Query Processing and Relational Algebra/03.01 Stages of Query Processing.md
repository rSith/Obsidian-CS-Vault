## 1. What is query processing?
**Query processing** is the series of steps a DBMS takes to turn a **high-level query** (usually SQL text) into an **efficient execution plan**, run it, and return the result. Its objective (lecture §1) is **the correct result with minimum resource usage** (CPU time, memory, I/O).

> [!tip] Analogy: a GPS app
> You type "take me to Kandy" (SQL string). The app first checks your words make sense (parsing), checks Kandy exists on its map (semantic check), works out many possible routes and picks the fastest (optimization), produces turn-by-turn directions (execution plan), then you drive it (execution) and arrive (results).

## 2. The stages (lecture §2, Figure 1)
```text
 SQL query (string)
        │
        ▼
 ┌──────────────────────┐   tokens, grammar check
 │ 1. Parsing           │──► parse / syntax tree           (syntax error → stop)
 └──────────────────────┘
        ▼
 ┌──────────────────────┐   tables, columns, types exist?
 │ 2. Semantic analysis │──► validated tree → translated into relational algebra
 └──────────────────────┘
        ▼
 ┌──────────────────────┐   rewrite RA, estimate costs   ◄── catalog statistics, indexes
 │ 3. Query optimization│──► best plan chosen
 └──────────────────────┘
        ▼
 ┌──────────────────────┐   algorithms + access paths fixed
 │ 4. Execution plan    │──► physical query plan
 └──────────────────────┘
        ▼
 ┌──────────────────────┐   scans, filters, joins, aggregation, sort
 │ 5. Query execution   │──► (6.) result presented to user/app
 └──────────────────────┘
```

### Stage 1: Parsing
- **Lexical analysis (scanning):** break the string into **tokens**: keywords (`SELECT`, `FROM`), identifiers (table/column names), operators, constants.
- **Syntax analysis:** check tokens against the **grammar** of SQL; build a **parse tree / syntax tree** (abstract syntax tree) showing the query's structure.
- If the syntax is wrong (e.g. `SELEC name FORM emp`), processing **stops** with an error.
- *Outcome:* a well-formed syntax tree.

### Stage 2: Semantic analysis (validation)
- Check the query **makes sense for this database schema**: do the tables and columns exist? Are data types compatible (no `salary > 'abc'`)? Are functions and aggregates used properly? Is the user authorised?
- Resolve names and references. The validated query is **translated into an internal form, usually a relational-algebra expression / query tree** (lecture §2.1).

### Stage 3: Query optimization
- The **optimizer** generates **many equivalent plans** (different orders of joins, where to apply selections, which indexes, which join algorithms) and chooses the one that minimizes estimated cost (CPU, memory, I/O).
- Uses **heuristic rules** (e.g. push selections down) and **cost estimates** from catalog statistics. Details: [[04.04 Query Optimization Strategies]], [[04.06 Heuristic Optimization and Transformation Rules]].

### Stage 4: Execution plan generation
- Produces the **query execution plan**: a detailed roadmap of **which operations, in which order, using which algorithms and access paths** (index scan vs table scan, hash join vs nested loop, sort method).

### Stage 5: Query execution
- The **runtime / query execution engine** follows the plan: reads data from disk or memory (table or index scans), applies filters (WHERE), performs joins, aggregates (GROUP BY, COUNT, SUM), sorts (ORDER BY), possibly **in parallel**.

### Stage 6: Result presentation
- The result rows (or an aggregate value) are formatted and returned to the user/application.

## 3. Model answers
### "Four important steps" (2022/23 Q4(a), 2023/24 Q4(a))
1. **Parsing and translation:** scan the string into tokens, check syntax, build a parse tree; check names against the catalog; translate into a relational-algebra expression (query tree).
2. **Optimization:** generate equivalent RA expressions and alternative access paths/algorithms; estimate the cost of each using catalog statistics; choose the cheapest.
3. **Execution plan (code) generation:** convert the chosen plan into an executable physical plan (operators + algorithms + access paths).
4. **Evaluation / execution:** the query-evaluation engine runs the plan and returns the result.

(If the question wants "parsing" and "semantic check" separately, combine plan generation and execution.)

### "Steps and their order" (2020/21 Q1(c), 30 marks)
Give the **five/six stages above in order**, each with what it does and its output, plus the diagram. Emphasise that **optimization happens before execution** and uses **statistics from the catalog**.

### "Techniques and how they contribute to efficiency" (2023/24 Q5(a))
| Technique | Stage | Contribution to efficiency |
|---|---|---|
| Translating to RA / query tree | 1–2 | gives a formal structure the optimizer can rewrite safely |
| Heuristic rewriting (predicate/projection push-down, × + σ → ⋈) | 3 | shrinks intermediate results early |
| Join reordering | 3 | smallest/most selective joins first |
| Cost-based plan selection (selectivity, cardinality, histograms) | 3 | picks cheapest access paths and join algorithms |
| Index scans vs table scans | 4 | fewer block reads for selective predicates |
| Join algorithms (nested loop, hash, sort-merge) | 4 | the right algorithm for the data size |
| **Pipelining** | 5 | passes tuples between operators without writing temporary tables ([[03.06 Pipelining and Materialization]]) |
| Parallel execution, caching/buffering | 5 | uses multiple CPUs/disks; avoids repeated reads |
