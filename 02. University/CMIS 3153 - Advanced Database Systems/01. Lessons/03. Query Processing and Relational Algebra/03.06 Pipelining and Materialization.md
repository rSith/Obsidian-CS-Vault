# 03.06 · Pipelining vs Materialization

> [!info] [[03.00 Query Processing and Relational Algebra|Lesson 3]] · Lecture L3 §3.6 · Priority 🟡 Medium (supports 2023/24 Q5(a) "techniques"; explains "(On the fly)" in 2020/21 Q2(b) plans)

## 1. What is it?
A query plan is a tree of operators (σ, π, ⋈ …). The output of one operator is the input of the next. There are two ways to pass data along:
- **Materialization:** run one operator **completely**, **store its whole result** (in memory or a temporary table on disk), then let the next operator read it.
- **Pipelining:** pass each result tuple **directly** to the next operator **as soon as it is produced**, without storing the intermediate result.

> [!tip] Analogy: a car assembly line
> **Materialization:** build all 1,000 chassis, park them in a warehouse, then fetch them one by one to add engines. **Pipelining:** each chassis rolls straight on to the engine station the moment it is finished. No warehouse needed, and the first finished car comes out much sooner.

## 2. How pipelining works
```text
   π_{name}            ← takes each tuple from σ, outputs name   ("on the fly")
     │
   σ_{salary>50000}    ← takes each tuple from the scan, passes it on if it qualifies
     │
   scan(Employees)     ← reads one tuple at a time
```
Each operator asks its child for the "next" tuple, processes it, and hands it up. In exam diagrams this is written as **"(On the fly)"**: the selection or projection is applied to tuples as they stream out of the operator below, at no extra I/O cost.

## 3. Benefits (lecture)
| Benefit | Why |
|---|---|
| **Reduced memory usage** | intermediate results are never held in full |
| **Improved I/O performance** | no temporary results written to and read back from disk |
| **Faster query execution** | the next operator starts immediately; first results appear early |
| **Better scalability** | large datasets are processed as a stream |

## 4. Challenges (lecture)
| Challenge | Explanation |
|---|---|
| **Backtracking and memory** | some operators need to see tuples again (e.g. the inner input of certain joins), so they must be stored temporarily |
| **Complex query plans** | some operators are hard to pipeline: **set operations** (∪, ∩, −) and **blocking** operators like **sorting** and **aggregation (GROUP BY)** need all their input before producing output |
| **Error handling and rollback** | with no complete intermediate result, recovering from an error mid-stream needs extra strategies |

## 5. Comparison
| | Materialization | Pipelining |
|---|---|---|
| Intermediate result | stored (temp table) | not stored |
| Extra I/O | write + read of temp results | none |
| Memory | holds whole intermediate result | small buffers |
| Time to first result | after each operator finishes | almost immediate |
| Works for every operator | yes | not for blocking operators (sort, aggregate, some set ops) |
| Reuse of an intermediate result | easy | hard |
