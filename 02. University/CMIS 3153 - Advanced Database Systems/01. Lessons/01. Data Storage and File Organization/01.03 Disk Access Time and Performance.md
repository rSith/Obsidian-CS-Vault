# 01.03 · Disk Access Time and Disk Performance

> - "Explain the key factors that influence disk performance, providing real-world examples" (2022/23 Q1(a))
> - "7200 RPM, average seek 8 ms, latency 4.17 ms … calculate the average time for an operation involving seeking and latency" (2022/23 Q1(c))
> - "Explain how disk-related factors can cause slow query responses even when CPU and memory are sufficient" (2023/24 Q1(a))
> - "7200 RPM, seek 9 ms, rotational latency half a rotation, 120 MB/s, 64 KB block … average time for one read" (2023/24 Q1(c))

## 1. What is it?
The **block access time** is the total time the disk needs to find one block and hand it to memory. It has three parts:

$$
\boxed{\text{block access time} = s + rd + btt}
$$

| Symbol | Name | Plain English |
|---|---|---|
| $s$ | **seek time** | time to **move the arm** so the head sits over the right track/cylinder |
| $rd$ | **rotational delay** (rotational latency) | time **waiting for the platter to spin** until the wanted block is under the head |
| $btt$ | **block transfer time** | time for the block's bytes to **pass under the head** and be copied |

> [!tip] Analogy: catching a particular seat on a merry-go-round
> You must first **walk** to the correct ring of horses (seek), then **wait** for your horse to come round (rotational delay), then **climb on** while it passes (transfer). Walking and waiting take far longer than climbing on, so **seek and rotational delay dominate**.

## 2. Each component in detail
### 2.1 Seek time $s$
Mechanical positioning of the read/write head on the correct track. Typical values (lecture): **5–10 ms on desktops, 3–8 ms on servers**. It depends on how far the arm has to move. Manufacturers quote an **average** seek time.

### 2.2 Rotational delay $rd$
Once on the track, the wanted block is, **on average, half a revolution away**.

If the disk spins at $p$ revolutions per minute:
$$
\text{time for one revolution} = \frac{60}{p}\ \text{s} = \frac{60{,}000}{p}\ \text{ms}
\qquad
rd = \frac12 \times \frac{60{,}000}{p} = \frac{30{,}000}{p}\ \text{ms}
$$

$rd$ is **inversely proportional** to rotation speed: faster disks wait less.

| rpm | one revolution | average $rd$ |
|---|---|---|
| 2,400 | 25 ms | **12.5 ms** |
| 3,600 | 16.67 ms | 8.33 ms |
| 5,400 | 11.11 ms | 5.56 ms |
| 7,200 | 8.33 ms | **4.17 ms** |
| 15,000 | 4 ms | 2 ms |

> [!warning] Typo in the lecture note (L1 §5.1)
> The lecture writes the formula as "$rd = \frac{3000}{p}$ msec" and says "$p = 1000$ rpm gives $rd = 3$". This is inconsistent with its own next line, $rd = \frac{30}{p}$ **seconds** (= $\frac{30{,}000}{p}$ ms). At 1000 rpm one revolution takes 60 ms, so $rd = 30$ ms. **Use $rd = 30{,}000/p$ ms** (it reproduces the 4.17 ms printed in the 2022/23 paper for 7200 rpm).

### 2.3 Transfer rate $tr$ and block transfer time $btt$
The **transfer rate** is how many bytes pass under the head per millisecond. One full track passes per revolution, so:
$$
tr = \frac{\text{track size (bytes)}}{\text{time for one revolution (ms)}}\ \text{bytes/ms}
\qquad
btt = \frac{B}{tr}\ \text{ms}
$$

> [!warning] Second typo in the lecture example
> The lecture computes $tr$ for a 50 KB track at 3600 rpm and prints "3600 bytes/msec", then uses $btt = B/3000$. The correct value is $50{,}000 / 16.67 = 3000$ bytes/ms; **3000 is right**, 3600 is a typo.

### 2.4 Bulk transfer rate $btr$ (reading many consecutive blocks)
When reading consecutive blocks the head also passes over the **interblock gaps** (size $G$), which hold no useful data. The **bulk transfer rate** counts only useful bytes:
$$
btr = \frac{B}{B+G}\times tr \ \text{bytes/ms}
$$
The useful time per block in a consecutive run is then $B / btr$ ms.

## 3. Reading more than one block
| Situation | Time (lecture formulas) |
|---|---|
| one random block | $s + rd + btt$ |
| $k$ **random** blocks (anywhere on disk) | $k(s + rd + btt)$ |
| $k$ **consecutive** blocks on the same track/cylinder | $s + rd + k \cdot btt$ |
| $k$ consecutive blocks, more accurately (gaps counted) | $s + rd + k \cdot (B/btr)$ |
| $k$ **non-contiguous** blocks on the **same cylinder** | lecture prints $s + k \cdot rd + btt$ ⚠️ |

> [!warning] Check this formula
> For $k$ non-contiguous blocks on the same cylinder the lecture writes $(s + k*rd + btt)$. Logically each block also needs its own transfer, so the full expression is $s + k(rd + btt)$; since $btt \ll rd$ the difference is small. Quote the lecture form if asked, but understand the logic.

The big saving: **consecutive blocks pay the seek and rotational delay only once.** That is why files that are scanned sequentially should be stored contiguously ([[01.04 Buffering of Blocks]]).

## 4. Worked examples
### Example A: Tutorial 1 Q1(e)–(g) (disk: 2400 rpm, $s$ = 30 ms, $B$ = 512, $G$ = 128, 20 blocks/track)
1. One revolution: $60{,}000/2400 = 25$ ms → $rd = 12.5$ ms.
2. Track size $= 20 \times (512+128) = 12{,}800$ B → $tr = 12{,}800/25 = 512$ bytes/ms.
3. $btt = 512/512 = 1$ ms.
4. $btr = \frac{512}{640}\times 512 = 409.6$ bytes/ms.
5. One block: $30 + 12.5 + 1 = 43.5$ ms.
6. 20 random blocks: $20 \times 43.5 = 870$ ms. 20 consecutive blocks with double buffering: $30 + 12.5 + 20\times 1 = 62.5$ ms (or $30 + 12.5 + 20 \times 1.25 = 67.5$ ms using $btr$). **About 13× faster.**

### Example B: 2022/23 Q1(c)
7200 rpm, $s$ = 8 ms, latency 4.17 ms (given). Operation with seek + latency:
$$
8 + 4.17 = \mathbf{12.17\ ms}
$$
(Check: $30{,}000/7200 = 4.17$ ms ✓.)

### Example C: 2023/24 Q1(c)
7200 rpm, $s$ = 9 ms, $rd$ = half a rotation, $tr$ = 120 MB/s, block = 64 KB, command processing overlaps with seek (so it adds nothing).
1. $rd = \frac12 \times \frac{60{,}000}{7200} = 4.17$ ms.
2. Transfer: $\frac{64\ \text{KB}}{120\ \text{MB/s}}$. With 1 KB = 1024 B and 1 MB = $10^6$ B: $65{,}536 / 120{,}000{,}000 = 0.546$ ms. (If both use the same base, $64/(120\times1024)\,\text{s} = 0.521$ ms; with decimal KB, 0.533 ms.)
3. Total $= 9 + 4.17 + 0.55 \approx \mathbf{13.7\ ms}$.

State your unit assumption in the exam; all three conventions give ≈ 13.7 ms.

## 5. Factors that influence disk performance (2022/23 Q1(a), 2023/24 Q1(a))
| Factor | Effect | Real-world example |
|---|---|---|
| **Seek time** | long arm moves on random access | an OLTP system doing thousands of random lookups per second (bank, airline booking) is limited by seeks, not CPU |
| **Rotational speed (rpm)** | lower rpm → longer $rd$ and lower $tr$ | a 5,400 rpm laptop disk vs a 15,000 rpm server disk: $rd$ 5.6 ms vs 2 ms |
| **Transfer rate / block size** | small blocks → more I/O requests; huge blocks → wasted transfer | full-table scans for reports benefit from large blocks |
| **Data placement (contiguous vs scattered)** | scattered blocks pay $s + rd$ every time | a fragmented file makes a "simple" scan take minutes instead of seconds |
| **Random vs sequential access pattern** | random I/O ≈ 40 ms/block; sequential ≈ 1 ms/block | an **unclustered index** fetching 300,000 rows randomly can be slower than a full scan ([[TUT 4 - Selectivity and Index Cost|Tutorial 4 Ex 3]]) |
| **Buffering / caching** | missing or too-small buffers → repeated reads | a buffer pool too small for the working set causes "thrashing" |
| **Interblock gaps** | reduce useful bandwidth ($btr < tr$) | |
| **Concurrent load / queueing** | many requests queue at one disk | a report run during peak hours slows every user |
| **Disk failures / RAID level** | RAID 5/6 writes need parity work | write-heavy logs on RAID 5 are slower than on RAID 10 ([[01.10 RAID]]) |

### Why queries are slow even with enough CPU and memory (2023/24 Q1(a))
The query is **I/O-bound**: the CPU sits idle waiting for the disk. Causes:
1. **Mechanical latency:** each random block read costs $s + rd$ (≈ 10–15 ms), millions of times slower than a memory access.
2. **Random rather than sequential access:** e.g. non-clustered index lookups, heap files, fragmented files → each block pays a full seek.
3. **Reading far more blocks than needed:** full table scans because there is no suitable index, or a poor [[04.03 Logical vs Physical Query Plans|physical plan]].
4. **Poor placement:** related blocks spread across cylinders; no contiguous allocation.
5. **Insufficient buffering** (the data needed is not in the buffer pool, so it is re-read).
6. **Contention:** many queries share one disk (queueing), or RAID parity overhead on writes.
7. **Remedies:** indexes (especially clustered for ranges), contiguous allocation, larger blocks/prefetching, double buffering, caching, SSDs, RAID 0/10 striping for parallel reads.

## 6. Exam-relevant points
- Always write the formula $s + rd + btt$ and **define each term** before calculating.
- Memorize $rd = \frac12 \cdot \frac{60{,}000}{p}$ ms; $btt = B/tr$; $btr = \frac{B}{B+G}tr$.
- Show units at every step (ms, bytes/ms).
- "Discuss" questions: name the component, say what causes it (arm movement / rotation / data passing the head), typical magnitude, and how to reduce it.
