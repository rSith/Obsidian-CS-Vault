# 01.05 · Records, Blocking and File Allocation

> [!info] [[01.00 Data Storage and File Organization|Lesson 1]] · Lecture L1 §5.3.1–§5.3.5 · Priority 🔴 High
> **Asked as:** "Differentiate between fixed length records and variable length records in a file" (2020/21 Q3(a)) · "What do you mean by spanned and unspanned organization of records?" (2020/21 Q3(b)) · record size $R$, blocking factor $bfr$ and blocks $b$ (2021/22 Q6(a)(b)) · "The role of file directories in file organization" (2022/23 Q7(d), see the file-header section)

## 1. Records and record types (§5.3.1)
- A **record** is a collection of related data values, one per **field**. A record usually describes one **entity** (e.g. one employee).
- A **record type** is the list of field names and their data types (like a `struct` in C or a class with only attributes).

```c
struct employee {
    char name[30];
    char ssn[9];
    int  salary;
    int  job_code;
    char department[20];
};
```
*Explanation:* each EMPLOYEE record has five fields. If `int` is 4 bytes, every record is 30 + 9 + 4 + 4 + 20 = **67 bytes**, the same size for every employee.

A **file** is a sequence of records, usually all of the same record type, spread over many disk blocks. A **database is stored as a collection of files**.

## 2. Fixed-length vs variable-length records (§5.3.2)
> [!tip] Analogy
> **Fixed-length** records are like an exam answer sheet with boxes of fixed size for "Name", "Index No."; you always know Name starts at box 1 and Index No. at box 31. **Variable-length** records are like handwritten letters: each one is a different length, so you need separators ("Dear …", line breaks) to know where each part ends.

**Fixed-length records:** every record in the file has **exactly the same size** in bytes. The position of each field inside the record is fixed, so a program can jump straight to "byte 30 = start of SSN".

**Variable-length records:** records in the file have **different sizes**. Reasons (lecture, also [[TUT 2 - Records, File Organization and B-Trees|Tutorial 2 Q1/Q7]]):
1. **Variable-length fields**: e.g. `Name` stored using only as many characters as needed.
2. **Repeating fields / repeating groups**: a field with several values for one record (e.g. several phone numbers).
3. **Optional fields**: present for some records, absent for others.
4. **Mixed files**: records of **different record types** stored together (e.g. a STUDENT record followed by that student's GRADE_REPORT records, clustered on the same block).

To "parse" a variable-length record, the system needs **separator characters** (e.g. `$` or `%`) or **length fields** stored before each value, or `<field-name, value>` pairs for optional fields.

| Aspect | Fixed-length | Variable-length |
|---|---|---|
| Size | same for every record | differs between records |
| Locating a field | by fixed offset (fast, simple) | by scanning separators / reading length fields |
| Wasted space | yes, when values are shorter than the reserved size or fields are empty | little |
| Locating record *i* | position = $i \times R$ (direct) | must scan or keep pointers |
| Updates | in place | a longer new value may not fit → record must move |
| Blocking | $bfr = \lfloor B/R \rfloor$ exactly | average $bfr$ only |
| Typical use | most relational tables | text, optional/repeating data, mixed files |

**When is a fixed-length representation of a variable-length record useful?** ([[TUT 2 - Records, File Organization and B-Trees|Tutorial 2 Q9]]) When the variation is small (e.g. names rarely exceed 30 chars), or when there are few optional fields: reserve the maximum size for each field (or a fixed number of slots for a repeating group) and accept some wasted space in exchange for simple, fast access.

## 3. Blocking and the blocking factor (§5.3.3)
A block is the **unit of transfer** between disk and memory, so records are packed into blocks. **Blocking** = storing several records in one block.

$$
bfr = \left\lfloor \frac{B}{R} \right\rfloor \quad\text{(records per block, rounded down)}
$$
$$
\text{unused space per block} = B - bfr \times R
\qquad
b = \left\lceil \frac{r}{bfr} \right\rceil \quad\text{(blocks needed for } r \text{ records)}
$$

where $B$ = block size, $R$ = record size, $r$ = number of records. $\lfloor x\rfloor$ rounds **down** (you cannot fit 4.49 records), $\lceil x\rceil$ rounds **up** (you need a whole extra block for leftovers).

## 4. Spanned vs unspanned organization (§5.3.3)
> [!tip] Analogy: packing books into boxes
> **Unspanned:** each book must fit entirely in one box; if the box has 10 cm left and the next book is 12 cm, that 10 cm stays empty. **Spanned:** you may tear the book and put the first half in this box and the rest in the next box, with a note "continued in box 7". No space is wasted, but reading that book needs two boxes.

- **Unspanned:** records are **not allowed to cross block boundaries**. Each record lies wholly inside one block. Wasted space per block $= B - bfr \cdot R$.
  - Used with **fixed-length records where $B > R$**, because each record then starts at a **known location** in the block, simplifying processing.
- **Spanned:** part of a record is stored in one block and the rest in another; a **pointer** at the end of the first block points to the block holding the remainder (if not the next consecutive block).
  - **Must** be used when a record is **larger than a block**.
  - Useful for **large variable-length records** to reduce lost space.
  - $bfr$ then means the **average** number of records per block.

| Aspect | Unspanned | Spanned |
|---|---|---|
| Record crosses block boundary? | never | allowed |
| Wasted space | $B - bfr \cdot R$ per block | almost none |
| Record > block size? | impossible | required |
| Record access | one block per record, simple | may need 2+ block reads per record |
| Typical use | fixed-length records, $B > R$ | very large or variable-length records |

## 5. Allocating file blocks on disk (§5.3.4)
| Method | How | Advantage | Disadvantage |
|---|---|---|---|
| **Contiguous** | file blocks on **consecutive** disk blocks | reading the whole file is very fast (with double buffering) | **expanding the file is difficult** |
| **Linked** | each block has a **pointer to the next** | easy to expand | reading the whole file is **slow** (blocks scattered) |
| **Clusters / extents (segments)** | groups of consecutive blocks; clusters are linked | compromise of both | some complexity |
| **Indexed** | one or more **index blocks** hold pointers to the file blocks | direct access to any block; easy to grow | extra index blocks |

Combinations are common.

## 6. File headers (file descriptors) (§5.3.5) and file directories
A **file header** (file descriptor) stores the information system programs need to access the file:
- **disk addresses of the file blocks** (e.g. address of the first/last block, or the table of blocks),
- **record format descriptions**: field lengths and field order (fixed-length unspanned records); field type codes, separator characters and record type codes (variable-length records).

To find a record, blocks are copied into memory buffers and searched using this header information. If the block holding the record is unknown, a **linear search** through all file blocks is needed: very slow for big files. The aim of a good file organization is to **locate the block containing a record with as few block transfers as possible**.

## 7. Worked example (Tutorial 1 Q2 = 2021/22 Q6(a)(b))
STUDENT record: Name 30, Ssn 9, Address 40, PHONE 10, Birthdate 8, Sex 1, Major_dept_code 4, Minor_dept_code 4, Class_code 4, Degree_program 3, **+1 byte deletion marker**. $B = 512$, $r = 20{,}000$, unspanned.
1. $R = 30+9+40+10+8+1+4+4+4+3+1 = \mathbf{114}$ bytes.
2. $bfr = \lfloor 512/114 \rfloor = \lfloor 4.49 \rfloor = \mathbf{4}$ records/block.
3. $b = \lceil 20{,}000/4 \rceil = \mathbf{5{,}000}$ blocks.
4. Wasted per block: $512 - 4\times114 = 56$ bytes.
