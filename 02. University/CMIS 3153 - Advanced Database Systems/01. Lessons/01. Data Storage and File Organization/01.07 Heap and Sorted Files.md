# 01.07 · Heap Files and Sorted (Sequential) Files

> [!info] [[01.00 Data Storage and File Organization|Lesson 1]] · Lecture L1 §7.1–§7.2 · Priority 🔴 High
> **Asked as:**
> - "A company maintains an employee database (Employee ID, Name, Department, Salary) and expects frequent updates … Discuss the pros and cons of sequential file organization versus indexed file organization" (2022/23 Q1(d))
> - "Discuss the suitability of sequential versus indexed file organization for frequently updated records" (2023/24 Q1(d))
> - linear search and binary search times (2021/22 Q6(c)–(e)) · "Describe the major problems associated with sorted files" (Tutorial 2 Q12)

## 1. Heap files (unordered files)
### What is it?
A **heap file** stores records **in no particular order**. A new record is simply **appended at the end** (or put into any free space).

> [!tip] Analogy
> A drawer where you throw receipts as they arrive. Adding a receipt is instant; finding a specific one means digging through the whole drawer.

### How each operation works (lecture §7.1)
| Operation | How | Cost (b = number of blocks) |
|---|---|---|
| **Insert** | copy the **last block** into a buffer, add the record, write the block back; the last block's address is kept in the **file header** | **very cheap**: about 2 block accesses |
| **Search** (any condition) | **linear search** block by block | average **b/2** blocks if one record matches; **b** blocks if none or several match |
| **Delete** | find the block, delete in the buffer, rewrite the block; leaves **unused space** | search cost + 1 write; needs **periodic reorganization** |
| **Sort** | expensive; needs **external sorting** | high |
| Access by position | record *i* is in block $\lfloor i/bfr \rfloor$, position $(i \bmod bfr)$ in that block (a **relative/direct file**) | 1 block |

Alternative to physical deletion: a **deletion marker** byte per record (that is why calculation questions include "+1 byte deletion marker").

### Key features (lecture §7.1.1)
1. Unordered storage. 2. Cheap insertion. 3. Deletion only marks space free; no reorganization triggered. 4. Search needs a sequential scan, slower as the file grows. 5. Good for **small datasets**. 6. Needs **space management** (free-space list or bitmap). 7. **No indexes** by default, but heaps are often combined with **secondary indexes**.

## 2. Sorted files (ordered / sequential files)
### What is it?
Records are **physically ordered** on disk by the value of one field, the **ordering field**. If the ordering field is also a **key** (unique), it is the **ordering key**.

> [!tip] Analogy
> A phone book sorted by surname. Finding "Perera" is fast (open the middle, go left or right). But adding a new "Fernando" means shifting every entry after it down one place.

### Advantages (lecture §7.2)
1. Reading records **in order** of the ordering key needs **no sorting**.
2. Finding the **next** record in order usually needs **no extra block access** (it is in the same block).
3. Searching on the ordering key can use **binary search** on blocks: about $\lceil \log_2 b \rceil$ block accesses instead of $b/2$.
4. **Range conditions** ($<, >, \le, \ge$) on the ordering field are efficient: matching records are **contiguous**.

Ordered files are stored on **contiguous cylinders** to minimize seek time.

### Binary search on blocks
```text
binary_search(K):           # blocks 1..b, sorted by key
    lo = 1; hi = b
    while lo <= hi:
        mid = (lo + hi) // 2
        read block mid into a buffer            # 1 block access
        if K < first key in block:  hi = mid - 1
        elif K > last key in block: lo = mid + 1
        else: search inside the block; stop
```
Each step halves the remaining blocks, so about $\lceil\log_2 b\rceil$ blocks are read, **whether or not the record is found**.

### Problems with sorted files ([[TUT 2 - Records, File Organization and B-Trees|Tutorial 2 Q12]])
| Problem | Why |
|---|---|
| **Insertion is expensive** | must find the correct position and **make space**; on average **half the records must move**, so half the blocks are read and rewritten |
| **Deletion** | leaves gaps; less severe if **deletion markers** + periodic reorganization are used |
| **Modifying the ordering field** | the record must move: delete + re-insert |
| **Searching on a non-ordering field** | binary search doesn't help → linear search |
| **Binary search is still costly on disk** | $\log_2 b$ random block reads; rarely used alone |

Common fix: insert new records into an unordered **overflow file** and **periodically merge** it into the main file (reorganization). Searches must then check both files.

**In practice** ordered files are rarely used alone; they are combined with a **primary index** → an **indexed-sequential file** ([[02.02 Primary Indexes]]). If the ordering field is not a key, the file is a **clustered file** ([[02.03 Clustering Indexes]]).

## 3. Average access cost (lecture Table 1)
| Organization | Access method | Average blocks to find a specific record |
|---|---|---|
| Heap (unordered) | sequential scan (linear search) | $b/2$ |
| Ordered (sorted) | sequential scan | $b/2$ |
| Ordered (sorted) | binary search | $\log_2 b$ |

> [!example] Tutorial 1 Q2 / 2021/22 Q6 ($b$ = 5000, $s$ = 30 ms, $rd$ = 12.5 ms, $btt$ = 1 ms, $B/btr$ = 1.25 ms)
> - Linear search, **contiguous + double buffering**: read $b/2 = 2500$ blocks → $30 + 12.5 + 2500 \times 1.25 = 3167.5$ ms.
> - Linear search, **not contiguous**: $2500 \times (30+12.5+1) = 108{,}750$ ms.
> - Binary search on Ssn: $\lceil\log_2 5000\rceil = 13$ blocks → $13 \times 43.5 = 565.5$ ms.
> Full working: [[01.12 Worked File and Disk Calculations]].

## 4. Sequential vs indexed file organization for frequently updated records (2022/23 Q1(d), 2023/24 Q1(d))
**Sequential file** = records stored in sorted order of a key (sorted file). **Indexed file** = data file plus an index (e.g. a B+-tree) giving direct access by key.

| Criterion | Sequential (sorted) | Indexed (e.g. B+-tree on Employee ID) |
|---|---|---|
| Insert new employee | **slow**: shift records or use an overflow file + reorganize | fast: insert into a data block + update the index (dynamic index absorbs growth) |
| Delete | gaps / markers; reorganization needed | delete record + index entry; B+-tree rebalances locally |
| Update **non-key** field (Salary, Department) | in place if fixed-length; but finding the record needs binary/linear search | find via index in a few I/Os, update in place |
| Update **ordering key** | record must move | update index entry |
| Lookup by Employee ID | binary search: $\log_2 b$ I/Os | index: index height + 1 (often 3–4 I/Os) |
| Lookup by Department | linear scan (unless sorted on it) | add a **secondary index** on Department |
| Full ordered report / batch processing | **excellent**: one sequential pass | good if clustered; extra overhead otherwise |
| Storage overhead | none | index storage |
| Maintenance overhead | periodic reorganization | every insert/update/delete also updates the index |

**Conclusion for a frequently updated employee table:** an **indexed organization** (dynamic B+-tree on Employee ID, possibly a secondary index on Department) suits it better: updates and lookups are local and logarithmic. A purely sequential file is only appropriate if most work is **batch processing** of the whole file in key order and updates can be applied in **periodic batches**.

## 5. Exam-relevant points
- Heap: insertion cheap, search $b/2$ (or $b$), deletion leaves holes.
- Sorted: binary search $\log_2 b$, efficient range queries, **expensive insertion/deletion**; overflow file + reorganization.
- For "sequential vs indexed" give a **pros/cons table** and a **justified conclusion tied to the scenario**.
