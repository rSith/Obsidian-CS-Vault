# 01.04 · Buffering of Blocks (Double Buffering)

> [!info] [[01.00 Data Storage and File Organization|Lesson 1]] · Lecture L1 §5.2 (+ §5.1 consecutive blocks, §5.3.4 allocation) · Priority 🔴 High (3 papers)
> **Asked as:**
> - "If you have a large file that is frequently scanned sequentially, explain how you would store the pages in the file on a disk." (2021/22 Q2(c))
> - "Define the concept of buffering in the context of disk I/O operations. Discuss its significance in improving the performance of data retrieval." (2022/23 Q1(b))
> - "Explain the role of buffering in disk input/output operations. Why is buffering considered important for efficient interaction between the CPU and storage devices?" (2023/24 Q1(b))

## 1. What is it?
A **buffer** is an area of **main memory** reserved to hold a copy of one disk block. **Buffering** means reading disk blocks into these memory areas so the CPU can work on them.

**Double buffering** uses **two (or more) buffers** so that **while the CPU processes the block in one buffer, the disk controller is already filling the other buffer with the next block**.

> [!tip] Analogy: two plates at a buffet
> You eat from plate A while a waiter fills plate B. When you finish A, B is already full, so you swap and the waiter refills A. You never sit waiting with an empty plate. With only one plate you would eat, wait for a refill, eat, wait…

## 2. Why is it used?
- The CPU is extremely fast and the disk is extremely slow ([[01.03 Disk Access Time and Performance]]). Without buffering, the CPU **idles** during every disk read.
- A separate **disk I/O processor (controller)** can transfer data **independently of and in parallel with** the CPU once started (lecture §5.2). Buffering lets us use that parallelism.

## 3. How double buffering works (lecture Figure 3)
```text
time ─────────────────────────────────────────────────────────►
Disk I/O:   [fill A: block i ][fill B: block i+1][fill A: block i+2][fill B: block i+3]
CPU:                          [process A: i     ][process B: i+1    ][process A: i+2   ]
```
1. All block addresses to be read are known in advance (e.g. a sequential scan).
2. The controller reads block *i* into buffer A.
3. As soon as A is full, the CPU starts processing A **and at the same time** the controller reads block *i+1* into buffer B.
4. When the CPU finishes A it moves to B (already filled), and the controller refills A with block *i+2*.
5. This continues until the file ends.

It works best when **processing a block takes less time than reading the next one** (the usual case).

### What it gains (lecture)
- **Continuous reading or writing** of consecutive blocks: the seek time and rotational delay are paid **only for the first block**; afterwards only transfer time is paid per block.
- Data is **kept ready for processing**, which reduces waiting time in programs.
- CPU and I/O **overlap**, so total time ≈ max(CPU time, I/O time) instead of their sum.

## 4. Storing a large, frequently scanned file (2021/22 Q2(c))
To make sequential scans fast:
1. **Allocate the file's blocks contiguously** (consecutive blocks on the same track, then the same cylinder, then adjacent cylinders): contiguous allocation ([[01.05 Records, Blocking and File Allocation]]).
2. Fill a whole **cylinder** before moving to the next, so the arm moves only between cylinders (one short seek per cylinder).
3. Read with **double buffering / prefetching**, so the CPU processes block *i* while block *i+1* is read.
4. Optionally use **large blocks or clusters/extents** to reduce the number of I/O requests.

Cost then becomes $s + rd + b \cdot btt$ (or $s + rd + b \cdot B/btr$) instead of $b(s + rd + btt)$.

> [!example] Numbers from Tutorial 1 (2400 rpm disk, $s$ = 30 ms)
> Reading 2,500 blocks **scattered**: $2500 \times 43.5 = 108{,}750$ ms ≈ **109 s**.
> Reading 2,500 **contiguous** blocks with double buffering: $30 + 12.5 + 2500 \times 1.25 = 3{,}167.5$ ms ≈ **3.2 s**. About 34× faster.

## 5. Significance: buffering and CPU–storage interaction (2022/23 Q1(b), 2023/24 Q1(b))
| Point | Explanation |
|---|---|
| Bridges the speed gap | memory and CPU work in ns; disks in ms. Buffers let the fast side work while the slow side catches up |
| Parallelism | the I/O controller and CPU work simultaneously |
| Fewer mechanical delays | consecutive reads pay seek + rotation once |
| Reuse (caching) | a block already in a buffer need not be read again (the DBMS **buffer pool**) |
| Smooth throughput | prevents the CPU from stalling on every request; programs wait less |
| Batching writes | modified blocks can be written back later in groups ("eventually" in the file operations of [[01.06 File Operations and Access Methods]]) |

> [!note] Beyond the lecture (textbook knowledge)
> Real DBMSs keep a large **buffer pool** with a **replacement policy** (e.g. LRU) that decides which buffered block to evict. The lecture covers double buffering only; mention the buffer pool as an extra point, not as lecture content.

## 6. Exam-relevant points
- Definition + the two-buffer picture + "CPU processes one buffer while the I/O processor fills the other" earns most of the marks.
- Always link it to **seek and rotational delay being paid only once** for consecutive blocks.
- For "how would you store a sequentially scanned file", say **contiguous blocks on the same cylinder + double buffering**.
