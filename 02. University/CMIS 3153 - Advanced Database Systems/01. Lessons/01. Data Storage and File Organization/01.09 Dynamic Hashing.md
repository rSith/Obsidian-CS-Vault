# 01.09 · Dynamic Hashing (Extendible and Linear Hashing)

> [!info] [[01.00 Data Storage and File Organization|Lesson 1]] · Lecture L1 §7.3.1.2 · Priority 🟢 Low (never asked directly; supports "pros and cons of hashing" answers)

## 1. The problem with static hashing
In ordinary (static) hashing the number of buckets $M$ is **fixed** when the file is created. If the file grows, buckets overflow and long overflow chains form; if it shrinks, space is wasted. Changing $M$ means **rehashing every record**, which is very expensive.

> [!tip] Analogy
> A school with exactly 10 classrooms. When enrolment doubles, classrooms overflow. Static hashing = rebuild the whole school. Dynamic hashing = add one classroom at a time, only moving the students who need to move.

## 2. Dynamic hashing (general idea)
The number of buckets **adapts to the size of the data**. The aim is to handle large, continuously growing data **without full-scale rehashing or reorganization**, absorbing overflow by splitting only the affected bucket.

## 3. Extendible (extendable) hashing
- Keeps a **directory**: an array of $2^d$ pointers to buckets.
- **Global depth $d$**: the number of hash-value bits used to index the directory.
- **Local depth $d'$** (per bucket): the number of bits that bucket actually depends on; several directory entries may point to the same bucket when $d' < d$.
- **Bucket overflow:**
  - If $d' < d$: split only that bucket into two (local depth + 1) and redistribute its records using one more bit; adjust directory pointers.
  - If $d' = d$: **double the directory** (global depth + 1), then split the bucket.
- Search: take the first (or last) $d$ bits of $h(K)$, follow the directory pointer → **one directory lookup + one bucket read**.

> [!example] Mini illustration
> Global depth 1: directory entries `0` → bucket A, `1` → bucket B. Bucket A overflows and has local depth 1 = global depth, so the directory doubles to `00, 01, 10, 11`; A splits into A0 (`00`) and A1 (`01`); `10` and `11` both still point to B (local depth 1).

## 4. Linear hashing
- **No directory.** Buckets are split **one at a time in a fixed linear order** (bucket 0, then 1, then 2 …), tracked by a "next to split" pointer, whenever an overflow (or load threshold) occurs.
- Uses two hash functions, $h_i(K) = K \bmod 2^i M$ and $h_{i+1}$; records in already-split buckets are addressed with $h_{i+1}$.
- The number of buckets grows **gradually and linearly**, avoiding a complete rehash.

> [!note] Lecture wording
> The lecture says linear hashing "uses a linear probe to manage the buckets". That phrase is loose: linear hashing grows the *number of buckets* linearly; it is not the same as linear probing ([[01.08 Hash Files and Collision Handling]]). The description above (split pointer, $h_i$/$h_{i+1}$) is the standard textbook mechanism.

## 5. Comparison
| | Static hashing | Extendible hashing | Linear hashing |
|---|---|---|---|
| Buckets | fixed $M$ | grows by splitting overflowing bucket | grows one bucket at a time, in order |
| Directory | none (header table) | **yes** (doubles when needed) | **no** |
| Growth cost | full rehash | split one bucket (+ occasional directory doubling) | split one bucket |
| Overflow chains | can get long | rare | temporary, until that bucket's turn to split |
