# 04.07 · The Role of Indexing in Query Optimization

> [!info] [[04.00 Query Optimization|Lesson 4]] · Lecture L4 §1.1 (scans), §1.2, §5.2, Essay Q1 · L2 §1 · [[TUT 4 - Selectivity and Index Cost|Tutorial 4]] · Priority 🔴 High
> **Asked as:** "Briefly explain the role of indexing in query optimization" (2022/23 Q5(a), 20 marks) · "Discuss how indexing influences query optimization and system performance in relational databases" (2023/24 Q2(a), 25 marks)

## 1. The idea
Indexes are the **access paths** the optimizer chooses between. For each table in a plan the optimizer asks: *is it cheaper to read the whole table, or to go through an index?* The answer depends on **selectivity**: how many rows the condition matches.

> [!tip] Analogy
> To find one recipe, use the cookbook's index. To cook **every** recipe in the book, just read it front to back: flipping to the index and back for every recipe would be slower. The optimizer makes the same judgement.

## 2. How indexes help the optimizer
| Role | Explanation |
|---|---|
| **Cheaper access paths** | an index scan replaces a full table scan for selective predicates (`=`, small ranges): $\approx$ height + matching rows vs $b$ blocks |
| **Join algorithms** | an index on the inner table's join column enables **index nested-loop joins**; sorted (clustered/B+-tree) inputs enable **merge joins** |
| **Avoiding sorts** | reading a B+-tree in order satisfies **ORDER BY / GROUP BY / MIN / MAX** without sorting |
| **Covering indexes** | a query answered from the index alone, no table access ([[02.09 Index Maintenance, Composite and Covering Indexes]]) |
| **Statistics** | indexes come with statistics (distinct values, levels $x$, first-level blocks $b_{l1}$) used in cost formulas ([[04.02 Query Cost and Cost Models]]) |
| **Uniqueness information** | a unique index tells the optimizer that `key = c` returns ≤ 1 row (e.g. 'Aquarius' joined first) |
| **Join ordering** | indexed, selective tables are good starting points |

## 3. When an index is *not* used
- **Low selectivity** (many matching rows): random I/O per row costs more than one sequential scan.
- **Non-clustered index on a large range** (Tutorial 4 Ex 3: 300,000 random reads vs a full scan).
- Function applied to the column (`WHERE YEAR(order_date) = 2025`), leading column of a composite index missing, type mismatch.
- **Low-cardinality** columns (status with 5 values): a **bitmap index** is more suitable than a B-tree.

### Selectivity
$$
\text{selectivity} = \frac{\text{matching rows}}{\text{total rows}}
$$
Optimizers often use a threshold (Tutorial 4 uses **< 0.10** for a non-clustered B-tree; an exercise uses 0.15). Selectivity below the threshold → index; above → full scan.

> [!example] Tutorial 4 Example 1
> Orders: 1,000,000 rows; `status = 'pending'` matches 250,000 → selectivity **0.25** > 0.10 → the B-tree index is **not** used (full scan). A **bitmap index** would suit `status` (5 distinct values, compresses well, fast to combine with other filters).

> [!example] Tutorial 4 Example 2
> B-tree height 3, row fetch 1 I/O: index lookup = 3 + 1 = **4 I/Os**; full scan of 50,000 pages = **50,000 I/Os** → the index is massively better.

## 4. Effect on overall system performance (2023/24 Q2(a))
**Positive:**
- Faster SELECTs, joins, sorting and grouping → lower response time and higher throughput.
- Less disk I/O and CPU per query → more concurrent users; less contention.
- Better plans: the optimizer has more (and cheaper) options.

**Negative:**
- **Write overhead:** every INSERT/UPDATE/DELETE updates all affected indexes (splits, merges).
- **Storage** for each index.
- **Too many / wrong indexes** can mislead or slow the optimizer (larger search space) and waste maintenance.
- Stale statistics on indexes → wrong estimates → bad plans.

**Guidelines:** index columns used in WHERE, JOIN, ORDER BY with high selectivity; choose the clustered index for range-heavy columns; use composite/covering indexes for frequent multi-column queries; drop unused indexes; keep statistics current; check plans with `EXPLAIN`.

## 5. How to optimize a query that does a full scan though an index exists (lecture essay Q1)
1. Check the plan (`EXPLAIN`). 2. Check selectivity: maybe the scan is genuinely cheaper. 3. Make predicates **sargable**: no functions or implicit casts on the indexed column. 4. Update statistics. 5. Use a composite or covering index matching the query. 6. As a last resort, use optimizer hints.
