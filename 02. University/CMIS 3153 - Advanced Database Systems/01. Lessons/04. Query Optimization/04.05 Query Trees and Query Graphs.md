## 1. What is a query tree?
A **query tree** is a tree data structure that represents a **relational algebra expression** (a query's logical plan):
- **Leaf nodes** = the **input relations** (base tables; also indexes or views if used).
- **Internal nodes** = **relational operators**: σ selection, π projection, ⋈ join, × product, aggregation (γ), sorting (τ).
- **Root** = the **final operation**, whose output is the query result.
- **Edges** = the flow of data from child to parent.

**Execution order:** start at the **leaves**, execute an internal node when its operands are available, finish at the **root**.

> [!tip] Analogy: a family tree upside-down / a river system
> Raw ingredients (tables) are at the bottom; streams merge (joins) and get filtered (σ) as they flow upwards, until one river (the result) reaches the root.

## 2. How to build a query tree from SQL (lecture essay Q6)
1. One **leaf per table** in FROM.
2. **Canonical (initial) tree:** combine all leaves with **Cartesian products (×)**, then one **σ** with the whole WHERE condition, then **π** with the SELECT list (plus γ for GROUP BY, τ for ORDER BY).
3. **Optimized tree:** apply heuristics ([[04.06 Heuristic Optimization and Transformation Rules]]): push σ down, replace × + σ by ⋈, push π down, reorder joins.

> [!example] Lecture practice Q1
> `SELECT name, age FROM employees WHERE age > 30 ORDER BY name;`
> ```text
> τ_{name}            (sort, root)
>    │
> π_{name, age}
>    │
> σ_{age > 30}
>    │
> employees           (leaf)
> ```

> [!example] Lecture practice Q2 = 2022/23 Q5(d)
> `SELECT e.name, d.department_name FROM employees e INNER JOIN departments d ON e.department_id = d.department_id WHERE e.salary > 50000;`
> **(i) Query tree (filter pushed below the join):**
> ```text
>                π_{e.name, d.department_name}
>                          │
>          ⋈_{e.department_id = d.department_id}
>               ╱                         ╲
>    σ_{e.salary > 50000}             departments d
>               │
>          employees e
> ```
> **(ii)** The **join is its own node** ⋈ with condition `e.department_id = d.department_id`. The filter `salary > 50000` uses only **employees** columns, so by the rule *commuting σ with ⋈* it is applied **before** the join (predicate push-down): fewer employee rows reach the join → smaller join input and output. Applying it **after** the join gives the same result but processes every employee in the join.
> ```text
> (filter after join, same result, more work)
> π ─ σ_{salary>50000} ─ ⋈ ─ (employees, departments)
> ```
> **(iii) Order of operations:** (1) scan employees, (2) apply σ salary > 50000, (3) scan departments, (4) join on department_id, (5) project name and department_name (and return results).

## 3. What is a query graph?
A **query graph** represents a query (originally a **relational calculus** expression) as a **graph**:
- **Relation nodes** (drawn as single circles) for each table/tuple variable,
- **Constant nodes** (double circles) for constants in the query (e.g. 'Stafford'),
- **Edges** for **join conditions** (between relation nodes) and **selection conditions** (relation node to constant node),
- attributes to be retrieved are listed beside each relation node.

It shows **which relations are connected and how**, but **not in what order** to perform the operations. There is **only one graph per query**.

> [!example] Lecture Example 1 (Stafford projects)
> ```sql
> SELECT P.Pnumber, P.Dnum, E.Lname, E.Address, E.Bdate
> FROM   PROJECT AS P, DEPARTMENT AS D, EMPLOYEE AS E
> WHERE  P.Dnum = D.Dnumber AND D.Mgr_ssn = E.Ssn AND P.Plocation = 'Stafford';
> ```
> **Query tree** (an order is fixed: (1) select PROJECT, (2) join DEPARTMENT, (3) join EMPLOYEE, then project):
> ```text
>                π_{P.Pnumber, P.Dnum, E.Lname, E.Address, E.Bdate}
>                                   │
>                     (3) ⋈_{D.Mgr_ssn = E.Ssn}
>                         ╱                 ╲
>          (2) ⋈_{P.Dnum = D.Dnumber}         E
>               ╱                ╲
>   (1) σ_{P.Plocation='Stafford'}  D
>               │
>               P
> ```
> **Query graph** (no order implied):
> ```text
>  [P.Pnumber, P.Dnum]            [E.Lname, E.Address, E.Bdate]
>         (P) ───P.Dnum=D.Dnumber─── (D) ───D.Mgr_ssn=E.Ssn─── (E)
>          │
>   P.Plocation='Stafford'
>          │
>     (('Stafford'))
> ```

## 4. Query trees vs query graphs (2022/23 Q5(c), 2023/24 Q5(b))
| | Query tree | Query graph |
|---|---|---|
| Represents | a **relational algebra** expression | a **relational calculus** expression (the query's connections) |
| Structure | hierarchical **tree**: leaves = relations, internal nodes = operators, root = result | **graph**: nodes = relations (and constants), edges = join/selection conditions; may contain **cycles** |
| Order of operations | **specified** (bottom-up) | **not specified** |
| Number per query | **many** equivalent trees | **one** graph |
| Main use | **execution planning** and heuristic/cost-based rewriting | **visualizing relationships**; deciding **which joins are possible** and good join orders; complex multi-table queries |
| Preferred by optimizers today | **yes**: the optimizer must express execution order | used as an aid; not enough alone |
| Detail | can show σ, π, γ, sort, algorithms | shows only relations, conditions, output attributes |

### How query graphs assist join ordering (2023/24 Q5(b))
- The **edges show which pairs of relations share a join condition**. Joining two relations **not** connected by an edge would be a **Cartesian product**, so the optimizer only considers join orders that follow edges.
- The **shape** of the graph (chain, star, cycle) tells the optimizer how many join orders are sensible and helps enumerate them (e.g. dynamic programming over connected sub-graphs).
- **Selection edges to constants** show which relations will be **reduced most** (e.g. `Pname = 'Aquarius'` on a key → 1 tuple), suggesting they should be joined **first**.
- Because a graph is **order-neutral**, the optimizer is free to explore any order; the chosen order is then written down as a query tree.

## 5. Purpose of query trees in optimization (lecture §4.1.2)
1. Abstract representation of the query → easy to analyse.
2. Breaks complex queries into small components (σ, π, ⋈).
3. Basis for generating and evaluating alternative logical and physical plans.
4. Supports transformations: join reordering, predicate push-down, projection push-down, removing redundant operations.
5. Lets the optimizer explore physical strategies (join algorithms, access paths, parallelism).
