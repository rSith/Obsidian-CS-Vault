# 04.06 · Heuristic Optimization of Query Trees and Transformation Rules

> [!info] [[04.00 Query Optimization|Lesson 4]] · Lecture L4 §4 (intro), §4.1.4, Example 2, transformation rules 1–12 · Priority 🔴 High
> **Asked as:**
> - 2021/22 Q7(c) (60 marks): initial tree for EMPLOYEE, WORKS_ON, PROJECT ('Aquarius', Bdate > 1957-12-31): (i) the SQL, (ii) why inefficient, (iii) how to transform it (**the lecture's own Example 2**)
> - 2023/24 Q5(c) (60 marks): Employee/Department/Works, Location = 'Colombo', Salary > 80000: initial tree, heuristic optimization, why better
> - 2022/23 Q5(d)(ii)(iii): filter before or after the join, order of operations

## 1. What is heuristic optimization?
**Heuristic optimization** transforms a query tree into an **equivalent but cheaper** tree using **rules of thumb**, without searching every possible plan. The main heuristic (lecture §4):

> **Apply SELECT and PROJECT before JOIN and other binary operations**, because the size of a join result is roughly a **multiplicative** function of the input sizes, while σ and π **reduce** sizes.

> [!tip] Analogy: packing for a trip
> You don't put your whole wardrobe in the car and then throw things out at the airport. You **filter** (choose clothes for the weather = σ) and **trim** (leave the hangers = π) at home, so the car (join) carries far less.

## 2. Common heuristic techniques (lecture §4.1.4)
1. **Reorder joins**: do the join with the smallest result first.
2. **Predicate push-down**: move σ as close to the base tables as possible.
3. **Projection push-down**: keep only columns needed later.
4. **Join elimination**: remove redundant/useless joins.
5. **Simplify expressions**: remove redundancy; compute common sub-expressions once.
6. **Choose efficient join algorithms** (nested loop, hash, merge).
7. **Use indexes** (index scan instead of full scan) when appropriate.

**Benefits:** speed, resource savings, scalability, practical (fast to compute).
**Limitations:** **not guaranteed optimal**; rules built for typical cases may suit some data distributions badly.

## 3. The heuristic algorithm (step by step)
1. **Break up** conjunctive selections into a cascade of single σ's (rule 1).
2. **Push each σ down** as far as its attributes allow (rules 2, 4, 6, 10).
3. **Rearrange leaves** so the **most restrictive** selections/joins run first, while **avoiding Cartesian products** (rules 5, 9).
4. **Combine × followed by a join condition σ into ⋈** (rule 12).
5. **Push π down**: break and move projection lists down, keeping only attributes needed above (rules 3, 4, 7, 11).
6. Identify sub-trees that can be executed by one algorithm / pipelined.

## 4. The lecture's worked example (Example 2) = 2021/22 Q7(c)
*Last names of employees born after 1957 who work on the project named 'Aquarius'.*

**(i) SQL represented by the initial tree**
```sql
SELECT Lname
FROM   EMPLOYEE, WORKS_ON, PROJECT
WHERE  Pname = 'Aquarius' AND Pnumber = Pno AND Essn = Ssn
  AND  Bdate > '1957-12-31';
```
(In the exam paper's sample tables WORKS_ON has `Pnumber` and PROJECT has `Pno`; the condition `Pnumber = Pno` matches them either way.)

**Step 0: initial (canonical) tree**
```text
π_{Lname}
   │
σ_{Pname='Aquarius' ∧ Pnumber=Pno ∧ Essn=Ssn ∧ Bdate>'1957-12-31'}
   │
   ×
 ╱   ╲
×     PROJECT
╱ ╲
EMPLOYEE  WORKS_ON
```
**(ii) Why it is inefficient**
- It first builds the **Cartesian product of all three tables**: $|E| \times |W| \times |P|$ tuples (e.g. 1,000 × 10,000 × 100 = 10⁹ tuples), almost all discarded later.
- **All selections are applied at the very end**, after the huge intermediate result exists, though only **one** PROJECT tuple ('Aquarius') and the employees born after 1957 are needed.
- **All columns** are carried through every step although only Lname (and join columns) are needed.
- The resulting intermediate files are huge in **I/O, memory and CPU** cost. That is why the canonical tree is never executed directly.

**(iii) Transformations**

**Step 1: push selections down** (cascade σ, then commute σ with ×):
```text
π_{Lname}
   │
σ_{Pnumber=Pno}
   │
   ×
 ╱        ╲
σ_{Essn=Ssn}   σ_{Pname='Aquarius'}
   │                 │
   ×              PROJECT
 ╱      ╲
σ_{Bdate>'1957-12-31'}  WORKS_ON
   │
EMPLOYEE
```
**Step 2: most restrictive selection first.** `Pname` is effectively unique, so σ on PROJECT returns **one tuple**: swap EMPLOYEE and PROJECT so PROJECT is joined first:
```text
π_{Lname}
   │
σ_{Essn=Ssn}
   │
   ×
 ╱             ╲
σ_{Pnumber=Pno}   σ_{Bdate>'1957-12-31'}
   │                     │
   ×                  EMPLOYEE
 ╱       ╲
σ_{Pname='Aquarius'}  WORKS_ON
   │
PROJECT
```
**Step 3: replace × + join condition by ⋈:**
```text
π_{Lname}
   │
⋈_{Essn=Ssn}
 ╱               ╲
⋈_{Pnumber=Pno}     σ_{Bdate>'1957-12-31'}
 ╱        ╲              │
σ_{Pname='Aquarius'} WORKS_ON  EMPLOYEE
   │
PROJECT
```
**Step 4: push projections down** (keep only attributes needed above):
```text
π_{Lname}
   │
⋈_{Essn=Ssn}
 ╱                         ╲
π_{Essn}                    π_{Ssn, Lname}
   │                             │
⋈_{Pnumber=Pno}              σ_{Bdate>'1957-12-31'}
 ╱            ╲                  │
π_{Pno}        π_{Essn, Pnumber} EMPLOYEE
   │               │
σ_{Pname='Aquarius'} WORKS_ON
   │
PROJECT
```
Attribute names in Step 4 follow the exam paper's tables (PROJECT.**Pno**, WORKS_ON.**Pnumber**); in the lecture/textbook version the two names are the other way round.

With the paper's sample data: Aquarius = project 43 → WORKS_ON row (13453, 43) → EMPLOYEE 13453 Ahmed, born 1978 → result **Ahmed**.

## 5. Second worked example: 2023/24 Q5(c)
```sql
SELECT E.Name, D.Dept_Name
FROM   Employee E, Department D, Works W
WHERE  E.Emp_ID = W.Emp_ID AND W.Dept_ID = D.Dept_ID
  AND  D.Location = 'Colombo' AND E.Salary > 80000;
```
**(i) Initial tree**
```text
π_{E.Name, D.Dept_Name}
   │
σ_{E.Emp_ID=W.Emp_ID ∧ W.Dept_ID=D.Dept_ID ∧ D.Location='Colombo' ∧ E.Salary>80000}
   │
   ×
 ╱   ╲
×     W
╱ ╲
E   D
```
**(ii) Optimized tree** (push σ down; join along connected tables (E–W–D, never E × D); replace × by ⋈; push π down):
```text
                  π_{E.Name, D.Dept_Name}
                           │
                 ⋈_{W.Dept_ID = D.Dept_ID}
               ╱                         ╲
     π_{E.Name, W.Dept_ID}          π_{D.Dept_ID, D.Dept_Name}
             │                               │
     ⋈_{E.Emp_ID = W.Emp_ID}         σ_{D.Location='Colombo'}
       ╱                ╲                    │
π_{Emp_ID, Name}    π_{Emp_ID, Dept_ID}      D
       │                 │
σ_{E.Salary>80000}       W
       │
       E
```
(An equally good alternative joins the small `σ_{Location='Colombo'}(D)` with W first, then E, if Colombo departments are the most restrictive selection.)

**(iii) Why it is more efficient**
- **No Cartesian products:** the initial tree builds $|E|\times|D|\times|W|$ tuples; the optimized tree only joins matching tuples.
- **Selections early:** only high-salary employees and Colombo departments enter the joins → far smaller intermediate results.
- **Projections early:** narrower tuples → more per block, fewer I/Os, less memory.
- **Join order follows join conditions**, starting with reduced inputs.
- Smaller inputs allow better **join algorithms** (hash join in memory) and **pipelining**; fewer disk reads/writes overall.

## 6. General transformation rules (lecture list)
| # | Rule | Statement |
|---|---|---|
| 1 | **Cascade of σ** | $\sigma_{c_1 \wedge c_2 \wedge \dots \wedge c_n}(R) = \sigma_{c_1}(\sigma_{c_2}(\dots(\sigma_{c_n}(R))\dots))$ |
| 2 | **Commutativity of σ** | $\sigma_{c_1}(\sigma_{c_2}(R)) = \sigma_{c_2}(\sigma_{c_1}(R))$ |
| 3 | **Cascade of π** | $\pi_{L_1}(\pi_{L_2}(\dots\pi_{L_n}(R))) = \pi_{L_1}(R)$ (only the last/outermost list matters) |
| 4 | **Commuting σ with π** | if $c$ uses only attributes in $A_1..A_n$: $\pi_{A_1..A_n}(\sigma_c(R)) = \sigma_c(\pi_{A_1..A_n}(R))$ |
| 5 | **Commutativity of ⋈ (and ×)** | $R \bowtie_c S = S \bowtie_c R$; $R \times S = S \times R$ |
| 6 | **Commuting σ with ⋈ (or ×)** | if $c$ involves only $R$: $\sigma_c(R \bowtie S) = \sigma_c(R) \bowtie S$; if $c = c_1 \wedge c_2$ ($c_1$ on R, $c_2$ on S): $\sigma_c(R \bowtie S) = \sigma_{c_1}(R) \bowtie \sigma_{c_2}(S)$ |
| 7 | **Commuting π with ⋈ (or ×)** | $L = \{A_1..A_n\} \cup \{B_1..B_m\}$; if join condition $c$ uses only attributes in $L$: $\pi_L(R \bowtie_c S) = \pi_{A_1..A_n}(R) \bowtie_c \pi_{B_1..B_m}(S)$; otherwise add the extra join attributes to the inner projections and apply a final $\pi_L$ |
| 8 | **Commutativity of set operations** | ∪ and ∩ are commutative; − is **not** |
| 9 | **Associativity** of ⋈, ×, ∪, ∩ | $(R\,\theta\,S)\,\theta\,T = R\,\theta\,(S\,\theta\,T)$ |
| 10 | **Commuting σ with set operations** | $\sigma_c(R\,\theta\,S) = \sigma_c(R)\,\theta\,\sigma_c(S)$ for θ ∈ {∪, ∩, −} |
| 11 | **π commutes with ∪** | $\pi_L(R \cup S) = \pi_L(R) \cup \pi_L(S)$ (**not** with − or ∩, see [[03.03 Set Operations and Joins]]) |
| 12 | **(σ, ×) → ⋈** | $\sigma_c(R \times S) = R \bowtie_c S$ when $c$ is a join condition |
| + | **De Morgan** | $\neg(c_1 \wedge c_2) = \neg c_1 \vee \neg c_2$; $\neg(c_1 \vee c_2) = \neg c_1 \wedge \neg c_2$ |

> [!note] Formulas
> The lecture's rule statements were figures; the formulas above are the standard Elmasri & Navathe statements that the lecture lists by name.

**Summary heuristic (lecture):** perform σ and π **as early as possible** (move them down the tree); execute the **most restrictive** σ and ⋈ first by reordering leaves, **avoiding Cartesian products**.

## 7. σ cannot be pushed below γ (2020/21 Q1(a)(ii))
A selection on non-grouping columns (e.g. `T.h > 21`) **must** be applied **before** grouping; a selection on an aggregate (HAVING) **must** be applied **after** it. Moving σ across γ changes the meaning. See [[03.03 Set Operations and Joins]].
