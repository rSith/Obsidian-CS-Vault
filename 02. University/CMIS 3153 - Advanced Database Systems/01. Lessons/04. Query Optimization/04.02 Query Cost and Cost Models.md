# 04.02 · Query Cost, Cost Models and Catalog Statistics

> [!info] [[04.00 Query Optimization|Lesson 4]] · Lecture L4 §1.2, §1.3, §5, §5.1, §5.2 · Priority 🟡 Medium
> **Asked as:** "Discuss the reasons for poor performance of queries and possible remedies." (2020/21 Q7(a), 20 marks; no dedicated lecture section; answer built from this note + [[04.07 Indexing in Query Optimization]])

## 1. What is the cost of a query?
The **cost of a query** is the amount of **resources** needed to process it and return the result. The optimizer can only choose the cheapest plan if it can **estimate** the cost of each plan.

> [!tip] Analogy
> Choosing between a taxi, a bus and a train: you estimate time, money and comfort for each before deciding. The optimizer estimates disk reads, CPU, memory and network for each plan.

## 2. What contributes to cost (lecture §1.2)
| Factor | Example |
|---|---|
| **Execution time** | joins of large tables, full scans |
| **CPU usage** | filtering, joins, sorting, aggregation (some algorithms are quadratic) |
| **Memory usage** | sorting, grouping, holding intermediate results; running out → external sort on disk |
| **I/O operations** | **number of disk blocks/pages read or written** (table scans vs index scans): usually the **dominant** factor |
| **Data transfer / network** | distributed or cloud databases; latency and bandwidth |
| Cloud / API cost | money charged per query or data scanned |

## 3. Cost components for query execution (lecture §5.1)
1. **Access cost to secondary storage (disk I/O):** reading/writing data blocks; depends on access structures (ordering, hashing, indexes) and on whether blocks are contiguous.
2. **Disk storage cost:** storing intermediate files.
3. **Computation (CPU) cost:** in-memory searching, sorting, merging, computing values.
4. **Memory usage cost:** number of buffers needed.
5. **Communication cost:** shipping the query and results; in distributed DBs, moving tables between sites ([[05.06 Distributed Query Processing and Semijoin]]).

## 4. Cost models (lecture §1.3)
A **cost model** is a mathematical framework the optimizer uses to **estimate** the resources a plan will need.
| Model | Idea | Weakness |
|---|---|---|
| **Simple** | basic rules: table scans cost more than index scans; nested loops cheaper for small data | ignores data distribution |
| **Statistical** | uses statistics: row counts, value distributions (**histograms**), **cardinality** and **selectivity** estimates | only as good as the statistics |
| **Cascades framework** | applies transformation rules to generate plans; **dynamic programming** to find the cheapest | complex |
| **Exponential models** | cost as exponential function of I/O, CPU, memory | accurate but expensive to compute |

## 5. Catalog information used in cost functions (lecture §5.2)
| Statistic | Symbol |
|---|---|
| number of records (tuples) | $r$ |
| average record size | $R$ |
| number of blocks | $b$ |
| blocking factor | $bfr$ |
| primary file organization (unordered, ordered, hashed …) | |
| indexes and their attributes; **number of index levels** | $x$ |
| number of first-level index blocks | $b_{l1}$ |
| number of **distinct values** of an attribute | $d$ |
| **attribute selectivity** (fraction of records satisfying an equality condition) | $sl$ |
| **selection cardinality** (average records satisfying equality) | $s = sl \times r$ |

- **Key attribute:** $d = r$, $sl = 1/r$, $s = 1$.
- **Non-key attribute** (values uniformly distributed): $sl = 1/d$, $s = r/d$.

> [!example] Selection cardinality
> EMPLOYEE has $r = 10{,}000$ rows and attribute `Dno` has $d = 50$ distinct values. For `Dno = 5`: $sl = 1/50 = 0.02$, $s = 10{,}000/50 = 200$ rows expected.

Cost estimates are **estimates**, so the chosen plan may not be the absolute best.

## 6. Reasons for poor query performance and remedies (2020/21 Q7(a))
| Reason | Remedy |
|---|---|
| **Missing or unsuitable indexes** → full table scans | create indexes on WHERE/JOIN columns; composite/covering indexes ([[02.09 Index Maintenance, Composite and Covering Indexes]]) |
| **Too many / unused indexes** slow down writes | drop redundant indexes |
| **Poorly written SQL**: `SELECT *`, functions on indexed columns, unnecessary DISTINCT/ORDER BY, correlated subqueries | **query refactoring**: select needed columns, rewrite subqueries as joins, remove redundant joins |
| **Cartesian products / bad join order** | correct join conditions; let optimizer reorder; heuristics |
| **Outdated statistics** → wrong selectivity estimates → bad plans | update statistics/histograms regularly |
| **Skewed data distribution** | histograms; partitioning |
| **Large intermediate results / sorting in memory overflow** | push selections/projections down; more memory; pipelining |
| **Disk I/O bottleneck**: scattered data, fragmentation, random I/O | contiguous storage, clustering, reorganization, buffering, SSD/RAID ([[01.03 Disk Access Time and Performance]]) |
| **Locking / concurrency contention** | shorter transactions, suitable isolation levels |
| **Repeated identical queries** | **query caching** / result caching |
| **Network cost** (distributed) | data localization, semijoins, replication |

Tools: examine the **execution plan** (`EXPLAIN`) to find the bottleneck (full scans, nested loops on large inputs, sorts).
