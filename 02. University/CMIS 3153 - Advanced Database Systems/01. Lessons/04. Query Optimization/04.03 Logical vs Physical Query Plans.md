# 04.03 · Logical vs Physical Query Plans (and Optimization)

> [!info] [[04.00 Query Optimization|Lesson 4]] · Lecture L4 §2, §2.1–§2.3 · Priority 🔴 High
> **Asked as:**
> - "Explain the difference between logical and physical query optimization, including examples of each." (2022/23 Q4(b) **and** 2023/24 Q4(b), 25 marks each)
> - "Draw a logical plan for the query (4-table join with GROUP BY/AVG)." (2020/21 Q2(a), 40 marks)
> - "Explain the THREE key steps of Query Optimisation using a diagram." (2021/22 Q7(a), 20 marks)

## 1. Two kinds of plan
| | **Logical query plan** | **Physical query plan** |
|---|---|---|
| Describes | **what** operations are needed | **how** each operation is executed |
| Made of | relational algebra operators: σ, π, ⋈, γ, sort | algorithms and access paths: table scan, index scan, nested-loop / hash / sort-merge join, external sort, pipelining |
| Depends on hardware / indexes? | **no**: independent of storage | **yes**: depends on available indexes, sort order, memory |
| Optimized by | **rewriting** with equivalence rules / heuristics (push σ and π down, reorder joins, × + σ → ⋈) | **cost-based choice** of algorithms and access paths using statistics |
| Output | an (optimized) RA expression / query tree | an executable plan |

> [!tip] Analogy: a recipe vs a kitchen schedule
> **Logical plan** = the recipe: "chop vegetables, fry onions, add rice, simmer". It does not say which knife or which stove.
> **Physical plan** = the actual schedule for *this* kitchen: "use the food processor (index) for vegetables, the large gas burner (hash join) for frying, the pressure cooker (sort-merge) for rice".

## 2. Logical query optimization
Works on the **query tree / RA expression**, before any physical details:
- **Predicate (selection) push-down:** apply σ as early as possible.
- **Projection push-down:** keep only needed columns early.
- **Join reordering:** smallest/most selective joins first; avoid Cartesian products.
- Replace σ over × by ⋈; remove redundant operations.

> [!example] Logical optimization
> `SELECT e.name FROM employees e JOIN departments d ON e.dept_id = d.dept_id WHERE d.dept_name = 'Sales'`
> Initial: $\pi_{name}(\sigma_{dept\_name='Sales'}(employees \bowtie departments))$
> Optimized: $\pi_{name}(employees \bowtie \sigma_{dept\_name='Sales'}(departments))$: the filter is applied to the small departments table **before** the join.

## 3. Physical query optimization
Chooses **implementations** for each logical operator, using cost estimates:
- **Access path:** full table scan vs index scan (clustered or not).
- **Join algorithm:** nested loop, index nested loop, hash join, sort-merge ([[04.01 Query Execution and Join Algorithms]]).
- **Sort method:** in-memory vs external merge sort; or avoid sorting by reading an index in order.
- Pipelining vs materialization; parallelism.

> [!example] Physical optimization (lecture walk-through)
> `SELECT first_name, last_name FROM employees WHERE department = 'Sales' ORDER BY first_name;`
> **Logical plan:** filter `department = 'Sales'` → project (first_name, last_name) → sort by first_name.
> **Physical plan:** **index scan** on `department` (if an index exists) instead of a full scan; **in-memory sort** if the result is small, otherwise **external merge sort**; if joins were present, choose **hash join** or **nested loops**.

## 4. Query plan optimization (lecture §2.3)
- **Logical plan optimization:** push filters/projections down the tree to shrink intermediate results.
- **Physical plan optimization:** pick index scan over full scan, or hash join over nested loops, based on estimated resource costs.

## 5. The three key steps of query optimization (2021/22 Q7(a))
```text
SQL query
   │  (1) PARSING AND TRANSLATION
   ▼        scanner + parser, validation → relational algebra expression / initial query tree
Relational algebra expression
   │  (2) OPTIMIZATION                      ◄── statistics about data (catalog)
   ▼        rewrite logically (heuristics), choose algorithms/access paths by cost
Execution plan (physical plan)
   │  (3) EVALUATION
   ▼        query-execution engine runs the plan against the data
Query output
```
1. **Parsing and translation** into an internal relational-algebra form.
2. **Optimization:** generate equivalent plans (logical rewriting + physical choices) and pick the lowest estimated cost using catalog statistics.
3. **Evaluation (execution):** the evaluation engine runs the chosen plan and returns results.
(Lecture L3 Figure 1 shows the same pipeline; see [[03.01 Stages of Query Processing]].)

## 6. Drawing a logical plan: 2020/21 Q2(a)
```sql
SELECT R.b, avg(U.k) AS avg
FROM   R, S, T, U
WHERE  R.a = S.d AND S.e = T.g AND T.h = U.i AND U.j = 5 AND (R.c + S.f) < 10
GROUP BY R.b;
```
"Any correct plan" is accepted. A clear one (selections pushed down):
```text
                     π_{R.b, avg}
                          │
              γ_{R.b, AVG(U.k) → avg}
                          │
                    ⋈_{T.h = U.i}
                  ╱              ╲
            ⋈_{S.e = T.g}       σ_{U.j = 5}
           ╱           ╲           │
   σ_{R.c+S.f<10}       T          U
          │
     ⋈_{R.a = S.d}
      ╱        ╲
     R          S
```
Note: $(R.c + S.f) < 10$ uses columns of **both** R and S, so it can only be applied **after** R ⋈ S (it cannot be pushed into either table alone).

## 7. Exam-relevant points
- Use the **what vs how** framing, give **one example each** (push-down for logical; index scan / hash join for physical).
- Mention that logical optimization is **independent of hardware/indexes**, physical optimization **uses statistics and costs**.
