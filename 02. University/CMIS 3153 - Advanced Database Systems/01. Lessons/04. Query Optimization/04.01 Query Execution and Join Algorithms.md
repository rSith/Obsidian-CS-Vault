# 04.01 · Query Execution and Join Algorithms

> [!info] [[04.00 Query Optimization|Lesson 4]] · Lecture L4 §1, §1.1 · Priority 🟡 Medium
> **Asked as:** "Consider two physical query plans (A: index nested loop with B+-tree indexes; B: hash join with file scans). Give two reasons (with explanation) why plan B may be faster than plan A." (2020/21 Q2(b), 60 marks) · Lecture essay Q8 "Compare and contrast join algorithms".

## 1. What is query execution?
**Query execution** is carrying out the operations of the chosen **execution plan**: scanning tables, filtering, joining, sorting and aggregating. It happens **after** optimization.

An **execution plan** is a tree (or graph) of operators that records the optimizer's choices:
- which **indexes** to use (if any),
- which **join algorithms** (nested loop, hash, sort-merge),
- whether to run in **parallel**,
- the **order of operations**.

## 2. Scan operations (access paths)
| Scan | How | Good when |
|---|---|---|
| **Table (full / file) scan** | read every block sequentially | most rows are needed, small table, or no useful index |
| **Index scan** | use an index to find matching rows (e.g. `WHERE age = 30`, `age BETWEEN 20 AND 30`) | few rows match (selective predicate) |
| Clustered index scan | data sorted like the index → matching rows contiguous | ranges |
| Non-clustered index scan | each match needs an extra lookup (random I/O) | very selective lookups |

## 3. Join algorithms
> [!tip] Analogy: matching guests to name tags
> **Nested loop:** for each guest, look through the entire pile of tags. **Index nested loop:** tags are in a labelled filing box, so each guest goes straight to the right tab. **Hash join:** sort the tags into 26 boxes by first letter, then each guest checks only their letter's box. **Sort-merge:** line up guests alphabetically and tags alphabetically and walk down both lines together.

### Nested loop join
```text
for each tuple r in R (outer):
    for each tuple s in S (inner):
        if r and s satisfy the join condition: output (r, s)
```
Simple; works for **any** join condition (incl. theta joins). Cost ≈ read R once + read S once **per R tuple/block** → efficient for **small tables**, very costly for large ones. **Block nested loop** reads S once per block (or per memory-full) of R.

**Index nested loop:** if S has an index on the join attribute, look up matches for each R tuple through the index instead of scanning S. Excellent when the **outer input is small** and the index is selective; poor when the outer input is large (one index probe + random row fetch **per outer tuple**).

### Hash join (equality joins only)
1. **Build:** read the smaller input and put each tuple in an in-memory **hash table** on the join key.
2. **Probe:** read the other input; hash each tuple's key and look for matches in the hash table.
Each input is read about **once** (≈ 3(M+N) I/Os with partitioning when it doesn't fit in memory). Suited for **large tables** with **no useful index**.

### Sort-merge join
1. Sort both inputs on the join attribute (unless already sorted, e.g. by a clustered index).
2. Merge: walk both sorted lists together, outputting matches.
Good when inputs are **already sorted** or the output must be sorted anyway; works for equality (and some inequality) joins.

| | Nested loop | Index nested loop | Hash join | Sort-merge |
|---|---|---|---|---|
| Join types | any (θ) | equality/range via index | **equality only** | equality (mostly) |
| Needs | nothing | index on inner join column | memory for hash table | sorted inputs (or a sort) |
| Best for | small inputs | small outer + selective index | large unsorted inputs | pre-sorted inputs / sorted output |
| I/O pattern | repeated scans | random probes | sequential | sequential |

## 4. Aggregation and sorting
`GROUP BY` and `ORDER BY` need **sorting** (or hashing), which is costly without a pre-sorted index. Aggregates (SUM, AVG, COUNT …) must **scan all input** rows of each group.

## 5. Execution phases (lecture)
1. **Fetch** data from tables or indexes.
2. **Apply filters** (WHERE) to reduce data.
3. **Join** using the chosen algorithm.
4. **Project** the required columns.
5. **Aggregate and sort** (GROUP BY, ORDER BY), usually last.

## 6. Applying it: 2020/21 Q2(b), why Plan B can beat Plan A
```text
Plan A                                           Plan B
π_{A.d,B.d}   (on the fly)                       π_{A.d,B.d}   (on the fly)
   │                                                  │
σ_{B.c<2000}  (on the fly)                         ⋈_{A.b=B.b}   (Hash join)
   │                                               ╱          ╲
⋈_{A.b=B.b}   (Index nested loop)            σ_{a>10}        σ_{B.c<2000}
 ╱        ╲                                     │                 │
σ_{a>10}    B (B+ tree index on B.b)            A (file scan)     B (file scan)
(B+ tree index on A.a)
 │
 A
```
1. **Index range scan on A.a may be worse than a file scan.** `a > 10` is a range predicate that may match a **large fraction** of A. If the B+-tree on A.a is **unclustered**, every matching tuple costs a **random I/O**; a sequential file scan reads each block once. (Tutorial 4: above ~10% selectivity, a full scan wins.)
2. **Index nested loop does one index probe per outer tuple.** For every qualifying A tuple, Plan A traverses the B+-tree on B.b and fetches matching B tuples (random I/O). With many outer tuples this is thousands of random reads. A **hash join** reads each (filtered) input **once** sequentially and matches in memory.
3. **Selection placement.** Plan B applies $\sigma_{B.c<2000}$ **before** the join (predicate push-down), so fewer B tuples are hashed and probed. Plan A applies it **after** the join "on the fly", so the join processes **all** of B's matching tuples, including many later discarded.
