# 02.05 · Clustered vs Non-Clustered Indexes, and Choosing Indexes

> [!info] [[02.00 Indexing Structures|Lesson 2]] · Lecture L2 §2.1.2, §2.1.6–§2.1.7, §3.4; L1 §7.3; L4 §1.1 · [[TUT 4 - Selectivity and Index Cost|Tutorial 4]] Ex 1, 3, 5 · Priority 🔴 High (all 4 papers)
> **Asked as:**
> - "Briefly explain what clustered and unclustered indexes are." (2020/21 Q6(b))
> - "Explain clustered indexing and non-clustered indexing, highlighting the key differences … examples where one might be preferred" (2022/23 Q2(b))
> - "Which indexing approach best supports frequent range and exact-match queries, with reference to clustered and non-clustered indexes" (2023/24 Q2(b))
> - "What would you consider in choosing … ii) hash versus tree indexes" (2020/21 Q5(b)(ii))
> - Workload question: R(a,b,c,d,e), 100,000 × `b < ?` and 10,000 × `c = ?` (2020/21 Q6(c))

## 1. Definitions
- **Clustered index:** the **data rows are stored physically in the same order as the index key**. The index and the table order agree. Only **one** per table.
- **Non-clustered (unclustered) index:** a **separate structure** of keys and **pointers** to rows; the rows themselves are **not** in index order. **Many** per table.

> [!tip] Analogy
> **Clustered:** a phone book. The entries *are* in surname order, so all "Silva"s are on one or two pages.
> **Non-clustered:** the index at the back of a cookbook listing recipes by ingredient. "Garlic → pages 12, 87, 140, 203." The recipes are scattered; you flip to each page separately.

## 2. Why the difference matters: range queries
For a range query such as `WHERE salary BETWEEN 40000 AND 60000`:
- **Clustered:** find the first match through the index, then read **consecutive blocks**. Cost ≈ index height + (matching rows ÷ rows per block).
- **Non-clustered:** each matching row may sit in a **different block** → potentially **one random I/O per row**.

> [!example] Tutorial 4 Example 3
> 5,000,000 log rows, ~100,000 per day, query for 3 days → **300,000** rows → selectivity $300{,}000/5{,}000{,}000 = 6\%$.
> **Clustered** index on `created_at`: rows are contiguous → a range scan is chosen.
> **Non-clustered:** 300,000 random reads is too expensive → the optimizer will probably do a **full table scan** instead.

> [!example] Tutorial 4 Exercise 3
> `order_id BETWEEN 100000 AND 150000` → 50,000 consecutive rows, 200 rows/page.
> Clustered: $50{,}000/200 = 250$ pages (+ a few index pages). Non-clustered: up to **50,000** random page reads.

## 3. Comparison table
| Aspect | Clustered | Non-clustered |
|---|---|---|
| Physical row order | same as index | independent of index |
| Number per table | **one** | many |
| Leaf level | contains / is the data rows (or points into ordered data) | contains pointers (row IDs) |
| Range queries | **excellent** (sequential I/O) | poor for large ranges (random I/O per row) |
| Exact match (one row) | fast | fast (one extra pointer hop) |
| ORDER BY on the key | no sort needed | may need sort or random reads |
| Insert/update cost | higher: rows may have to move to keep order, page splits | lower for the table, but each index must be updated |
| Storage | no separate copy of rows | separate structure |
| Typical columns | primary key, date/time, frequently range-searched column | foreign keys, lookup columns (email, name), filters with few matches |

## 4. Which index best supports frequent range **and** exact-match queries? (2023/24 Q2(b))
- A **B+-tree** supports both: equality = one root-to-leaf path; range = find the start, then follow **linked leaves** ([[02.08 B+ Trees]]).
- Make it **clustered** on the column that has the **heaviest range workload** (only one allowed), because ranges gain the most from physical order.
- Use **non-clustered** B+-tree (or hash) indexes for other columns that are mostly **exact-match** and **highly selective** (few rows per value); one extra pointer per row is cheap when few rows match.
- A **hash** index is best for pure equality but **cannot** serve ranges ([[01.08 Hash Files and Collision Handling]]).

## 5. Hash vs tree indexes (2020/21 Q5(b)(ii))
| Consider | Hash index | Tree (B+-tree) index |
|---|---|---|
| Equality `=` | **best**: ~1–2 I/Os | good: height + 1 (≈ 3–4 I/Os) |
| Range `<`, `>`, `BETWEEN` | **not supported** | **supported** efficiently |
| ORDER BY / MIN / MAX / prefix `LIKE 'ab%'` | no | yes |
| Data growth | static hashing degrades; needs rehash or dynamic hashing | balanced automatically |
| Skewed data | long chains for hot values | unaffected |
| Joins | hash join / equi-join probes | merge join, index nested loop |

**Decision rule:** use a hash index only if the column is queried **almost exclusively by equality**; otherwise a B+-tree.

## 6. Choosing indexes for a workload: 2020/21 Q6(c)
`R(a, b, c, d, e)`, ≥ 1000 distinct values per attribute. Two workloads considered **independently**:
- **A:** 100,000 queries `SELECT * FROM R WHERE b < ?` (range)
- **B:** 10,000 queries `SELECT * FROM R WHERE c = ?` (equality)

| | Workload A | Workload B |
|---|---|---|
| Search key | **b** | **c** |
| Clustered? | **Clustered**: range queries return many rows; physical order turns them into sequential I/O | **Unclustered** is enough: with ≥1000 distinct values, each lookup returns ~0.1% of rows; (clustered would also work if A did not need it) |
| Hash or B+-tree? | **B+-tree**: hash cannot answer `<` | **Hash** (or B+-tree): pure equality |
| Justification | without an index every query scans the whole relation | a hash lookup goes straight to the matching bucket |

If both workloads ran together on one table, give the single clustered index to **b** (the larger, range workload) and an **unclustered hash index on c**.

## 7. Selectivity rule of thumb ([[TUT 4 - Selectivity and Index Cost|Tutorial 4]])
$$
\text{selectivity} = \frac{\text{rows matching the predicate}}{\text{total rows}}
$$
Low selectivity values (few rows) → index pays off. If selectivity is above a threshold (e.g. 10% for non-clustered B-tree), the optimizer prefers a full scan. **Low-cardinality** columns (e.g. status with 5 values) are better served by **bitmap indexes**. See [[04.07 Indexing in Query Optimization]].
