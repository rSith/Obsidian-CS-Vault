# 02.03 · Clustering Indexes

> [!info] [[02.00 Indexing Structures|Lesson 2]] · Lecture L2 §2.1.2, §2.1.6 · Priority 🔴 High
> **Asked as:** "What is a primary index, a clustering index and a secondary index? Discuss when each of these indexes are used" (2021/22 Q1(a)) · "Why can databases have at most one primary or clustering index on a file, but several secondary indexes?" (2021/22 Q1(b))

## 1. What is it?
If a data file is **physically ordered on a non-key field** (a field where many records can share the same value, e.g. `DeptNumber`), the file is a **clustered file**, the field is the **clustering field**, and the index on it is a **clustering index**.

The lecture also uses the broader everyday meaning: a **clustered index** is one where **the data rows are physically stored on disk in the same order as the index**.

Entries: $\langle$ clustering field value, block pointer $\rangle$, with **one entry for each distinct value**, pointing to the **first block** containing that value. Therefore it is **non-dense (sparse)**.

> [!tip] Analogy
> A school's student files are kept in cabinet drawers **grouped by class** (all Grade 10A together, then 10B …). A small label list says "10A starts in drawer 3, 10B starts in drawer 5". Many students share a class (non-key), and the label list has one line per class, not per student.

## 2. How it works
1. Sort the data file by the clustering field (e.g. Dept_no).
2. For each **distinct** value, create one index entry pointing to the first block that contains it.
3. To find all employees of department 5: find entry 5 in the index → read its block → read forward while Dept_no = 5.

### Insertion problem and the block-cluster solution (lecture Figures 2–3)
Because records are physically ordered, inserting or deleting causes reorganization. Common fix: **reserve a whole block (or cluster of contiguous blocks) for each value** of the clustering field; all records with that value go there (with linked overflow blocks if needed). Inserts and deletes then become simple.

## 3. Key characteristics (lecture §2.1.6)
1. **Physical order of data** = index order.
2. By default, many DBMSs make the **primary key the clustered index** (or a unique key if none).
3. **One per table**: rows can be physically sorted in only one way.
4. **Efficient range queries**: e.g. salary between 40,000 and 60,000 with a clustered index on salary; matching rows are adjacent.
5. **Faster retrieval** of many consecutive rows.
6. **Overhead** on insert/update/delete: inserting in the middle may require moving rows → extra I/O.

## 4. Why only one primary/clustering index but many secondary indexes? (2021/22 Q1(b))
- A primary or clustering index **depends on the physical order of the records** in the data file (it uses block anchors or the first block of each value).
- A file's records can be **physically sorted on only one field (or field combination) at a time**, just as a bookshelf can be sorted by author **or** by title, not both.
- So there can be **at most one** primary **or** clustering index (not one of each).
- **Secondary indexes** do **not** rely on physical order: each is a separate **dense** structure of pointers to wherever the records happen to be. You can build as many as you like (subject to storage and update overhead).

## 5. When each index type is used (2021/22 Q1(a))
| Index | Use when |
|---|---|
| **Primary** | the file is sorted on a **unique key** that is often searched or range-scanned (e.g. Emp_ID, Order_ID) |
| **Clustering** | the file is sorted on a **non-unique** field that is often used to fetch **groups** of records or ranges (e.g. Dept_no, Order_Date) |
| **Secondary** | fast access on **other** fields the file is not sorted on (e.g. Email, Name); several allowed |
