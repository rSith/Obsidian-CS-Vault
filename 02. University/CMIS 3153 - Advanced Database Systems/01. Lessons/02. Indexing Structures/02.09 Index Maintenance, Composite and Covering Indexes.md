## 1. Index maintenance: the hidden price of fast reads
An index is a **second copy of (part of) the data**, kept in sorted/tree order. Whenever the table changes, **every index on it must change too**.

> [!tip] Analogy
> A textbook with **five** indexes at the back (by topic, by author, by formula, …). Adding one new page means updating all five indexes. The more indexes, the faster you can *find* things, but the slower it is to *edit* the book.

### Effect of each operation
| Operation | What happens to each index | Extra cost |
|---|---|---|
| **INSERT** | a new entry is added to **every** index in its sorted position; B+-tree leaf may **split**, possibly propagating upward; a **clustered** index may require moving rows / page splits to keep physical order | 1 index traversal + write per index; occasional splits |
| **DELETE** | the entry is removed from every index; nodes may **underflow → redistribute or merge**; sorted files leave gaps (deletion markers) | traversal + write per index; occasional merges |
| **UPDATE of an indexed column** | treated as **delete old entry + insert new entry** in that index; updating a **clustered** key may **move the row** physically (and then secondary indexes that point to its physical location need updating) | the most expensive case |
| **UPDATE of a non-indexed column** | indexes untouched (if the row stays in place) | none |
| **Bulk load** | building indexes row by row is slow; better to load first, then create/rebuild the index | |

### Other costs
- **Storage space** for each index.
- **Locking/concurrency:** writers must lock index pages too; hot spots (e.g. ever-increasing keys) can cause contention.
- **Fragmentation** over time (half-empty pages after many splits/deletes) → periodic rebuild/reorganize.
- **Index creation** itself scans and sorts the whole table.

### Benefits that must be weighed against the costs
- SELECTs with WHERE / JOIN / ORDER BY on the indexed column read far fewer blocks.
- UPDATE and DELETE statements **with a WHERE clause** also benefit, because finding the rows to change is faster.

### Applying it to the exam scenarios
**Students(Student_ID, Name, Age, GPA)**, frequent `GPA > threshold` queries (2022/23):
- An index on GPA makes the range query fast ([[02.07 B-Trees]]).
- Every new student → insert into the GPA index (and the Student_ID index).
- Every GPA change at the end of a semester → delete + reinsert in the GPA index; if GPA were the **clustered** key, the row would physically move. So: make **Student_ID** the clustered/primary index and GPA a **non-clustered** B+-tree, or rebuild the GPA index after bulk GPA updates.
- Deleting graduates → removes entries from all indexes; possible merges.

**Orders(Order_ID, Customer_ID, Order_Date, Total_Amount, Order_Status)**, frequent `Total_Amount > x`, continuous inserts/updates/cancellations (2023/24):
- Continuous **inserts** → every index grows; with **Order_ID / Order_Date** (ever-increasing) as the clustered key, new rows append at the end (no mid-file splits).
- A non-clustered B+-tree on **Total_Amount** serves the range query; inserts go to random leaf positions → occasional splits.
- **Status updates / cancellations** do not touch the Total_Amount index unless Total_Amount changes; an index on Order_Status would be updated on every status change (and is low-cardinality → poor B-tree candidate; a bitmap index suits warehouses, not busy OLTP).
- **Advice:** index only columns that are frequently searched; avoid redundant indexes ([[02.00 Indexing Structures|Lab Exercise 6: drop unused indexes]]); monitor with `EXPLAIN`.

## 2. Indexes on multiple keys (composite indexes) (lecture §4)
A **composite (multi-column, multi-key) index** is a single index on a **concatenation of columns**, e.g. `(customer_id, order_date)`. **Column order matters**: the index is sorted by the first column, then by the second within equal first values, like a phone book sorted by surname then first name.

```sql
CREATE INDEX idx_customer_date ON orders(customer_id, order_date);

SELECT *
FROM   orders
WHERE  customer_id = 123
  AND  order_date > '2023-01-01';
```
*Explanation:* the index jumps straight to `customer_id = 123` and, because the entries for that customer are sorted by date, scans only the dates after 2023-01-01. A query on `order_date` **alone** cannot use this index efficiently (the leading column is missing).

**Benefits (lecture):** faster filtering/sorting on several columns; **covering index** possibility; faster joins on multiple columns.

> [!example] Tutorial 4 Example 4: composite index selectivity
> 10 M rows; index (country, city, age); 50 countries, ~200 cities per country, ~80 ages.
> country = 'UK' → $10{,}000{,}000/50 = 200{,}000$ rows; city = 'London' → $200{,}000/200 = 1{,}000$; age = 30 → $1{,}000/80 \approx 13$ rows. All index columns specified with equality → an **index seek**.

## 3. Covering index
If an index contains **all the columns a query needs** (in WHERE and SELECT), the DBMS answers the query **from the index alone**, without touching the table.

> [!example] Tutorial 4 Example 7
> Index (last_name, first_name); 500 rows with last_name = 'Brown'.
> `SELECT last_name, first_name …` (covering): ~3 I/Os to seek + 2–3 leaf pages ≈ **5–6 I/Os**.
> `SELECT * …` (non-covering): the same + **500 random row fetches** ≈ **503 I/Os**.

## 4. Lab SQL from the lecture
```sql
-- Exercise 1: simple index
CREATE INDEX idx_last_name ON employees(last_name);
EXPLAIN SELECT * FROM employees WHERE last_name = 'Smith';

-- Exercise 3: composite index with a range on the second column
CREATE INDEX idx_category_price ON products(category, price);
SELECT * FROM products WHERE category = 'Electronics' AND price BETWEEN 100 AND 500;

-- Exercise 5: index on a join (foreign key) column
CREATE INDEX idx_customer_id ON orders(customer_id);
SELECT o.*
FROM   customers c JOIN orders o ON o.customer_id = c.customer_id
WHERE  c.last_name = 'Smith';

-- Exercise 6: drop an unused index
DROP INDEX idx_last_name;
```
*Explanation:* `EXPLAIN` shows the plan the optimizer chose, so you can confirm an index scan rather than a full table scan.

## 5. Exam-relevant points
- Always answer "impact on insert/update/delete" **operation by operation**, mention **splits/merges**, **clustered key movement**, **multiple indexes multiply the cost**, **storage**, and end with **guidelines** (index selectively, choose a stable clustered key, batch/rebuild).
- Composite index: **leftmost-prefix** rule; column order chosen by how queries filter.
