# 02.06 · Multilevel Indexes (and Static vs Dynamic Indexes)

> [!info] [[02.00 Indexing Structures|Lesson 2]] · Lecture L2 §2.2, Example 3, §3 intro · Priority 🟡 Medium
> **Asked as:** "How does the multilevel indexing structure improve the efficiency of searching an index file?" (2021/22 Q1(d)) · "Discuss the circumstances under which a static tree index might be preferred over a dynamic tree index." (2023/24 Q3(b))

## 1. What is it?
A **multilevel index** is an **index on an index**. The first-level index is itself an ordered file, so we build a **primary (sparse) index on it** (second level), then an index on that (third level), and so on, until the **top level fits in one block**.

> [!tip] Analogy: finding a house
> Country → province → city → street → house. Each level narrows the search by a big factor, so you only look at **one sign per level**. A binary search would instead keep halving a single huge list.

## 2. Why it is faster
- Binary search on a single-level index of $b_i$ blocks reads $\lceil\log_2 b_i\rceil$ blocks, halving the search space each time.
- A multilevel index divides the search space by the **fan-out** $fo$ at each level (often 50–300), reading **one block per level**.

**Fan-out** $fo$ = index blocking factor $bfr_i$ = number of entries per index block. All levels have the same $fo$ because all entries are `(key, block pointer)` of the same size.

## 3. How many levels?
$$
r_2 = \left\lceil \frac{r_1}{fo} \right\rceil,\quad r_3 = \left\lceil \frac{r_2}{fo}\right\rceil,\ \dots \quad\text{until one block}
\qquad
t = \lceil \log_{fo} r_1 \rceil
$$
A search reads **one block per level + one data block**: $t + 1$ block accesses.

## 4. Worked example (lecture Example 3)
Dense secondary index from Example 2: $r_1 = 30{,}000$ entries, $fo = 68$, $b_1 = 442$ blocks.
1. Level 2: $b_2 = \lceil 442/68 \rceil = 7$ blocks. (The lecture prints "⌈422/68⌉", a typo for 442; the result 7 is the same.)
2. Level 3: $b_3 = \lceil 7/68 \rceil = 1$ block → top level, $t = 3$.
3. Search cost: $t + 1 = 4$ block accesses, compared with **10** using binary search on the single-level index.

```text
Level 3 (1 block)      [ top ]
Level 2 (7 blocks)     [ ][ ][ ][ ][ ][ ][ ]
Level 1 (442 blocks)   [ ][ ][ ] … [ ]          ← dense secondary index
Data file (3000 blocks)
```

## 5. Static multilevel index (ISAM) and its problem
The lecture's Figure 4 shows a **two-level primary index resembling ISAM** (Indexed Sequential Access Method). All levels are **physically ordered files**, so **insertions and deletions are a problem**: entries must shift, blocks overflow. ISAM-style structures handle this with **overflow pages**, which slowly degrade performance until the file is rebuilt.

**Solution:** a **dynamic multilevel index** that leaves **free space in each block** and uses **insertion/deletion algorithms that split and merge blocks** as the file grows and shrinks: the **B-tree** and **B+-tree** ([[02.07 B-Trees]], [[02.08 B+ Trees]]).

## 6. Static vs dynamic tree index (2023/24 Q3(b))
| | Static (ISAM-style) | Dynamic (B+-tree) |
|---|---|---|
| Structure after creation | fixed; non-leaf levels never change | changes with every insert/delete (splits, merges) |
| Growth | overflow chains under leaf pages | node splits; height grows at the root |
| Balance | can become unbalanced (long overflow chains) | always balanced |
| Concurrency | **simple**: index pages are never modified, so no locking of non-leaf pages | needs locking of nodes during splits/merges |
| Space use | pages can be 100% full | nodes typically 50–100% full (~67% avg) |
| Maintenance cost | none per update; occasional full rebuild | small cost on every update |

**When is static preferred?**
1. Data is **read-mostly or static** (archives, historical data, data warehouses, reference tables, lookup tables loaded in bulk).
2. Updates are **rare** or arrive in **periodic batches** (rebuild the index after each batch).
3. **High concurrency of readers**: no locking of index pages is needed.
4. The data distribution is **known and stable**, so the index can be packed full (100% utilization, fewer pages, sometimes one level fewer).
5. **Simplicity / predictable performance** for sequential scans.
