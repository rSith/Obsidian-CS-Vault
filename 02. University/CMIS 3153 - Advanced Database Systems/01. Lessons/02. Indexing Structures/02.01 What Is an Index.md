# 02.01 · What Is an Index? (Purpose, Single-Level, Ordered, Dense vs Sparse)

> [!info] [[02.00 Indexing Structures|Lesson 2]] · Lecture L2 §1, §2.1.1–§2.1.4 · Priority 🔴 High
> **Asked as:** "What is the main purpose of using indexes in a database?" (2020/21 Q6(a)) · "What is indexing in database systems? Discuss the purpose and advantages of indexing for improving query performance." (2022/23 Q2(a))

## 1. What is it?
An **index** is an **additional file on disk** that provides a **secondary access path** (an alternative way to reach records) **without changing where the records are physically stored** in the data file. Each index entry is a pair:

$$
\langle \text{key value},\ \text{pointer} \rangle
$$

The pointer is a **block address** (or record address) in the data file. The field the index is built on is the **indexing field**.

> [!tip] Analogy
> A data file is a novel; the index is the alphabetical index at the back. The novel's pages are not rearranged; the index simply tells you where to look.

## 2. Why is it used? (purpose and advantages)
| Purpose / advantage | Explanation |
|---|---|
| **Speed up retrieval** | find records by searching a **small sorted** index (binary search or a tree) instead of scanning the whole data file ($b/2$ blocks) |
| **Fewer disk block accesses** | e.g. 3,000-block file: binary search on data 12 accesses → primary index 7 → multilevel index 4 ([[02.06 Multilevel Indexes]]) |
| **Search on other fields** | the data file can only be sorted one way; secondary indexes allow fast search on other columns |
| **Efficient range queries** | ordered (tree) indexes find the first match then scan forward |
| **Faster joins, ORDER BY, GROUP BY** | the optimizer can use index order or index lookups ([[04.07 Indexing in Query Optimization]]) |
| **Enforce uniqueness** | a primary/unique index rejects duplicate keys |
| **Covering queries** | if the index holds all needed columns, the table need not be read ([[02.09 Index Maintenance, Composite and Covering Indexes]]) |

**Costs (always mention):** extra disk space, and every INSERT/UPDATE/DELETE must also update the index.

## 3. How a single-level index works (lecture §2.1.1)
Parts: an **index table** (index keys + pointers) and the **data table**.
1. **Creation:** build the index on a chosen field and sort it by key.
2. **Query:** look up the key in the index → get the pointer → read the record directly.
3. **Insert/delete:** add or remove the corresponding `(key, pointer)` entry.

**Why single-level:** simple; fine for small datasets; small enough to sit in memory.
**Limitation:** does not scale; large single-level indexes become slow to search and maintain → [[02.06 Multilevel Indexes]].

## 4. Ordered indexes (lecture §2.1.2–§2.1.3)
An **ordered index** keeps entries **sorted** by key, which allows **binary search** ($O(\log n)$) and efficient **range queries**. Inserts and deletes must keep the order, which costs extra (shifting entries).

A **single-level ordered index** = a sorted index stored at one level: simple + binary-searchable; good for small/medium datasets; still limited for huge ones.

**Types of ordered index (lecture):**
| Type | Built on | Data file ordered by it? |
|---|---|---|
| **Primary** | the **ordering key** (unique) of an ordered file | yes |
| **Clustering (clustered)** | an **ordering non-key** field (duplicates allowed); rows physically stored in index order | yes |
| **Secondary** | a **non-ordering** field (key or non-key) | no |
| **Unclustered (non-clustered)** | separate structure of pointers; rows not in index order | no |

## 5. Dense vs sparse indexes (lecture §2.1.4)
| | **Dense index** | **Sparse (non-dense) index** |
|---|---|---|
| Entries | **one per record** (N rows → N entries) | **only some records**: typically **one per block** (or every Nth record) |
| Requirement | works on any file | data file must be **sorted** on the index field |
| Size | larger | much smaller |
| Lookup | entry points directly to the record; can answer "does key exist?" from the index alone | find the largest entry ≤ key, then search inside that block |
| Examples | **secondary index** on a key | **primary index**, **clustering index** |

> [!example] Dense vs sparse picture
> ```text
> Data file (sorted by ID), 3 records/block:
>   Block 1: 10 20 30 | Block 2: 40 50 60 | Block 3: 70 80 90
> Dense index:  10→B1 20→B1 30→B1 40→B2 50→B2 60→B2 70→B3 80→B3 90→B3   (9 entries)
> Sparse index: 10→B1 40→B2 70→B3                                     (3 entries, one per block)
> To find 50 with the sparse index: largest entry ≤ 50 is 40 → read block 2 → find 50.
> ```

## 6. Exam-relevant points
- Definition: **separate file**, **secondary access path**, **(key, pointer)**, **does not move the data**.
- Purpose: fewer block accesses; search on non-ordering fields; ranges; joins/sorting; uniqueness.
- Always add the **trade-off**: storage + maintenance overhead on updates.
- Dense vs sparse: one entry per record vs one per block; sparse needs a sorted data file.
