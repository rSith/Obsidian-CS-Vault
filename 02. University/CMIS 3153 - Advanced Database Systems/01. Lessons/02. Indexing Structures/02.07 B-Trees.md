# 02.07 · B-Trees

> [!info] [[02.00 Indexing Structures|Lesson 2]] · Lecture L2 §3, §3.1–§3.3.2 · [[TUT 2 - Records, File Organization and B-Trees|Tutorial 2 Q13]] · Priority 🔴 High
> **Asked as:**
> - "Explain how B-tree indexing could be used to speed up these GPA-based queries. Describe the structure of a B-tree index and its operations." (2022/23 Q2(c)(ii), Students table)
> - "Explain the structure and key operations of a B-tree index and discuss how a B-tree index on the Total_Amount field improves the efficiency of range queries." (2023/24 Q2(c)(ii), Orders table)

## 1. Background: trees and search trees
- A **tree** is made of **nodes**. The top node is the **root** (no parent); nodes with no children are **leaves**; others are **internal** nodes. The **level** of the root is 0; each child is one level deeper.
- A tree is **balanced** if **all leaves are at the same level**. An unbalanced tree can have long paths that make some searches slow.
- A **search tree of order $p$**: each node has at most $p$ pointers and $p-1$ keys, arranged $P_1, K_1, P_2, K_2, \dots, K_{q-1}, P_q$ with $q \le p$, such that
  1. $K_1 < K_2 < \dots < K_{q-1}$ inside the node;
  2. every value $X$ in the subtree under $P_i$ satisfies $K_{i-1} < X < K_i$ (with the obvious ends).

Ordinary search trees **do not guarantee balance**. **B-trees add rules that keep the tree balanced.**

> [!tip] Analogy: a well-organised filing cabinet
> Each drawer label says "A–F", "G–M", "N–S", "T–Z". Inside each drawer, folders have more labels. Every path from the cabinet to an individual file has the **same number of steps**, and each drawer is kept between half-full and full, so no drawer is empty and none bursts.

## 2. What is a B-tree?
A **B-tree** is a **self-balancing search tree** designed for disks: each node is one **disk block** holding **many keys and pointers**, so the tree is short and wide and a search reads only a few blocks.

### Structure (lecture §3.3)
- **Balanced:** all leaves are at the **same depth**.
- Each node holds **multiple keys** (sorted) and **child pointers**; the keys divide the key range into intervals.
- In a B-tree, **every key value appears exactly once** in the tree, **together with a data pointer** (to the record or its block), in internal **and** leaf nodes.
- Leaf nodes look like internal nodes but their tree pointers are NULL.
- Nodes are kept **between half-full and full**, which makes inserts and deletes easy.

### Order $p$ ([[TUT 2 - Records, File Organization and B-Trees|Tutorial 2 Q13]])
- Each node has **at most $p$ tree pointers** and **$p-1$ keys**.
- Each internal node (except the root) has **at least $\lceil p/2 \rceil$ children** (so at least $\lceil p/2\rceil - 1$ keys).
- The root has at least 2 children (unless it is the only node).

Node layout (Elmasri notation):
$$
\langle P_1, \langle K_1, Pr_1\rangle, P_2, \langle K_2, Pr_2\rangle, \dots, \langle K_{q-1}, Pr_{q-1}\rangle, P_q \rangle
$$
$P_i$ = tree pointer (to a child), $Pr_i$ = data pointer (to the record), $K_i$ = key.

## 3. Operations
### 3.1 Search
Start at the root; compare the search key with the node's keys; if equal, follow its data pointer; otherwise follow the child pointer for the interval containing the key; repeat. **Cost = height** (one block per level): $O(\log_m N)$.

### 3.2 Insertion (lecture §3.3.1)
1. Search down to the correct **leaf**.
2. If the leaf has room, insert the key in sorted position. Done.
3. If the leaf is **full**: **split** it into two halves and **push the middle key up** into the parent.
4. If the parent is full too, split it and push its middle key up. Continue upward.
5. If the **root** splits, a **new root** is created → the tree **grows in height by one** (that is how all leaves stay at the same depth).

> [!example] Insert 1–7 into a B-tree where each node holds at most 2 keys (order 3)
> ```text
> insert 1,2:   [1 2]
> insert 3:     [1 2 3] overflow → split, push 2 up        [2]
>                                                         /   \
>                                                      [1]     [3]
> insert 4:          [2]            insert 5:  [3 4 5] overflow → push 4 up
>                   /   \                          [2 4]
>                [1]   [3 4]                      /  |  \
>                                              [1]  [3]  [5]
> insert 6, 7: [5 6 7] overflow → push 6 up → root [2 4 6] overflows → push 4 up (new root)
>                     [4]
>                   /     \
>                [2]       [6]
>               /   \     /   \
>             [1]   [3] [5]   [7]
> ```

### 3.3 Deletion (lecture §3.3.2)
1. **Find** the key.
2. **Key in a leaf:** remove it. If the leaf still has the minimum number of keys, done.
3. **Key in an internal node:** replace it with its **predecessor** (largest key in the left subtree) or **successor** (smallest in the right subtree), then delete that key from its leaf.
4. **Underflow** (too few keys):
   - **Borrow (redistribute):** if a neighbouring sibling has more than the minimum, move the separating key **down from the parent** into the underfull node and move a key **from the sibling up** into the parent.
   - **Merge:** if both siblings have only the minimum, merge the node with a sibling **plus the separating parent key**. The parent loses a key and may underflow → repeat upwards.
5. If the **root** becomes empty, remove it → the tree **shrinks by one level**.

### 3.4 Efficiency
Search, insert and delete are all $O(\log_m N)$ (lecture), where $m$ is the order: the work is proportional to the height.

## 4. B-tree for a range query (2022/23 Q2(c)(ii), 2023/24 Q2(c)(ii))
Query: `SELECT * FROM Students WHERE GPA > 3.5` (or `Orders WHERE Total_Amount > 10000`).
1. **Build** a B-tree index on GPA: `CREATE INDEX idx_gpa ON Students(GPA);`
2. **Search** for the first key > 3.5: root → internal → leaf, about 3–4 block reads even for millions of rows.
3. **Scan forward** in key order to collect all keys > 3.5, following data pointers to the rows.
   - In a plain **B-tree**, keys are spread over all levels, so the scan uses an **in-order traversal** (moving up and down the tree).
   - In a **B+-tree** (what DBMSs actually use) all keys are in the **leaves**, which are **linked**, so the scan just walks the leaf chain ([[02.08 B+ Trees]]).
4. Rows are fetched via pointers: cheap if the index is **clustered** or few rows match; expensive if the index is non-clustered and the range is large.

**Why it helps:** without an index the DBMS reads **every block** of the table; with the index it reads $\approx$ height + matching leaf blocks + matching rows. The tree stays **balanced** while students/orders are inserted, updated and deleted, so performance stays predictable.

## 5. Distinctions: B-tree vs B+-tree (preview)
| | B-tree | B+-tree |
|---|---|---|
| Where keys/data pointers live | every node (each key once) | **data pointers only in leaves**; internal nodes hold copies of keys as signposts |
| Leaf links | no | **yes** (linked list) |
| Range scan | in-order traversal | walk the leaf chain |
| Fan-out | lower (internal nodes also carry data pointers) | higher → shorter tree |
