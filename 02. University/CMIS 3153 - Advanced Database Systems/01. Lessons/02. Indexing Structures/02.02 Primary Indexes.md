# 02.02 · Primary Indexes

> [!info] [[02.00 Indexing Structures|Lesson 2]] · Lecture L2 §2.1.2, §2.1.5, Example 1 · Priority 🔴 High
> **Asked as:** "Discuss the difference between a primary index and a secondary index, using a simple example" (2020/21 Q5(a)) · "What is a primary index, a clustering index and a secondary index? Discuss when each is used" (2021/22 Q1(a)) · "Discuss what you would consider in choosing the primary index" (2020/21 Q5(b)(i))

## 1. What is it?
A **primary index** is an ordered index built on the **ordering key field** of an **ordered (sorted) data file**: the field that is both **unique** and the field the file is **physically sorted by**.

It is a small ordered file of fixed-length entries with two fields:
$$
\langle K(i),\ P(i) \rangle
$$
- $K(i)$: the **primary key** value of the **first record in block $i$** of the data file,
- $P(i)$: a **pointer to block $i$** (a block address).

> [!tip] Analogy: dictionary guide words
> Each dictionary page shows its first word at the top ("apple … ", "banana …"). You don't need an entry for every word: knowing the first word of each page tells you which page any word is on. That first word is the **block anchor**.

## 2. Key terms
- **Block anchor (anchor record):** the first record in each block of the data file; its key goes into the index.
- **Non-dense (sparse):** there is **one index entry per data block**, not per record. Number of index entries $r_i = b$ (data blocks).
- A file with a primary index is called an **indexed-sequential file**.

## 3. How a search works
To find key $K$: binary-search the index for entry $i$ with
$$
K(i) \le K < K(i+1)
$$
then read block $P(i)$ and search inside it.
$$
\text{block accesses} = \lceil \log_2 b_i \rceil + 1
$$
(binary search on the $b_i$ index blocks, plus 1 data block).

## 4. Worked example (lecture Example 1)
EMPLOYEE file: $r = 30{,}000$ records, $R = 100$ bytes, $B = 1024$ bytes, ordered on a key field of $V = 9$ bytes; block pointer $P = 6$ bytes.
1. $bfr = \lfloor 1024/100\rfloor = 10$ records/block → $b = \lceil 30{,}000/10\rceil = 3{,}000$ blocks.
2. **Without index:** binary search on data file $\lceil\log_2 3000\rceil = 12$ block accesses.
3. Index entry size $R_i = 9 + 6 = 15$ bytes → $bfr_i = \lfloor 1024/15\rfloor = 68$ entries/block.
4. Index entries $r_i = b = 3{,}000$ (one per data block) → $b_i = \lceil 3000/68\rceil = 45$ index blocks.
5. Binary search on index: $\lceil\log_2 45\rceil = 6$, plus 1 data block = **7 block accesses** (vs 12).

## 5. Advantages and problems
**Advantages:** very small index (sparse) → fast binary search; data in key order → efficient range queries and ordered retrieval.
**Problems:** **insertion and deletion** are hard because the data file is physically ordered: inserting a record may shift records and change block anchors. Remedies (textbook): an unordered **overflow file** merged periodically, or a linked list of overflow records per block, or deletion markers.

## 6. What to consider when choosing the primary index (2020/21 Q5(b)(i))
Only **one** primary (or clustering) index is possible, because the file can be physically sorted **only one way**. Choose its field by asking:
1. **Which field is used most in range queries, ORDER BY, GROUP BY, or sequential processing?** Physical order helps these most.
2. **Is it unique?** A unique ordering key gives a primary index; a non-unique one gives a [[02.03 Clustering Indexes|clustering index]].
3. **How often is the field updated?** Changing the ordering field moves the record; choose a **stable** field (e.g. ID, not salary).
4. **Insert pattern:** an ever-increasing key (order ID, timestamp) appends at the end, avoiding mid-file inserts.
5. **Joins:** a frequently joined key can benefit from physical order (merge joins).
6. **Workload weight:** compare the queries that would benefit vs the update overhead.

## 7. Distinctions
| | Primary index | Secondary index |
|---|---|---|
| Field | ordering **key** of the file | a **non-ordering** field |
| File sorted by it? | yes | no |
| Dense? | **sparse**: one entry per **block** (block anchors) | **dense** (for a key field): one entry per **record** |
| Number per file | **at most one** | **many** |
| Size | small ($r_i = b$) | larger ($r_i = r$) |
| Example (lecture) | 45 index blocks → 7 accesses | 442 index blocks → 10 accesses |
