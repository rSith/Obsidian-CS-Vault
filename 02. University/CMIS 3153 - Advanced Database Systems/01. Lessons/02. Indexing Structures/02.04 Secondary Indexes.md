# 02.04 · Secondary Indexes (and the Index Types Summary)

> [!info] [[02.00 Indexing Structures|Lesson 2]] · Lecture L2 §2.1.7, Example 2, Summary table · Priority 🔴 High
> **Asked as:** primary vs secondary index with an example (2020/21 Q5(a)) · primary, clustering and secondary indexes and when used (2021/22 Q1(a)) · why several secondary indexes are allowed (2021/22 Q1(b))

## 1. What is it?
A **secondary index** is an index on a field that is **not** the field the data file is ordered by (a **non-ordering field**). It may be a key (unique, e.g. Email) or a non-key (e.g. City).

Entries: $\langle$ indexing-field value, **block pointer or record pointer** $\rangle$. For a key field there is **one entry per record**, so a secondary index is **dense**.

> [!tip] Analogy
> A library shelves books by **call number** (the physical order). The catalogue lets you look up by **author** too: each author card points to wherever that book sits. You can have catalogues by author, by subject and by title at the same time. Each is a secondary index.

## 2. Key characteristics (lecture §2.1.7)
1. Built on **non-primary-key** columns.
2. A **separate data structure** (B-tree or hash table) storing pointers to rows.
3. **Speeds up queries** on those columns (e.g. Name, Salary).
4. **Many per table** are allowed.
5. Stores the indexed values + row identifiers (pointers).
6. Usually **non-clustered**: does not change the physical row order.
7. **Overhead** on INSERT, UPDATE, DELETE, since every secondary index must be updated too.

## 3. Worked example (lecture Example 2)
Same file as [[02.02 Primary Indexes|Example 1]]: $r = 30{,}000$, $b = 3{,}000$ blocks, $B = 1024$. Search on a non-ordering **key** field, $V = 9$ bytes, $P = 6$ bytes.
1. **Without index:** linear search, $b/2 = 1{,}500$ block accesses on average.
2. $R_i = 15$ bytes → $bfr_i = 68$.
3. Dense index → $r_i = r = 30{,}000$ entries → $b_i = \lceil 30{,}000/68\rceil = 442$ blocks.
4. Binary search on index: $\lceil\log_2 442\rceil = 9$, + 1 data block = **10 block accesses**.

10 is vastly better than 1,500, but slightly worse than the primary index (7), because the dense index is **10× longer** (442 vs 45 blocks).

## 4. Primary vs secondary index: with a simple example (2020/21 Q5(a))
`STUDENT(Reg_No, Name, Email, Faculty)`, file **sorted by Reg_No**.
- **Primary index on Reg_No:** one entry per **block**, e.g. `⟨232001, block 1⟩, ⟨232011, block 2⟩, …`. To find 232017: largest anchor ≤ 232017 is 232011 → read block 2.
- **Secondary index on Email:** one entry per **student**, sorted by email: `⟨amal@…, block 7⟩, ⟨binu@…, block 2⟩, …`. Records are not in email order, so every record needs its own entry.

| | Primary | Secondary |
|---|---|---|
| Indexing field | ordering key | non-ordering field |
| Data file order | sorted by this field | unrelated |
| Density | sparse (per block) | dense (per record) for keys |
| Count per file | ≤ 1 | many |
| Index size | small | large |
| Range scans | very efficient (contiguous data) | each match may be a different block (random I/O) |
| Update overhead | anchors change on reorganization | every insert/delete/update of the field |

## 5. Lecture summary table of index types
| Type of index | Number of (first-level) index entries | Dense or non-dense | Block anchoring on the data file |
|---|---|---|---|
| **Primary** | number of **blocks** in the data file | non-dense | **yes** |
| **Clustering** | number of **distinct index field values** | non-dense | yes/no (yes if each value starts a new block) |
| **Secondary (key)** | number of **records** in the data file | **dense** | no |
| **Secondary (non-key)** | number of records (option 1) or number of distinct values (options 2, 3) | dense or non-dense | no |
