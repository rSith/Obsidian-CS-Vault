# 02.08 · B+ Trees

> [!info] [[02.00 Indexing Structures|Lesson 2]] · Lecture L2 §3.4, §3.4.1, §3.4.2 · [[TUT 2 - Records, File Organization and B-Trees|Tutorial 2 Q14–Q15]] · Priority 🔴 High (**a full question in 2022/23 and 2023/24**)
> **Asked as:**
> - 2022/23 Q3(a)–(e): nodes read/updated when inserting 90; draw the tree after inserting 42, 79; after deleting 23 (redistribute), 50 (each 20 marks)
> - 2023/24 Q3(a): "Explain the structure and properties of a B+ tree. Discuss how B+ trees maintain balance and why this is important"
> - 2023/24 Q3(c): order $d = 2$; insert 16 three-letter strings; show the tree after every 4 insertions; utilization

## 1. What is it?
A **B+-tree** is a variant of the [[02.07 B-Trees|B-tree]] optimized for **range queries and sequential access**. It is the default index structure in most relational DBMSs.

The two big differences from a B-tree:
1. **All data entries (keys with data pointers) are in the leaf nodes.** Internal nodes contain **only keys used as signposts** ("go left if smaller than 50") plus child pointers.
2. **Leaf nodes are linked together** in a (doubly) linked list in key order.

> [!tip] Analogy: a library with a guide board and one long shelf
> The guide boards in the corridor ("A–F → aisle 1, G–M → aisle 2") don't hold any books; they only point the way (internal nodes). All the books are on the shelves, and the shelves run continuously in order (linked leaves), so once you find the first book in a range you just walk along the shelf.

## 2. Structure
```text
                       [ 50 ]                         ← root (internal): keys only
                 /                \
          [ 40 | 45 ]          [ 60 | 78 ]            ← internal nodes: keys only
          /    |    \          /    |    \
  [23 32]⇄[40 41 43 44]⇄[45 48]⇄[50 59]⇄[60 66]⇄[78 80 85 86]   ← leaves: ALL data entries, linked
```
- **Internal node:** $\langle P_1, K_1, P_2, K_2, \dots, K_{q-1}, P_q\rangle$ (tree pointers and keys only).
- **Leaf node:** $\langle\langle K_1, Pr_1\rangle, \dots, \langle K_{q-1}, Pr_{q-1}\rangle, P_{next}\rangle$: keys with **data pointers** and a pointer to the **next leaf**.
- **Search rule:** in a node with keys $K_1 < \dots < K_{q-1}$, follow $P_1$ if $X < K_1$, $P_i$ if $K_{i-1} \le X < K_i$, $P_q$ if $X \ge K_{q-1}$.

### Order (two notations you will meet)
| Notation | Meaning | Used in |
|---|---|---|
| **order $p$** (Elmasri / lecture / Tutorial 2) | at most $p$ pointers per internal node; leaf order $p_{leaf}$ = max data entries per leaf | lecture, Tutorial 2 Q14 |
| **order $d$** (Ramakrishnan, the exam papers) | every non-root node has **$d$ to $2d$ entries** (keys); max pointers $2d+1$ | 2022/23 Q3, 2023/24 Q3(c): "$d = 2$, max pointers 5, max entries 4" |

With $d = 2$: each node holds **2–4 keys** (root may hold 1–4); an internal node has 3–5 children.

## 3. Properties (2023/24 Q3(a))
1. **Balanced:** every leaf is at the same depth; every search costs exactly the height.
2. **Minimum occupancy:** every node except the root is at least **half full** → height stays $O(\log_{fo} N)$ and space is used well.
3. **Sorted keys** inside nodes and across leaves.
4. **All data in leaves**; internal nodes are a "guide" that may contain keys no longer in the data.
5. **Linked leaves** → efficient range scans and ordered output.
6. **High fan-out** (internal nodes carry no data pointers) → very shallow trees: 3–4 levels for millions of rows.
7. **Dynamic:** grows and shrinks gracefully through splits and merges; no periodic reorganization.

### How balance is maintained (and why it matters)
- **Insertions grow the tree only at the root:** when a node overflows it splits, and the split propagates up; if the root splits, a new root is created, so **every leaf moves down one level together**.
- **Deletions shrink the tree only at the root:** underfull nodes **borrow** (redistribute) or **merge**; if the root loses its last key, it is removed, and every leaf moves up together.
- **Why it matters:** search cost is **guaranteed** = height (no "unlucky" long paths), costs are predictable and logarithmic, and minimum occupancy keeps the index compact. For a database, this means **every lookup takes ~3–4 disk reads**, even as the table changes constantly.

## 4. Insertion algorithm (lecture §3.4.1, with the exam convention)
1. **Search** down to the correct leaf.
2. If the leaf has space: insert the entry in sorted order. Done.
3. **Leaf overflow** ($2d+1$ entries): split into two leaves: **first $d$ entries stay**, the remaining $d+1$ move to a new leaf. **Copy up** the **first key of the new (right) leaf** into the parent. Fix the leaf links.
4. **Internal overflow** ($2d+1$ keys): split: first $d$ keys stay, last $d$ keys move to a new node, and the **middle key is pushed up** (it moves; it does not stay in either child).
5. If the **root** splits, create a new root with the pushed-up key → height + 1.

> [!important] Copy up vs push up
> **Leaf split → copy up** (the key stays in the leaf because leaves must hold every data entry).
> **Internal split → push up** (the key moves to the parent; internal keys are only signposts).

## 5. Deletion algorithm (lecture §3.4.2, with the exam convention)
1. Find the leaf; remove the entry.
2. If the leaf still has $\ge d$ entries: done (internal keys may stay even if that key value is gone).
3. **Underflow** ($< d$ entries):
   - **Redistribute (borrow)** from an adjacent **sibling with the same parent** that has more than $d$ entries: move entries across so both have $\ge d$, and **update the separating key in the parent** to the new first key of the right node.
   - Otherwise **merge** with that sibling: combine the two leaves, **delete the separating key** (and pointer) from the parent, fix leaf links.
4. If the parent (internal) underflows: redistribute through the parent (**rotate**: parent key down, sibling key up) or **merge** two internal nodes **pulling the separating key down** from their parent. This may propagate up.
5. If the root ends up with no keys, its only child becomes the new root → height − 1.

## 6. Worked exam example: 2022/23 Q3 (order $d = 2$)
**Figure 3.1:**
```text
                                A[50]
                 ┌────────────────┴──────────────────────┐
             B[40|45]                              C[60|78|87|90]
       ┌────────┼────────┐             ┌───────┬───────┼───────┬───────┐
   D[23 32] E[40 41 43 44] F[45 48]  G[50 59] H[60 66] I[78 80 85 86] J[88 89] K[96 99]
```
**(a) Insert 90.** Read **A** (90 ≥ 50 → C), **C** (90 ≥ 90 → rightmost child K), **K**. K = [96 99] has space → K becomes **[90 96 99]**. Nodes **read: A, C, K**; node **updated: K** only.
> Some students follow 90 into J because 90 "equals" a key; under the rule "follow the pointer to the right of $K_i$ when $X \ge K_i$", it goes to **K**.

**(b) Insert 42.** Path A → B (40 ≤ 42 < 45) → E. E = [40 41 43 44] is full → 5 entries 40 41 42 43 44 → split: **E = [40 41]**, **E′ = [42 43 44]**, copy up **42** → **B = [40 42 45]** (room, so no further split).
```text
                    B[40|42|45]
        ┌───────┬───────┴──────┬────────┐
    D[23 32] E[40 41] E′[42 43 44] F[45 48]
```

**(c) Insert 79.** Path A → C (78 ≤ 79 < 87) → I. I = [78 80 85 86] full → 78 79 80 85 86 → **I = [78 79]**, **I′ = [80 85 86]**, copy up **80**. C would become [60 78 80 87 90]: 5 keys → overflow → split: **C = [60 78]**, **C′ = [87 90]**, push up **80** → **A = [50 80]**.
```text
                                 A[50|80]
            ┌───────────────────────┼─────────────────────────┐
        B[40|45]                C[60|78]                    C′[87|90]
     (D, E, F unchanged)   ┌───────┼───────┐          ┌───────┼───────┐
                        G[50 59] H[60 66] I[78 79]  I′[80 85 86] J[88 89] K[96 99]
```
Height unchanged (the root had room).

**Figure 3.2** (for d, e):
```text
                         A[50]
            ┌──────────────┴──────────────┐
        B[40|45]                       C[60|78]
   ┌────────┼────────┐           ┌────────┼────────┐
D[23 32] E[40 41 43 44] F[45 48] G[50 59] H[60 66] I[78 80 85 86]
```
**(d) Delete 23 (redistribute if possible).** D = [32] underflows (needs ≥ 2). Its sibling E (same parent B) has 4 entries → **redistribute**: move 40 to D → **D = [32 40]**, **E = [41 43 44]**, and the separator in B changes from 40 to 41 → **B = [41 45]**.
```text
        B[41|45]
   ┌───────┼────────┐
D[32 40] E[41 43 44] F[45 48]
```

**(e) Delete 50.** G = [59] underflows. Its only sibling under C is H = [60 66], which has exactly $d = 2$ entries → cannot lend → **merge G and H → [59 60 66]**, and remove separator 60 from C → **C = [78]**: C now underflows (1 key < 2). C's sibling B = [40 45] has only 2 keys → cannot lend → **merge B and C**, pulling down separator **50** from A: new node **[40 45 50 78]**. A is now empty → removed; the merged node is the **new root** → **height decreases by 1**.
```text
                     [40 | 45 | 50 | 78]                      ← new root
     ┌──────────┬─────────┼─────────┬──────────────┐
  D[23 32] E[40 41 43 44] F[45 48] G[59 60 66] I[78 80 85 86]
```
> 50 can remain as a separator even though record 50 was deleted (internal keys are only signposts). Writing 59 in its place is also a correct tree.

## 7. Worked exam example: 2023/24 Q3(c) (order $d = 2$, strings)
Insert, in order: era, ban, bat, kin, day, log, rye, max, won, ace, ado, bug, cop, gas, let, fax. Alphabetical order: ace < ado < ban < bat < bug < cop < day < era < fax < gas < kin < let < log < max < rye < won.

**After 4 insertions (era, ban, bat, kin):** one leaf, which is the root.
```text
[ban bat era kin]
```
**Insertions 5–8 (day, log, rye, max):**
- *day* → [ban bat day era kin] overflows → split [ban bat] | [day era kin], copy up **day** → root [day].
- *log* → right leaf [day era kin log].
- *rye* → [day era kin log rye] overflows → [day era] | [kin log rye], copy up **kin** → root [day kin].
- *max* → [kin log max rye].
```text
              [day | kin]
      ┌────────────┼──────────────┐
  [ban bat]   [day era]   [kin log max rye]
```
**Insertions 9–12 (won, ace, ado, bug):**
- *won* → [kin log max rye won] overflows → [kin log] | [max rye won], copy up **max** → root [day kin max].
- *ace* → [ace ban bat]; *ado* → [ace ado ban bat].
- *bug* → [ace ado ban bat bug] overflows → [ace ado] | [ban bat bug], copy up **ban** → root [ban day kin max] (now full, but no overflow).
```text
                   [ban | day | kin | max]
     ┌──────────┬──────────┼──────────┬──────────────┐
 [ace ado] [ban bat bug] [day era] [kin log] [max rye won]
```
**Insertions 13–16 (cop, gas, let, fax):** all fit without splits.
- *cop* → [ban bat bug cop]; *gas* → [day era gas]; *let* → [kin let log]; *fax* → [day era fax gas].
```text
                        [ban | day | kin | max]
     ┌───────────────┬────────────┼─────────────┬──────────────┐
 [ace ado] [ban bat bug cop] [day era fax gas] [kin let log] [max rye won]
```
**(ii) Utilization** (definition given in the question: entries in all nodes ÷ maximum entries those nodes can store):
- Nodes: 1 root + 5 leaves = 6 nodes, each can hold 4 → capacity $6 \times 4 = 24$.
- Entries: root 4 + leaves (2 + 4 + 4 + 3 + 3) = 4 + 16 = 20.
$$
\text{utilization} = \frac{20}{24} = 0.833 \approx 83.3\%
$$
(Counting leaves only: 16/20 = 80%.) These states were checked with a small simulation of the algorithm above.

## 8. Why B+-trees are preferred over B-trees ([[TUT 2 - Records, File Organization and B-Trees|Tutorial 2 Q15]])
1. **Higher fan-out:** internal nodes hold no data pointers, so more keys fit per block → fewer levels → fewer disk reads.
2. **Efficient range queries and sequential scans:** walk the **linked leaves** instead of an in-order traversal across levels.
3. **Uniform search cost:** every search ends at a leaf (same number of reads).
4. **Simpler insert/delete:** data entries are only in leaves; internal keys are just copies.
5. **Full scans** read only the leaf level.
