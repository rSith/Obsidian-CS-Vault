## Why this lesson matters
Big organisations (banks, airlines, a company with branches in Colombo, London and Singapore) cannot keep all their data on one computer in one place: it would be too slow for distant users, a single point of failure, and too small. A **distributed database** spreads one logical database over many networked computers (**sites**) while letting users treat it as **one database**.

> [!tip] Analogy: a library network
> A city has several branch libraries. Each branch keeps the books its readers use most (fragmentation), popular books are stocked at several branches (replication), and the shared online catalogue lets you search all branches as if they were one library (transparency). If one branch closes for a day, the others still work (availability).

## Exam pattern
Recent papers give a **scenario** (multinational logistics company; branches in Colombo/London/Singapore or New York/London/Singapore) and ask you to **apply** the concepts: which features make it a DDB, which fragmentation/replication to use and why, how distributed queries run, and which CAP properties to prioritise. Generic answers lose marks; **tie every point to the scenario**.
