# 05.06 · Distributed Query Processing and Optimization (and the Semijoin)

> [!info] [[05.00 Distributed Database Systems|Lesson 5]] · Lecture L5 §5.5, §5.5.1–§5.5.3 · Priority 🔴 High
> **Asked as:**
> - "Customer order reports frequently involve queries that access data from multiple locations. Explain how distributed query processing and optimization would be performed, and discuss the main challenges involved." (2023/24 Q6(c), 25 marks)
> - "Explain how query processing and transaction management would be handled to ensure consistency and efficiency across the sites." (2023/24 Q7(d)(ii); transaction part in [[05.07 Distributed Concurrency Control and Recovery]])

## 1. What changes when data is distributed?
All the centralized steps ([[03.01 Stages of Query Processing]]) still apply, but now relations (or fragments) sit at **different sites** and moving data over the **network** is often the **most expensive** part, especially over a **WAN**. So the optimizer's main goal becomes **minimizing data transfer**.

> [!tip] Analogy: assembling a report from three offices
> You could courier **all** the filing cabinets from Colombo and London to Singapore and do the work there (huge shipping cost), or send a short request so each office prepares only its own summary and couriers back a few pages. Distributed query optimization picks the cheapest shipping plan.

## 2. Stages of distributed query processing (lecture §5.5.1)
| Stage | What happens | Where |
|---|---|---|
| **1. Query mapping** | translate the query into an **algebraic query on global relations** using the **global conceptual schema** (ignoring distribution); normalize, check semantics, simplify, restructure | control site |
| **2. Localization** | map the global query to **queries on fragments**, using fragmentation and replication information (replace each global relation by the union/join of its fragments; pick replicas) | control site |
| **3. Global query optimization** | choose the strategy closest to optimal from candidate orderings; cost = weighted CPU + I/O + **communication** (time is the preferred unit); communication often dominates | control site |
| **4. Local query optimization** | each site optimizes its own sub-query with centralized techniques | each site |
| **5. Join processing** | joins between sites: **ship query to data**, **ship data to query**, or hybrid | |
| **6. Aggregation** | **partial aggregates** at each site (e.g. local SUM and COUNT), then combined | |
| **7. Result merging** | sub-results sent to the result site and merged | result site |
The lecture notes the first three stages run at a **central control site**, local optimization **locally**.

## 3. Data transfer costs: the lecture example (§5.5.2)
EMPLOYEE at **site 1**: 10,000 records × 100 bytes = **1,000,000 bytes**. DEPARTMENT at **site 2**: 100 records × 35 bytes = **3,500 bytes**. Query submitted at **site 3** (result site). Result record = 40 bytes.

**Q:** for each employee, name and department name → $\pi_{Fname,Lname,Dname}(EMPLOYEE \bowtie_{Dno=Dnumber} DEPARTMENT)$, 10,000 result rows = 400,000 bytes.
| Strategy | Bytes transferred |
|---|---|
| 1. Ship both relations to site 3, join there | 1,000,000 + 3,500 = **1,003,500** |
| 2. Ship EMPLOYEE to site 2, join, send result to site 3 | 1,000,000 + 400,000 = **1,400,000** |
| 3. Ship DEPARTMENT to site 1, join, send result to site 3 | 3,500 + 400,000 = **403,500** ✔ |

**Q′:** for each department, its name and manager's name → 100 result rows = 4,000 bytes.
| Strategy | Bytes |
|---|---|
| 1 | 1,003,500 |
| 2 | 1,000,000 + 4,000 = 1,004,000 |
| 3 | 3,500 + 4,000 = **7,500** ✔ |

If the result site is **site 2**: (1) ship EMPLOYEE to site 2 → 1,000,000 bytes for both Q and Q′; (2) ship DEPARTMENT to site 1 and the result back → 403,500 (Q) or 7,500 (Q′).

**Lesson:** move the **smaller** relation, and do the work where the **big** relation lives.

## 4. Semijoin (lecture §5.5.3)
**Idea:** reduce a relation **before** shipping it, by sending only the **join column** of one relation to the other site, keeping only the tuples that will actually join.

Steps for Q/Q′ with result at site 2:
1. At site 2, project the **join attribute** of DEPARTMENT and send it to site 1:
   $F = \pi_{Dnumber}(DEPARTMENT)$ = 4 × 100 = **400 bytes** (Q); $F' = \pi_{Mgr\_ssn}(DEPARTMENT)$ = 9 × 100 = **900 bytes** (Q′).
2. At site 1, join $F$ with EMPLOYEE and send back only the needed attributes of matching tuples:
   $R = \pi_{Dno,Fname,Lname}(F \bowtie_{Dnumber=Dno} EMPLOYEE)$ = 34 × 10,000 = **340,000 bytes**; $R' = \pi_{Mgr\_ssn,Fname,Lname}(F' \bowtie_{Mgr\_ssn=Ssn} EMPLOYEE)$ = 39 × 100 = **3,900 bytes**.
3. At site 2, join $R$ (or $R'$) with DEPARTMENT and present the result.

Totals: **340,400 bytes** for Q (little gain: every employee joins), **4,800 bytes** for Q′ (huge gain: only 100 of 10,000 employees are managers).

**Semijoin operator:** $R \ltimes S = \pi_{attrs(R)}(R \bowtie S)$: "the tuples of R that have a match in S". It pays off when **only a small fraction** of tuples participate in the join.

## 5. Model answer: Colombo/London/Singapore order reports (2023/24 Q6(c))
**How it is performed**
1. User submits a global query (e.g. "total sales per product across all branches this month") against the **global schema**.
2. **Mapping/decomposition** into a global RA expression.
3. **Localization:** `Orders` is replaced by `Orders_Colombo ∪ Orders_London ∪ Orders_Singapore`; the replicated `Product` table is read from the local copy.
4. **Global optimization:** push selections (month = …) and **partial aggregation** to each site (`SUM(amount) GROUP BY product` locally), so only small summaries cross the network; choose the cheapest site for joins (ship small tables to the large ones); use **semijoins** to filter remote orders by, e.g., a list of qualifying customer IDs.
5. **Local optimization** at each branch (indexes, local join algorithms), **parallel execution** at the three sites.
6. **Result merging:** site results are unioned and final aggregates computed (sum of partial sums; for AVG combine sums and counts).

**Main challenges**
- **Communication cost and latency** over WAN (dominant cost; continents apart).
- **Estimating costs** across sites (statistics about remote fragments may be stale; network speed varies).
- **Large search space** of strategies (which site does what, ordering, semijoins).
- **Replica selection and consistency**: which copy to read; avoid stale data.
- **Site or link failures** during execution; partial results.
- **Heterogeneity** (different DBMS/schemas) if the branches' systems differ.
- **Data skew/load imbalance** among sites; **security** of data in transit; **time zones/currencies** in reports.
