# 05.07 · Distributed Concurrency Control, Recovery and Fault Tolerance

> [!info] [[05.00 Distributed Database Systems|Lesson 5]] · Lecture L5 §5.6, §5.6.1, §5.6.1.1–§5.6.1.2, §5.6.2, Exercise 3 · Priority 🟡 Medium
> **Asked as:** "Short note: Fault tolerance in Distributed Databases" (2022/23 Q7(f), 25 marks) · "Explain how query processing and **transaction management** would be handled to ensure consistency and efficiency across the sites." (2023/24 Q7(d)(ii)) · part of "issues in DDB design" (2021/22 Q3(b))

## 1. Why is it harder than in a centralized DB? (lecture §5.6.1)
| Problem | Explanation |
|---|---|
| **Multiple copies of data** | concurrency control must keep replicas consistent; recovery must bring a failed site's copy up to date |
| **Failure of individual sites** | the system should keep running with the remaining sites; a recovering site must catch up before rejoining |
| **Failure of communication links** | extreme case: **network partitioning**: sites split into groups that can only talk within their group |
| **Distributed commit** | a transaction touching several sites must commit everywhere or nowhere, even if some site fails during commit → **two-phase commit** |
| **Distributed deadlock** | a cycle of waits may span several sites; deadlock detection must be extended |

> [!tip] Analogy: a group wedding gift
> Five friends in five cities each pay a share of a gift. Either **all** pay and the gift is bought (commit) or **nobody** pays (abort). Someone must coordinate, ask "are you ready to pay?", collect every "yes", then say "pay now". That is two-phase commit.

## 2. Concurrency control using a distinguished copy (lecture §5.6.1.1)
For replicated items, one copy is chosen to manage the locks.
### Primary site technique
- **One site is the coordinator** for all transaction management; all locks are managed there (two-phase locking); if all transactions follow 2PL, **serializability** is guaranteed.
- **+** simple (an extension of centralized 2PL); data locked at one site, accessible at any site.
- **−** the primary site can be **overloaded**; if it fails, the **whole system is inaccessible** (single point of failure).
- **Primary site with backup site:** a backup shadows the primary and takes over if it fails.

### Primary copy technique
- Instead of one site, **each data item has a primary copy** (spread over sites); locking an item locks only its primary copy.
- **+** load is spread; no single overloaded site.
- **−** identifying the primary copy is complex; needs a **distributed directory** (possibly at every site).

### Recovery from coordinator failure
| Situation | Action |
|---|---|
| Primary site, **no backup** | abort and restart all active transactions at all sites; **elect** a new coordinator; resume |
| Primary site **with backup** | suspend active transactions; backup becomes primary; choose a new backup; resume |
| Primary and backup both fail (or no backup) | **election** process selects a new coordinator |

## 3. Concurrency control by voting (lecture §5.6.1.2)
- **No distinguished copy.** A lock request is sent to **all sites holding a copy**.
- Each copy keeps its own lock and **grants or denies**.
- If a **majority** grant, the transaction holds the lock and informs all copies; otherwise, after a **time-out**, it cancels and informs all sites.
- **Truly distributed** (decision shared by all sites); but **more messages** than distinguished-copy methods, and very complex if site failures during voting are handled.

## 4. Recovery in distributed databases (lecture §5.6.2)
**Goal:** return to a **consistent state** after node crashes or network failures **without losing data**. Challenges: failures can occur at any node; changes are spread over replicas/nodes.

**Techniques (lecture)**
- **Logs:** transaction logs record changes → **undo/redo** to reach a consistent state.
- **Checkpointing:** periodically save the database state to stable storage → recovery need not replay the whole log.
- **Distributed commit protocols:** all nodes **either commit or roll back** together:
  - **Two-Phase Commit (2PC):** all nodes agree to commit or abort.
  - **Three-Phase Commit (3PC):** extension of 2PC that handles a **coordinator or participant crash during commit**.

> [!note] 2PC and 3PC mechanics are textbook knowledge
> The lecture only names 2PC and 3PC. The step-by-step mechanism below is the standard version (Elmasri & Navathe; Silberschatz) and is given so you can explain it in an answer.

### Two-Phase Commit (2PC)
```text
Coordinator                              Participants (sites)
   │ ── PREPARE (can you commit?) ─────────►│
   │                                         │ write changes + "ready" to log (force to disk)
   │ ◄──────────── VOTE YES / VOTE NO ───────│
   │ all YES? → log COMMIT  (else log ABORT)
   │ ── GLOBAL COMMIT / GLOBAL ABORT ───────►│
   │                                         │ commit/abort locally, release locks
   │ ◄──────────────── ACK ──────────────────│
```
- **Phase 1 (voting/prepare):** each participant prepares and votes. A "yes" is a promise it can commit even after a crash.
- **Phase 2 (decision):** commit only if **all** voted yes; otherwise abort.
- **Weakness:** **blocking**: if the coordinator crashes after participants voted yes, they must wait (holding locks) until it recovers.

### Three-Phase Commit (3PC)
Adds a **pre-commit** phase between voting and commit (prepare → pre-commit → commit) and uses time-outs, so that participants can decide safely **without waiting for a failed coordinator** → **non-blocking** (assuming no network partition), at the cost of more messages.

## 5. Fault tolerance in distributed databases (2022/23 Q7(f))
**Fault tolerance** = the system keeps working correctly despite failures of sites, disks or links.
| Mechanism | How it provides fault tolerance |
|---|---|
| **Replication / redundancy** | copies at several sites; reads/writes redirected to surviving replicas (lecture §2 pts 2, 5, 7) |
| **No single point of failure** | decentralization; faults isolated at their site (§2 pt 9, §4.4) |
| **Backup / primary-backup sites** | backup coordinator takes over; election of a new coordinator (§5.6.1.1) |
| **Voting / quorum** | a majority can continue even if some copies are unreachable (§5.6.1.2) |
| **Logging and checkpointing** | recover a crashed site to a consistent state (§5.6.2) |
| **Atomic commit (2PC/3PC)** | multi-site transactions never half-commit |
| **Handling network partitions** | CAP choice: keep consistency or availability during partitions ([[05.02 CAP Theorem]]) |
| **Catch-up on recovery** | a recovered site's copy is brought up to date before rejoining |
| **Disaster recovery** | geographically separate copies survive site-wide disasters |
Plus measures within a site: [[01.10 RAID]].

## 6. Transaction management across Colombo/London/Singapore (2023/24 Q7(d)(ii), transaction part)
- Most orders touch only the **local fragment** → handled as **local transactions** (fast, no global coordination).
- An order touching **several sites** (e.g. stock from another branch) runs as a **distributed transaction**: sub-transactions at each site, coordinated by the originating site using **2PC** (or 3PC) so all parts commit or none.
- **Concurrency control:** distributed two-phase locking with **primary copy** locking for replicated items (or quorum/voting), plus **distributed deadlock detection** (time-outs or global wait-for graph).
- **Replica consistency:** synchronous update for critical data (stock, payments); asynchronous propagation for catalogue data.
- **Recovery:** local logs + checkpoints at each site; coordinator election if the coordinator fails.
