# 05.03 · Properties of a DDBS: Transparency, Autonomy, Reliability and Availability

> [!info] [[05.00 Distributed Database Systems|Lesson 5]] · Lecture L5 §4, §4.1–§4.5 · Priority 🔴 High
> **Asked as:**
> - "Explain how the core properties of distributed databases impact the design and operation of a system like the one described (multinational logistics)." (2022/23 Q6(c)(i))
> - "… explain its key characteristics … transparency" (2023/24 Q7(c))
> - "Explain possible issues associated with Distributed Database design." (2021/22 Q3(b))

## 1. Transparency (lecture §4.1)
**Transparency** = **hiding implementation details** from users and application developers. In a centralized DB this just means logical/physical data independence; in a DDB there are **extra** transparencies because data and software are spread over sites.

> [!tip] Analogy: a phone call
> You dial a number and talk. You don't know which cell towers, exchanges or undersea cables carry your voice (location transparency), whether the call was re-routed (replication), or that your voice was cut into packets (fragmentation). The network hides it all.

| Transparency | Meaning | Example |
|---|---|---|
| **Data organization (distribution / network) transparency** | freedom from network details and physical placement | |
| ↳ **Location transparency** | the command is the **same regardless of where the data is** and where the command is issued | `SELECT * FROM Orders` works in Colombo and London alike |
| ↳ **Naming transparency** | once named, an object is accessed **unambiguously without saying where it is**; requires system-wide **unique names**, efficient location lookup, ability to **move** data transparently, autonomous creation of names | `Orders`, not `london_server.db1.Orders` |
| **Replication transparency** | users are **unaware of copies** stored at multiple sites | the DDBMS picks a nearby replica and keeps copies consistent |
| **Fragmentation transparency** | users query a table **as if it were unfragmented**; the DDBMS turns a global query into fragment queries | `Orders` is really `Orders_Colombo ∪ Orders_London ∪ Orders_Singapore` |
| **Design transparency** | freedom from knowing how the DDB was designed | |
| **Execution transparency** | freedom from knowing where a transaction executes | |

## 2. Autonomy (lecture §4.2)
**Autonomy** = how far each site/node can **operate independently**. High autonomy → flexibility and site-specific maintenance.
| Type | Meaning |
|---|---|
| **Design autonomy** | each node chooses its own data model and transaction-management techniques |
| **Communication autonomy** | each node decides how much information to share with others |
| **Execution autonomy** | each node runs its operations independently ("users act as they please") |

Trade-off: more autonomy → harder global consistency and query processing (heterogeneity, [[05.05 Homogeneous, Heterogeneous and Federated Systems]]).

## 3. Reliability and availability (lecture §4.3)
- **Reliability:** the probability that the system is **running (not down) at a certain point in time**.
- **Availability:** the probability that the system is **continuously available during a time interval**.
- **Failure:** the system's behaviour deviates from its specification. **Error:** the subset of system states that causes the failure. **Fault:** the cause of an error. (fault → error → failure)
- DDBs improve both by **isolating faults at their site of origin** and by **replication**: if a failed site's data is replicated elsewhere, users are not affected at all.

## 4. Additional functions a DDBMS must provide (lecture §4.5)
1. **Keeping track of data distribution**: fragments, replicas (expanded catalog).
2. **Distributed query processing**: access remote sites, ship queries and data.
3. **Distributed transaction management**: strategies for multi-site transactions; synchronize access; maintain integrity.
4. **Replicated data management**: which copy to read; keep copies consistent.
5. **Distributed database recovery**: recover from site crashes and **communication link failures**.
6. **Security**: data security and authorization across sites.
7. **Distributed directory (catalog) management**: global or local directory placement.

## 5. Issues in distributed database design (2021/22 Q3(b))
> [!note] Built from several lecture sections
> There is no single "design issues" list in the lecture; this answer combines §4.5, §5.1–§5.3 and §5.6.
| Issue | Why it is hard |
|---|---|
| **Fragmentation** | deciding the units of distribution (horizontal, vertical, mixed); must be complete and reconstructable |
| **Allocation** | which site stores which fragment; depends on access patterns; a complex optimization problem |
| **Replication** | how many copies, where; better availability/reads vs costly updates and consistency |
| **Distributed catalog/directory** | where metadata lives; global vs local; keeping it consistent |
| **Distributed query processing** | communication cost dominates; choosing strategies (semijoins) |
| **Concurrency control** | multiple copies, distributed locking, **distributed deadlock** |
| **Recovery and commit** | site failures, link failures, **network partitioning**, **distributed commit** (2PC/3PC) |
| **Heterogeneity** | different DBMSs/data models/schemas/query languages (federated systems) |
| **Security** | across sites and networks |
| **Consistency vs availability** | CAP trade-offs |

## 6. Applying the properties to a logistics company (2022/23 Q6(c)(i))
| Property | Impact on design and operation |
|---|---|
| **Location/naming transparency** | dispatchers in any region query `Inventory` or `Shipments` without knowing which data centre holds them; data can be moved between regions without changing applications |
| **Fragmentation transparency** | inventory is fragmented **horizontally by region/warehouse** for local speed, yet a global "where is item X in stock?" query sees one table |
| **Replication transparency** | routes and product master data are replicated to every region for fast reads; the DDBMS keeps copies in step |
| **Autonomy** | each regional warehouse system can keep operating (receive, pick, ship) even if links to other regions fail; regions may manage local schemas/maintenance |
| **Reliability and availability** | failure of one warehouse's server doesn't stop others; replicas let operations continue; supports 24/7 global shipping |
| **Distributed transaction management** | an inter-warehouse transfer updates two sites atomically (2PC) to keep inventory consistent |
| **Performance** | queries run locally where data lives; parallel processing for global reports |
