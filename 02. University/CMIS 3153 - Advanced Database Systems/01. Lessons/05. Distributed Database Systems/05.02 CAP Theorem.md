# 05.02 · The CAP Theorem

> [!info] [[05.00 Distributed Database Systems|Lesson 5]] · Lecture L5 §3, Exercise 2 · Priority 🔴 High (3 sub-questions in 2 papers)
> **Asked as:**
> - "Discuss the CAP Theorem (Consistency, Availability, Partition Tolerance) and how it applies to distributed databases." (2022/23 Q6(b))
> - "For this logistics system, which properties of the CAP Theorem would be prioritized, and why?" (2022/23 Q6(c)(ii))
> - "Using the CAP theorem, analyse the trade-offs the company must consider when designing this distributed database system." (2023/24 Q6(d), Colombo/London/Singapore orders)

## 1. What is it?
The **CAP theorem** (Brewer's theorem) says a distributed data store **can guarantee only two of these three properties at the same time**:

| Letter | Property | Meaning (lecture) |
|---|---|---|
| **C** | **Consistency** | every read returns the **most recent write**; all nodes show the **same data** at the same time |
| **A** | **Availability** | **every request gets a response** (read or write), even if some nodes are down; the data may not be the latest |
| **P** | **Partition tolerance** | the system **keeps operating even when the network splits** and some nodes cannot talk to others |

> [!tip] Analogy: two bank branches and a broken phone line
> Branch A and Branch B share your account balance. The phone line between them is cut (a **partition**). You try to withdraw money at Branch A.
> - **Choose Consistency:** Branch A refuses ("we can't confirm your balance with Branch B") → you get no service (**not available**) but no one ever sees a wrong balance.
> - **Choose Availability:** Branch A lets you withdraw using its last known balance → you are served, but Branch B may show a different (stale) balance (**not consistent**) until the line is fixed.
> You cannot have both while the line is down.

## 2. The key insight (lecture)
- In a real network, **partitions will happen** (cables fail, data centres lose connectivity), so a distributed system must be **partition tolerant**.
- Therefore, **during a partition**, the system must choose between:
  - **Consistency** → reject (or delay) some requests, or
  - **Availability** → accept requests and possibly return **stale** data.
- When there is **no** partition, a system can provide both C and A.

## 3. The three combinations (lecture)
| Type | Keeps | Gives up during a partition | Examples (lecture) | Typical uses |
|---|---|---|---|---|
| **CP** | Consistency + Partition tolerance | availability (some requests refused/blocked) | **HBase, ZooKeeper** (also MongoDB in default config, Google Spanner, textbook) | banking, payments, inventory counts, bookings |
| **AP** | Availability + Partition tolerance | consistency (temporarily stale data; **eventual consistency**) | **Cassandra, Couchbase** (also DynamoDB, textbook) | social media feeds, shopping carts, product catalogues, tracking/logging |
| **CA** | Consistency + Availability | partition tolerance | single-site RDBMS | **theoretical** for a distributed system: impossible to keep both C and A while partitioned |

**Eventual consistency:** if no new updates arrive, all replicas will **eventually** become identical (used by many NoSQL AP systems; acceptable for social media and e-commerce browsing).

## 4. How CAP applies to distributed database design
- **Replication** creates the problem: once data has copies at several sites, keeping them identical requires communication, which a partition interrupts.
- Designers decide **per kind of data**, not once for the whole system: critical data → CP; data that tolerates staleness → AP.
- Choices are implemented through: synchronous vs asynchronous replication, quorum/voting ([[05.07 Distributed Concurrency Control and Recovery]]), distributed commit (2PC), conflict resolution.
- In practice systems **balance** the three (lecture), which led to different database models (NoSQL) tuned for consistency or availability.

## 5. Scenario answers
### Multinational logistics company (2022/23 Q6(c)(ii))
Warehouses, shipping routes and inventory across regions; large transactional volume; **high availability** and **consistency across sites** required.
- **P is mandatory**: sites are in different regions connected by WANs, so partitions will occur.
- **Inventory levels, stock allocation, order/shipment status changes → prioritise C (CP).** Two regions must not both allocate the last pallet; wrong stock counts cause over-selling, failed deliveries and financial loss. During a partition, block or queue conflicting updates rather than accept inconsistent ones.
- **Shipment tracking, route/location updates, dashboards, analytics → prioritise A (AP)** with eventual consistency: a tracking page a few seconds out of date is acceptable, and these must stay available to drivers and customers.
- **Conclusion:** a **CP core** for transactional inventory/orders (e.g. synchronous replication within a region + 2PC across sites), **AP** for read-heavy, tolerant data, and **local fragments** so each region can keep working on its own data during a partition.

### Colombo / London / Singapore customer orders (2023/24 Q6(d))
| Trade-off | Consequence for the company |
|---|---|
| **Choose C over A (CP)** | during a WAN outage, a branch may be unable to place/modify orders that touch other regions' data → lost sales, but no double-selling, correct payments and stock |
| **Choose A over C (AP)** | every branch keeps taking orders during outages; replicas may disagree (e.g. same stock sold twice); needs **reconciliation** later (conflict resolution, refunds) |
| **Latency vs consistency (even without partitions)** | strong consistency across continents means **synchronous** round trips (London–Singapore ≈ 150–200 ms) on every write → slower orders; asynchronous replication is faster but stale |
| **Design compromise** | **fragment orders horizontally by branch** so most orders are local (no cross-site coordination); keep **payments/stock** strongly consistent (CP); replicate **product catalogue/customer profiles** asynchronously for availability (AP); use quorum reads/writes where both matter |

- Give **CP and AP examples** (HBase/ZooKeeper; Cassandra/Couchbase).
