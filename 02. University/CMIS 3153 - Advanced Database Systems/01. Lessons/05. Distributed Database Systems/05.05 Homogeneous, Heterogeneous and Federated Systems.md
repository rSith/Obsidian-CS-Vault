# 05.05 · Homogeneous, Heterogeneous and Federated Distributed Databases

> [!info] [[05.00 Distributed Database Systems|Lesson 5]] · Lecture L5 §5.4, §5.4.1–§5.4.3 · Priority 🟡 Medium
> **Asked as:** "Compare homogeneous and heterogeneous databases." (2021/22 Q3(c), 25 marks)

## 1. Two factors that classify DDBMSs
1. **Degree of homogeneity** of the DDBMS software (same or different software at the sites).
2. **Degree of local autonomy** (can a site work as a standalone DBMS?). No provision to work standalone = **no local autonomy**.

> [!tip] Analogy
> **Homogeneous:** a chain of identical franchise restaurants with the same menu system and the same cash registers. **Heterogeneous:** a food court of independent restaurants, each with its own till and menu format; a shared ordering app must translate between them. **Federated:** that shared ordering app with one common menu (global schema) over all the independent restaurants.

## 2. Homogeneous DDBS (lecture §5.4.1)
- **All sites run identical DBMS software** (e.g. all Oracle, or all DB2, or all Sybase).
- Sites are **aware of each other** and **agree to cooperate** in processing requests.
- Local sites **give up part of their autonomy**: they cannot freely change schemas or DBMS software.
- The DBMS software must cooperate to exchange transaction information (multi-site transactions).
- The **operating systems may differ** (Linux, Windows, Unix …).

## 3. Heterogeneous DDBS (lecture §5.4.2)
- Sites may use **different schemas** and **different DBMS software** (and even data models).
- Sites **may not be aware** of each other; they may offer **limited cooperation** in transaction processing.
- **Schema differences** complicate **query processing**; **software differences** hinder **multi-site transactions**.

Two kinds:
| | **Federated database system (FDBS)** | **Multidatabase system** |
|---|---|---|
| Global view | data accessed through a **single global conceptual schema** | **no global schema**; a schema is built **dynamically** by the application when needed |
| Local autonomy | **minimum** (sites follow a centralized access policy) | **full** local autonomy |
(The lecture notes the distinction is not strictly followed; both are hybrids between distributed and centralized systems.)

## 4. Comparison (2021/22 Q3(c))
| Aspect | Homogeneous | Heterogeneous |
|---|---|---|
| DBMS software | **same** at all sites | **different** DBMSs (and possibly data models) |
| Schemas | common/compatible | may differ; need mapping/translation |
| Awareness and cooperation | sites know and cooperate fully | may be unaware; limited cooperation |
| Local autonomy | reduced (cannot change schema/software freely) | higher (sites keep their systems) |
| Query processing | straightforward: same language and optimizer | needs translation between query languages/data types; harder optimization |
| Transaction management | standard distributed protocols (2PC) | difficult: different concurrency/commit mechanisms |
| Design / administration | easier, uniform | complex: global schema integration, conflict resolution |
| Typical origin | designed as a DDB from the start (top-down) | integrating **existing/legacy** databases after mergers (bottom-up) |
| Example | all branches run Oracle RAC | head office on Oracle, a branch on MySQL, a legacy hierarchical system |

## 5. Federated DBMS issues: sources of heterogeneity (lecture §5.4.3)
1. **Differences in data models:** legacy hierarchical/network, relational, object, even flat files; hard to map to one global schema or one language.
2. **Differences in constraints:** different facilities for keys, referential integrity, triggers; conflicting constraints must be reconciled in the global schema (e.g. ER relationships become referential constraints in relational).
3. **Differences in query languages:** even with one data model, SQL-89 vs SQL-92 vs SQL-99 vs SQL:2008, different data types, operators, string functions.

These, combined with the different kinds of autonomy, create **semantic heterogeneity** that the FDBS must resolve.
