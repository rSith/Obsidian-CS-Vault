## 1. Definitions (lecture §1)
- A **distributed database (DDB)** is a **collection of multiple, logically related databases distributed over a computer network**.
- A **distributed database management system (DDBMS)** is the **software that manages the DDB and makes the distribution transparent** to users.
- The DDB consists of **loosely coupled sites (nodes)** that **share no physical component** (each has its own CPU, memory, disks).
- A **transaction** may access data at **one or more sites**, and several networked computers execute it **in a unified manner**.

> [!tip] Analogy
> A franchise of shops: each shop has its own till and stockroom (local database), but head office can see total stock and sales across all shops as one picture (one logical database), and a customer can order an item that is physically in another shop.

### Key ingredients (for "identify the features")
1. **Multiple sites** with their own processors and storage.
2. **Connected by a network** (LAN/WAN).
3. **Logically related data**: one **global schema** describes the whole database.
4. **DDBMS software** at each site that cooperates with the others.
5. **Transparency**: users see one database, not the pieces ([[05.03 Transparency, Autonomy and Reliability]]).
6. **Distributed transactions/queries** that span sites.

## 2. Why distribute? (lecture §2, benefits)
| Benefit | Explanation |
|---|---|
| **Scalability** | **horizontal scaling**: add nodes rather than buying a bigger server; **elastic scalability** in the cloud: scale up/down with demand |
| **High availability** | replication across nodes; if one node fails, others serve the data |
| **Geographic distribution** | data stored close to users → lower latency; compliance with local data laws |
| **Performance** | **parallel processing** of queries across nodes; **load balancing** |
| **Fault tolerance and consistency options** | replication; **eventual consistency** for apps that tolerate delay |
| **Cost efficiency** | cheap commodity hardware; cloud integration |
| **Disaster recovery** | copies in several locations survive a site disaster |
| **Big data and real-time processing** | volumes beyond one machine; IoT, social media, finance |
| **Decentralization and security** | **no single point of failure**; per-node access control, encryption |
| **Flexible data models** | relational + key-value + document + graph |
| **Multi-tenancy** | many customers share a system with isolated data (SaaS) |
| **Microservices** | each service has its own database instance, scaling independently |

Lecture §4.4 "advantages": (1) **easier, more flexible application development** at distributed sites; (2) **increased reliability and availability** (faults isolated at their site); (3) **improved performance** (data localization reduces contention and WAN delays); (4) **easier expansion** (add data, sites, processors without reconfiguration).

## 3. Architecture (2021/22 Q3(a), 2023/24 Q7(c))
> [!warning] Only partly covered by the lecture
> The lecture gives Figure 1 ("distributed database environment": sites connected by a communication network) and the homogeneous/heterogeneous figures, but **no formal architecture model**. The layered description below combines Figure 1 with the standard textbook architecture (Elmasri & Navathe, Ch. 23; Özsu & Valduriez). This information could not be fully verified from the available course materials.

```text
                     Users / applications (at any site)
                                  │
              ┌───────────── Global schema (one logical DB) ─────────────┐
              │     global query processor · global transaction manager   │
              │     global (distributed) data dictionary / catalog         │
              └───────────────────────────────────────────────────────────┘
                 │                       │                         │
   ┌─────────────▼──────────┐ ┌──────────▼─────────────┐ ┌─────────▼─────────────┐
   │ Site 1 (Colombo)       │ │ Site 2 (London)        │ │ Site 3 (Singapore)    │
   │ DDBMS components       │ │ DDBMS components       │ │ DDBMS components      │
   │ local DBMS + local     │ │ local DBMS + local     │ │ local DBMS + local    │
   │ schema, local data     │ │ schema, local data     │ │ schema, local data    │
   │ (fragments/replicas)   │ │ (fragments/replicas)   │ │ (fragments/replicas)  │
   └──────────┬─────────────┘ └──────────┬─────────────┘ └──────────┬────────────┘
              └──────────────── Communication network (LAN/WAN) ─────┘
```
**Components / layers**
1. **Global conceptual schema:** one logical description of all data; users query this.
2. **Fragmentation schema:** how each global relation is split into fragments.
3. **Allocation schema:** which site stores which fragment (and replicas).
4. **Local schemas and local DBMSs** at each site that store and manage their part.
5. **DDBMS layer** at each site: **global query processor/optimizer**, **distributed transaction manager** (concurrency control, 2PC), **replication manager**, **recovery manager**, **global catalog/directory**.
6. **Communication network** connecting all sites.

Common styles: **client–server** (clients send queries to server sites), **peer-to-peer/collaborating servers** (every site is a full DDBMS), **multidatabase/federated** (autonomous existing databases under a global layer, [[05.05 Homogeneous, Heterogeneous and Federated Systems]]).

## 4. Distributed vs centralized database (2022/23 Q6(a), 2023/24 Q7(c))
| Aspect | Centralized DB | Distributed DB |
|---|---|---|
| **Data storage** | one site / one server | spread over multiple sites; **fragmented** and/or **replicated** |
| **Processing** | one DBMS processes all queries | queries split into sub-queries at many sites; **parallel** processing; results merged |
| **Transparency** | only logical/physical data independence | must also hide **location, fragmentation, replication, naming** (distribution transparency) |
| Failure | single point of failure | failures isolated; other sites keep working |
| Performance | remote users suffer network latency | data close to users; load balanced |
| Scalability | vertical (bigger machine) | horizontal (more machines) |
| Query cost | I/O + CPU | I/O + CPU + **communication** (often dominant) |
| Concurrency / recovery | local locking and logging | **distributed** locking, deadlock detection, **2PC/3PC** |
| Complexity / cost of design | simpler | complex: fragmentation, allocation, catalog, consistency |
| Consistency | immediate | trade-offs (CAP; eventual consistency) |

## 5. Elastic scalability (lecture exercise 4)
**Elastic scalability** = the ability of a cloud DDB to **automatically add or remove nodes** as load rises and falls (e.g. Black Friday traffic), paying only for what is used. Cloud platforms provide on-demand virtual machines/storage, automatic **sharding** (horizontal partitioning) and rebalancing. **Challenges:** moving data when nodes join/leave (rebalancing), keeping replicas consistent during changes, cost control, and latency spikes during scaling.
