# 07.02 · OLTP vs OLAP (Operational vs Analytical Data)

> [!info] [[07.00 Data Warehousing and OLAP|Lesson 7]] · DW1 §1 (intro), §1.1, §1.2, §1.6; DW2 pp. 8–10 · Priority 🟡 Medium
> **Asked as:** "Define OLTP systems and explain their key characteristics. How do they differ from OLAP systems in terms of workload, data access patterns, and performance requirements?" (2023/24 Q7(b), 25 marks)

## 1. Definitions
- **OLTP (online transaction processing):** systems that run the **day-to-day operations** of an organisation through many short **transactions**: **insertions, updates and deletions**, plus simple queries. Traditional relational (and object/network/hierarchical) databases are **transactional databases** that support OLTP. They are optimised for queries that **touch a small part of the database** and transactions that insert/update **a few tuples** (DW1 §1).
- **OLAP (online analytical processing):** the **analysis of complex data from the data warehouse**: summarising, aggregating, slicing large historical datasets for **decision support**; often uses distributed computing (DW1 §1.1).

> [!tip] Analogy: a supermarket
> **OLTP** is the checkout counter: thousands of quick beeps per hour, each adding one sale, must never be slow or wrong. **OLAP** is the head-office analyst asking "how did snack sales in the North change each month over five years?": few questions, each scanning millions of sales.

## 2. Key characteristics of OLTP (DW2 p. 8 + DW1)
- **Purpose:** day-to-day business operations (sales transactions, student registrations, bank account updates).
- **Data:** **current**, **highly detailed**, **frequently updated**, short-term.
- **Operations:** many short **read/write transactions** (INSERT/UPDATE/DELETE), each touching few rows, usually via indexes.
- **Users:** many concurrent clerks, customers, applications.
- **Design:** **normalised** relational schema (avoid redundancy and update anomalies).
- **Requirements:** **fast response** (milliseconds), **high throughput** (transactions/second), **ACID** consistency, concurrency control, recovery, high availability.

## 3. OLTP vs OLAP
| Aspect | OLTP (operational) | OLAP (analytical / data warehouse) |
|---|---|---|
| **Purpose** | run daily operations | **decision making**, analysis, reporting |
| **Workload** | huge numbers of **short, simple transactions**; read **and write** | fewer **long, complex, ad-hoc queries**; mostly **read-only**; periodic **bulk loads** |
| **Data** | current, detailed, operational | **historical**, summarised/aggregated, integrated from many sources |
| **Data access pattern** | **random access to few rows** by key (index lookups); point queries | **scans of millions of rows**; aggregations (SUM, AVG), GROUP BY, joins across fact and dimension tables; roll-up/drill-down/slice/dice |
| **Updates** | **frequent**, real-time | **periodic** (nightly/weekly refresh); nonvolatile |
| **Queries** | simple, predefined | complex, unpredictable |
| **Performance requirement** | **low latency per transaction**, high transactions/second, strict consistency, concurrency | **query throughput / response time on large scans** (seconds–minutes acceptable); fast aggregation |
| **Schema** | normalised (3NF) | **denormalised multidimensional**: star/snowflake schemas, data cubes |
| **Indexing** | B+-trees on keys; few indexes to keep writes fast | many indexes incl. **bitmap indexes**, materialised aggregates |
| **Size** | GB | TB–PB (often 10–100× the sources) |
| **Users** | clerks, customers, apps (many) | managers, analysts, executives (fewer) |
| **Unit of work** | transaction | query / report |
| **System** | operational database | data warehouse / OLAP server |

(DW2 p. 10 summary: Purpose daily operations vs decision making; Updates frequent vs periodic; Data current vs historical; Queries simple vs complex; System OLTP vs OLAP.)

## 4. Why keep them separate
Running heavy OLAP queries on the OLTP system would **slow down transactions** (locks, I/O contention), and OLTP's normalised, current-only data is a poor fit for trend analysis. A warehouse **separates operational and analytical workloads** (DW2 conclusion).
