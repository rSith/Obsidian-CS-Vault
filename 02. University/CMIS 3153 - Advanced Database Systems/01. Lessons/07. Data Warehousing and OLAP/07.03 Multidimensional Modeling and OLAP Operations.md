# 07.03 · Multidimensional Modeling and OLAP Operations

> [!info] [[07.00 Data Warehousing and OLAP|Lesson 7]] · DW1 §1.4, §1.4.1, §1.6 · Priority 🟢 Low (not yet examined; likely candidate for a future short note)

## 1. Data cubes
Traditional databases store **two-dimensional** data (like a spreadsheet: products × regions). **Multidimensional models** place data in **data cubes** (called **hypercubes** with more than three dimensions). Example dimensions: **fiscal period (time), product, region**.
- 2-D: sales revenue with products as rows and regions as columns.
- 3-D cube: add **fiscal quarter**; each cell = sales for one product, one quarter, one region.
- For dimensional data, **query performance can be much better** than in the relational model; users query directly in any combination of dimensions.

> [!tip] Analogy: a Rubik's cube of numbers
> One axis is products, one is regions, one is quarters. Each small cube holds a sales figure. Turning the cube (pivot) shows a different face; zooming in or out (drill-down/roll-up) changes the level of detail; cutting a slice shows one quarter only.

## 2. OLAP operations (DW1 §1.4, §1.6)
| Operation | Meaning | Example |
|---|---|---|
| **Roll-up** | move **up** a hierarchy, grouping into larger units (**summarise**) | weekly → quarterly → annual; product → product category |
| **Drill-down** | move **down** to finer detail (the complement of roll-up) | country → region → sub-region; product → style |
| **Pivot (rotation)** | rotate the cube to view other axes (**cross-tabulation**) | regions as rows, quarters as columns, products as the 3rd dimension |
| **Slice and dice** | **projection operations on dimensions**: fix one dimension value (slice) or a sub-range of several (dice) | Q1 only; Q1–Q2 for North and South |
| **Sorting** | order data by ordinal values | |
| **Selection** | data available by value or range | |
| **Derived (computed) attributes** | computed from stored and derived values | profit = revenue − cost |

## 3. Multidimensional schemas (DW1 §1.4.1)
- **Fact table:** one tuple per **recorded fact**; holds **measured variables** (e.g. sales amount, quantity) and **foreign keys pointing to dimension tables**.
- **Dimension table:** tuples of attributes describing a dimension (Product: name, brand, category; Time: day, month, quarter, year).

| Schema | Structure | + | − |
|---|---|---|---|
| **Star schema** | one fact table + **one (denormalised) table per dimension** | simple, few joins, fast queries | redundancy in dimension tables |
| **Snowflake schema** | dimension tables **normalised into hierarchies** (Product → Category → Department) | less redundancy, easier maintenance | more joins, slower queries |
| **Fact constellation** | **several fact tables sharing dimension tables** (e.g. business results and business forecast sharing Product) | models several processes | more complex; limits possible queries (lecture) |

```text
Star schema
                 ┌───────────┐
                 │ TIME dim  │
                 └─────┬─────┘
 ┌───────────┐   ┌─────┴─────────┐   ┌───────────┐
 │ PRODUCT   ├───┤  SALES FACT   ├───┤ REGION    │
 │ dim       │   │ prod_id, time_│   │ dim       │
 └───────────┘   │ id, region_id,│   └───────────┘
                 │ units, revenue│
                 └─────┬─────────┘
                 ┌─────┴─────┐
                 │ CUSTOMER  │
                 └───────────┘
```
Some installations normalise warehouses up to 3NF to access the finest level of detail.

## 4. Bitmap indexing
A **bitmap index** stores a **bit vector for each value** of an indexed column: bit $i$ = 1 if row $i$ has that value. Works very well for **low-cardinality** domains (gender, status, region). Bitwise AND/OR of vectors combine conditions quickly. (Also [[TUT 4 - Selectivity and Index Cost|Tutorial 4 Ex 1]].)

> [!example] Bitmap index on `region`
> Rows: 1 North, 2 South, 3 North, 4 East → North = 1010, South = 0100, East = 0001. `region = 'North' OR region = 'East'` = 1010 OR 0001 = 1011 → rows 1, 3, 4.
