# 07.04 · Building a Data Warehouse (ETL, Metadata, Design, Problems)

> [!info] [[07.00 Data Warehousing and OLAP|Lesson 7]] · DW1 §1.2 (Figure 1), §1.5, §1.7, §1.8 · Priority 🟢 Low (not yet examined)

## 1. The big picture
```text
 Data sources                   Acquisition (ETL)                 Warehouse            Back end
 ─────────────                  ─────────────────                 ─────────            ────────
 OLTP databases ─┐                                                                    ┌─ OLAP
 legacy systems ─┼─► Extract ─► Clean/Transform/Reformat ─► Load ─► Data warehouse ──┼─ DSS / EIS
 files ──────────┘                                                (+ metadata)       └─ Data mining
                                                                       ▲                  │
                                                                       └── new info (rules) back
```
Design should support **ad-hoc queries** (any meaningful combination of attribute values); choose a schema reflecting anticipated usage.

> [!tip] Analogy: a water treatment plant
> Water from many rivers (sources) is **pumped in** (extract), **filtered and treated** (clean/transform) and **stored in a reservoir** (load) from which the city draws clean water (OLAP queries).

## 2. Three design activities
1. **Acquisition** of data for the warehouse.
2. Ensuring **data storage** meets query requirements efficiently.
3. Considering the **environment** the warehouse lives in.

### 2.1 Acquisition (ETL) steps
1. **Extract** from multiple, heterogeneous sources.
2. **Format** for consistency within the warehouse.
3. **Clean** to ensure validity: hard to automate, the **most labour-demanding** part. **Back flushing** = upgrading the source data with the cleaned data.
4. **Fit** into the warehouse data model (e.g. convert relational, OO or legacy network/hierarchical data to a multidimensional model).
5. **Load**: the sheer volume makes loading a major task; design a proper **refresh policy** (usually incremental).

### 2.2 Storage processes
Store per the warehouse model; create/maintain data structures and **access paths**; provide **time-variant** data as new data arrives; support updating; **refresh**; **purge** old data.

### 2.3 Environment / design considerations
Usage projections; fit of the data model; characteristics of available sources; **design of the metadata component**; **modular** component design; design for **manageability and change**; distributed and parallel architectures.

## 3. Metadata repository
A key component, holding:
- **Technical metadata:** acquisition processing, storage structures, data descriptions, warehouse operations and maintenance, access support.
- **Business metadata:** relevant business rules and organisational details.

## 4. Distributed vs federated warehouses
| | Distributed warehouse | Federated warehouse |
|---|---|---|
| Idea | one warehouse spread over sites | **decentralised confederation of autonomous warehouses** (often data marts) |
| Issues | all DDB issues: replication, partitioning, communication, consistency | integrating autonomous components |
| Metadata | **single replicated** repository at each site | **each component has its own** metadata repository |
| Benefits | load balancing, performance scalability, higher availability | lets large organisations federate data marts instead of one huge warehouse |

## 5. Warehouses vs views (DW1 §1.7)
**Alike:** both are read-only extracts with subject orientation. **Different:**
| Data warehouse | View |
|---|---|
| **persistent** storage | materialised on demand (virtual) |
| usually **multidimensional** | relational |
| can be **indexed** independently | cannot be indexed independently of base tables |
| provides specific functionality (roll-up, drill-down …) | no such functionality |
| large amounts of **integrated, temporal** data from many databases | an extract of **one** database |

## 6. Problems and open issues (DW1 §1.8)
**Difficulties:** huge **lead time** (years to build and maintain); **data quality and consistency**; regularly revising **usage projections** and accommodating added/removed sources without redesign; administration requires broader skills.
**Open issues:** renewed attention to data cleaning, indexing, partitioning and views for warehousing; automating acquisition, data-quality management, access-path selection, self-maintainability, performance optimisation; incorporating domain and business rules so warehouses become more intelligent and self-governing.
