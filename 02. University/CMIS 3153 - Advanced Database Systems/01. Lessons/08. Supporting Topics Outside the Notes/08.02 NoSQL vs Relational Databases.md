# 08.02 · NoSQL vs Relational Databases: When to Choose Which

## 1. What are they?
- **Relational databases (RDBMS):** data in **tables** with a **fixed schema**, relationships through **foreign keys**, queried with **SQL**, transactions with **ACID** guarantees. Examples: MySQL, PostgreSQL, Oracle, SQL Server.
- **NoSQL ("not only SQL") databases:** non-relational stores designed for **huge scale, flexible schemas and distribution**. Four main families:

| Family | Data model | Examples (lecture-named in bold) | Typical use |
|---|---|---|---|
| **Key-value** | key → opaque value | Redis, **DynamoDB** | caching, sessions, shopping carts |
| **Document** | JSON-like documents | **MongoDB**, **Couchbase** | content, catalogues, user profiles |
| **Wide-column (column-family)** | rows with flexible column families | **Cassandra**, **HBase** | time series, IoT, logging at scale |
| **Graph** | nodes and edges | Neo4j | social networks, recommendations, fraud detection |

> [!tip] Analogy
> A relational database is a **well-designed filing system with standard forms**: every form has the same boxes, cross-references are exact, and the clerk guarantees every transaction is complete. A NoSQL store is a **warehouse of labelled boxes**: you can throw in boxes of any shape, add more warehouses easily, and find a box quickly by its label, but cross-box queries and strict consistency are up to you.

## 2. Comparison
| Aspect | Relational | NoSQL |
|---|---|---|
| **Data model** | tables, rows, columns; normalised | key-value, document, column-family, graph; often denormalised |
| **Schema** | **fixed**, defined up front (schema-on-write) | **flexible / schema-less** (schema-on-read) |
| **Query language** | **SQL**, declarative; powerful **joins** and aggregates | product-specific APIs/query languages; joins limited or absent |
| **Transactions / consistency** | **ACID**, strong consistency | often **BASE** (Basically Available, Soft state, Eventual consistency); tunable consistency; many now offer limited ACID |
| **CAP choice** | traditionally consistency (CA on one site; CP when distributed) | many are **AP** (Cassandra, Couchbase); some **CP** (HBase, MongoDB) |
| **Scalability** | mainly **vertical** (bigger server); horizontal scaling (sharding) is harder | designed for **horizontal** scaling across commodity nodes (sharding built in) |
| **Fault tolerance** | replication, failover, RAID, 2PC | built-in **replication** across nodes/data centres; no single point of failure |
| **Performance** | excellent for complex queries and transactions | very high throughput for simple reads/writes on huge volumes |
| **Maturity / tools** | very mature, standard, many tools and skills | younger; varied, non-standard |
| **Data integrity** | constraints, keys, foreign keys enforced | mostly in the application |

## 3. When to choose which
**Choose relational when:**
- data is **structured** and relationships are important (orders–customers–products);
- you need **ACID transactions** and **strong consistency** (banking, payments, inventory, accounting, student records);
- you need **complex queries, joins, reporting** and ad-hoc SQL;
- the schema is **stable**; data volume fits a well-provisioned server or a modest cluster.

**Choose NoSQL when:**
- data volume and traffic are **massive** and must **scale horizontally** (social media, IoT, logs, clickstreams);
- the data is **semi-structured or changes shape** often (JSON documents, product attributes);
- **availability and low latency** matter more than immediate consistency (AP; **eventual consistency** acceptable, lecture L5 §2);
- access is mostly **simple lookups by key** or specific patterns (graph traversals → graph DB).

**Often both (polyglot persistence):** e.g. an e-commerce site keeps orders and payments in an RDBMS, the product catalogue in a document store, sessions/carts in a key-value store and recommendations in a graph DB. The lecture notes this flexibility as a benefit of distributed systems (L5 §2 pt 10: combining relational for structured data with NoSQL for unstructured data).

## 4. Relational vs NoSQL **distributed** databases (L5 Exercise 5)
| | Distributed relational | Distributed NoSQL |
|---|---|---|
| Scalability | fragmentation/replication designed by the DBA; distributed joins expensive | automatic **sharding** and rebalancing; elastic |
| Fault tolerance | replicas + 2PC/3PC; coordinator failover | replication with quorums; hinted handoff; no master (e.g. Cassandra) |
| Consistency | strong (serializability; 2PC) at the cost of latency/availability | tunable/eventual; prioritises availability under partitions |
