# 08.01 · The Three-Schema Architecture and Data Independence

## 1. What is it?
The **three-schema architecture** (ANSI/SPARC architecture) describes a database at **three levels**, each with its own **schema** (description). Its goal is to **separate users' views of the data from how the data is physically stored**.

> [!tip] Analogy: a restaurant
> - **External level** = the **menus**: a kids' menu, a vegetarian menu, a drinks menu. Each customer sees only what concerns them.
> - **Conceptual level** = the **full list of dishes and ingredients** the restaurant offers: one complete, organised description.
> - **Internal level** = the **kitchen**: which fridge holds what, shelf positions, cooking equipment.
> The kitchen can be rearranged without reprinting the menus, and a new menu can be printed without rebuilding the kitchen.

## 2. The three levels
```text
   End users / applications
   ┌────────────┐ ┌────────────┐ ┌────────────┐
   │ External   │ │ External   │ │ External   │   EXTERNAL LEVEL (views)
   │ view 1     │ │ view 2     │ │ view n     │
   └─────┬──────┘ └─────┬──────┘ └─────┬──────┘
         └──── external/conceptual mapping ───┘
                        │
              ┌─────────▼─────────┐
              │ Conceptual schema │                CONCEPTUAL LEVEL
              └─────────┬─────────┘
             conceptual/internal mapping
              ┌─────────▼─────────┐
              │  Internal schema  │                INTERNAL LEVEL
              └─────────┬─────────┘
                        │
                 Stored database (files, indexes on disk)
```
| Level | Describes | Who uses it | Example |
|---|---|---|---|
| **Internal (physical)** | **physical storage structures** and **access paths**: file organizations, record formats, indexes, blocking, hashing (Lessons 1–2) | DBA, DBMS | STUDENT stored as a heap file with a B+-tree index on Reg_No |
| **Conceptual (logical)** | the **whole database for a community of users**: entities, data types, relationships, constraints, operations; hides storage details | DBA, designers | `STUDENT(Reg_No, Name, Faculty, GPA)`, keys, foreign keys |
| **External (view)** | **user views**: the part of the database a particular user group is interested in; hides the rest | end users, application programs | a view showing only `Name, GPA` to the exam office |

**Mappings:** the DBMS transforms requests and results between levels (**external/conceptual mapping** and **conceptual/internal mapping**).

## 3. Data independence
**Data independence** = the ability to **change the schema at one level without having to change the schema at the next higher level**. Only the **mapping** between the two levels changes.

| Type | Change made at | What stays unchanged | Examples |
|---|---|---|---|
| **Logical data independence** | **conceptual schema** | **external schemas** and application programs | add a new column/table, split a table, add a constraint: existing views and programs still work |
| **Physical data independence** | **internal schema** | **conceptual schema** (and therefore external) | create/drop an index, change file organization (heap → hashed), move files to a new disk, change block size, use RAID |

- **Physical data independence** is easier to achieve and is common (users never see files or indexes).
- **Logical data independence** is harder, because programs depend more closely on the logical structure.

## 4. How the architecture supports data independence
- Each level is described **separately**, and the **mappings** absorb changes: when the internal schema changes, the DBA updates the conceptual/internal mapping; when the conceptual schema changes, the external/conceptual mappings are updated (e.g. view definitions).
- Applications are written against **external schemas**, so they are insulated from both kinds of change.
- **Link to this course:** the optimizer chooses indexes and file organizations (internal level) without changing the SQL (conceptual/external): physical data independence in action. In a **distributed DB**, transparency extends this idea to location, fragmentation and replication ([[05.03 Transparency, Autonomy and Reliability]]). Relational algebra itself provides logical data independence (L3 §3.2: [[03.05 Relational Algebra, SQL and Database Design]]).
