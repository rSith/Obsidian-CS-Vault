# 01.11 · Errors a Compiler Cannot Detect

> [!info] [[01.00 Introduction to Compilers|Lesson 1]] · Theory Notes 1 + 7 (limitations of syntax analyzers) · Priority 🟡 Medium
> **Asked as:** "A student writes a C program that compiles successfully but produces incorrect output. (i) Which compiler phase(s) might still have worked correctly and why? (ii) What types of errors are not detected by the compiler? Explain with examples." (2023/24 Q2d, 40 marks)

## 1. The key idea

A compiler checks **form and language rules**, not **intent**. A program can be perfectly valid C and still not be the program the programmer *meant* to write.

## 2. "Compiles successfully" means all phases worked

If the program compiled, then:

| Phase | Why it must have worked |
|---|---|
| Lexical analysis | Every lexeme formed a valid token. |
| Syntax analysis | The token arrangement matched the grammar, so a parse tree was built. |
| Semantic analysis | All types were compatible and all identifiers declared. |
| Intermediate code, optimization, code generation | They completed and produced an executable. |

So the wrong output is **not** a compilation failure. It comes from errors the compiler is not designed to detect.

## 3. Errors not detected by the compiler

| Type | What it is | Example |
|---|---|---|
| **Logical errors** | The code is valid but the logic is wrong | `area = length + width;` instead of `*`; wrong loop bound `for (i = 0; i <= n; i++)` |
| **Run-time errors** | Depend on values known only while the program runs | division by zero `x / y` when `y == 0`; array index out of bounds; null pointer use; infinite loop |
| **Semantic errors beyond the language rules** | Type-correct but meaningless use | using an **uninitialized** variable; wrong operator precedence that is still type-correct, e.g. `avg = a + b / 2;` |

## 4. Link to the lecture: limitations of syntax analysis

Theory Notes 7 lists what the syntax analyzer **cannot** determine (see [[07.10 Limitations of Syntax Analysis]]):
- if a token is valid,
- if a token is declared before it is used,
- if a token is **initialized before it is used**,
- if an operation performed on a token type is valid.

Declaration and type checks are done later by semantic analysis. But **initialization before use** and **whether the values make sense at run time** are generally not guaranteed by the compiler. They are found by **testing and debugging**.

> [!warning] Beyond the slides
> The lecture does not discuss logical or run-time errors directly. The categories above are standard material, connected to the lecture's list of syntax-analyzer limitations.

## 5. Example answer sketch

```c
#include <stdio.h>
int main() {
    int a = 10, b = 0, avg;
    avg = a + b / 2;          // logic: should be (a + b) / 2
    printf("%d", a / b);      // run-time: division by zero
    return 0;
}
```

This compiles (all phases succeed) but prints a wrong average and crashes at run time.

## 6. Exam-relevant points
- (i) **All phases worked.** Justify phase by phase.
- (ii) Name **logical** and **run-time** errors (plus uninitialized use), each with a short code example.
- Conclude: found by **testing/debugging**, not compilation.
