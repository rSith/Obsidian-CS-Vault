## 1. Intermediate Code Generation (phase 4)

> [!abstract] Theory Notes 1
> "After semantic analysis the compiler generates an **intermediate code** of the source code for the target machine. It represents a program for some **abstract machine**. It is **in between the high-level language and the machine language**. This intermediate code should be generated in such a way that it makes it **easier to be translated into the target machine code**."

**Why generate intermediate code instead of machine code directly?** (2023/24 Q2c)

| Reason | Explanation |
|---|---|
| **Easier translation** (from the notes) | Going straight from high-level source to machine code is a big jump. Intermediate code splits it into two smaller, easier steps. |
| **Portability / re-targeting** | Intermediate code is not tied to one processor. One front end can serve many machines: only the code generator changes. With *m* languages and *n* machines you need *m + n* components instead of *m × n* compilers. |
| **Optimization** | Machine-independent optimization is much easier on a clean, uniform intermediate form than on real machine code. |

> [!warning] Beyond the slides
> Only "easier to translate into the target machine code" is in the lecture. Portability and optimization are standard reasons (and the m + n argument is a textbook one), added for full marks.

**Example (three-address code, illustrative):** `a = b + c * d;` becomes

```text
t1 = c * d
t2 = b + t1
a  = t2
```

## 2. Code Optimization (phase 5)

> [!abstract] Theory Notes 1
> "Optimization can be assumed as something that **removes unnecessary code lines**, and **arranges the sequence of statements** in order to **speed up the program execution without wasting resources (CPU, memory)**."

**Why is optimization critical?** (2022/23 Q2a)
- The definition of a compiler requires target code that is **efficient in time and space** ([[01.01 What is a Compiler]]). Correctness alone is not enough.
- **Speed:** fewer and better-ordered instructions mean faster execution.
- **Resources:** less CPU time and memory wasted.
- Readable source code is often not the most efficient. The optimizer lets programmers keep code readable without paying a performance price.
- **Constraint:** optimization must **never change the meaning** of the program.

**Example (illustrative):**

```c
x = 4 * 2;          // becomes  x = 8;          (constant folding)
y = a * b + a * b;  // becomes  t = a * b; y = t + t;  (remove repeated work)
if (0) { … }        // removed completely        (dead code)
```

### Embedded systems (2023/24 Q1d)

**(i) Why optimization is especially important:** embedded devices have **very limited memory and slow processors**, often run on **batteries**, and may have **real-time deadlines**. Unoptimized code may simply **not fit** in memory or may **miss its deadline**. On a desktop that is an inefficiency, but on an embedded device it is a **failure**. You cannot add more hardware, so the compiler is the only way to improve performance.

**(ii) Phases that matter most:**
1. **Code Optimization:** removes unnecessary code and rearranges statements, which directly reduces instruction count and memory use.
2. **Code Generation:** chooses the actual machine instructions and allocates registers. Good register use avoids slow memory accesses.
3. **Intermediate Code Generation:** produces the machine-independent form on which systematic optimization is possible.
- Supporting role: the **symbol table**, used to allocate memory efficiently to identifiers.
- *Front end = correctness; back end = performance.*

## 3. Code Generation (phase 6)

> [!abstract] Theory Notes 1
> "In this phase, the code generator takes the **optimized representation of the intermediate code** and maps it to the **target machine language**. The code generator translates the intermediate code into a sequence of (generally) **re-locatable machine code**. Sequence of instructions of machine code performs the task as the intermediate code would do."

- **Re-locatable** means the code can be placed anywhere in memory. The [[01.06 Linker and Loader|linker and loader]] decide the final addresses.
- Also decides **register allocation** and instruction selection (standard knowledge, not stated in the notes).

## 4. Comparison of the three back-end phases

| | Intermediate Code Generation | Code Optimization | Code Generation |
|---|---|---|---|
| Input | Annotated syntax tree | Intermediate code | Optimized intermediate code |
| Output | Intermediate (abstract machine) code | Better intermediate code | Re-locatable target machine code |
| Machine dependent? | No | (Mostly) no | **Yes** |
| Purpose | Ease translation, portability | Speed, less memory/CPU | Produce real machine instructions |
