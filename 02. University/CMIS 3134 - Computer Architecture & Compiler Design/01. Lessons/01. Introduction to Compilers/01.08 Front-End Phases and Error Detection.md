# 01.08 · Front-End Phases: Lexical, Syntax and Semantic Analysis (and how they catch errors)

> [!info] [[01.00 Introduction to Compilers|Lesson 1]] · Theory Notes 1, 6, 7 · Priority 🔴 High
> **Asked as:** "Differentiate Lexical Analysis and Syntax Analysis" (2019/20 Q2b) · the **swapped** syntax/semantic statement (2021/22 Q2c) · "three analyses performed at the front end" (2022/23 Q1b) · "explain Lexical, Syntax, Semantic Analysis and Symbol Table, highlighting… detection and reporting of errors" (2023/24 Q1b) · "`int x = "10" + 5;` — identify the phase that detects the error" (2023/24 Q1c)

## 1. Lexical Analysis (phase 1)

> [!abstract] Theory Notes 1
> "The first phase of scanner works as a **text scanner**. This phase scans the source code as a **stream of characters** and converts it into meaningful **lexemes**. Lexical analyzer represents these lexemes in the form of **tokens** as `<token-name, attribute-value>`."

- **Input:** characters. **Output:** tokens.
- Removes **whitespace and comments**.
- **Errors:** a sequence of characters that matches no token pattern (for example an illegal character such as `@` in C code, or a malformed number like `12ab`).
- Built on [[02.00 Regular Expressions|regular expressions]] and finite automata.
- Full details: [[06.00 Lexical Analysis]].

## 2. Syntax Analysis (phase 2)

> [!abstract] Theory Notes 1
> "The next phase is called the syntax analysis or **parsing**. It takes the token produced by lexical analysis as input and generates a **parse tree (or syntax tree)**. In this phase, **token arrangements are checked against the source code grammar**, i.e. the parser checks if the expression made by the tokens is syntactically correct."

- **Input:** tokens. **Output:** parse tree.
- **Errors:** wrong *structure*, such as a missing semicolon, unbalanced parentheses, or `if x > 0 {` written without brackets.
- Built on **context-free grammars**. Full details: [[07.00 Syntax Analysis]].

## 3. Semantic Analysis (phase 3)

> [!abstract] Theory Notes 1
> "Semantic analysis checks whether the **parse tree constructed follows the rules of language**. For example, assignment of values is between **compatible data types**, and adding **string to an integer**. Also, the semantic analyzer keeps track of identifiers, their types and expressions; whether identifiers are **declared before use** or not etc. The semantic analyzer produces an **annotated syntax tree** as an output."

- **Input:** parse tree. **Output:** annotated syntax tree (the tree with type information attached).
- **Errors:** type mismatches, undeclared identifiers, using a variable before declaring it, invalid operation for a type.
- Uses the [[01.10 Symbol Table and Error Handler|symbol table]] to look up declared types.

## 4. Comparison tables

### Lexical vs Syntax Analysis (2019/20 Q2b)

| | Lexical Analysis | Syntax Analysis |
|---|---|---|
| Phase number | 1st | 2nd (uses phase 1's output) |
| Input | Stream of characters | Stream of tokens |
| Output | Tokens `<token-name, attribute-value>` | Parse tree / syntax tree |
| Job | Recognise the **words** of the language | Check the **arrangement** of the words against the grammar |
| Theory used | Regular expressions / finite automata | Context-free grammar / push-down automata |
| Typical error | Illegal character, invalid token | Missing `;`, unbalanced `( )` |
| Also | Removes whitespace and comments, passes tokens on demand | Builds the structure used by later phases |

### Syntax vs Semantic Analysis (2021/22 Q2c, the swapped statement)

> *"Syntax Analysis checks whether the constructed parse tree follows the rules of language and Semantic Analysis checks whether the token arrangements follow the source code grammar."*

**Do you agree? No.** The two definitions are **swapped**.

| | Syntax Analysis | Semantic Analysis |
|---|---|---|
| Checks | **Token arrangements** against the **source code grammar** | Whether the **parse tree** follows the **rules of the language** |
| Checks *form* or *meaning*? | Form | Meaning |
| Output | Parse tree | Annotated syntax tree |
| Example error | `int x = 5` (missing `;`) | `int x = "10" + 5;` (string + int) |

**Justification by ordering:** syntax analysis is the phase that *builds* the parse tree, so it cannot be the phase that checks a tree that does not exist yet.

## 5. Worked example: `int x = "10" + 5;` (2023/24 Q1c)

**Which phase detects the error? Semantic Analysis.**

| Phase | Result | Why |
|---|---|---|
| Lexical | ✅ passes | Every lexeme is a valid token: `int` keyword, `x` identifier, `=` operator, `"10"` string literal, `+` operator, `5` constant, `;` punctuator. |
| Syntax | ✅ passes | The arrangement `type identifier = expression ;` is grammatically correct, so a valid parse tree is built. |
| Semantic | ❌ **error** | It checks **type compatibility**: it finds a **string being added to an integer**, and the result assigned to an `int`. The lecture names "adding string to an integer" as exactly this phase's job. |

**How it detects it:** it walks the parse tree, looks up the type of `x` in the symbol table (`int`), computes the type of each operand (`"10"` is a string, `5` is an int) and finds that `+` is not valid for string + int and that the result is not assignable to `int`.

> [!note] Language detail
> In real C, `"10" + 5` is pointer arithmetic on a string literal, and assigning it to an `int` gives a type error or warning. Either way, the error is about **types**, so it is detected at the semantic analysis level. The course answer is: **semantic analysis, type compatibility**.

## 6. How each phase contributes to error detection (2023/24 Q1b)

| Component | Detects | Example |
|---|---|---|
| Lexical | Invalid tokens | `int 9x;` is caught by some scanners as a malformed identifier (illustrative) |
| Syntax | Grammar / structure errors | `if (a < b { … }` (missing `)`) |
| Semantic | Meaning / type errors | undeclared variable, `int x = "10" + 5;` |
| Symbol table | Not a detector itself, but the store that **makes** "undeclared" and "type mismatch" detectable | holds names, types and scopes |
| Error handler | Records and reports errors from all phases and lets compilation **continue** (recovery), so many errors are reported in one run | (none) |

## 7. Exam-relevant points
- The swapped-statement questions are always answered **"No"**, then **correct both definitions**, then **justify**.
- For the error question: name the phase, then explain **why the earlier phases let it through**. That part carries most of the marks.
- *Syntax checks form, semantics checks meaning.*
