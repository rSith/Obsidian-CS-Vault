# 03.07 · DFA vs NDFA

> [!info] [[03.00 Automata|Lesson 3]] · Theory Notes 3 (comparison table) + handwritten notes · Priority 🔴 High (4 of 5 papers)
> **Asked as:** "Compare and contrast DFA and NDFA" (2019/20 Q3c, 2020/21 Q3c, 2022/23 Q5c) · "Why might NFAs be computationally easier to design for certain problems, even though DFAs are simpler in execution?" (2022/23 Q5b, 2023/24 Q5b)

## 1. The lecture's comparison table (Theory Notes 3)

| DFA | NDFA |
|---|---|
| The transition from a state is to a **single particular next state** for each input symbol. Hence it is called deterministic. | The transition from a state can be to **multiple next states** for each input symbol. Hence it is called non-deterministic. |
| **Empty string transitions are not seen** in DFA. | NDFA **permits empty string (ε) transitions**. |
| **Backtracking is allowed** in DFA. | In NDFA, backtracking is **not always possible**. |
| Requires **more space**. | Requires **less space**. |
| A string is accepted by a DFA if it **transits to a final state**. | A string is accepted by an NDFA if **at least one of all possible transitions ends in a final state**. |

## 2. Extra rows worth adding

| | DFA | NDFA |
|---|---|---|
| Transition function | $\delta: Q \times \Sigma \rightarrow Q$ | $\delta: Q \times \Sigma \rightarrow 2^Q$ |
| Missing transitions | Not allowed (needs a dead state) | Allowed (∅) |
| Ease of **design** | Harder: every case handled explicitly | Easier: can "guess" |
| Ease of **execution** | Simple: one current state, one path | Harder: must follow all paths (a set of states) |
| Power | **Equal**: every NDFA has an equivalent DFA ([[04.01 NDFA to DFA - Subset Construction\|subset construction]]) | (same) |

**Similarities (the "compare" half):** both are 5-tuples (Q, Σ, δ, q0, F); both have one initial state and a set of final states; both are drawn with the same state-diagram conventions; both recognise exactly the **regular languages**.

> [!quote] Quotable line (handwritten notes)
> "Every DFA is an NDFA, but every NDFA is not a DFA."

## 3. Why NDFAs are easier to design but DFAs are simpler to run (2022/23 Q5b, 2023/24 Q5b)

**Easier to design:**
- **Guessing / parallel paths.** An NDFA can branch into several states at once, so it can "guess" where a pattern starts. The designer does not have to plan for every case.
- **Fewer states.** Example: "second-last symbol is a" needs 3 states as an NDFA, but the DFA must remember the last two symbols (4 states). For "n-th last symbol" the DFA can need up to $2^n$ states.
- **No dead state needed.** Missing transitions simply mean that path dies.
- **ε-transitions** let you join sub-machines together. This is how [[08.04 Regular Expression to Finite Automaton|RE → finite machine]] construction works.

**But DFAs are simpler in execution:**
- Exactly **one current state** at every step, so it is one table lookup per symbol, with no backtracking.
- Running an NDFA means tracking a **set** of current states, which is more work per symbol.

**Conclusion:** *design with an NDFA for clarity, then convert it to a DFA for execution.* They are equally powerful, so nothing is lost. A compiler's lexical analyzer generator does exactly this.

> [!warning] Beyond the slides
> The lecture gives only the 5-row table. The design-vs-execution reasoning, the state-count example and the $2^n$ remark are standard explanations needed for the "why" questions.
