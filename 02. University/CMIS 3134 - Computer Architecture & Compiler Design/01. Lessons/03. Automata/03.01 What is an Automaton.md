# 03.01 · What is an Automaton? (and what a Finite Automaton cannot do)

## 1. Definition

> [!abstract] Theory Notes 3
> "The term "Automata" is derived from the **Greek word "αὐτόματα" which means "self-acting"**. An automaton (Automata in plural) is an **abstract self-propelled computing device** which **follows a predetermined sequence of operations automatically**.
> An automaton with a **finite number of states** is called a **Finite Automaton (FA)** or **Finite State Machine (FSM)**."

## 2. Why "self-acting"?

- Once started, it needs **no outside control** or human help.
- Its behaviour is **fixed in advance** by its transition rules: given the current state and the next input symbol, the next state is already decided.
- It works **step by step, automatically**: read a symbol → change state → read the next symbol … until the input ends.
- It is an **abstract** (mathematical) machine, not a physical one, which makes it a precise tool for reasoning about computation.

## 3. Why are automata significant in computing?

| Area | Use |
|---|---|
| **Compilers** | The [[06.00 Lexical Analysis\|lexical analyzer]] is a finite automaton. Every token RE becomes an FA (the lecture: "use finite automata for verification"). |
| **Pattern matching / text search** | Searching for words and regex matching. |
| **Digital circuits** | [[05.00 Moore and Mealy Machines\|Moore and Mealy machines]] model sequential circuits such as vending machines and controllers. |
| **Protocols** | Network protocols and user interfaces are designed as state machines. |
| **Theory** | Automata show what can and cannot be computed with limited memory. Finite automata recognise **regular languages**; push-down automata recognise **context-free languages** ([[07.01 Why Regular Expressions Are Not Enough]]). |

> The lecture gives the definition only. The "significance" table is standard background, needed for the 2022/23 Q4a "why is it significant" half.

## 4. The Java question (asked 3 years in a row)

> **State whether we can design a finite state machine for: (i) accepting all valid Java codes; (ii) accepting all valid Java codes that never go into an infinite loop. Justify.**

Your handwritten notes (p. 6) state: an automaton **can be used to find if a Java programme is a valid one, but it cannot be used to identify an infinite loop.**

**(i) Yes.** Whether a program is *valid Java* is a question about its **syntax**: a fixed, finite set of rules applied to the program **text**. A machine can read the text and decide whether it follows the rules. This is exactly what a compiler's front end does.

**(ii) No.** Whether a program **ever goes into an infinite loop** depends on its **run-time behaviour**, not just its text. This is the **halting problem**, which is proven **undecidable**: no machine (finite or otherwise) can decide it for all programs. A finite automaton in particular has only finite memory, so it cannot keep track of unbounded loop counters and program states.

> [!note] Precision point (for extra credit)
> Strictly, checking full Java syntax needs more than a *finite* automaton, because nested brackets need unbounded memory, so a **push-down automaton** (a CFG parser) is used ([[07.01 Why Regular Expressions Are Not Enough]]). The course answer (from your notes) is still **(i) yes, (ii) no**. Mentioning the push-down automaton shows deeper understanding. "Halting problem" and "undecidable" are standard terms and are not in the notes.

## 5. Exam-relevant points
- Mention the **Greek origin** and the meaning **"self-acting"**.
