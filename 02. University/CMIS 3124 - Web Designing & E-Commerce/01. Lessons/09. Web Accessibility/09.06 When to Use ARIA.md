# 09.06 · When Should You Use ARIA?

> [!info] [[09.00 Web Accessibility|Lesson 9]] · Lecture ref L9.8 · Priority 🟡 Medium (supports Q8(c) and Q8(d))

The lecture gives **four situations** where ARIA is appropriate:

## 1. Defining landmarks
- ARIA roles provide **landmark cues** for assistive technologies **when native HTML can't be used, or when retrofitting old code**.
- The `role` attribute can define landmarks:
  - to **replicate the semantics of HTML5 elements** such as `nav` and `header`;
  - to give **semantics to functional areas**, e.g. `search`, `tablist`, `tab`, `listbox`.
- **When an ARIA landmark appears more than once per page**, differentiate the landmarks for screen readers using **`aria-label`** (lecture: "multiple nav landmarks").

```html
<nav aria-label="Main">…</nav>
<nav aria-label="Footer">…</nav>
<div role="search">…</div>
```
A screen reader now announces "Main navigation" and "Footer navigation" instead of two identical "navigation" regions.

## 2. Announcing dynamic content updates
- **Screen readers have difficulty announcing dynamic content updates** (content that changes without a page reload: chat messages, cart totals, error messages).
- Use **`aria-live`** to inform screen-reader users when an area is updated:

```html
<section aria-live="polite">...</section>
```

| Value | Behaviour (lecture) | Use for |
|---|---|---|
| **`off`** | **Default**: updates are **not announced** | Unimportant changes |
| **`polite`** | Updates are announced **only if the user is idle** | "3 items in cart", new chat message |
| **`assertive`** | Updates are announced **as soon as possible** (interrupting) | "Session expiring!", critical errors |

## 3. Creating accessible labels and descriptions
- **Preferred:** label elements with **visible, clearly written text using native HTML** (e.g. `<label>`). It is the *simplest, easiest to maintain, and helpful to people with cognitive disabilities*.
- **If native accessible text isn't available**, ARIA can add accessible labels or descriptions: **`aria-label`** and **`aria-labelledby`**.
- **Ensure consistency between what sighted users see and what screen-reader users hear.**

| `aria-labelledby` | `aria-label` |
|---|---|
| **Programmatically associates** an element with **text that already exists on the page** (but isn't in a `<label>`) | **Applies the label text directly in the attribute value** |
| References the **`id`** of the labelling element | The text is invisible, so only assistive technologies get it |
| Lecture example: a `<section>` labelled by the `<h2>` "Search Filters" | Lecture example: `<section aria-label="Search Filters">` |

```html
<!-- aria-labelledby -->
<section aria-labelledby="filters-h">
  <h2 id="filters-h">Search Filters</h2>
  …
</section>

<!-- aria-label -->
<section aria-label="Search Filters">…</section>
<button aria-label="Close">×</button>      <!-- icon-only button gets a name -->
```

### Constraints of ARIA labels (lecture)
1. **ARIA labels only work on labelable elements**: a link, button or form control, or an element with specific HTML or ARIA semantics. (On a plain `<div>` with no role, `aria-label` is ignored.)
2. **ARIA labels override HTML elements' default text and accessible names.** `<button aria-label="Submit form">Send</button>` is announced as "Submit form", not "Send".

## 4. Enhancing keyboard accessibility
- HTML has **built-in keyboard support** for buttons, form controls and links:
  - **Tab** moves between controls;
  - **Enter/Return** selects or activates controls;
  - **Up/Down arrows** move between options in a `<select>`.
- But sometimes code uses **non-semantic elements** for buttons and controls, or focusable controls for the wrong purpose. **`tabindex`** helps:

| Value | Effect (lecture) | Typical use |
|---|---|---|
| **`tabindex="0"`** | Lets elements **not normally focusable** (`<div>`, `<span>`, `<p>`, `<a>` with no `href`) **receive focus** in the normal tab order | A custom `<div role="button">` |
| **`tabindex="-1"`** | **Removes** interactive elements from the default tab order. On a **non-interactive** element, it allows **programmatic focus with `focus()`** scripting | A **modal dialog** that should get focus when opened; **inactive tabs** in a tab widget |

> [!warning] Beyond the slides
> Positive values (`tabindex="1"` and above) force a custom tab order. This is considered **bad practice**.
