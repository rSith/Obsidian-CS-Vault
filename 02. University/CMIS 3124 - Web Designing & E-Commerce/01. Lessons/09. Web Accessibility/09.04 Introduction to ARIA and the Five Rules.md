# 09.04 · Introduction to ARIA and the Five ARIA Rules

> [!info] [[09.00 Web Accessibility|Lesson 9]] · Lecture ref L9.5–L9.6 · Priority 🔴 High
> **Asked as:** "'Web developers should only use Accessible Rich Internet Applications (ARIA) when absolutely necessary'. Comment on this statement." (2023/24 Q8(c), 4 marks)

## 1. What is ARIA?
**ARIA (Accessible Rich Internet Applications)** is a set of HTML **attributes** (`role="…"` and `aria-…`) that tell **assistive technologies** (e.g. screen readers):
- **what an element is** (role),
- **extra information about it** (properties),
- **what condition it is in** (states).

```html
<div role="button" aria-pressed="false">Mute</div>
```

## 2. Why ARIA? (lecture)
| Reason | Explanation |
|---|---|
| **Improved accessibility** | Helps assistive technologies understand the **purpose and state** of web elements, making interaction easier for users with disabilities |
| **Dynamic content** | Useful when content **updates** and assistive technologies need to be **notified of changes** on the page |
| **Custom widgets** | Helps developers create accessible **custom widgets** such as **menus, grids and tab panels** |

## 3. The key slogan
> **"Only use ARIA when absolutely necessary."**
> *ARIA can be a valuable tool when you are creating something complex that doesn't map to native HTML elements.*

### Why be careful?

> [!note]
> The points below explain the slogan. They come from the study guide and the ARIA rules themselves.

- **ARIA changes only what is announced; it adds no behaviour.** `<div role="button">` is *announced* as a button, but it is **not focusable** and does **not respond to Enter/Space** unless you add `tabindex` and JavaScript. A real `<button>` does all this **for free**.
- **Wrong ARIA overrides correct native semantics** and can make a page **less** accessible.

```html
<!-- ❌ Needs ARIA + tabindex + JavaScript to behave like a button -->
<div role="button" tabindex="0" onclick="save()" onkeydown="if(event.key==='Enter')save()">Save</div>

<!-- ✅ Native HTML: role, focus and keyboard support built in -->
<button onclick="save()">Save</button>
```

## 4. The five ARIA rules (lecture)

| Rule | Lecture explanation |
|---|---|
| **#1 Use native HTML when possible** | **HTML is the foundation of web accessibility.** ARIA **should not be used if native HTML can provide sufficient structure and semantics**. **When used incorrectly, ARIA can introduce significant accessibility barriers.** |
| **#2 Don't change native HTML semantics, unless you really have to** | Most HTML elements have **default semantics conveyed to screen-reader users**. When necessary, ARIA **can override and change** those semantics. (Example: don't write `<h2 role="button">`.) |
| **#3 All interactive elements must be usable with the keyboard** | **ARIA design patterns define standard keyboard interactions** for custom widgets (tabs, accordions, stateful UI), so **everyone can use them with a keyboard**, and screen-reader instructions **match the actual functionality** |
| **#4 Interactive elements must be properly semantic and visible** | Any **keyboard-focusable** element must have proper semantics (native HTML **or** ARIA roles) so it is identified as a **link, button, form control**, etc. Interactive elements **must be visible**. |
| **#5 All interactive elements must have an accessible name** | Text describing the element (its **"accessible name"**) must be presented to screen-reader users. **If native HTML methods aren't available, ARIA can define it** (e.g. `aria-label`). |

> [!tip] Memory hook
> **"Native, Don't change, Keyboard, Visible, Name"** → N-D-K-V-N.

## 5. Model answer for 2023/24 Q8(c) (4 marks)
1. **Agree.** ARIA adds roles, properties and states for assistive technologies, but **Rule #1 says to use native HTML when possible**. Native elements (`<button>`, `<nav>`, `<label>`) already carry semantics **and** keyboard support.
2. ARIA changes only **what screen readers announce**. It **does not add behaviour** (focus, keyboard handling), which the developer must then build.
3. Used incorrectly, ARIA **introduces significant accessibility barriers**: it can **override native semantics** (Rule #2), and ARIA labels **override visible text**, which confuses users.
4. ARIA **is necessary** for complex features with **no native equivalent**: custom widgets (tabs, sliders, trees), announcing **dynamic updates** (`aria-live`), landmarks in old code, and accessible names where no visible label exists.
