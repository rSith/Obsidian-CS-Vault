# 09.07 · Making a Tab Widget Accessible with ARIA

> [!info] [[09.00 Web Accessibility|Lesson 9]] · Lecture ref L9.9 · Priority 🔴 High
> **Asked as:** "Illustrate how ARIA roles, properties, and states can be used to improve the accessibility and interactivity of the tab widget." (2023/24 Q8(d), **6 marks**). This is **the same as the lecture exercise** (slides 36–38).

## 1. ARIA roles beyond native HTML
Some ARIA roles identify common UI features that **go beyond standard HTML**: **combobox, slider, tabpanel, tree**. A **tab widget** is one of them, because HTML has no `<tabs>` element.

## 2. The problem: a common tab structure (lecture)
- A simple tab pattern: a set of tabs the user clicks; the **corresponding panels become visible or invisible** depending on which tab is selected.
- The tab functionality is **controlled by JavaScript**.
- ⚠️ **"Nothing is conveyed to a screen reader about the purpose of this widget, nor are the tabs keyboard accessible."**

The inaccessible starting markup (as given in the 2023/24 paper):
```html
<div class="tabs">
  <div>
    <button id="tab-1">Windows</button>
    <button id="tab-2">macOS</button>
    <button id="tab-3">Linux</button>
  </div>
  <div class="tab-panels">
    <div id="panel-1"><p>How to run this application on Windows</p></div>
    <div id="panel-2"><p>How to run this application on macOS</p></div>
    <div id="panel-3"><p>How to run this application on Linux</p></div>
  </div>
</div>
```

## 3. The fix in three steps (lecture)

### Step 1: add ROLES
*"Define the **tablist**, **tab** and **tabpanel** roles for assistive technology using ARIA."*
| Element | Role |
|---|---|
| The container of the buttons | `role="tablist"` (+ an `aria-label` describing the group) |
| Each button | `role="tab"` |
| Each panel | `role="tabpanel"` |

### Step 2: add PROPERTIES
*"Allows us to **programmatically relate tabs to their corresponding tabpanels**" and "makes the tabs **keyboard accessible** by using the **tabindex** attribute."*
| Property | Where | Purpose |
|---|---|---|
| `aria-controls="panel-1"` | Each **tab** | Says which panel this tab controls |
| `aria-labelledby="tab-1"` | Each **panel** | The panel is named by its tab |
| `tabindex="0"` | The **selected** tab | In the tab order |
| `tabindex="-1"` | The **other** tabs | Out of the tab order (arrow keys move between tabs) |
| `tabindex="0"` | Each **panel** | The panel content can receive focus |

### Step 3: add STATES
*"Define the **active/inactive states** of the tabs and tabpanels with **`aria-selected`** and **`aria-hidden`** attributes."*
| State | Where |
|---|---|
| `aria-selected="true"` | The active tab |
| `aria-selected="false"` | The inactive tabs |
| `hidden` (or `aria-hidden="true"`) | Inactive panels |

## 4. ⭐ The complete accessible widget (lecture solution)
```html
<div class="tabs">
  <div role="tablist" aria-label="Select your operating system">
    <button role="tab" aria-selected="true"  aria-controls="panel-1" id="tab-1" tabindex="0">
      Windows
    </button>
    <button role="tab" aria-selected="false" aria-controls="panel-2" id="tab-2" tabindex="-1">
      macOS
    </button>
    <button role="tab" aria-selected="false" aria-controls="panel-3" id="tab-3" tabindex="-1">
      Linux
    </button>
  </div>
  <div class="tab-panels">
    <div id="panel-1" role="tabpanel" tabindex="0" aria-labelledby="tab-1">
      <p>How to run this application on Windows</p>
    </div>
    <div id="panel-2" role="tabpanel" tabindex="0" aria-labelledby="tab-2" hidden>
      <p>How to run this application on macOS</p>
    </div>
    <div id="panel-3" role="tabpanel" tabindex="0" aria-labelledby="tab-3" hidden>
      <p>How to run this application on Linux</p>
    </div>
  </div>
</div>
```
> [!note]
> The lecture slide uses the `hidden` attribute on inactive panels, although the step-3 slide text mentions `aria-hidden`. Both hide the panel from screen readers; `hidden` also hides it visually. Either is acceptable. Note also that the slide contains "smart quotes" (`“false"`), which are typos in the slide; always use straight quotes in code.

## 5. Interactivity: JavaScript keeps the states in sync

> [!note] Beyond the slides
> The lecture says the tab functionality "is controlled by JavaScript" but does not show the script. This sketch shows what it must do.

```javascript
const tabs = document.querySelectorAll('[role="tab"]');

function selectTab(newTab) {
  tabs.forEach(tab => {
    const selected = tab === newTab;
    tab.setAttribute('aria-selected', selected);          // STATE
    tab.tabIndex = selected ? 0 : -1;                       // PROPERTY (roving tabindex)
    document.getElementById(tab.getAttribute('aria-controls')).hidden = !selected;
  });
  newTab.focus();
}

tabs.forEach((tab, i) => {
  tab.addEventListener('click', () => selectTab(tab));
  tab.addEventListener('keydown', e => {                    // Rule #3: keyboard usable
    if (e.key === 'ArrowRight') selectTab(tabs[(i + 1) % tabs.length]);
    if (e.key === 'ArrowLeft')  selectTab(tabs[(i - 1 + tabs.length) % tabs.length]);
  });
});
```
A screen reader now announces, for example: *"macOS, tab, selected, 2 of 3"*.

## 6. Marking guide (6 marks)
- **Roles (2):** `tablist` (+ `aria-label`), `tab`, `tabpanel`.
- **Properties (2):** `aria-controls` (tab → panel), `aria-labelledby` (panel → tab), `tabindex` 0 / -1.
- **States (2):** `aria-selected` true/false; `hidden`/`aria-hidden` on inactive panels; JavaScript updates them.
