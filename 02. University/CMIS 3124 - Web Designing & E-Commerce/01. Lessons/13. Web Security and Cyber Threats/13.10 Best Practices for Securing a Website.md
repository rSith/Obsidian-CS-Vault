# 13.10 · Best Practices for Securing a Website

> [!info] [[13.00 Web Security and Cyber Threats|Lesson 13]] · Lecture ref L13.10 · Priority 🔴 High. Used for "ways to improve online-banking security" (2017/18 Q4(d), 2018/19 Q2(d)), Gmail 2FA, SSL, and password questions.

## The 11 best practices (lecture)

| # | Practice | Lecture explanation / how |
|---|---|---|
| 1 | **Keep software updated** | Patch the CMS, plugins, server and libraries; most attacks exploit known bugs |
| 2 | **Beware of SQL injection** | **Parameterised queries and input validation** ([[13.03 SQL Injection]]) |
| 3 | **Prevent cross-site scripting (XSS)** | **Sanitise user input** to block scripts that could run in users' browsers and steal data ([[13.07 Cross-Site Scripting (XSS)]]) |
| 4 | **Limit error messages** | **Avoid exposing system details** in error messages |
| 5 | **Validate user input** | Check on the **server**, not only in the browser |
| 6 | **Access control** | Least privilege; role-based permissions |
| 7 | **Use strong passwords** | **Enforce complex password policies** against **brute-force** attacks |
| 8 | **Implement HTTPS** | **Encrypt data during transmission** and **prevent interception** ([[12.04 Tools for Ethical Web Development]]) |
| 9 | **Enable two-factor authentication (2FA)** | An **extra layer**: a second verification beyond the password ([[10.07 Authentication in E-Commerce]]) |
| 10 | **Monitor and log activity** | Detect suspicious behaviour early; audit trails |
| 11 | **Use modern and secure tech stacks** | Build with **updated, secure frameworks** |

> [!note]
> The lecture lists all 11 names but explains only some of them. Where it gives no explanation (e.g. access control, validate input, monitor and log), the "how" is a short added interpretation.

> [!tip] Mnemonic
> **"Update, Inject-proof, Script-proof, Hide errors, Validate, Control, Passwords, HTTPS, 2FA, Monitor, Modern"**: group them as **Patch · Input · Identity · Encryption · Monitoring**.

## Applying it: improving online-banking security (older scenario)
1. **Strong authentication:** MFA/2FA, an OTP for every transaction, biometrics; strong password policies.
2. **HTTPS/TLS everywhere**; updated, secure software; session timeouts ([[02.05 Sessions and Cookies]]).
3. **Monitoring and logging** plus **AI/ML fraud and anomaly detection** ([[13.11 AI and ML in Web Security]]).
4. **Zero Trust:** continuous verification, least privilege, device checks ([[13.12 Zero Trust Security]]); **DevSecOps** for the banking apps ([[13.13 DevSecOps]]).
5. **Customer awareness** against phishing and smishing; **transaction alerts** for all activity (withdrawals *and* deposits).

## Applying it: remembering passwords safely while travelling (2018/19 Q5(c))
- Use a **reputable password manager** protected by one strong master password and 2FA.
- Or use **memorable passphrases / mnemonics**; **never write the PIN with the card** or share it; don't store passwords in plain text or email.
- Set up **recovery options** (backup codes, recovery email) **before travelling**, and keep the bank's number handy to block the card.

> [!warning]
> The password-manager advice is general security practice. The lecture's point is only "use strong passwords".
