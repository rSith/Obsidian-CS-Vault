# 13.03 · SQL Injection (SQLi)

> [!info] [[13.00 Web Security and Cyber Threats|Lesson 13]] · Lecture ref L13.3 · Priority 🔴 High
> **Asked as:** short note on SQL injection: definition, how it happens, prevention (2023/24 Q6(d)(i), 2 marks).

## 1. What is it?
**SQL injection** is an attack in which the attacker **inserts malicious SQL code into an input** (form field, cookie, request) so that the **website's database executes the attacker's command**. It can **bypass logins** and **read, change or delete data**.

**SQL (Structured Query Language)** is the language used to talk to databases such as MySQL (`SELECT`, `INSERT`, `UPDATE`, `DELETE`).

## 2. Why is it possible?
The application **builds SQL by concatenating user input** directly into the query string. The database cannot tell the developer's SQL from the attacker's.

```php
// ❌ VULNERABLE: input pasted straight into the SQL
$sql = "SELECT * FROM users WHERE username = '" . $_POST['user'] .
       "' AND password = '" . $_POST['pass'] . "'";
```

If the attacker types `' OR 1=1 -- ` as the password, the query becomes:
```sql
SELECT * FROM users WHERE username = 'admin' AND password = '' OR 1=1 -- '
```
`1=1` is **always true**, so the login check is bypassed. (`--` comments out the rest.)

## 3. How it happens (lecture)
| Route | Explanation |
|---|---|
| **Through user inputs** | Attackers enter SQL code into an **input field**; when the form is submitted to the server, the attacker's code executes |
| **Through cookie modification** | Attackers **manipulate ("poison") cookies**; when the cookies are sent back to the server, they deliver SQL code into the database ([[02.05 Sessions and Cookies]]) |
| **Through server variables** | Attackers **slip SQL code into the browser's requests** (e.g. HTTP headers) |

## 4. Types of SQL injection (lecture)

| Type | How it works | Lecture example |
|---|---|---|
| **In-band** | Malicious queries sent **directly through the application interface**; results come back the same way | `SELECT * FROM users WHERE username = 'admin' AND password = '' OR 1=1;` bypasses authentication and **logs in as admin** because `1=1` is always true |
| **Error-based** | Exploits **database error messages** to **learn the database structure** and refine the attack | `SELECT * FROM users WHERE id = 1';` (the stray quote causes an error that reveals details) |
| **Blind** | **No error messages**; the attacker **infers** information by **observing the application's behaviour** to Boolean conditions | `SELECT * FROM users WHERE id = 1 AND 1=1;` vs `1=0`: if the responses differ, the query worked |
| **Out-of-band** | Uses a **different communication channel** to exfiltrate data (e.g. makes the database send a **DNS or HTTP request** containing the data) | `SELECT * FROM users WHERE id = 1; -- ;` |
| **Time-based blind** | Sends a query that causes a **time delay** (e.g. `SLEEP`) and infers true/false from the **response time** | `SELECT * FROM users WHERE id = 1 AND SLEEP(5);`: a 5-second wait means true |

## 5. Prevention (lecture: 6 methods)

### (1) Prepared statements and parameterised queries
*"Ensure that user inputs are treated as **data** rather than **part of the SQL query**."*
```php
$stmt = $conn->prepare("SELECT * FROM users WHERE username = ? AND password = ?");
$stmt->bind_param("ss", $username, $password);   // "ss" = two strings
$stmt->execute();
```
The `?` placeholders are filled **after** the SQL structure is fixed, so `' OR 1=1 --` is treated as a literal password, not SQL.

### (2) Stored procedures
*"They don't dynamically construct SQL queries."*
```sql
CREATE PROCEDURE GetUserByUsername (IN username VARCHAR(50))
BEGIN
   SELECT * FROM users WHERE username = username;
END;
```
> [!warning] Slide bug
> In this slide example the **parameter has the same name as the column** (`username = username`). Inside MySQL, `username` then refers to the parameter on **both** sides, so the condition is **always true** and the query returns **all users**. Use a different parameter name:
> ```sql
> CREATE PROCEDURE GetUserByUsername (IN p_username VARCHAR(50))
> BEGIN
>    SELECT * FROM users WHERE username = p_username;
> END;
> ```

### (3) Whitelist input validation
Validate inputs **before** using them. **Only allow certain characters and patterns**, e.g. alphanumeric input for usernames or email formats.
```php
if (!preg_match('/^[A-Za-z0-9_]{3,20}$/', $username)) { die("Invalid username"); }
```

### (4) Object-Relational Mapping (ORM) frameworks
ORMs **prevent dynamic query construction** by **handling query generation automatically** (e.g. Laravel Eloquent, Hibernate).

### (5) Restrict database privileges
Grant the **minimum required permissions** (least privilege): the app can do `SELECT` and `INSERT`, but **not** `DROP TABLE` or `ALTER`. Even a successful injection then does less damage.

### (6) Error handling
**Don't display detailed database errors** to users. **Log them internally** and show a **generic message**. This defeats error-based SQLi.

## 6. Short note for 2023/24 Q6(d)(i) (2 marks)
- **Definition:** injecting malicious SQL through application input so that the database executes it (bypass login, steal/alter/delete data).
- **How:** through form inputs (e.g. `' OR 1=1 --` in a login box), poisoned cookies or server variables, when the app concatenates input into queries.
- **Prevention:** prepared statements/parameterised queries, stored procedures, whitelist input validation, ORM, least database privilege, generic error messages.
