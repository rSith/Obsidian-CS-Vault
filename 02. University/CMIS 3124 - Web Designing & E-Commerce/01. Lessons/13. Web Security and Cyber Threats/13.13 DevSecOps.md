# 13.13 · Secure DevOps (DevSecOps)

> [!info] [[13.00 Web Security and Cyber Threats|Lesson 13]] · Lecture ref L13.13 · Priority 🔴 High
> **Asked as:** "Define Secure DevOps. How does it differ from DevOps?" (2023/24 Q6(b), 4 marks)

## 1. The three parts of Secure DevOps (lecture)
| Part | Lecture meaning |
|---|---|
| **Security** | **Introducing security earlier in the software development cycle**, e.g. programmers ensure the code is **free of vulnerabilities**, and security practitioners **test further before release** |
| **Development** | **Planning, coding, building and testing** the application |
| **Operations** | **Release, monitor and fix** any issues that arise |

## 2. How it works: DevOps → CI/CD → DevSecOps (lecture)

| Concept | Lecture definition |
|---|---|
| **DevOps** | A software development practice that **brings development and operations teams together**, using **tools and automation** for **collaboration, communication and transparency** |
| **CI/CD** (continuous integration and continuous delivery) | Uses **automated build-and-test steps** to **reliably and efficiently deliver small changes**; CI/CD tools **release new versions** and **respond quickly to issues** |
| **DevSecOps** | **Introduces security into DevOps by integrating security assessments throughout the CI/CD process**; makes security a **shared responsibility** of all team members; the **development team collaborates with the security team before writing any code**; operations **continue to monitor** for security issues **after deployment** |

```text
DevOps:     Plan → Code → Build → Test → Release → Deploy → Monitor   (security often a separate, late gate)

DevSecOps:  Plan → Code → Build → Test → Release → Deploy → Monitor
             ▲threat   ▲SAST/   ▲SCA    ▲DAST/              ▲monitor &
              model    code      (open- IAST                 fix
                       analysis  source)
            ← shift left ───────────────────────── shift right →
```

## 3. DevOps vs DevSecOps (2023/24 Q6(b))
| DevOps | DevSecOps |
|---|---|
| Unites **development + operations** | Unites **development + security + operations** |
| Focus: **speed and reliability** of delivery | Speed **and security** |
| Security is often a **separate step at the end** (or another team's job) | Security is **integrated into every stage** and is **everyone's responsibility** |
| Vulnerabilities found late → costly to fix | **Shift left:** vulnerabilities caught **early**, cheaper to fix; **shift right:** monitored after release |
| | Automated security tools (SAST, SCA, IAST, DAST) inside CI/CD |

> [!note]
> This comparison table combines lecture points. The lecture defines each term separately.

## 4. Benefits (lecture)
Catch software vulnerabilities **early** · **Reduce time to market** · Ensure **regulatory compliance** · Build a **security-aware culture** · **Develop new features securely**

## 5. Components (lecture)
| Component | Meaning |
|---|---|
| **Code analysis** | Investigate **source code for vulnerabilities**; ensure it follows best practices |
| **Change management** | Tools to **track, manage and report changes**, preventing **accidental vulnerabilities** from a change |
| **Compliance management** | Ensure the software **meets regulatory requirements** |
| **Threat modelling** | Investigate security issues that might arise **before and after deployment**; fix known issues and release updates |
| **Security training** | Train developers and operations teams in the **latest security guidelines** |

## 6. Best practices (lecture)
- **Shift left:** check for vulnerabilities in the **earlier stages** of development (e.g. developers write secure code).
- **Shift right:** focus on security **after deployment**.
- **Use automated security tools** in the CI/CD process, so security checks **don't slow development**.
- **Promote security awareness.**

## 7. Tools (lecture)
| Tool | What it does | When |
|---|---|---|
| **SAST**: Static Application Security Testing | **Analyses proprietary source code** for vulnerabilities (without running it) | Early (coding) |
| **SCA**: Software Composition Analysis | Visibility into **open-source software** used, for risk, security and **licence compliance** | Build |
| **IAST**: Interactive AST | Evaluates vulnerabilities in the **production environment** using **security monitors running inside the application** | Running app |
| **DAST**: Dynamic AST | **Mimics hackers** by testing the app's security **from outside the network** | Running app |

> [!tip] Static vs dynamic
> **S**tatic = **S**ource code, not running. **D**ynamic = **D**eployed, running, attacked from outside. **I**nteractive = **I**nside the running app. **SCA** = **S**oftware **C**omponents (open-source libraries).

## 8. Challenges (lecture)
1. **Resistance to the cultural shift:** software teams focus on building and deploying, security teams on keeping the app safe; **top leadership must get both teams on the same page**.
2. **Complex tool integration:** integrating tools from **different vendors** into the continuous delivery pipeline is hard.

## 9. Model answer for 2023/24 Q6(b) (4 marks)
- **Secure DevOps (DevSecOps):** integrating **security practices and automated security testing into every stage** of the DevOps/CI-CD pipeline, making security a **shared responsibility** of developers, security and operations teams.
- **DevOps:** unites development and operations with automation and **CI/CD** to deliver software quickly and reliably; security is often a **separate step at the end**.
- **Difference:** DevSecOps **shifts security left** (threat modelling, code analysis/SAST and SCA early) and **right** (DAST/IAST, monitoring after release). Security teams collaborate **from the start**, so vulnerabilities are caught early and are cheaper to fix, and compliance is ensured.
