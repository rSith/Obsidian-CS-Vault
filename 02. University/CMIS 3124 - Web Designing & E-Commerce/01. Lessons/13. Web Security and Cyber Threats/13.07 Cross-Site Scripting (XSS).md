# 13.07 · Cross-Site Scripting (XSS)

> [!info] [[13.00 Web Security and Cyber Threats|Lesson 13]] · Lecture ref L13.7 · Priority 🔴 High
> **Asked as:** short note on XSS: definition, how it happens, prevention (2023/24 Q6(d)(ii), 2 marks).

## 1. What is XSS? (lecture)
- **"A vulnerability in a web application that allows a third party to execute a script in the user's browser on behalf of the web application."**
- **Consequences:** **account compromise, account deletion, privilege escalation, malware infection**.
- *"A malicious website can use JavaScript to read data from other websites' responses by embedding them in an iframe, run scripts, and modify page contents."*

**In simple words:** the attacker gets **their JavaScript** to run on **your trusted website** in **other users' browsers**. Because the browser trusts the site, the script can steal **session cookies**, change the page, or redirect users.

## 2. Types (lecture)

| Type | How it works (lecture) | Example |
|---|---|---|
| **Reflected XSS** | The **input must be provided each time** to execute. The victim requests a page with the **payload in the request**, and the payload comes **back embedded in the response** as a script. | **XSS in a search field** (a malicious link `…/search?q=<script>…</script>` is sent to the victim) |
| **Stored XSS** | The **payload is stored on the server**; the script **runs on every visit** without anyone submitting it again | **XSS in a comment thread**: every reader runs the attacker's script |
| **DOM-based XSS** | Arises when **user-supplied data is given to DOM objects without proper sanitising** | The lecture's PHP greeting example (below) |

Lecture example code (unsafe: echoes input straight into the page):
```php
<?php
if (isset($_GET["firstname"]) && isset($_GET["lastname"])) {
    $firstname = $_GET["firstname"];
    $lastname  = $_GET["lastname"];
    if ($firstname == "" or $lastname == "") {
        echo "<font color=\"red\">Please enter both fields...</font>";
    } else {
        echo "Welcome " . $firstname . " " . $lastname;   // ❌ no sanitising
    }
}
?>
```
An attacker sends the link:
```text
page.php?firstname=<script>alert(document.cookie)</script>&lastname=x
```
The `<script>` is inserted into the HTML and **runs** in the victim's browser, where it could send their cookie to the attacker.

> [!note]
> Strictly, this PHP example is a **server-side reflected** case: PHP echoes the input. Classic DOM-based XSS happens entirely in client-side JavaScript (e.g. `element.innerHTML = location.hash`). The lecture places this example under DOM-based XSS. Know the lecture's label, but understand the idea.

## 3. Prevention

> [!note]
> The lecture's XSS slides give no prevention list. The best-practice slide says *"Sanitize user input to block scripts that could run in users' browsers"*. The other measures come from the study guide and OWASP (the lecture's reference).

| Measure | How |
|---|---|
| **Sanitise and validate user input** | Reject or clean `<script>` and other dangerous input (lecture best practice) |
| **Encode / escape output** | Convert `<` `>` `"` `'` into HTML entities before inserting into the page, e.g. PHP `htmlspecialchars()` |
| **Content Security Policy (CSP)** | An HTTP header that tells the browser which script sources are allowed |
| **HttpOnly cookies** | JavaScript cannot read the cookie, so `document.cookie` theft fails |
| **Frameworks that auto-escape** | React, templating engines |

```php
echo "Welcome " . htmlspecialchars($firstname) . " " . htmlspecialchars($lastname);  // ✅
// <script> becomes &lt;script&gt; → shown as text, not executed
```

## 4. Short note for 2023/24 Q6(d)(ii) (2 marks)
- **Definition:** a web-app vulnerability that lets an attacker run a malicious script in another user's browser **as if it came from the trusted site** (steal cookies or sessions, deface pages, redirect).
- **How:** unsanitised input is placed into pages: **reflected** (payload in the request, e.g. a search field), **stored** (saved on the server, e.g. a comment), **DOM-based** (user data written into the DOM unsanitised).
- **Prevention:** sanitise and validate input, encode/escape output, Content Security Policy, HttpOnly cookies.

## SQLi vs XSS
| SQL injection | XSS |
|---|---|
| Injects **SQL** | Injects **JavaScript/HTML** |
| Executes on the **database server** | Executes in **other users' browsers** |
| Steals or alters **database data** | Steals **sessions/cookies**, defaces pages |
| Fix: **prepared statements** | Fix: **output encoding / sanitising** |
