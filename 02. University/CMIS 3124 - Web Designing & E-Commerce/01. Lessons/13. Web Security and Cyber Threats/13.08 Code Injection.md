# 13.08 · Code Injection

> [!info] [[13.00 Web Security and Cyber Threats|Lesson 13]] · Lecture ref L13.8 · Priority 🔴 High
> **Asked as:** short note on code injection: definition, how it happens, prevention (2023/24 Q6(d)(iii), 2 marks).

## 1. What is it? (lecture)
- The attacker **injects code that is then interpreted/executed by the application**.
- It **exploits poor handling of untrusted data**.
- It **happens due to a lack of proper input/output data validation**.

**Untrusted data** is anything the user (or attacker) can control: form fields, URL parameters, cookies, headers.

## 2. Lecture example: PHP `eval()`
*"When a developer uses the PHP `eval()` function and passes it untrusted data that an attacker can modify, code injection could be possible."*

```php
$myvar = "varname";
$x = $_GET['arg'];
eval("$myvar = $x;");   // ❌ executes whatever is in $x as PHP code
```

**How the attack works:**
- Normal request: `page.php?arg=10` → evaluates `varname = 10;`
- Malicious request: `page.php?arg=1; system("id")` → evaluates `varname = 1; system("id");` → **the server runs an operating-system command chosen by the attacker**.

`eval()` turns a **string into code** and runs it. If any part of the string comes from the user, the user can write code.

## 3. Prevention

> [!note]
> The lecture gives the definition and the example. The prevention list comes from the study guide and OWASP, and it follows the lecture's "lack of input/output validation" cause.

| Measure | Explanation |
|---|---|
| **Never pass user input to `eval()`** or similar interpreters | Avoid dynamic code execution entirely |
| **Strict whitelist input validation** | Accept only the expected format (e.g. digits only) |
| **Output encoding** | Treat data as data, not code |
| **Least privilege** for the application | Even if code runs, it can do little |
| **Keep frameworks patched** | Remove known injection bugs |
| **Code analysis (SAST)** in DevSecOps | Find dangerous functions such as `eval()` before release ([[13.13 DevSecOps]]) |

```php
// ✅ Safer: validate and don't use eval at all
$x = filter_input(INPUT_GET, 'arg', FILTER_VALIDATE_INT);
if ($x === false || $x === null) { die("Invalid input"); }
$varname = $x;
```

## 4. Short note for 2023/24 Q6(d)(iii) (2 marks)
- **Definition:** an attack that injects code which the application interprets and executes, exploiting poor handling of untrusted data.
- **How:** a lack of input/output validation, e.g. PHP `eval()` given a `$_GET` parameter the attacker controls, so arbitrary server-side code runs.
- **Prevention:** avoid `eval()` and dynamic execution of input; validate and sanitise input (whitelists); encode output; least privilege; code review and static analysis.

## Code injection vs SQL injection vs XSS
| | Code injection | SQL injection | XSS |
|---|---|---|---|
| What is injected | Application code (e.g. PHP) | SQL | Client-side script |
| Where it runs | App server | Database | Victim's browser |
