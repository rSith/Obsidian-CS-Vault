# 06.08 · HTTP Caching and ETags

> [!info] [[06.00 Responsive Web Design|Lesson 6]] · Lecture ref L6.13 · Priority 🟡 Medium (supports "leverage browser caching")

## 1. What is HTTP caching? (lecture)
- The **web browser stores copies of web resources** (images, CSS, JS, pages).
- **When the resources are needed again, the browser retrieves them without requesting the server.**
- **Benefit:** faster pages, less data, less server load.

## 2. The problem and the solution (lecture)
- **Problem:** *what if the content of web pages changes frequently?* The browser might show an **old (stale)** copy.
- **Solution:** **ETags**. HTTP headers carry **ETags, which are tokens generated by the server**. *"Analysing the necessary ETag tokens from servers should be confirmed and ensured by the web developer."*

## 3. How ETags work, step by step

> [!note] Beyond the slides
> The slide gives only the problem and solution. This standard request/response flow (from the study guide) explains it.

1. **First visit:** the server sends the file with `200 OK` and a header such as `ETag: "v7"` (a fingerprint of that version).
2. **Revisit:** the browser asks again and includes `If-None-Match: "v7"`, meaning "I have version v7; has it changed?"
3. **If unchanged:** the server replies **`304 Not Modified`** with **no body**, and the browser uses its cached copy (fast, almost no data).
4. **If changed:** the server replies `200 OK` with the **new file** and a **new ETag** (`"v8"`).

```http
# First request
GET /style.css HTTP/1.1

HTTP/1.1 200 OK
ETag: "v7"
(body: the CSS file)

# Later request
GET /style.css HTTP/1.1
If-None-Match: "v7"

HTTP/1.1 304 Not Modified      ← no body; use the cached copy
```
