# 02.06 · Client–Server and Three-Tier Architecture

> [!info] [[02.00 Web Architecture and Development|Lesson 2]] · Lecture ref L2.9–L2.10 · Priority 🔴 High
> **Asked as:** "What is three-tiered web architecture? Provide a breakdown of what each layer … would be responsible for within an online doctor channeling service." (2023/24 Q1(c), **6 marks**)

---

## Part A: Client–server architecture

### 1. What is it?
**Client–server architecture** is **"a computing model in which the server hosts, delivers and manages most of the resources and services to be consumed by the client."** It has **one or more client computers connected to a central server** over a network or Internet connection.

- **Client:** the device or program that **asks** for a service (your browser).
- **Server:** the computer that **provides** the service (a web server).

### 2. Components and connectors (lecture)
- **Client**
- **Server**
- **Load balancer** (spreads requests across servers: see [[02.08 Web Application Architecture Components]])
- **Network-layer protocols** (e.g. TCP/IP, HTTP)

### 3. Typical data flow (7 steps, lecture)
1. The **client requests data** from the server.
2. The **load balancer routes the request** to the appropriate server.
3. The **server processes** the client request.
4. The **server queries the appropriate database** for some data.
5. The **database returns the queried data** to the server.
6. The **server processes the data and sends it back** to the client.
7. **The process repeats.**

```text
Client ─► Load balancer ─► Server ─► Database
   ▲                         │  ◄────────┘
   └──────── response ───────┘
```

### 4. Negative behaviours (lecture)
- **Greater potential for failure due to centralised control.** If the central server fails, everyone is affected.
- **Vulnerable to Denial-of-Service (DoS) attacks**, *because the number of servers is much smaller than the number of clients* ([[13.09 Denial of Service]]).
- **Very expensive to install and manage** the network.

### 5. Qualities supported and inhibited
The slides call these "Network Function Programmables".

> [!warning]
> "NFP" in software architecture usually means **non-functional properties** (quality attributes). The slide expands it as "Network Function Programmables", which looks like a slide error. Use "qualities/properties" in an answer, and mention the slide's term only if you are asked for it.

| Supported | Meaning |
|---|---|
| **Scalability** | Can scale **horizontally** (add more servers) or **vertically** (make a server more powerful) |
| **Availability** | Servers typically do not need to shut down or restart for many days |
| **Dependability** | Processing and resource allocation are done by a **dedicated set of machines** |
| **Heterogeneity** | **Clients are consumers** of services and **servers are providers** |

| Inhibited | Meaning |
|---|---|
| **Robustness** | If many clients send requests at once to a **single central server**, it can be overloaded, slow down drastically, or even fail |
| **Transparency** | Clients only send requests with their input data. They **don't see how the data is distributed across servers**, so it looks like there is only one central server |

## Part B: Three-tiered architecture

### 1. What is it?
**Three-tier architecture** splits an application into **three logical (and usually physical) layers**: **presentation, application (logic) and data**. Each tier can be **developed, maintained, secured and scaled independently**.

> [!note]
> The lecture's three-tier diagram is an image. The tier descriptions below follow the study guide and the standard model, and they match the lecture's "flow of information" slides.

| Tier | Responsibility | Typical technology |
|---|---|---|
| **Presentation tier** | The **user interface**: shows information and collects user input | HTML, CSS, JavaScript in the browser / mobile app |
| **Application (logic) tier** | Processes requests using the **business logic** (rules, calculations, validation); talks to the data tier | PHP, Java, Node.js on a web/application server |
| **Data tier** | **Stores and manages data**; answers queries | MySQL, PostgreSQL database server |

> **Key rule:** the presentation tier **never talks to the database directly**. Everything goes through the logic tier.

### 2. Flow of information and requests (lecture, 6 steps)
1. **User interaction:** the user interacts with the presentation tier (e.g. enters data into a web form).
2. **Request processing:** the presentation tier sends the user's request to the application tier.
3. **Business logic:** the logic tier executes the business logic, processes the data, and may interact with the data tier.
4. **Data access:** if necessary, the application tier communicates with the data tier to **read** or **write** data.
5. **Response:** the logic tier formulates a response based on the processed data and business rules, and packages it in the format the presentation tier needs.
6. **Display:** the presentation tier receives the response and **displays** it to the user (e.g. updates a web page).

### 3. Benefits (lecture list) with explanations
| Benefit | Why |
|---|---|
| **Scalability** | Each tier can be scaled separately (e.g. add more app servers during peak times) |
| **Maintainability** | A change in one tier (e.g. a new UI) does not require rewriting the others |
| **Flexibility** | Tiers can use different technologies and can be replaced |
| **Improved security** | Users never touch the database directly; the logic tier validates everything |
| **Reliability** | A failure in one tier is contained |
| **Developer specialisation** | Front-end, back-end and database teams work in parallel |

### 4. The "new view": three-tier with web services
In the newer view, the **web server is more active** and connects to a **Web Services server**, which in turn connects to various data sources, including database servers and other sources.

| **Database approach** (former view) | **Web services approach** (new view) |
|---|---|
| Gives the application **direct access to the database** | **Responds to an application's request** |
| `SELECT` (what's there?), `INSERT` (add), `UPDATE` (change) | **Validates and authenticates** the request, then responds |
| **The application decides** what happens to the database | **The service decides** what happens to the database |

**What web services add:** a database server just gets and updates data on command. A web service **adds processing**, e.g. **processing credit-card transactions** or providing **real-time data such as stock quotes or weather**. See [[02.07 Web Services, XML and JSON]].

## Part C: Worked example (2023/24 Q1(c)): online doctor-channelling service

| Tier | Responsibilities in a doctor-channelling system |
|---|---|
| **Presentation** | Patient-facing web/mobile UI: search doctors by specialty, hospital and date; view sessions and fees; fill in the booking form; pay; show the confirmation and appointment number; client-side validation |
| **Application (logic)** | Authenticate patients; **check doctor availability**; allocate the appointment number and time; **calculate channelling + hospital fees**; process payment through a gateway; apply cancellation/refund rules; send SMS/email confirmations |
| **Data** | Database of **doctors, specialties, hospitals, schedules, patients, appointments, payments**; executes queries and updates; keeps data consistent and backed up |

**Flow:** the patient books (presentation) → logic checks the slot in the DB → the booking is saved (data) → confirmation returned → displayed.
