# 02.05 · Sessions and Cookies

> [!info] [[02.00 Web Architecture and Development|Lesson 2]] · Lecture ref L2.5, L2.7 · Priority 🟡 Medium
> **Asked as:** purpose of cookies, problems from cookies, precautions against cookies (2017/18 Q6(b)(i)–(iii)).

## Why we need them
[[02.04 HTTP Protocol|HTTP is stateless]]: the server forgets you after every request. Sessions and cookies are the main ways a website **remembers** who you are and what you did, for example that you are logged in or what is in your shopping cart.

---

## Part A: Sessions

### What is a session?
A **session** is **"a series of related browser requests that come from the same client during a certain time period."**
*Example:* from the moment you log in to an online store until you log out, all your clicks belong to one session. The **server** stores the session data (who you are, what is in your cart).

### Session management
- A **key part of tuning a web application for best performance**.
- **Factors to consider** (lecture):
  1. **Session length**
  2. **Expected number of users** hitting the server (the slide says "servlet")
  3. **Expected amount of data to store for each user**
  4. **Heap size** allocated to the server instance (the memory available)

Why? Every active session uses server memory. Many users × lots of data × long sessions can run the server out of memory.

### Session timeout
- You can **specify an interval of time after which HTTP sessions expire**.
- **When a session expires, all data stored in the session is discarded.**
- *Practical example:* online banking logs you out after a few minutes of inactivity. This protects you if you leave a shared computer.

## Part B: Cookies

### What is a cookie?
A **cookie** is:
- **"A small piece of text stored on a web browser"**;
- made of **one or more name–value pairs** containing bits of information such as **user preferences** (e.g. `theme=dark`);
- **"sent as an HTTP header by a web server to a web browser and then sent back unchanged by the browser each time it accesses that server."**

### How a cookie travels

```text
1. Browser ──GET /index.php──────────────────────────► Server
2. Browser ◄──Response + header:  Set-Cookie: lang=si ─ Server   (browser stores it)
3. Browser ──GET /products.php + header: Cookie: lang=si ──► Server  (sent back unchanged)
4. Server reads lang=si → shows the page in Sinhala
```

### Setting a cookie in PHP

> [!note]
> The lecture slide "Setting a cookie" is an image. This standard PHP example illustrates it.

```php
<?php
// name, value, expiry time (now + 30 days), path
setcookie("user", "Kasun", time() + (86400 * 30), "/");
?>
<html><body>
<?php
if (isset($_COOKIE["user"])) {
    echo "Welcome back, " . $_COOKIE["user"];
} else {
    echo "Cookie not set";
}
?>
</body></html>
```

- `setcookie()` must be called **before any HTML output**, because it sends an HTTP **header**.
- `$_COOKIE["user"]` reads the cookie that the browser sends back on later visits.

### What cookies are used for (lecture)
1. **Authenticating:** keeping you logged in.
2. **Session tracking:** linking your requests together (e.g. a session ID cookie, shopping cart).
3. **Remembering specific information** about users (preferences such as language and theme).

### Cookie expiration: when a cookie is *not* sent any more (lecture)
1. **At the end of the user session** (when the browser is shut down) **if the cookie is not persistent**.
2. **An expiration date has been specified and has passed**.
3. **The expiration date has been changed** (by the server or script) **to a date in the past**.
4. **The user deletes the cookie**.

## Part C: Session vs Cookie

| | Session | Cookie |
|---|---|---|
| Stored on | **Server** | **Client (browser)** |
| Capacity | Can hold more data | Small text only |
| Security | Safer (the user cannot see or edit it) | Can be read or modified on the client |
| Lifetime | Ends at logout or **timeout** | Until the browser closes (non-persistent) or the **expiry date** |
| Link | The server usually identifies the session through a **session-ID cookie** | |

> This comparison table is a synthesis. The lecture defines each term separately.

## Part D: Problems with cookies and precautions (2017/18 Q6(b))

**Problems:**
- **Privacy / tracking:** third-party **tracking cookies** record browsing history and preferences, a form of spyware ([[13.06 Spyware]]).
- **Session hijacking:** a stolen session cookie (e.g. through [[13.07 Cross-Site Scripting (XSS)|XSS]]) lets an attacker impersonate you.
- **Cookie poisoning:** attackers modify cookie values to inject SQL ([[13.03 SQL Injection]]).
- **Shared computers:** the next user may be logged in as you; plain-text cookies can expose data.

**Precautions (users):** delete cookies regularly or clear them on exit; use private browsing on shared computers and log out; block third-party cookies; accept only necessary cookies in consent banners ([[10.10 GDPR]]); use HTTPS sites; keep the browser updated; use anti-spyware.

**Precautions (developers):** set the `Secure`, `HttpOnly` and `SameSite` flags; use short expiry; never store passwords in cookies.

> [!warning]
> The problems and precautions are not on the cookie slides. They link this lesson to Lesson 13 (spyware, SQLi) and Lesson 12 (privacy and consent), as the study guide does.

## Exam-relevant points
- Cookie = **small text, name–value pairs, sent as HTTP header, returned unchanged**; uses = **authentication, session tracking, remembering information**.
- Four **expiry conditions**.
- Session = **related requests from the same client over a time period**; four **management factors**; **timeout discards the data**.
