# 05.07 · The IP Protocol: IPv4 Datagram Header

> [!info] [[05.00 Network Layer|Lesson 5]] · Lecture ref Ch5-L2 slides 1–7 · Priority 🟢 Low (not asked in the six papers, but core lecture content)

## 1. Structure
- *"An IPv4 datagram consists of a **header** part and a **body or payload** part."*
- *"The header has a **20-byte fixed part** and a **variable-length optional part**."*
- Bits are transmitted **left to right, top to bottom**, high-order bit of Version first.

```text
0       4       8               16                              31
+-------+-------+---------------+-------------------------------+
|Version|  IHL  |Type of service|          Total length         |
+-------+-------+---------------+---+---+---+-------------------+
|        Identification         |   |DF |MF |  Fragment offset  |
+---------------+---------------+---+---+---+-------------------+
|  Time to live |   Protocol    |        Header checksum        |
+---------------+---------------+-------------------------------+
|                         Source address                        |
+---------------------------------------------------------------+
|                      Destination address                      |
+---------------------------------------------------------------+
|                Options (0 or more 32-bit words)               |
+---------------------------------------------------------------+
```

## 2. Fields (lecture)
| Field | Purpose |
|---|---|
| **Version** | Which version of the protocol the datagram belongs to (4) |
| **IHL** (Internet Header Length) | Header length is not constant, so IHL tells **how long the header is, in 32-bit words** (min 5 = 20 bytes) |
| **Type of service** | Top 6 bits mark the packet with its **service class** (priority, e.g. voice) |
| **Total length** | Everything in the datagram (header + data); **max 65,535 bytes** |
| **Identification** | Lets the destination tell **which packet a newly arrived fragment belongs to**; all fragments of a packet share it |
| **DF** (Don't Fragment) | Order to routers **not to fragment** the packet |
| **MF** (More Fragments) | Set on **all fragments except the last**, so the receiver knows when all have arrived |
| **Fragment offset** | Where in the original packet this fragment belongs |
| **TtL** (Time to live) | **Counter limiting packet lifetime**; decremented at each hop, packet discarded at 0 (stops looping packets; compare flooding's hop counter) |
| **Protocol** | Which **transport process** to give the packet to: **TCP, UDP** or others |
| **Header checksum** | Verifies the header only *(textbook detail)*; recomputed at each hop since TTL changes |
| **Source / Destination address** | IP addresses of the source and destination **network interfaces** |
| **Options** | *"An escape to allow subsequent versions… to include information not present in the original design, to permit experimenters to try out new ideas, and to avoid allocating header bits to information that is rarely needed."* Examples (lecture table): security, strict/loose source routing, record route, timestamp |

## 3. Fragmentation step by step *(how the fields work together)*
1. A router must forward a 4,000-byte packet onto a link whose maximum size is 1,500 bytes, and **DF = 0**.
2. It splits the data into fragments, each with a copy of the header and the **same Identification**.
3. Every fragment except the last has **MF = 1**; each carries its **Fragment offset**.
4. The destination host collects fragments with the same Identification, orders them by offset, and **reassembles** the packet when the fragment with **MF = 0** and all earlier pieces have arrived.
(If DF = 1 and the packet is too big, the router discards it instead.) This solves the layer design issue of **message size** ([[01.12 Design Issues for the Layers]]).

## IPv4 vs IPv6 *(comparison requested in the study brief; IPv6 is not in the CMIS 3114 slides)*
| IPv4 | IPv6 |
|---|---|
| **32-bit** addresses (~4.3 billion) | **128-bit** addresses (practically unlimited) |
| Dotted decimal: 192.168.1.10 | Hexadecimal with colons: 2001:db8::1 |
| Variable header (20 B + options), header checksum | Fixed 40-byte header, no header checksum |
| Routers may fragment | Only the source fragments |
| NAT widely needed | No NAT needed; better for IoT |
