# 03.02 · Framing: Byte Count, Byte Stuffing, Bit Stuffing, Coding Violations

> [!info] [[03.00 Data Link Layer|Lesson 3]] · Lecture ref Ch3-L1 slides 11–21 · Priority 🔴 High (**every paper** has a framing question)
> **Asked as:**
> - Byte count: "Explain how the following character frames are to be transmitted using the Byte Count method: ABCD / EFG / HIJKLM" + "Is it possible to recover from a transmission error?" (2019/20 Q6b,c) · "Describe with an example the Byte-count technique… Explain the major disadvantage… using the same example. Propose a method to overcome the disadvantage" (2021/22 Q5b, 2023/24 Q5c)
> - Byte stuffing: "… A B ESC C ESC FLAG FLAG D … What is the output after byte stuffing?" (2018/19 Q5c) · "Explain the Byte stuffing framing technique using the special bit patterns called Flag and escape" (2020/21 Q5b, 2022/23 Q5d)
> - Bit stuffing: "What is the string actually transmitted after bit stuffing? String: 0111101111101111110" (2023/24 Q5b)

## 1. Why framing?
*"The bit stream received by the data link layer from the physical layer is **not guaranteed to be error free**. Bits may have different values and the number of bits received may be less than, equal to, or more than the number transmitted."*

**Solution:** the DLL **breaks the bit stream into discrete frames**, computes a short token called a **checksum** for each frame, and includes it in the frame. At the destination the checksum is **recomputed**; if it differs, an error occurred and the DLL acts (e.g. **discards the bad frame** and possibly sends back an error report).

**The hard part:** the receiver must find **where each frame starts and ends**. The lecture gives four methods.

## 2. Method 1: Byte count
*"Use a field in the header to specify the **number of bytes in the frame**. When the data link layer at the destination sees the byte count, it knows how many bytes follow and hence where the end of the frame is."* The count **includes the count byte itself**.

Lecture example (a): `5 1 2 3 4 | 5 6 7 8 9 | 8 0 1 2 3 4 5 6 | 8 7 8 9 0 1 2 3` → frames of 5, 5, 8, 8 characters.

### Worked: ABCD / EFG / HIJKLM (2019/20 Q6b)
Frame length = number of characters + 1 (for the count byte):

```text
 ┌───┬───┬───┬───┬───┐┌───┬───┬───┬───┐┌───┬───┬───┬───┬───┬───┬───┐
 │ 5 │ A │ B │ C │ D ││ 4 │ E │ F │ G ││ 7 │ H │ I │ J │ K │ L │ M │
 └───┴───┴───┴───┴───┘└───┴───┴───┴───┘└───┴───┴───┴───┴───┴───┴───┘
      Frame 1 (5)        Frame 2 (4)            Frame 3 (7)
 Transmitted stream:  5 A B C D 4 E F G 7 H I J K L M
```

### The disadvantage: cannot resynchronise after an error
If the **count byte itself is corrupted**, the receiver loses track of frame boundaries **permanently**.
- Lecture example (b): the second count 5 is garbled into 7 → the receiver takes 7 characters as frame 2 (**wrong**), then reads a data byte as the next count, and every later frame is wrong.
- Same example as above (what 2021/22 and 2023/24 ask for): suppose the count **4** of frame 2 is corrupted to **6**:
```text
 Sent:      5 A B C D | 4 E F G | 7 H I J K L M
 Received:  5 A B C D | 6 E F G 7 H | I J K L M …
                         frame 2 (wrong: 6 bytes)  then "I" is read as a count → garbage
```
- Even if the checksum shows frame 2 is bad, the receiver **cannot tell where the next frame starts**. Asking for retransmission does not help because it does not know how many bytes to skip.
- **Answer to 2019/20 Q6(c): No.** Byte count **cannot recover** (resynchronise) from an error in the count field.

**Fix:** use a method with **unique start/end markers**: **flag bytes with byte stuffing** or **flag bits with bit stuffing**, so the receiver can always **search for the next flag** to resynchronise.

## 3. Method 2: Flag bytes with byte stuffing
- *"To enable resynchronization, each frame **starts and ends with special bytes**,"* usually the same byte, the **FLAG** byte, used as both start and end delimiter.

```text
 ┌──────┬────────┬───────────────────┬─────────┬──────┐
 │ FLAG │ Header │   Payload field   │ Trailer │ FLAG │
 └──────┴────────┴───────────────────┴─────────┴──────┘
```
- *"**Two consecutive flag bytes** indicate the end of one frame and the start of the next."* If the receiver loses synchronisation, *"it can just search for two flag bytes to find the end of the current frame and the start of the next frame."*

**Problem:** what if the FLAG byte pattern occurs **inside the data** (e.g. in a photo or binary file)?

**Byte stuffing rule:**
1. The sender inserts a special **escape byte (ESC)** just **before each "accidental" FLAG** in the data.
2. If an **ESC** occurs in the data, it is **also stuffed with an ESC**.
3. The receiver **removes the escape bytes** (a byte after an ESC is taken as data) before giving the data to the network layer.

### Lecture examples (four cases)
| Original | After stuffing |
|---|---|
| A FLAG B | A **ESC** FLAG B |
| A ESC B | A **ESC** ESC B |
| A ESC FLAG B | A **ESC** ESC **ESC** FLAG B |
| A ESC ESC B | A **ESC** ESC **ESC** ESC B |

*"However stuffing bytes **wastes bandwidth**."*

### Worked: 2018/19 Q5(c)
Input fragment: `A B ESC C ESC FLAG FLAG D`
Go byte by byte; put an ESC before every ESC and every FLAG:

| Input | A | B | ESC | C | ESC | FLAG | FLAG | D |
|---|---|---|---|---|---|---|---|---|
| Output | A | B | **ESC** ESC | C | **ESC** ESC | **ESC** FLAG | **ESC** FLAG | D |

**Output:** `A B ESC ESC C ESC ESC ESC FLAG ESC FLAG D` (8 bytes → 12 bytes). In the complete frame this sits between a starting FLAG and an ending FLAG.

## 4. Method 3: Flag bits with bit stuffing
- Framing at the **bit level**, so frames can contain **any number of bits**.
- Each frame begins and ends with the flag pattern **01111110** (0x7E).
- **Bit stuffing:** *"Whenever the sender's data link layer encounters **five consecutive 1s** in the data, it automatically **stuffs a 0 bit** into the outgoing bit stream."* The receiver **deletes the 0 that follows five 1s** (destuffing).
- So six 1s in a row can **only** occur in a flag → *"the boundary between two frames can be unambiguously recognized by the flag pattern."* If the receiver loses track, it just scans for flags. **USB** uses bit stuffing.

Lecture example:
```text
(a) original:            011011111111111111110010
(b) on the line:         011011111011111011111010010    (three stuffed 0s)
(c) after destuffing:    011011111111111111110010
```

### Worked: 2023/24 Q5(b)
String: **0111101111101111110** (19 bits). Count the 1s; after **every fifth consecutive 1, insert a 0** (the count restarts after the stuffed 0 or any real 0):

```text
 Input:   0 1111 0 11111   0 11111   1 0
 Output:  0 1111 0 11111 0 0 11111 0 1 0
                          ▲          ▲   stuffed bits
```
Step through: `0` · `1111` (four 1s, no stuff) · `0` · `11111` → **stuff 0** · `0` · `11111` → **stuff 0** · `1` · `0`.

**Transmitted string (before adding flags):** `011110111110011111010` (21 bits, **2 stuffed zeros**). With flags: `01111110 011110111110011111010 01111110`.

> [!warning] Check the digits
> The 2023/24 paper's string is **0111101111101111110** (19 digits: the last run is six 1s). The older note [[3114 Topic Map & Past Papers]] lists it with an extra 1 (20 digits); the paper scan confirms 19.

## 5. Method 4: Physical layer coding violations
- Use **reserved signals** (that never occur in normal data) to mark the start and end of frames. Because they are reserved, frames are easy to find and **no stuffing is needed**.
- Many protocols **combine methods** for safety. Ethernet and 802.11 start a frame with a long **preamble** (72 bits is typical for 802.11) so the receiver can prepare, followed by a **length (count) field** in the header to find the end.

## 6. Comparison

| Method | Marker | Overhead | Recovers after error? | Used in |
|---|---|---|---|---|
| Byte count | Count field in header | 1 byte/frame | **No** | (historic) |
| Flag bytes + byte stuffing | FLAG byte; ESC stuffing | Stuffed bytes (bandwidth waste) | **Yes** (search for flags) | PPP |
| Flag bits + bit stuffing | 01111110; stuff 0 after five 1s | Few bits; frames of any bit length | **Yes** | HDLC, **USB** |
| Coding violations | Reserved signals | None (no stuffing) | Yes | Ethernet/802.11 (with preamble + length) |
