# 03.03 · Error Control and Flow Control

> [!info] [[03.00 Data Link Layer|Lesson 3]] · Lecture ref Ch3-L1 slides 22–23 · Priority 🟡 Medium (the ideas behind every protocol question)

## 1. Error control
For **unacknowledged connectionless** service the sender may just keep sending without checking. But for **reliable, connection-oriented** service that is *"not fine at all."* The lecture's tools:

| Tool | Why it is needed |
|---|---|
| **Positive / negative acknowledgements (+/− ACKs)** | Receiver tells the sender a frame arrived correctly (ACK) or was damaged (NAK) |
| **Timers at the sender** | If a frame (or its ACK) is **lost completely**, no ACK will ever arrive; the timer expires and the sender **retransmits** |
| **Sequence numbers for frames** | A retransmission could deliver a frame **twice**; numbers let the receiver **discard duplicates** |
| **Goal** | *"Each frame must be passed to the network layer at the destination **exactly once**, no more and no less."* |

**Step by step (stop-and-wait style):**
1. Sender sends frame 0 and **starts a timer**.
2. Receiver checks the checksum; if correct, passes frame 0 up and sends **ACK 0**.
3. If the ACK arrives before the timer expires, the sender sends frame 1.
4. If the frame or the ACK is lost, the **timer expires** and the sender **retransmits** frame 0.
5. If the receiver gets frame 0 again (because the ACK was lost), it sees the **same sequence number**, **discards the duplicate**, and re-sends the ACK.

## 2. Flow control
**Problem:** *"a sender that systematically wants to transmit frames **faster than the receiver can accept them**."* (A fast server sending to a slow phone: the receiver's buffers overflow and frames are lost.)

| Approach | How it works (lecture) | Typical layer |
|---|---|---|
| **Feedback-based flow control** | *"The receiver sends back information to the sender giving it **permission to send more** data, or at least telling the sender how the receiver is doing."* | Data link layer, TCP (window advertisements) |
| **Rate-based flow control** | *"The protocol has a **built-in mechanism that limits the rate** at which senders may transmit data, **without using feedback** from the receiver."* | Rarely in DLL; some transport protocols |

Sliding window protocols ([[03.09 Sliding Window and Go-Back-N]]) combine **error control and feedback-based flow control**: the receiver's ACKs both confirm frames and allow the sender to send more.

## 3. Flow control vs congestion control *(comparison requested in the study brief; congestion control is outside the Ch1–5 slides)*

| Flow control | Congestion control |
|---|---|
| Protects the **receiver** from a fast sender | Protects the **network** (routers/links) from too much traffic |
| **Point-to-point** between one sender and one receiver | **Global**: involves all hosts and routers |
| Receiver feedback (window size) | Network signals: packet loss, delay; sender reduces rate |
| DLL and transport (TCP window) | Network layer (OSI lists "congestion" as a network-layer job) and TCP |

See [[06.03 TCP Flow Control and Congestion Control]] for TCP's mechanisms (textbook material).
