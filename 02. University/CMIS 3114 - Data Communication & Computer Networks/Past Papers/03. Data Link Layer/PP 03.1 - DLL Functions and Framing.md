## A. Functions / responsibilities of the DLL

> **2019/20 Q6(a), 2022/23 Q5(a):** Describe two main functions of the Data Link Layer of the OSI reference model.
> **2023/24 Q5(a):** Describe two main responsibilities of the Data Link Layer of the OSI reference model.

### Expected answer (any two, well explained)
1. **Providing a service interface to the network layer / framing:** the DLL takes packets from the network layer and **encapsulates them into frames** (header + payload + trailer) for transmission, delivering them to the network layer on the neighbouring machine.
2. **Dealing with transmission errors (error control):** a **checksum** in each frame lets the receiver detect damaged frames; with **acknowledgements, timers and sequence numbers** lost or duplicated frames are handled so each frame is delivered **exactly once**. Turns the raw line into one that *"appears free of undetected transmission errors."*
3. **Regulating data flow (flow control):** prevents a **fast sender from swamping a slow receiver** (feedback-based or rate-based).
(Also: **medium access control** on shared channels: the MAC sublayer.)

## B. Services provided to the network layer

> **2020/21 Q5(a):** Describe two services provided to the Network layer by the Data link layer
> **2021/22 Q5(a):** Describe two services provided to the Network layer by the Data link layer of the OSI reference model.

### Expected answer (any two)
1. **Unacknowledged connectionless service** (e.g. **Ethernet**): no connection, no acknowledgements; lost frames are not detected or recovered at the DLL. Suitable when the **error rate is very low** and for **real-time traffic (voice)**, where late data is worse than bad data.
2. **Acknowledged connectionless service** (e.g. **802.11 WiFi**): no connection, but **each frame is individually acknowledged**; if not acknowledged within a time limit it is **resent**. Suitable for **unreliable wireless** channels.
3. **Acknowledged connection-oriented service** (e.g. **satellite / long-distance telephone circuits**): three phases: **establish** the connection (initialise counters), **transfer numbered frames**, **release**. Guarantees each frame is received **exactly once and in order**. Suitable for long, unreliable links.

## C. Byte count

> **2019/20 Q6(b):** Explain how the following character frames are to be transmitted using the Byte Count method. [ABCD / EFG / HIJKLM]
> **2019/20 Q6(c):** Is it possible to recover from a transmission error in the above technique? Explain your answer.
> **2021/22 Q5(b):** Describe with an example, the Byte-count technique in the data link layer. Explain the major disadvantage of this technique using the same example. Propose a method to overcome the disadvantage.
> **2023/24 Q5(c):** Using an example describe the Byte-count technique in the data link layer. Explain the major disadvantage of this technique using the same example. Propose a method to overcome the disadvantage.

### Expected answer
A field in the **header** gives the **number of bytes in the frame** (including the count byte), so the receiver knows where the frame ends.

**Frames ABCD, EFG, HIJKLM:**
```text
 | 5 | A | B | C | D | 4 | E | F | G | 7 | H | I | J | K | L | M |
   └─ frame 1 (5) ─┘   └ frame 2 (4)┘   └──── frame 3 (7) ────┘
 Transmitted: 5 A B C D 4 E F G 7 H I J K L M
```

**Disadvantage (same example):** if the **count is corrupted**, the receiver **loses synchronisation** and cannot find the start of later frames. E.g. the second count 4 is changed to 6:
```text
 Received: 5 A B C D | 6 E F G 7 H | I J K L M …
 Frame 2 is read as 6 bytes "6 E F G 7 H" (wrong), then "I" is taken as the next count → all later frames are wrong.
```
Even if the checksum detects the bad frame, the receiver **does not know how many bytes to skip** to reach the next frame start, so retransmission doesn't help. **Answer to 2019/20 Q6(c): No**: byte count cannot recover (re-synchronise) after an error in the count.

**Fix:** use **flag bytes with byte stuffing** (each frame starts and ends with a FLAG; the receiver searches for the next FLAG to resynchronise) or **flag bits with bit stuffing** (01111110), or combine a preamble with the length field.

## D. Byte stuffing

> **2018/19 Q5(c):** The following data fragment occurs in the middle of a data stream for which the byte-stuffing algorithm is used: … A B ESC C ESC FLAG FLAG D … What is the output after byte stuffing?
> **2020/21 Q5(b), 2022/23 Q5(d):** Explain the Byte stuffing framing technique using the special bit patterns called Flag and escape.

### Expected answer: explanation
- Each frame **starts and ends with a special FLAG byte**; two consecutive FLAGs mark the end of one frame and the start of the next, so a receiver that loses synchronisation just **searches for FLAG bytes**.
- If a FLAG byte occurs **in the data**, the sender inserts an **ESC (escape) byte before it**; if an **ESC** occurs in the data it is also preceded by an ESC.
- The receiver **removes each ESC** and treats the following byte as ordinary data.
- Examples: `A FLAG B → A ESC FLAG B`; `A ESC B → A ESC ESC B`; `A ESC FLAG B → A ESC ESC ESC FLAG B`; `A ESC ESC B → A ESC ESC ESC ESC B`.
- Disadvantage: stuffing **wastes bandwidth**; tied to 8-bit bytes.
```text
 | FLAG | Header |  Payload (stuffed)  | Trailer | FLAG |
```

### Solution: 2018/19 Q5(c)
Go byte by byte; put an **ESC before every ESC and every FLAG** in the data:

| In | A | B | ESC | C | ESC | FLAG | FLAG | D |
|---|---|---|---|---|---|---|---|---|
| Out | A | B | **ESC** ESC | C | **ESC** ESC | **ESC** FLAG | **ESC** FLAG | D |

Output sequence (8 bytes → 12 bytes; inside the frame it sits between the start and end FLAGs):
**`A B ESC ESC C ESC ESC ESC FLAG ESC FLAG D`**

## E. Bit stuffing

> **2023/24 Q5(b):** The following bit string needs to be transmitted at the datalink layer. What is the string actually transmitted after bit stuffing? String: 0111101111101111110

### Solution
Rule: frames are delimited by **01111110**; whenever the sender sees **five consecutive 1s in the data**, it **inserts a 0**.
```text
 Data:    0 1111 0 11111   0 11111   1 0
                        ↓          ↓
 Sent:    0 1111 0 11111 0 0 11111 0 1 0
```
- `0` · `1111` (four 1s, no stuffing) · `0` · `11111` → **insert 0** · `0` · `11111` → **insert 0** · `1` · `0`.

**Transmitted: `011110111110011111010`** (19 → 21 bits; 2 stuffed bits). With flags: `01111110 011110111110011111010 01111110`. The receiver deletes the 0 after every five consecutive 1s.

> [!warning] Read the string carefully
> The paper's string has **19 digits** (the last group is six 1s). An older note in the vault lists 20 digits; the scan confirms 19.
