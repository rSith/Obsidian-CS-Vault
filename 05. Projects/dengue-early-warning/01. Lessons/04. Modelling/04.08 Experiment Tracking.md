# 04.08 · Experiment Tracking

> [!info] [[04.00 Modelling|Lesson 4]] · Roadmap Phase 4 · Priority 🟡 Supporting
> **Builds on:** [[Machine Learning in Production]]
> **Used for:** the single results table that shows every model you tried and how each scored.

## 1. Definition
> [!note] Experiment tracking
> **Experiment tracking** is recording, for every model you train, **what you ran** (code, data, settings) and **what you got** (scores), so that any result can be found, compared and reproduced later.

## 2. Why it is used
After two weeks of modelling you will have trained dozens of models. Without a record you cannot answer:
- Which settings gave the best score?
- Did adding humidity help, or was that the run where I also changed the split?
- Can I produce that result again for the report?

A model whose result you cannot reproduce is not a result.

## 3. What to record
| Field | Why |
|---|---|
| Date and time | Order of events |
| Git commit | The exact code |
| Data version | Which download, which date range |
| Feature set | A name such as "weather + cases" |
| Model and settings | `ridge`, `alpha=10` |
| Split | Which weeks were validation |
| Horizon | 4, 6 or 8 weeks |
| Scores | Validation MAE, and skill against each baseline |
| Notes | Why you ran it, what you noticed |

## 4. Syntax: a CSV log
Enough for the first ten or twenty runs.
```python
import csv
import subprocess
from datetime import datetime
from pathlib import Path

LOG = Path("reports/experiments.csv")

def log_run(model: str, features: str, params: dict, horizon: int,
            val_mae: float, notes: str = "") -> None:
    commit = subprocess.run(["git", "rev-parse", "--short", "HEAD"],
                            capture_output=True, text=True).stdout.strip()
    row = {"time": datetime.now().isoformat(timespec="seconds"), "commit": commit,
           "model": model, "features": features, "params": str(params),
           "horizon": horizon, "val_mae": round(val_mae, 2), "notes": notes}
    is_new = not LOG.exists()
    with LOG.open("a", newline="") as f:
        writer = csv.DictWriter(f, fieldnames=list(row))
        if is_new:
            writer.writeheader()
        writer.writerow(row)

log_run("ridge", "weather+cases", {"alpha": 10}, horizon=4, val_mae=44.0,
        notes="first model with rolling rainfall")
```
Commit your code **before** a run, so the logged commit matches the code that produced the number.

## 5. Syntax: MLflow
MLflow is a tool that does the same job with a web page for comparing runs.
```python
import mlflow

mlflow.set_experiment("dengue-h4")

with mlflow.start_run(run_name="ridge-weather-cases"):
    mlflow.log_params({"model": "ridge", "alpha": 10, "features": "weather+cases"})
    mlflow.log_metric("val_mae", 44.0)
    mlflow.sklearn.log_model(model, "model")      # saves the fitted pipeline too
```
```powershell
mlflow ui        # then open http://127.0.0.1:5000
```
It writes to a local `mlruns/` folder, which is already in this project's `.gitignore`.

| | CSV log | MLflow |
|---|---|---|
| Setup | None | One install |
| Compare runs | Open the file, sort | Web page with sorting and charts |
| Stores the model | No | Yes |
| Use when | Fewer than about 20 runs | More runs, or you want a model registry later |

## 6. Example: what the table lets you say
| time | model | features | params | val_mae |
|---|---|---|---|---|
| 12 Jan | persistence | | | 52.0 |
| 12 Jan | seasonal | | | 61.0 |
| 14 Jan | ridge | weather | alpha=10 | 58.5 |
| 14 Jan | ridge | weather+cases | alpha=10 | 44.0 |
| 18 Jan | hist_gb | weather+cases | lr=0.05, iter=400 | 39.0 |
| 18 Jan | hist_gb | cases only | lr=0.05, iter=400 | 41.5 |

From this table you can write two findings: *"Adding past cases to weather cut the error from 58.5 to 44.0"*, and *"Weather features improved the best model from 41.5 to 39.0, about 6 %."* The second comparison, the same model with and without weather, is the heart of the report. The numbers are invented.

## 7. Making runs reproducible
- **Fix random seeds:** `random_state=42` in every model that has one.
- **Pin package versions** in `requirements.txt`.
- **Never edit raw data.**
- **Change one thing per run.** If two things change, you cannot tell which one mattered.

## 8. Common mistakes
- **"I'll remember."** Nobody does.
- **Logging only the good runs.** The failures show what does not work, and make the report honest.
- **Changing several things at once.**
- **Logging the test score for every run.** Track validation scores; the test score is recorded once, at the end.
- **Uncommitted code.** The logged commit then points to different code.
- **Keeping results only in notebook output cells,** which vanish when the notebook is re-run.

## 9. Exam and viva focus
- **Define** experiment tracking and say what is recorded: code version, data version, hyperparameters, metrics, artefacts.
- **Reproducibility:** the ability to get the same result again from the same code, data and settings.
- **Ablation study:** removing one part (such as the weather features) to measure what it contributes.
- **Hyperparameter vs parameter.**
- **Why log failed experiments?** To avoid repeating them and to report honestly.
