# 06.05 · REST API Design and Status Codes

> [!info] [[06.00 Database and Flask API|Lesson 6]] · Roadmap Phase 6 · Priority 🟡 Supporting
> **Builds on:** [[02.04 HTTP Protocol]] · [[02.07 Web Services, XML and JSON]]. Those notes explain HTTP itself; this one is about **designing** an API that others can use without asking you questions.

## 1. Definition
> [!note] REST
> **REST** (Representational State Transfer) is a style for designing web APIs. Data is organised as **resources**, each with its own URL, and the standard HTTP methods say what to do with them.

> [!note] Resource
> A **resource** is a thing the API exposes: a district, a set of forecasts, the latest alerts.

## 2. Why it is used
An API is a promise to its clients. If it follows conventions, a front-end developer (you, in Lesson 7) can guess how it behaves. If every endpoint is shaped differently, each one must be studied separately and mistakes are easy.

## 3. How it works: the principles
| Principle | Meaning |
|---|---|
| **Client–server** | The dashboard and the API are separate programs that talk only through HTTP |
| **Stateless** | Each request carries everything the server needs. The server remembers nothing about earlier requests. |
| **Uniform interface** | Resources are **nouns** in the URL; the HTTP method is the **verb** |
| **Representation** | The client receives a representation of the resource, here JSON |
| **Cacheable** | Responses can say whether they may be stored and reused |

### Methods
| Method | Purpose | Safe (changes nothing) | Idempotent (repeating gives the same result) |
|---|---|---|---|
| `GET` | Read | ✅ | ✅ |
| `POST` | Create | ❌ | ❌ |
| `PUT` | Replace | ❌ | ✅ |
| `PATCH` | Change part | ❌ | Not guaranteed |
| `DELETE` | Remove | ❌ | ✅ |

This project's API is read-only, so every endpoint is a `GET`.

### Status codes for your own API
| Code | Name | Send it when |
|---|---|---|
| `200` | OK | The request worked |
| `201` | Created | A `POST` made a new resource |
| `204` | No Content | It worked and there is nothing to return |
| `400` | Bad Request | A parameter is missing or malformed |
| `401` | Unauthorized | The client has not identified itself |
| `403` | Forbidden | The client is known but not allowed |
| `404` | Not Found | The resource does not exist (unknown district) |
| `405` | Method Not Allowed | For example a `POST` to a read-only URL |
| `429` | Too Many Requests | The client is calling too often |
| `500` | Internal Server Error | A bug in your code |
| `503` | Service Unavailable | The database is down |

**4xx means the client made a mistake. 5xx means the server did.**

## 4. Design rules, with this project's endpoints
| Rule | Do | Avoid |
|---|---|---|
| Nouns, in the plural | `/api/districts` | `/api/getDistricts` |
| Filter with query parameters | `/api/predictions?district=Colombo` | `/api/predictionsForColombo` |
| Lower case, hyphens | `/api/alerts/latest` | `/api/Alerts_Latest` |
| A version in the path once others depend on it | `/api/v1/districts` | Changing fields without warning |
| The same field names everywhere | `week_start` in every response | `week_start` here, `weekStart` there |
| Dates in ISO 8601 | `"2026-11-07"` | `"07/11/26"` |
| Units stated | `"unit": "reported cases per week"` | A bare number |

## 5. Example: one good response and one good error
```http
GET /api/predictions?district=Colombo
```
```json
{
  "district": "Colombo",
  "unit": "reported cases per week",
  "last_updated": "2026-10-10",
  "forecasts": [
    {
      "week_start": "2026-11-07",
      "horizon_weeks": 4,
      "predicted_cases": 262.0,
      "lower": 180.0,
      "upper": 390.0,
      "alert_level": "Watch",
      "model_version": "v1"
    }
  ]
}
```
```http
GET /api/predictions?district=Nowhere      →   404 Not Found
```
```json
{ "error": { "code": "unknown_district", "message": "No district named 'Nowhere'." } }
```
The error has a stable `code` for programs and a `message` for people. Every error from the API uses this same shape.

## 6. Documenting the API
For each endpoint the README needs five things:
1. method and URL;
2. parameters, and which are required;
3. an example request;
4. an example response;
5. the errors it can return.

If a reader can call the API correctly from the README alone, the documentation is complete.

## 7. Common mistakes
- **Verbs in URLs** (`/getAlerts`). The method is the verb.
- **`200 OK` with an error in the body.**
- **`500` for a mistake by the client.** A missing parameter is `400`.
- **A different error format on each endpoint.**
- **Renaming or removing a field** that the dashboard uses. Add fields; do not change existing ones.
- **Numbers sent as strings** (`"262.0"`), or dates in a local format.
- **No units.** Is it cases per week, or per 100,000 people?
- **Returning everything.** Thousands of rows nobody asked for. Offer filters.
- **Calling something REST only because it returns JSON.**

## 8. Exam and viva focus
- **Define REST and list its constraints:** client–server, stateless, cacheable, uniform interface, layered system.
- **What does stateless mean?** No client session is kept on the server between requests.
- **Safe vs idempotent methods;** classify `GET`, `POST`, `PUT`, `DELETE`.
- **`PUT` vs `POST`;** **`PUT` vs `PATCH`.**
- **Status code classes** and the meaning of 200, 201, 400, 401, 403, 404, 500.
- **`401` vs `403`:** not identified vs identified but not permitted.
- **REST vs SOAP:** REST uses plain HTTP and usually JSON and is lightweight; SOAP is a protocol with XML messages and strict contracts.
