# 06.02 · SQL Joins, Aggregation and Indexes

> [!info] [[06.00 Database and Flask API|Lesson 6]] · Roadmap Phase 6 · Priority 🔴 Core
> **Course link:** [[CMIS 3153 Course Home]]
> **Used for:** the queries behind every API endpoint, such as "the latest forecast for each district".

## 1. Definitions
| Term | Meaning |
|---|---|
| **Join** | Combining rows from two tables by matching a column they share |
| **Aggregation** | Turning many rows into one summary value: `SUM`, `AVG`, `COUNT`, `MIN`, `MAX` |
| **`GROUP BY`** | Making one summary row per group |
| **Index** | A separate, sorted structure that lets the database find rows without reading the whole table |

## 2. Why they are used
Normalisation split the data across tables ([[06.01 Relational Schema Design and Normalisation]]). **Joins** put it back together when you ask a question. **Aggregation** answers "how many" and "how much". **Indexes** keep the answers fast as the tables grow.

## 3. Joins
| Join | Keeps |
|---|---|
| `INNER JOIN` | Only rows with a match in **both** tables |
| `LEFT JOIN` | Every row of the left table; unmatched right columns become `NULL` |
| `RIGHT JOIN` | Every row of the right table |
| `FULL OUTER JOIN` | Every row of both (not in MySQL; combine a left and a right join with `UNION`) |

```sql
-- Forecasts beside what really happened.
-- LEFT JOIN: a forecast for a future week has no actual count yet, and must still appear.
SELECT p.week_start, p.predicted_cases, c.cases AS actual_cases
FROM predictions p
LEFT JOIN weekly_cases c
       ON c.district_id = p.district_id AND c.week_start = p.week_start
WHERE p.district_id = 1 AND p.horizon_weeks = 4
ORDER BY p.week_start;
```
These are the same joins as pandas `merge`: [[02.01 Pandas Merge, GroupBy, Resample and Shift]].

## 4. Aggregation
```sql
-- Yearly totals per district, keeping only district-years above 5000 cases
SELECT d.name, YEAR(c.week_start) AS yr, SUM(c.cases) AS total_cases
FROM weekly_cases c
JOIN districts d ON d.id = c.district_id
WHERE c.week_start >= '2015-01-01'          -- filters ROWS, before grouping
GROUP BY d.name, YEAR(c.week_start)
HAVING SUM(c.cases) > 5000                  -- filters GROUPS, after grouping
ORDER BY total_cases DESC;
```

| `WHERE` | `HAVING` |
|---|---|
| Filters rows **before** grouping | Filters groups **after** grouping |
| Cannot use `SUM`, `COUNT`, … | Can use them |

**The order in which a query is carried out** is not the order in which it is written:

```text
FROM / JOIN → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT
```
This explains why a name given in `SELECT` cannot be used in `WHERE`: `WHERE` runs first.

## 5. Example: the latest forecast for each district
This is the query behind `GET /api/alerts/latest`. Two ways to write it.

**With a subquery:**
```sql
SELECT d.name, p.week_start, p.predicted_cases, p.alert_level
FROM predictions p
JOIN districts d ON d.id = p.district_id
WHERE p.horizon_weeks = 4
  AND p.created_at = (SELECT MAX(p2.created_at)
                      FROM predictions p2
                      WHERE p2.district_id = p.district_id
                        AND p2.horizon_weeks = 4);
```
**With a window function** (MySQL 8 and later):
```sql
SELECT name, week_start, predicted_cases, alert_level
FROM (
    SELECT d.name, p.week_start, p.predicted_cases, p.alert_level,
           ROW_NUMBER() OVER (PARTITION BY p.district_id
                              ORDER BY p.created_at DESC) AS rn
    FROM predictions p
    JOIN districts d ON d.id = p.district_id
    WHERE p.horizon_weeks = 4
) ranked
WHERE rn = 1;
```
`ROW_NUMBER()` numbers each district's forecasts from newest to oldest. Keeping `rn = 1` keeps the newest.

## 6. Indexes
Without an index the database reads every row to find the ones you want (a **full table scan**). An index is like the index of a book: a sorted list that points straight to the right place.

```sql
CREATE INDEX idx_predictions_lookup
    ON predictions (district_id, horizon_weeks, created_at);

EXPLAIN SELECT * FROM predictions WHERE district_id = 1 AND horizon_weeks = 4;
```
`EXPLAIN` shows whether the index is used.

| Indexes | |
|---|---|
| **Speed up** | `WHERE`, `JOIN`, `ORDER BY` on the indexed columns |
| **Slow down** | `INSERT`, `UPDATE`, `DELETE`, because the index must be updated too |
| **Cost** | Extra disk space |

- A **primary key is indexed automatically.**
- In a multi-column index the **order matters**. The index above helps a search on `district_id`, or on `district_id` and `horizon_weeks`, but not a search on `created_at` alone. This is the **leftmost-prefix rule**.
- This project's tables are small (tens of thousands of rows). Index the columns your endpoints filter on and no more.

## 7. Common mistakes
- **A join with no `ON` condition.** Every row is paired with every row.
- **`INNER JOIN` where `LEFT JOIN` was needed.** Future forecasts silently disappear from the chart.
- **Filtering the right-hand table in `WHERE` after a `LEFT JOIN`.** It turns the join back into an inner join. Put that condition in `ON`.
- **Selecting a column that is neither grouped nor aggregated.**
- **`WHERE` with an aggregate.** Use `HAVING`.
- **`SELECT *` in the API.** You send columns you do not need, and the output changes when the table changes.
- **A function on an indexed column in `WHERE`**, such as `WHERE YEAR(week_start) = 2025`. The index cannot be used. Write `WHERE week_start >= '2025-01-01' AND week_start < '2026-01-01'`.
- **An index on every column.**

## 8. Exam and viva focus
- **Join types** and what each returns. Be ready to write the result of a small example by hand.
- **`WHERE` vs `HAVING`.**
- **Logical order of execution** of a `SELECT` statement.
- **Aggregate functions:** `COUNT`, `SUM`, `AVG`, `MIN`, `MAX`. `COUNT(*)` counts rows; `COUNT(column)` skips `NULL`.
- **What is an index? One advantage and one disadvantage.**
- **Clustered vs non-clustered index:** the table's rows are stored in the order of the clustered index (the primary key in MySQL's InnoDB); other indexes are separate structures pointing to the rows.
