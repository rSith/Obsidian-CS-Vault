# 06.01 · Relational Schema Design and Normalisation

> [!info] [[06.00 Database and Flask API|Lesson 6]] · Roadmap Phase 6 · Priority 🔴 Core
> **Course link:** [[CMIS 3153 Course Home]]
> **Used for:** the four tables that hold districts, cases, weather and forecasts.

## 1. Definitions
| Term | Meaning |
|---|---|
| **Relational database** | Data stored in tables that are linked to each other by shared values |
| **Schema** | The design: which tables exist, their columns, types and rules |
| **Primary key (PK)** | The column or columns that identify each row uniquely |
| **Composite key** | A primary key made of more than one column |
| **Foreign key (FK)** | A column that points to the primary key of another table |
| **Normalisation** | Organising tables so that **each fact is stored in one place only** |
| **ER diagram** | A drawing of the tables (entities) and the links (relationships) between them |

## 2. Why it is used
Put everything in one wide table and Colombo's population is written on a thousand rows. Then:

| Problem | What goes wrong |
|---|---|
| **Update anomaly** | The population changes; you update 999 rows and miss one. The data now disagrees with itself. |
| **Insert anomaly** | You cannot add a new district until it has at least one week of cases. |
| **Delete anomaly** | Delete a district's case rows and its coordinates vanish too. |

Normalisation removes all three by giving each kind of thing its own table.

## 3. How it works: the normal forms
| Form | Rule | Broken by |
|---|---|---|
| **1NF** | Every cell holds one value; no repeating groups | A column `weeks` holding `"1,2,3"` |
| **2NF** | 1NF, and every non-key column depends on the **whole** key | `population` in a table keyed by `(district_id, week_start)`: it depends on the district only |
| **3NF** | 2NF, and no non-key column depends on **another non-key column** | `province` and `province_capital` both in `districts`: the capital depends on the province |

A common way to remember 3NF: every non-key column must depend on **the key, the whole key, and nothing but the key**.

## 4. The project schema
```text
districts (1) ───────< weekly_cases
    │  └──────────────< weekly_weather
    └─────────────────< predictions            "<" = many rows on this side
```
One district has many weekly rows. This is a **one-to-many** relationship.

```sql
CREATE TABLE districts (
    id          INT AUTO_INCREMENT PRIMARY KEY,
    name        VARCHAR(50)  NOT NULL UNIQUE,
    latitude    DECIMAL(8,5) NOT NULL,
    longitude   DECIMAL(8,5) NOT NULL,
    population  INT          NOT NULL
);

CREATE TABLE weekly_cases (
    district_id INT  NOT NULL,
    week_start  DATE NOT NULL,
    cases       INT  NOT NULL CHECK (cases >= 0),
    PRIMARY KEY (district_id, week_start),                 -- composite key
    FOREIGN KEY (district_id) REFERENCES districts(id)
);

CREATE TABLE weekly_weather (
    district_id INT  NOT NULL,
    week_start  DATE NOT NULL,
    rain_mm     DECIMAL(7,2),
    temp_mean   DECIMAL(5,2),
    humidity    DECIMAL(5,2),
    PRIMARY KEY (district_id, week_start),
    FOREIGN KEY (district_id) REFERENCES districts(id)
);

CREATE TABLE predictions (
    id              BIGINT AUTO_INCREMENT PRIMARY KEY,
    district_id     INT           NOT NULL,
    week_start      DATE          NOT NULL,        -- the week being predicted
    horizon_weeks   TINYINT       NOT NULL,
    predicted_cases DECIMAL(10,2) NOT NULL,
    lower_bound     DECIMAL(10,2),
    upper_bound     DECIMAL(10,2),
    alert_level     ENUM('Normal', 'Watch', 'Warning') NOT NULL,
    model_version   VARCHAR(20)   NOT NULL,
    created_at      DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (district_id) REFERENCES districts(id),
    UNIQUE (district_id, week_start, horizon_weeks, model_version)
);
```

## 5. Example: why each choice was made
| Choice | Reason |
|---|---|
| District name appears only in `districts` | Stored once; other tables use `district_id` |
| `(district_id, week_start)` as the key of the weekly tables | Exactly one row per district per week; a duplicate is rejected by the database itself |
| `week_start` is a `DATE`, not year and week numbers | A date is unambiguous: [[01.05 Dates and Epidemiological Weeks]] |
| `CHECK (cases >= 0)`, `NOT NULL` | The database refuses impossible data |
| `predictions` has its own `id` and a `created_at` | The same week is forecast several times as it gets closer; every forecast is kept |
| `model_version` on every prediction | You can always say which model made which forecast: [[08.06 Model Versioning and Retraining]] |
| `UNIQUE (...)` on predictions | Re-running the pipeline cannot insert the same forecast twice |
| `lower_bound`, `upper_bound` instead of `lower`, `upper` | `LOWER` and `UPPER` are SQL function names; avoiding them prevents confusion |
| `alert_level` is stored, not recomputed | It records what the system said at the time, even if thresholds change later |

## 6. Common mistakes
- **One giant table** copied from the CSV.
- **No primary key.** Duplicates creep in and nothing stops them.
- **Storing dates as text.** Sorting and date arithmetic then fail.
- **Storing the district name in every table.** One spelling change breaks the joins.
- **Overwriting a forecast** when a newer one arrives. You lose the ability to check past forecasts against what happened.
- **`FLOAT` for values you compare for equality.** Use `DECIMAL` or integers.
- **Skipping the ER diagram.** Draw it first; changing a diagram is cheaper than changing tables.
- **Over-normalising.** A separate table for alert levels with three fixed values adds joins for no benefit.

## 7. Exam and viva focus
- **Define** primary key, foreign key, composite key, candidate key.
- **Define normalisation** and state its purpose: remove redundancy and the insert, update and delete anomalies.
- **State 1NF, 2NF and 3NF** and give an example that breaks each.
- **Partial dependency vs transitive dependency:** depends on part of a composite key (breaks 2NF) vs depends on another non-key column (breaks 3NF).
- **Relationship types:** one-to-one, one-to-many, many-to-many (which needs a linking table).
- **Referential integrity:** every foreign key value must exist in the table it points to.
- **Draw an ER diagram** for a small scenario.
