# 00.01 · Git Branching and Commit Messages

> [!info] [[00.00 Setup and Domain Knowledge|Lesson 0]] · Roadmap Phase 0 · Priority 🔴 Core
> **Builds on:** [[What is Version Control]] · [[Introduction to GitHub]]
> **Used for:** one branch per phase, and a commit history that proves your progress.

## 1. Definition
> [!note] Branch
> A **branch** is a movable label that points to one commit. Creating a branch gives you a separate line of work, so you can change files without touching the stable version on `main`.

> [!note] Commit message
> A **commit message** is the short text saved with a commit. It tells a future reader what changed and why.

## 2. Why it is used
- The project runs for about six months. You will break things. A branch lets you experiment and throw the experiment away.
- `main` always holds work that runs. Anything half-finished lives on a branch.
- A clear history lets you answer "when did the results change, and what did I change that day?"
- Recruiters and lecturers read commit history. It is evidence that you built the project step by step.

## 3. How it works
Git stores **commits**. Each commit is a snapshot of the project and remembers its parent, so commits form a chain.

```text
main:      A ── B ── C
                      \
phase-1:               D ── E      ← HEAD (you are here)
```

- A **branch** is only a pointer to a commit. Making one is instant and copies no files.
- **HEAD** is the pointer to the branch you are working on now.
- A new commit moves the current branch forward by one.
- **Merge** brings the work of one branch into another.

| Merge type | When it happens | Result |
|---|---|---|
| **Fast-forward** | `main` has no new commits since the branch started | `main` simply moves forward to the branch tip. No extra commit. |
| **Merge commit** | Both branches have new commits | Git makes a new commit with two parents. |
| **Conflict** | Both branches changed the same lines | Git stops. You choose which lines to keep, then commit. |

## 4. Syntax
```bash
git switch -c phase-1-data-collection   # create a branch and move to it
git status                              # what changed?
git add src/collect_weather.py          # stage one file
git commit -m "Add Open-Meteo weather collector"
git log --oneline --graph               # see the history as a graph

git switch main                         # go back to main
git merge phase-1-data-collection       # bring the finished phase in
git branch -d phase-1-data-collection   # delete the merged branch
git push -u origin main                 # send main to GitHub (first time)
```

## 5. Example: one phase from start to finish
1. `git switch -c phase-1-data-collection`
2. Work in small steps. Commit after each one that works:
   - `Add weather collector for one district`
   - `Cache API responses in data/raw`
   - `Loop weather collector over all districts`
3. When the phase checklist is complete: `git switch main`, then `git merge phase-1-data-collection`.
4. `git push`.

### Writing a good commit message
| Rule | Good | Bad |
|---|---|---|
| Start with a verb, as an instruction | `Add lag features for rainfall` | `added stuff` |
| Keep the first line short (about 50 characters) | `Fix week join across year end` | `fixed the bug where the weeks did not match when…` |
| Say what and why, not how | `Drop 2020 from endemic channel (reporting disrupted)` | `changed line 42` |
| One change per commit | `Add pytest for lag features` | `Add tests, fix scraper, update README` |

A useful test: the first line should finish the sentence *"If applied, this commit will …"*.

## 6. Common mistakes
- **Working directly on `main`.** A broken experiment then breaks the only good copy.
- **One huge commit at the end of the day.** You cannot undo part of it.
- **Messages like "update" or "final".** They tell a reader nothing.
- **Committing data, `.venv/` or `.env`.** Set up `.gitignore` first.
- **Deleting a branch before merging it.** The work becomes hard to find. `git branch -d` refuses to do this; `-D` forces it, so avoid `-D`.
- **Forgetting which branch you are on.** Run `git status` before you commit.

## 7. Exam and viva focus
- **Define:** branch, commit, HEAD, merge, merge conflict.
- **Fast-forward vs merge commit:** fast-forward only moves a pointer; a merge commit has two parents.
- **Why branch?** Isolation, safe experiments, a stable `main`, parallel work.
- **Git vs GitHub:** Git is the version-control tool on your computer; GitHub is a website that hosts Git repositories.
