# 08.03 · Docker and Docker Compose

> [!info] [[08.00 Automation and MLOps|Lesson 8]] · Roadmap Phase 8 · Priority 🟡 Supporting
> **Builds on:** [[00.02 Python Virtual Environments]] (the same idea, one level down) · [[06.06 Environment Variables and Configuration]]
> **Used for:** packaging the Flask app and MySQL so they run the same way on your laptop and on a server.

## 1. Definitions
| Term | Meaning |
|---|---|
| **Container** | A running, isolated package holding a program and everything it needs: code, Python, libraries, system tools |
| **Image** | The read-only template a container is started from |
| **Dockerfile** | A text file of instructions for building an image |
| **Registry** | A store of images, such as Docker Hub |
| **Docker Compose** | A tool that starts several containers together from one YAML file |
| **Volume** | Storage that lives outside a container, so data survives when the container is removed |

An image is to a container what a class is to an object, or a recipe to a meal.

## 2. Why it is used
- **"It works on my machine."** A virtual environment fixes the Python packages. It does not fix the Python version, the operating system or the database. A container fixes all of them.
- **One command to start everything.** The app and its database come up together, already connected.
- **Hosts understand it.** Most cloud services can run a container directly.

| | **Virtual machine** | **Container** |
|---|---|---|
| Contains | A whole operating system | Only the program and its libraries |
| Shares the host's kernel | No | Yes |
| Size | Gigabytes | Megabytes |
| Starts in | Minutes | Seconds |
| Isolation | Stronger | Lighter |

## 3. How it works
```text
Dockerfile ──docker build──▶ Image ──docker run──▶ Container (running)
```
An image is built in **layers**, one per instruction. Docker **caches** each layer and rebuilds only from the first line that changed. That is why the order of lines in a Dockerfile matters.

## 4. Syntax: a Dockerfile for the Flask app
```dockerfile
FROM python:3.13-slim                 # start from a small official Python image

WORKDIR /app                          # folder inside the container

COPY requirements.txt .               # 1. copy ONLY the requirements first
RUN pip install --no-cache-dir -r requirements.txt   # 2. install (cached unless requirements change)

COPY . .                              # 3. then copy the code (changes often)

EXPOSE 8000
CMD ["gunicorn", "--bind", "0.0.0.0:8000", "app:create_app()"]
```

| Instruction | Does |
|---|---|
| `FROM` | Chooses the base image |
| `WORKDIR` | Sets the working folder |
| `COPY` | Copies files from your computer into the image |
| `RUN` | Runs a command **while building** |
| `EXPOSE` | Documents the port the app listens on |
| `CMD` | The command run **when a container starts** |

`gunicorn` is a production web server for Python apps. Flask's own `flask run` is for development only. Add `gunicorn` to `requirements.txt`.

```powershell
docker build -t dengue-app .          # build an image named dengue-app
docker run -p 8000:8000 dengue-app    # run it; host port 8000 → container port 8000
docker ps                             # list running containers
docker logs <container>               # see its output
```

A `.dockerignore` file keeps things **out** of the image:
```text
.venv/
.git/
.env
data/
__pycache__/
```

## 5. Example: the app and MySQL together
```yaml
# docker-compose.yml
services:
  web:
    build: .
    ports:
      - "8000:8000"
    environment:
      DATABASE_URL: mysql+pymysql://dengue:${MYSQL_PASSWORD}@db:3306/dengue
    depends_on:
      db:
        condition: service_healthy        # wait until MySQL is ready

  db:
    image: mysql:8.4
    environment:
      MYSQL_DATABASE: dengue
      MYSQL_USER: dengue
      MYSQL_PASSWORD: ${MYSQL_PASSWORD}
      MYSQL_ROOT_PASSWORD: ${MYSQL_ROOT_PASSWORD}
    volumes:
      - db_data:/var/lib/mysql            # keep the data outside the container
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "localhost"]
      interval: 10s
      retries: 5

volumes:
  db_data:
```
```powershell
docker compose up --build       # build and start both
docker compose logs -f web      # follow the app's log
docker compose down             # stop and remove the containers (the volume stays)
```
`${MYSQL_PASSWORD}` is read from a `.env` file beside the compose file, which stays out of Git.

> [!important] Inside Compose, the database's address is its service name
> From the `web` container, MySQL is at **`db:3306`**, not `localhost:3306`. Inside a container, `localhost` means that container itself.

## 6. Common mistakes
- **`localhost` in the database address** inside a container.
- **No volume for the database.** `docker compose down` then deletes every row.
- **Copying the code before installing the requirements.** Every code change reinstalls all packages.
- **Secrets written in the Dockerfile** or copied in with `.env`. Anyone with the image can read them.
- **No `.dockerignore`.** The image carries your data, your `.venv` and your Git history.
- **Binding to `127.0.0.1` inside the container.** The app is then unreachable from outside. Bind to `0.0.0.0`.
- **The app starts before MySQL is ready** and crashes. Use the health check.
- **`flask run --debug` as the container's command.**
- **Using the `latest` tag.** The base image changes under you. Name a version.
- **Getting stuck here.** The roadmap is clear: if Docker blocks you, demo the project locally. Deployment is a bonus.

## 7. Exam and viva focus
- **Define** container, image, Dockerfile, registry.
- **Image vs container:** template vs running instance.
- **Container vs virtual machine:** the comparison table above.
- **Benefits of containers:** consistency across environments, isolation, fast start, easy scaling, portability.
- **What does Docker Compose do?** Defines and runs a multi-container application from one file.
- **Why are volumes needed?** A container's own files disappear when it is removed.
- **What is a layer, and why does instruction order matter?** Build caching.
- **Containerisation and microservices:** each service in its own container.
