# 08.05 · Model Monitoring: Data Drift and Concept Drift

> [!info] [[08.00 Automation and MLOps|Lesson 8]] · Roadmap Phase 8 · Priority 🔴 Core
> **Builds on:** [[03. Self-Study/ML in Production/Machine Learning in Production|Machine Learning in Production]], where drift and monitoring are introduced. This note applies them to a weekly forecast.
> **Used for:** the monitoring table that records weekly error and raises a retraining flag.

## 1. Definitions
> [!note] Model monitoring
> **Model monitoring** is measuring a deployed model continuously, to notice when it stops performing as it did in testing.

| Term | What changes | Symbol |
|---|---|---|
| **Data drift** (covariate shift) | The **inputs** look different from the training data | $P(X)$ changes |
| **Concept drift** | The **relationship** between inputs and the answer changes | $P(y \mid X)$ changes |
| **Label drift** | The overall level of the **answer** changes | $P(y)$ changes |

## 2. Why it is used
A model is fitted to the past. The world moves on, and nothing in the code changes to tell you. The test MAE measured in Phase 5 is true only for the period it was measured on. Without monitoring, a model can decay for months while the dashboard keeps looking confident.

## 3. How it works: examples from this project
| What happens in the world | Kind of drift | Effect |
|---|---|---|
| An unusually wet monsoon, wetter than any training year | Data drift | The model must predict from inputs it never saw; tree models cannot extrapolate ([[04.06 Gradient Boosting]]) |
| A dengue serotype returns that few people are immune to | Concept drift | The same weather now produces many more cases |
| A vaccination or mosquito-control campaign | Concept drift | The same weather now produces fewer cases |
| A change in how cases are notified or counted | Concept drift | The numbers mean something different |
| A district's population grows | Label drift | Counts rise at the same underlying risk |

Drift can be **sudden** (a new reporting rule), **gradual** (urban growth), or **recurring** (seasons, which are *not* drift if the model already has seasonal features).

## 4. What to monitor
### A. Performance: the direct measure
Compare each forecast with what really happened, once the truth is known.

> [!warning] The truth arrives late
> A forecast for 4 weeks ahead cannot be checked for 4 weeks, plus the reporting delay ([[01.06 Reporting Delay and Data Availability]]). With a 7-week delay, a forecast made today is scored about **11 weeks** later. Performance monitoring always lags. That is why inputs are watched too.

### B. Inputs: the early signal
Compare the recent distribution of each feature with its distribution in the training data. A large difference warns of trouble before the errors are known.

### C. Operations
Did the pipeline run? Did data arrive for every district? Is anything missing or out of range? See [[08.01 Pipeline Scripts and Logging]].

## 5. Syntax
**Performance monitoring and the retraining flag:**
```python
# forecasts joined to the actual counts that have now arrived
m = predictions.merge(actuals, on=["district_id", "week_start"])
m["abs_error"] = (m["cases"] - m["predicted_cases"]).abs()

weekly_mae = m.groupby("week_start")["abs_error"].mean()
rolling_mae = weekly_mae.rolling(8).mean()               # smooth out single bad weeks

TEST_MAE = 39.0                                          # measured once in Phase 5
retrain_flag = rolling_mae.iloc[-1] > 1.3 * TEST_MAE     # 30 % worse than in testing
```
Store `week_start`, `weekly_mae`, `rolling_mae` and `retrain_flag` in a monitoring table every week.

**Input drift with a statistical test:**
```python
from scipy.stats import ks_2samp

stat, p_value = ks_2samp(train["rain_sum4"], recent["rain_sum4"])
```
The Kolmogorov–Smirnov test compares two samples. A large `stat` (near 1) means the distributions differ strongly.

## 6. Example: the Population Stability Index
A common single number for input drift. Split the training values into bins, then compare the share of values in each bin then and now:

$$\text{PSI} = \sum_{i} (a_i - e_i)\,\ln\!\left(\frac{a_i}{e_i}\right)$$

$e_i$ is the share of **training** values in bin $i$ and $a_i$ the share of **recent** values.

| Bin (rain in 4 weeks) | Training share $e$ | Recent share $a$ | $(a - e)\ln(a/e)$ |
|---|---|---|---|
| 0–100 mm | 0.40 | 0.20 | 0.139 |
| 100–250 mm | 0.40 | 0.40 | 0.000 |
| above 250 mm | 0.20 | 0.40 | 0.139 |
| **PSI** | | | **0.28** |

| PSI | Usual reading |
|---|---|
| below 0.1 | No meaningful change |
| 0.1 – 0.25 | Moderate change; watch |
| above 0.25 | Large change; investigate |

Here 0.28 says recent weeks are much wetter than the training data. These cut-offs are conventions, not laws.

## 7. Seasons are not drift
A wet June compared with a dry February will always look like "drift". Compare like with like: this June against **previous Junes**, or use the anomalies from [[02.04 Cross-Correlation and Lag Analysis]].

## 8. Acting on a flag
A flag is a reason to **look**, not an order to retrain.
1. Check the pipeline and the data first. Most "drift" is a broken input.
2. Look at which districts and weeks went wrong.
3. Decide: a data problem to fix, a known event to note, or a real change that needs retraining ([[08.06 Model Versioning and Retraining]]).
4. Write down what you found. Missed outbreaks belong in the error analysis.

## 9. Common mistakes
- **No monitoring at all.** The most common state of a deployed student model.
- **Forgetting that the truth is delayed,** and reading "no errors yet" as "no problems".
- **One bad week triggers retraining.** Use a rolling average.
- **Comparing different seasons** and calling the difference drift.
- **Monitoring twenty statistics** and looking at none. Start with one: rolling MAE.
- **Retraining automatically on every flag,** including on data that is itself broken.
- **Overwriting old forecasts,** so they can never be scored: [[06.01 Relational Schema Design and Normalisation]].
- **Blaming the model for a change in the reporting system.**
