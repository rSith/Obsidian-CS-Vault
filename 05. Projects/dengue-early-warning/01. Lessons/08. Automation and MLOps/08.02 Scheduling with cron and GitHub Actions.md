# 08.02 · Scheduling with cron and GitHub Actions

> [!info] [[08.00 Automation and MLOps|Lesson 8]] · Roadmap Phase 8 · Priority 🟡 Supporting
> **Builds on:** [[08.01 Pipeline Scripts and Logging]] · [[03. Self-Study/GitHub Foundations/Introduction to GitHub|Introduction to GitHub]]
> **Used for:** running the weekly pipeline without you starting it.

## 1. Definitions
> [!note] Scheduler
> A **scheduler** starts a program automatically at set times.

> [!note] cron
> **cron** is the standard scheduler on Linux and macOS. A **cron expression** is five fields that say when to run.

> [!note] GitHub Actions
> **GitHub Actions** is GitHub's automation service. A **workflow** is a file in your repository describing jobs that GitHub runs on its own machines, on a schedule or when code is pushed.

## 2. Why it is used
A warning system that updates only when you remember to run it is not a warning system. Scheduling also removes a human from a boring, repetitive task where mistakes creep in.

| | **cron on a server** | **GitHub Actions** |
|---|---|---|
| Needs | A machine that is always on | Only a GitHub repository |
| Cost | The server | Free allowance for public repositories |
| Keeps files between runs | Yes | **No.** Each run starts on a fresh machine. |
| Good for | A project already living on a server | A student project with no server |

## 3. How cron expressions work
```text
┌───────── minute        (0–59)
│ ┌─────── hour          (0–23)
│ │ ┌───── day of month  (1–31)
│ │ │ ┌─── month         (1–12)
│ │ │ │ ┌─ day of week   (0–6, Sunday = 0)
│ │ │ │ │
30 2 * * 1
```
`*` means "every". The example reads: at **02:30, every Monday**.

| Expression | Runs |
|---|---|
| `0 8 * * *` | Every day at 08:00 |
| `30 2 * * 1` | Mondays at 02:30 |
| `0 */6 * * *` | Every 6 hours |
| `0 0 1 * *` | Midnight on the 1st of each month |
| `*/15 * * * *` | Every 15 minutes |

## 4. Syntax: cron on a Linux server
```bash
crontab -e        # opens your schedule for editing
```
```cron
30 8 * * 1 cd /home/user/dengue-early-warning && .venv/bin/python -m src.pipeline >> logs/cron.log 2>&1
```
- `cd …` first: cron starts in your home folder, not the project.
- `.venv/bin/python`: the full path, because cron does not activate the environment.
- `>> logs/cron.log 2>&1`: add both normal output and errors to a log file.

## 5. Example: a scheduled GitHub Actions workflow
```yaml
# .github/workflows/weekly.yml
name: Weekly pipeline

on:
  schedule:
    - cron: "30 2 * * 1"       # Mondays 02:30 UTC = 08:00 in Sri Lanka
  workflow_dispatch:           # adds a "Run workflow" button for manual runs

jobs:
  run:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4            # get the repository's code

      - uses: actions/setup-python@v5
        with:
          python-version: "3.13"
          cache: pip

      - run: pip install -r requirements.txt

      - run: pytest -q                       # do not run the pipeline if tests fail

      - run: python -m src.pipeline
        env:
          DATABASE_URL: ${{ secrets.DATABASE_URL }}
```

| Part | Meaning |
|---|---|
| `on:` | What starts the workflow |
| `jobs:` | Groups of steps; each job runs on its own fresh machine |
| `runs-on:` | The kind of machine |
| `uses:` | A ready-made action written by someone else |
| `run:` | A shell command |
| `secrets.NAME` | A value stored in the repository's settings, never shown in logs |

Add the secret under *Settings → Secrets and variables → Actions*: [[06.06 Environment Variables and Configuration]].

## 6. Things that surprise people
> [!warning] GitHub Actions schedules
> - **Times are in UTC.** Sri Lanka is UTC+5:30, so 08:00 local is 02:30 UTC.
> - **Runs can start late,** sometimes by many minutes, when GitHub is busy. Do not depend on the exact minute.
> - **A schedule runs only from the default branch** (`main`).
> - **In a public repository, scheduled workflows are switched off after 60 days with no repository activity.** GitHub emails a warning first.
> - **The machine starts empty.** Files written during one run are gone the next. Results must go to the database, or be committed, or be saved as artefacts.
> - **The database must be reachable from the internet.** A MySQL server on your laptop is not.

## 7. Continuous integration
The same tool can run your tests on **every push**, so a broken change is caught at once:
```yaml
on: [push, pull_request]
```
This is **continuous integration (CI)**. Deploying automatically after the tests pass is **continuous delivery or deployment (CD)**.

## 8. Common mistakes
- **Forgetting the time zone.**
- **Relative paths in cron.** Use `cd` or full paths.
- **No log of the scheduled run.** When it fails, there is nothing to read.
- **A secret typed into the workflow file.** The file is public.
- **Assuming files persist** between GitHub Actions runs.
- **Wrong indentation in YAML.** Indentation is the structure. Use spaces, never tabs.
- **Not testing the workflow.** Use `workflow_dispatch` to run it by hand before trusting the schedule.
- **A pipeline that is not safe to re-run,** combined with a manual retry: [[08.01 Pipeline Scripts and Logging]].
- **Nobody checks whether it ran.** Turn on failure emails, and show "last updated" on the dashboard so a stalled pipeline is visible.
