# 08.04 · Cloud Deployment Basics

> [!info] [[08.00 Automation and MLOps|Lesson 8]] · Roadmap Phase 8 · Priority 🟢 Optional
> **Builds on:** [[08.03 Docker and Docker Compose]] · [[02.06 Client-Server and Three-Tier Architecture]] · [[03. Self-Study/ML in Production/Machine Learning in Production|Machine Learning in Production]]
> **Used for:** making the dashboard reachable at a public web address. The roadmap calls this a bonus, not the core.

## 1. Definitions
> [!note] Deployment
> **Deployment** is putting software onto a machine where its users can reach it, and keeping it running there.

> [!note] Cloud computing
> **Cloud computing** is renting computing resources (servers, databases, storage) over the internet, paying for what you use, instead of owning the machines.

| Model | You manage | The provider manages | Example of use |
|---|---|---|---|
| **IaaS**, infrastructure as a service | The operating system, the runtime, your app | The physical machines and network | A virtual machine you log in to |
| **PaaS**, platform as a service | Your app and its settings | Everything underneath | "Push your code and we run it" hosts |
| **SaaS**, software as a service | Nothing; you only use it | The whole application | Web mail |

## 2. Why it is used
- A dashboard on `localhost` can be seen by one person: you.
- A public link in a README, CV or LinkedIn post lets a recruiter or lecturer try the project in ten seconds.
- A real early-warning system must be reachable by the people it warns.

## 3. How it works
```text
Your code on GitHub ──▶ host builds it (from the Dockerfile or requirements.txt)
                              │
                              ▼
            host runs your start command, with your environment variables
                              │
                              ▼
          https://your-app.example  ──▶  Flask  ──▶  managed database
```

| Piece | What you must provide |
|---|---|
| **Start command** | How to run the app with a production server: `gunicorn --bind 0.0.0.0:$PORT "app:create_app()"` |
| **Port** | Many hosts tell the app which port to use through an environment variable named `PORT`. The app must listen on it. |
| **Environment variables** | `DATABASE_URL` and any other secrets, typed into the host's settings page |
| **Database** | A database the host provides, or one hosted elsewhere and reachable over the internet |
| **Health check** | A URL the host calls to see whether the app is alive: `/api/health` |

## 4. Choosing where to deploy
| Option | Effort | Notes |
|---|---|---|
| **PaaS host** | Low | Connect the repository and set variables. The usual choice for a student project. |
| **A small virtual machine** | Higher | You install Docker and run `docker compose up`. More control, more to maintain. |
| **Static site + scheduled job** | Low | The pipeline writes forecasts to JSON files; the dashboard is plain HTML and JavaScript with no server. No database, no cost. |

> [!warning] Check the current terms before you choose
> Free tiers change often. Things to look for: whether the service **sleeps when idle** (the first visit then takes many seconds), whether a **free database expires** after some weeks, which **database types** are offered (many offer PostgreSQL, not MySQL), and monthly limits. Because the code uses SQLAlchemy, switching from MySQL to PostgreSQL is mostly a change of the connection address: [[06.03 SQLAlchemy]].

## 5. Example: a deployment checklist
- [ ] The app runs locally from a clean copy of the repository, using only the README
- [ ] `gunicorn` is in `requirements.txt`, and the start command uses it
- [ ] The app listens on `0.0.0.0` and on the port the host gives it
- [ ] Debug mode is **off**
- [ ] Every secret is an environment variable; none is in the repository
- [ ] The database is created, the tables exist and the historical data is loaded
- [ ] `/api/health` returns `{"status": "ok"}` at the public address
- [ ] The dashboard loads over **HTTPS** and its API calls succeed
- [ ] The scheduled pipeline can reach the same database
- [ ] The dashboard shows "last updated", so a stalled pipeline is visible
- [ ] You know where to read the host's logs

## 6. If it does not work out
The roadmap's fallback is sensible: **run the dashboard locally for demos.** Record a short video of it working. A project with a sound evaluation and a local demo is stronger than a deployed project with a weak evaluation.

## 7. Common mistakes
- **Deploying the development server** (`flask run`).
- **Debug mode left on** in public.
- **Listening on `127.0.0.1` or a fixed port** the host does not route to.
- **The database address still says `localhost`.**
- **Secrets committed** to make deployment "easier".
- **A database on your laptop** that the cloud app cannot reach.
- **Never reading the logs.** The reason for a failed start is almost always there.
- **Relying on files written to disk.** On many hosts the disk is wiped at each restart. Keep data in the database.
- **Spending three weeks on deployment** and none on the report.
