# 08.01 · Pipeline Scripts and Logging

> [!info] [[08.00 Automation and MLOps|Lesson 8]] · Roadmap Phase 8 · Priority 🔴 Core
> **Builds on:** [[03.05 Python Functions and Modules]] · [[04. Concepts/Machine Learning/Machine Learning Pipeline|Machine Learning Pipeline]]
> **Used for:** `src/pipeline.py`, the one command that updates the whole system each week.

## 1. Definitions
> [!note] Pipeline script
> A **pipeline script** runs a fixed series of steps in order, where each step uses the result of the one before. Here: collect → build features → predict → write alerts → log metrics.

> [!note] Logging
> **Logging** is writing a time-stamped record of what a program did, to a file or the screen, so you can see afterwards what happened.

> [!note] Idempotent
> A step is **idempotent** if running it twice gives the same result as running it once.

## 2. Why it is used
- A scheduled job runs when nobody is watching. If it fails at 2 a.m., the **log** is the only witness.
- Seven manual steps will, sooner or later, be done in the wrong order or forgotten. One script does them the same way every time.
- A silent failure is the worst kind: the dashboard keeps showing last month's forecast as if it were fresh.

## 3. How it works: four rules
| Rule | Meaning |
|---|---|
| **Each step is a function** | Small, named, testable; `main()` only calls them in order |
| **Log every step** | Start, finish, and how many rows it handled |
| **Fail loudly** | On an error: log it, stop, and exit with a non-zero code so the scheduler knows |
| **Safe to re-run** | A second run for the same week must not create duplicates |

### Log levels
| Level | Use for | Example |
|---|---|---|
| `DEBUG` | Detail for finding bugs | "Request URL: …" |
| `INFO` | Normal progress | "Collected 25 districts, 175 rows" |
| `WARNING` | Odd, but the run can continue | "No new case report this week" |
| `ERROR` | A step failed | "Database connection refused" |
| `CRITICAL` | The program cannot go on | "Model file missing" |

Setting the level to `INFO` shows `INFO` and everything more serious.

## 4. Syntax
```python
import logging

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s %(levelname)s %(name)s: %(message)s",
    handlers=[logging.FileHandler("logs/pipeline.log"), logging.StreamHandler()],
)
logger = logging.getLogger(__name__)

logger.info("Collected %d rows for %d districts", n_rows, n_districts)
logger.warning("No new case report found for week %s", week)
logger.exception("Step failed")      # inside an except block: also records the full error trace
```
A log line then looks like:
```text
2026-10-12 08:00:03 INFO pipeline: Collected 175 rows for 25 districts
```

## 5. Example: the pipeline skeleton
```python
# src/pipeline.py
import logging
import sys

logger = logging.getLogger("pipeline")


def main() -> int:
    steps = [collect_weather, collect_cases, build_features, predict, write_alerts, log_metrics]
    for step in steps:
        logger.info("Starting %s", step.__name__)
        try:
            step()
        except Exception:
            logger.exception("Step %s failed; stopping", step.__name__)
            return 1                       # non-zero = failure
        logger.info("Finished %s", step.__name__)
    logger.info("Pipeline completed")
    return 0                               # zero = success


if __name__ == "__main__":
    logging.basicConfig(level=logging.INFO,
                        format="%(asctime)s %(levelname)s %(name)s: %(message)s")
    sys.exit(main())
```
```powershell
python -m src.pipeline
```
The **exit code** is how the outside world learns the result. `0` means success; anything else means failure. Schedulers and GitHub Actions mark the run red when the code is not zero.

## 6. Making it safe to re-run
| Step | Risk on a second run | Fix |
|---|---|---|
| Download | Fetching the same files again | Skip files that already exist: [[01.01 HTTP Requests and REST APIs in Python]] |
| Insert cases and weather | Duplicate rows, or a primary-key error | **Upsert**: insert or update: [[06.03 SQLAlchemy]] |
| Insert predictions | The same forecast stored twice | The `UNIQUE` rule on the table: [[06.01 Relational Schema Design and Normalisation]] |

## 7. Checks worth logging as warnings or errors
- No new case data arrived this week (expected sometimes: [[01.06 Reporting Delay and Data Availability]]).
- Fewer than 25 districts in the new data.
- A value outside its possible range.
- A forecast that is negative or enormous.
- The newest data is older than expected.

A pipeline should **refuse to publish a forecast built on bad input**, and say why in the log.

## 8. Common mistakes
- **`print` instead of logging.** No time, no level, no file, and nothing left after the terminal closes.
- **`except: pass`.** The error disappears and the run "succeeds" with missing data.
- **Catching the error, logging it, and carrying on** to predict from half the data.
- **Exit code 0 after a failure.** The scheduler shows green.
- **Logging secrets,** such as the full database address with its password.
- **Not safe to re-run,** so a retry after a crash doubles the data.
- **One huge `main()`** with all the logic inside.
- **Logs committed to Git.** Add `logs/` to `.gitignore`.
- **No summary line.** End every run with the week processed and the number of forecasts written.

## 9. Exam and viva focus
- **What is a data pipeline?** A sequence of automated steps moving data from source to result. Related term: **ETL** (extract, transform, load).
- **Why log instead of print?** Levels, timestamps, files, and control over what is shown.
- **Name the log levels** in order of severity.
- **Idempotence:** define it and say why a scheduled job needs it.
- **Exit codes:** zero for success, non-zero for failure.
- **Exception handling:** `try` / `except` / `finally`; why catching everything silently is harmful.
- **Fail fast:** stop at the first error instead of producing a wrong result.
