# 08.06 · Model Versioning and Retraining

> [!info] [[08.00 Automation and MLOps|Lesson 8]] · Roadmap Phase 8 · Priority 🟡 Supporting
> **Builds on:** [[04.08 Experiment Tracking]] · [[03. Self-Study/ML in Production/Machine Learning in Production|Machine Learning in Production]] · [[03. Self-Study/GitHub Foundations/What is Version Control|What is Version Control]]
> **Used for:** knowing which model made which forecast, and replacing a model safely.

## 1. Definitions
> [!note] Model versioning
> **Model versioning** is giving every trained model a unique name (`v1`, `v2`, …) and recording exactly how it was made, so any version can be identified, compared and restored.

> [!note] Retraining
> **Retraining** is fitting the model again on newer data, to keep it up to date.

> [!note] Model registry
> A **model registry** is a store of model versions with their details and their status (for example "in production" or "archived").

## 2. Why it is used
- **Traceability.** When a forecast turns out badly wrong, the first question is "which model said that?" Without a version on every forecast there is no answer.
- **Fair comparison.** You cannot tell whether `v2` is better than `v1` if `v1` no longer exists.
- **Rollback.** If a new model misbehaves, you must be able to return to the last good one in minutes.
- **Reproducibility.** A result in your report must be traceable to a specific model, dataset and code version.

## 3. How it works: what makes a version
Code alone does not define a model. Four things do:

| Ingredient | Recorded as |
|---|---|
| **Code** | Git commit |
| **Data** | The date range used and the download date |
| **Settings** | Hyperparameters, feature list, horizon |
| **Environment** | Python and scikit-learn versions |

Change any one and you have a different model. Git versions the code ([[00.01 Git Branching and Commit Messages]]). The model file and its details need their own record.

## 4. Syntax: save a model with its details
```python
import json
import subprocess
from datetime import date
from pathlib import Path

import joblib
import sklearn

version = "v2"
models = Path("models")

joblib.dump(model, models / f"model_{version}.joblib")

details = {
    "version": version,
    "trained_on": str(date.today()),
    "git_commit": subprocess.run(["git", "rev-parse", "--short", "HEAD"],
                                 capture_output=True, text=True).stdout.strip(),
    "train_period": ["2012-01-07", "2026-06-26"],
    "horizon_weeks": 4,
    "features": list(X_train.columns),
    "params": model[-1].get_params(),
    "sklearn_version": sklearn.__version__,
    "validation_mae": 39.0,
}
(models / f"model_{version}.json").write_text(json.dumps(details, indent=2, default=str))
```
Every row written to `predictions` then carries `model_version = "v2"`: [[06.01 Relational Schema Design and Normalisation]]. **MLflow's model registry** does the same job with a web page: [[04.08 Experiment Tracking]].

## 5. When to retrain
| Trigger | Meaning | Good | Bad |
|---|---|---|---|
| **On a schedule** | Every few months | Simple; predictable | May retrain when nothing changed, or too late |
| **On a flag** | When monitoring shows the error has grown: [[08.05 Model Monitoring - Data Drift and Concept Drift]] | Responds to real change | Needs monitoring that works |
| **On new data** | After a season or a year of new observations | More examples, especially of outbreaks | |

A sensible plan for this project: retrain after each main season, and earlier if the flag fires.

## 6. Example: replacing a model safely
The model in use is the **champion**. A newly trained one is the **challenger**.

1. Train the challenger (`v3`) on data up to now.
2. Score champion and challenger on the **same recent weeks**, which neither was trained on.
3. Compare both against the baselines as well ([[04.02 Forecasting Baselines - Persistence and Seasonal]]).
4. Promote the challenger **only if it is clearly better**. Otherwise keep the champion.
5. Keep the old model file. Record the decision and the numbers.
6. If the new model misbehaves in use, switch the pipeline back to the old version. This is a **rollback**.

| Version | Trained to | MAE on Jul–Sep 2026 | Decision |
|---|---|---|---|
| v2 (champion) | Dec 2025 | 47.0 | |
| v3 (challenger) | Jun 2026 | 41.5 | Promote |

The numbers are invented.

> [!warning] A newer model is not automatically a better one
> Training on recent data can also mean training on a broken month, or on an epidemic that distorts everything. Always compare before replacing.

## 7. What must not change when you retrain
- **The feature code.** Retraining uses the same `src/features.py`: [[03.05 Python Functions and Modules]].
- **The split discipline.** New data is added to training; evaluation is always on weeks after the training period: [[04.01 Time-Based Splits and Time-Series Cross-Validation]].
- **The original test result.** It was measured once, for `v1`. A retrained model gets its own evaluation on its own unseen weeks.
- **The alert thresholds,** unless you re-derive them deliberately and say so.

## 8. Common mistakes
- **Saving every model as `model.joblib`,** overwriting the last.
- **No version stored with the forecasts.**
- **Recording the code version but not the data** it was trained on.
- **Loading a model with a different scikit-learn version** than it was saved with. It may fail, or load and behave differently.
- **Retraining and deploying in one automatic step,** with no comparison.
- **Evaluating the new model on weeks it was trained on.**
- **Deleting old models** to save space. They are small. Keep them.
- **Committing model files to Git.** Keep them out (they are in `.gitignore`) and store the details file and the training script instead.

## 9. Exam and viva focus
- **Why version models?** Reproducibility, traceability, comparison, rollback.
- **What must be versioned besides code?** Data, hyperparameters, environment, the model file itself.
- **Model registry:** what it stores.
- **Retraining strategies:** scheduled vs triggered by performance.
- **Champion–challenger** evaluation.
- **Rollback:** returning to a previous version after a bad release.
- **Why is ML harder to version than ordinary software?** The behaviour depends on data as well as code.
