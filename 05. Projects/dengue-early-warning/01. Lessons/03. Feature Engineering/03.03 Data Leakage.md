# 03.03 · Data Leakage

> [!info] [[03.00 Feature Engineering|Lesson 3]] · Roadmap Phase 3 · Priority 🔴 Core
> **Used for:** every phase from here on. Leakage is the most likely way for this project to produce results that look excellent and are wrong.

## 1. Definition
> [!note] Data leakage
> **Data leakage** happens when a model is trained or evaluated using information that **would not be available at the moment a real prediction is made**. The measured accuracy is then better than the accuracy in real use.

## 2. Why it matters
Leakage gives no error message. The code runs, the charts look good and the error is low. You find out only when the live system performs far worse than the test, which for an early-warning system means missed outbreaks.

## 3. How it gets in
| Type | What happens | Example in this project |
|---|---|---|
| **Future information in a feature** | A feature uses data from after the forecast week | A rolling average that includes later weeks |
| **Unavailable information** | The data is from the past, but was not *published* yet | Using last week's cases when they appear seven weeks late |
| **Target leakage** | A feature is made from the answer itself | A "cases per 100,000" column built from the target week |
| **Preprocessing leakage** | A step is fitted on all the data before splitting | Scaling with the mean of the whole dataset, test years included |
| **Split leakage** | Training and test rows are mixed in time | A random train/test split |
| **Tuning leakage** | Choices are made by looking at the test set | Picking the alert threshold that scores best on the test years |

## 4. Where to look in this project
1. **Lags and rolling windows** that reach past the forecast week: [[03.02 Lag and Rolling-Window Features]].
2. **The reporting delay**: [[01.06 Reporting Delay and Data Availability]].
3. **Interpolated gaps.** Interpolation uses the *next* real value: [[02.02 Data Quality Checks and Missing Data]].
4. **Scalers and encoders** fitted before the split. Keep them inside a pipeline: [[04.04 scikit-learn Pipelines and ColumnTransformer]].
5. **Random splits**, and time-series cross-validation applied to a table sorted by district instead of by date: [[04.01 Time-Based Splits and Time-Series Cross-Validation]].
6. **The gap between training and validation.** The target is $h$ weeks ahead, so the last $h$ training rows have answers that lie *inside* the validation period. Leave a gap of $h$ weeks.
7. **The "normal" level for alerts** computed from all years, including years after the week being judged: [[05.02 Endemic Channel and Alert Thresholds]].
8. **The final test set** used more than once.

## 5. How to detect it
- **Results too good to be true.** An error far below what published studies report is a warning, not a triumph.
- **One feature dominates** the importance chart and you cannot explain why.
- **Performance collapses** on newer data.
- **Read rows by hand.** For a few random rows, write the date each feature value comes from and the date it was published. Any date after the forecast week is a leak.
- **The change-the-future test.** Change the data *after* some week, rebuild the features, and check that features *up to* that week did not change. If they did, they depend on the future. A ready-made version is in [[03.06 Unit Testing with pytest]].

## 6. Example
A student builds `cases_rolling_mean4` with `rolling(4, center=True)`. For week 10 this averages weeks 9, 10, 11 and 12. The model's validation error is one third of the baseline's. In live use, weeks 11 and 12 do not exist yet, the feature cannot even be computed the same way, and the real error is no better than the baseline.

The fix is one word, removing `center=True` and shifting first, but nothing in the output said so.

## 7. How to prevent it
| Habit | Stops |
|---|---|
| Ask of every feature: *"on the forecast day, did this number exist?"* | Future and unavailable information |
| One feature function used for training **and** live prediction | Training and live features drifting apart |
| Split by time, with a gap of $h$ weeks | Split leakage |
| Fit scalers and encoders inside a `Pipeline` | Preprocessing leakage |
| Tune on validation data; open the test set once | Tuning leakage |
| Write an "availability table": each feature, its source, its delay | Forgetting the delay |
| Unit tests for the feature code | Leaks that return later |

## 8. Common mistakes
- **Believing a great result** without asking why it is great.
- **Checking only the features** and forgetting the split, the scaler and the thresholds.
- **Fixing a leak and not re-running** every result that depended on it.
- **Thinking "it is historical data, so it is all available".** Available now is not the same as available then.
- **Re-using the test set** after each improvement. Each look teaches you a little about it.

## 9. Exam and viva focus
- **Define** data leakage and say why it is dangerous: over-optimistic evaluation that fails in deployment.
- **Target leakage vs train–test contamination.**
- **Why is a random split wrong for time series?** The model trains on weeks that come after the weeks it is tested on.
- **Why fit the scaler on training data only?** The test data must stay unseen; its statistics are information.
- **Name three ways to prevent leakage:** time-based split, pipelines, checking feature availability.
- **How would you test for leakage?** The change-the-future test.
