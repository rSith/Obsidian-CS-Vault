# 03.02 · Lag and Rolling-Window Features

> [!info] [[03.00 Feature Engineering|Lesson 3]] · Roadmap Phase 3 · Priority 🔴 Core
> **Builds on:** [[02.01 Pandas Merge, GroupBy, Resample and Shift]] · [[03.01 Forecast Origin, Horizon and Target]]
> **Used for:** the main inputs of the model: past weather and past cases.

## 1. Definitions
> [!note] Lag feature
> A **lag feature** is the value of a variable from a fixed number of weeks earlier. `rain_lag4` is the rainfall four weeks before the forecast week.

> [!note] Rolling-window feature
> A **rolling-window feature** summarises a variable over a stretch of recent weeks: the **total** rainfall of the last 4 weeks, or the **average** temperature of the last 8.

## 2. Why they are used
- A model sees one row at a time. It has no memory of earlier rows. Lag features **put the past into the row**.
- A single week of rain is noisy. Mosquito numbers depend on **sustained** wet or warm periods. A rolling total captures that better than any one week.
- The change between two lags tells the model whether cases are **rising or falling**, which a single value cannot.

## 3. How it works
Take six weeks of rainfall for one district:

| week | rain | `shift(1)` | `shift(1).rolling(4).sum()` | `rolling(4).sum()` (no shift) |
|---|---|---|---|---|
| 1 | 10 | NaN | NaN | NaN |
| 2 | 40 | 10 | NaN | NaN |
| 3 | 5 | 40 | NaN | NaN |
| 4 | 0 | 5 | NaN | 55 |
| 5 | 20 | 0 | **55** | 65 |
| 6 | 30 | 20 | **65** | 55 |

- `shift(1)` moves everything down one week.
- `rolling(4).sum()` adds the current row and the three before it.
- **Shift first, then roll:** at week 5 the result is $10 + 40 + 5 + 0 = 55$, the four weeks *before* week 5.
- **Roll without shifting:** week 5 gives 65, which includes week 5's own value.

## 4. Syntax
```python
CASE_DELAY = 7        # weeks until a case count is published
WEATHER_DELAY = 1     # weeks until weather data is available

df = df.sort_values(["district", "week_start"])
g = df.groupby("district")

# Lagged weather (lags chosen in Phase 2, counted from the forecast week)
df["rain_lag2"] = g["rain_mm"].shift(2)
df["rain_lag4"] = g["rain_mm"].shift(4)
df["temp_lag4"] = g["temp_mean"].shift(4)

# Rolling weather: shift by the delay first, then roll
df["rain_sum4"]  = g["rain_mm"].transform(lambda s: s.shift(WEATHER_DELAY).rolling(4).sum())
df["temp_mean8"] = g["temp_mean"].transform(lambda s: s.shift(WEATHER_DELAY).rolling(8).mean())

# Lagged cases: the newest count available is CASE_DELAY weeks old
df["cases_last"] = g["cases"].shift(CASE_DELAY)
df["cases_prev"] = g["cases"].shift(CASE_DELAY + 1)
df["cases_change"] = df["cases_last"] - df["cases_prev"]     # rising or falling?
```

> [!important] The shift is the availability delay
> The rule is not "always shift by 1". The rule is: **shift by however many weeks pass before that number is known.** Weather is known within days. Case counts are known weeks later. Each variable gets its own delay.

## 5. Example: what one finished row means
| Column | Value | Reads as |
|---|---|---|
| `week_start` | 2 Aug | The forecast is made in this week |
| `rain_lag4` | 85 | Rain in the week of 5 July |
| `rain_sum4` | 310 | Total rain in the four weeks before 2 Aug |
| `cases_last` | 290 | Newest published count (week of 14 June) |
| `cases_change` | +45 | It was rising |
| `target` | 402 | Cases in the week of 30 Aug, the answer |

If you can read every row like this and each value existed on 2 August, the features are sound.

## 6. The empty rows at the start
A lag of 8 leaves the first 8 weeks of each district without a value. Handle them **the same way everywhere**:
- drop rows with any missing feature before training, **or**
- use a model that accepts `NaN` (scikit-learn's `HistGradientBoostingRegressor` does).

The live pipeline must do exactly what training did. That is one reason for a single feature function: [[03.05 Python Functions and Modules]].

## 7. Common mistakes
- **No `groupby("district")`.** Values cross from one district into the next.
- **Rolling without shifting**, so a window includes a week that is not available yet.
- **`rolling(..., center=True)`.** A centred window looks forwards as well as backwards.
- **Not sorting by date first.**
- **Gaps in the weeks.** If a week is missing from the table, "4 rows back" is 5 weeks back. Build the full grid first: [[02.02 Data Quality Checks and Missing Data]].
- **Too many lags.** Lags 1 to 16 of five variables is 80 columns that are almost copies of each other. Keep the few that Phase 2 supports.
- **Using cases from last week** when they are published seven weeks late.

## 8. Exam and viva focus
- **Define** lag feature and rolling-window feature, with one example each.
- **Why do tabular models need lag features?** Each row is treated alone; lags carry the history into the row.
- **Why shift before rolling?** So the window holds only values available at forecast time.
- **What does a rolling mean do to a noisy series?** It smooths it.
- **Why do lag features create missing values?** The earliest rows have no earlier rows to draw from.
