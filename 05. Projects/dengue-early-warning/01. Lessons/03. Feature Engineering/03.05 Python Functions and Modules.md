# 03.05 · Python Functions and Modules

> [!info] [[03.00 Feature Engineering|Lesson 3]] · Roadmap Phase 3 · Priority 🟡 Supporting
> **Used for:** moving working notebook code into `src/`, so the same feature code runs in training, in tests and in the weekly pipeline.

## 1. Definitions
| Term | Meaning |
|---|---|
| **Function** | A named block of code that takes inputs (parameters) and returns a result. |
| **Module** | One `.py` file. `src/features.py` is the module `src.features`. |
| **Package** | A folder of modules. `src/` is a package. |
| **Import** | Loading a module so its functions can be used elsewhere. |

## 2. Why it is used
Notebook cells are good for trying ideas and bad for everything after that:
- they cannot be **imported** by another program;
- they cannot be **tested** automatically;
- they depend on the **order** the cells happened to be run in.

The project needs the feature code in three places: training, the tests, and the live pipeline. If each has its own copy, the copies drift apart, and the live model receives features built differently from the ones it was trained on. **One function, imported three times,** removes that risk.

## 3. How it works
```text
dengue-early-warning/
├── src/
│   ├── __init__.py        makes src a package
│   └── features.py        the module
├── notebooks/03_features.ipynb
└── tests/test_features.py
```
When Python runs `from src.features import add_lag`, it finds the `src` folder, runs `features.py` once, and gives you the name `add_lag`.

## 4. Syntax
```python
# src/features.py
import pandas as pd


def add_lag(df: pd.DataFrame, column: str, k: int) -> pd.DataFrame:
    """Add `<column>_lag<k>`: the value of `column` k weeks earlier, per district."""
    out = df.sort_values(["district", "week_start"]).copy()
    out[f"{column}_lag{k}"] = out.groupby("district")[column].shift(k)
    return out


if __name__ == "__main__":            # runs only with: python -m src.features
    weekly = pd.read_csv("data/processed/weekly.csv", parse_dates=["week_start"])
    print(add_lag(weekly, "rain_mm", 4).tail())
```

| Piece | Purpose |
|---|---|
| `df: pd.DataFrame` | **Type hint:** tells the reader (and the editor) what kind of value is expected |
| `-> pd.DataFrame` | The type that is returned |
| `"""..."""` | **Docstring:** one line saying what the function does |
| `.copy()` | The function does not change the table it was given |
| `if __name__ == "__main__":` | Code that runs when the file is executed directly, but not when it is imported |

Using it from a notebook:
```python
%load_ext autoreload
%autoreload 2                     # pick up edits to src/ without restarting the kernel
from src.features import add_lag
```

## 5. Example: from cell to function
**Before**, in a notebook cell:
```python
weekly["rain_lag4"] = weekly.groupby("district")["rain_mm"].shift(4)
weekly["temp_lag4"] = weekly.groupby("district")["temp_mean"].shift(4)
weekly["rain_lag8"] = weekly.groupby("district")["rain_mm"].shift(8)
```
**After**:
```python
for column, k in [("rain_mm", 4), ("temp_mean", 4), ("rain_mm", 8)]:
    weekly = add_lag(weekly, column, k)
```
The logic now exists once. A fix to it reaches every caller.

## 6. What makes a function good
- **It does one thing**, and its name says what.
- **It takes what it needs as parameters** and does not read variables from outside itself.
- **It returns a result** and does not change its inputs.
- **Same inputs, same output.** That is what makes it testable.
- **No hidden settings.** Values such as the horizon are parameters with defaults: `def build_features(weekly, horizon=4)`.

## 7. Common mistakes
- **`ModuleNotFoundError: No module named 'src'`.** Python was started from the wrong folder. Run commands from the project root.
- **Copy and paste between notebook and `src/`.** Import instead.
- **Functions that depend on a global variable.** They work in the notebook and fail elsewhere.
- **Changing the input table in place.** The caller's data changes without warning. Work on a copy.
- **Hard-coded paths** such as `C:\Users\...`. Use `pathlib.Path` and paths relative to the project.
- **One enormous function.** Split it into steps that can each be tested.
- **Circular imports:** module A imports B and B imports A. Move the shared code to a third module.

## 8. Exam and viva focus
- **Function vs module vs package.**
- **Parameter vs argument:** the name in the definition vs the value passed in the call.
- **Local vs global scope.**
- **What does `if __name__ == "__main__":` do?** Separates "run as a script" from "imported as a module".
- **DRY** ("don't repeat yourself") and why duplicated code is risky.
- **Benefits of modular code:** reuse, testing, readability, easier maintenance.
