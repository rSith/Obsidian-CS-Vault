# 03.06 · Unit Testing with pytest

> [!info] [[03.00 Feature Engineering|Lesson 3]] · Roadmap Phase 3 · Priority 🟡 Supporting
> **Builds on:** [[03.05 Python Functions and Modules]]
> **Used for:** proving that the feature code does what you think, and catching leaks before they reach the model.

## 1. Definition
> [!note] Unit test
> A **unit test** is a small piece of code that runs one function on a known input and checks that the output is what it should be.

> [!note] pytest
> **pytest** is a Python tool that finds your test functions, runs them all, and reports which passed and which failed.

## 2. Why it is used
A wrong feature does not crash anything. It produces numbers, the model trains, and the results are quietly worse or falsely better. A test turns "I think the lag is right" into a check that runs in a second, every time you change the code.

## 3. How it works
- pytest looks in `tests/` for files named `test_*.py`.
- Inside them it runs every function whose name starts with `test_`.
- A test **passes** if it finishes without an error and **fails** if an `assert` is false.

Each test follows three steps, often called **Arrange, Act, Assert**:
1. **Arrange:** build a tiny input where you know the right answer.
2. **Act:** call the function.
3. **Assert:** check the result.

## 4. Syntax
```python
assert value == expected                     # exact match
assert value == pytest.approx(0.3333, abs=1e-4)   # numbers with decimals
pd.testing.assert_series_equal(a, b)         # two pandas Series
with pytest.raises(ValueError):              # the code SHOULD raise this error
    function(bad_input)
```
```powershell
pytest                 # run everything
pytest -q              # short output
pytest -k lag          # only tests with "lag" in the name
pytest -x              # stop at the first failure
```

## 5. Example: three tests for the lag function
These test `add_lag` from [[03.05 Python Functions and Modules]].

```python
# tests/test_features.py
import pandas as pd
from src.features import add_lag


def make_df() -> pd.DataFrame:
    weeks = list(pd.date_range("2024-01-06", periods=12, freq="7D"))
    return pd.DataFrame({
        "district": ["A"] * 12 + ["B"] * 12,
        "week_start": weeks * 2,
        "rain_mm": list(range(12)) + list(range(100, 112)),
    })


def test_lag4_takes_the_value_from_four_weeks_earlier():
    out = add_lag(make_df(), "rain_mm", 4)
    a = out[out["district"] == "A"].reset_index(drop=True)
    assert a.loc[9, "rain_mm_lag4"] == a.loc[5, "rain_mm"]     # week 10 gets week 6


def test_lag_does_not_cross_districts():
    out = add_lag(make_df(), "rain_mm", 4)
    b = out[out["district"] == "B"].reset_index(drop=True)
    assert b.loc[:3, "rain_mm_lag4"].isna().all()               # B's first 4 weeks are empty


def test_features_do_not_use_the_future():
    df = make_df()
    changed = df.copy()
    cutoff = pd.Timestamp("2024-02-24")
    changed.loc[changed["week_start"] > cutoff, "rain_mm"] = 999   # rewrite the future

    before = add_lag(df, "rain_mm", 4)
    after = add_lag(changed, "rain_mm", 4)
    past = before["week_start"] <= cutoff
    pd.testing.assert_series_equal(before.loc[past, "rain_mm_lag4"],
                                   after.loc[past, "rain_mm_lag4"])
```
The third test is the **change-the-future test** from [[03.03 Data Leakage]]. If changing later weeks alters a feature for an earlier week, that feature depends on the future. Write one such test for the whole feature function.

## 6. What is worth testing
| Test | Catches |
|---|---|
| A lag returns the right earlier value | An off-by-one shift |
| Nothing crosses from one district to another | A missing `groupby` |
| Features do not change when the future changes | Leakage |
| The output has one row per district per week | A merge that duplicated rows |
| The target for origin $t$ equals cases at $t + h$ | A target shifted the wrong way |
| The function raises an error on a table with missing weeks | Bad input passing silently |

You need a few sharp tests, not hundreds. The roadmap asks for at least two.

## 7. Common mistakes
- **Testing on the real dataset.** You cannot know the right answer by eye. Use 10–20 invented rows.
- **A test with no `assert`.** It always passes.
- **Copying the function's logic into the test.** The test then repeats the same mistake. Write the expected answer by hand.
- **One test checking ten things.** When it fails you do not know which.
- **Tests that depend on each other** or on files that may not exist.
- **Deleting a failing test** instead of finding out why it fails.
- **Never running the tests.** Run `pytest` before every commit.

## 8. Exam and viva focus
- **Define** unit test. **Unit vs integration test:** one function alone vs several parts working together.
- **Arrange, Act, Assert.**
- **Why test?** Find errors early, change code safely, document what the code should do.
- **Regression test:** a test that makes sure an old bug does not come back.
- **Test-driven development:** write the test first, then the code that passes it.
- **Can tests prove code is correct?** No. They show the presence of bugs, not their absence.
