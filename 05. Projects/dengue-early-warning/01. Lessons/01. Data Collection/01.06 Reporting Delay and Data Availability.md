# 01.06 · Reporting Delay and Data Availability

> [!info] [[01.00 Data Collection|Lesson 1]] · Roadmap Phase 1 · Priority 🔴 Core
> **Used for:** deciding which case numbers the model is allowed to use on the day it makes a forecast. This one idea changes the feature design in Phase 3.

## 1. Definition
> [!note] Reporting delay
> The **reporting delay** is the time between the end of a week and the day that week's case count is published.

> [!note] Data vintage
> A **vintage** is the data *as it was known on a particular date*. The same week can have different values in different vintages, because late reports are added afterwards.

## 2. Why it matters
A forecast can use only what exists **on the day it is made**. Your historical file is complete, so it is easy to give the model numbers that would not have been published yet. The model then looks accurate in testing and fails when it runs for real.

## 3. How it works
Checked on 8 October 2026:

| Source | Newest week published | Delay |
|---|---|---|
| Weekly Epidemiological Report | 15–21 August | about 7 weeks |
| National Dengue Control Unit weekly update | week 37 (early September) | about 4 weeks |
| National Dengue Control Unit daily update | dated 6 October | about 2 days |
| Weather APIs | a few days ago | about 1 week or less |

Draw the timeline:

```text
        newest case week                today              week you want to predict
              │◀──── delay (d weeks) ───▶│◀─ lead time (h weeks) ─▶│
──────────────●──────────────────────────●─────────────────────────●──────▶ time
              │◀───────────── real horizon = d + h weeks ──────────▶│
```

$$\text{real horizon} = d + h$$

With the Weekly Epidemiological Report, $d = 7$. A forecast for 4 weeks from today is really a forecast $7 + 4 = 11$ weeks beyond the newest case count.

## 4. What to do about it
1. **Measure the delay** for each source: how many weeks behind is it on the day your pipeline runs?
2. **Record it as a setting**, not a guess buried in the code:
   ```python
   CASE_DELAY_WEEKS = 7      # newest case week available = this week − 7
   WEATHER_DELAY_WEEKS = 1
   ```
3. **Build features with the delay.** The newest case feature is "cases $d$ weeks ago", not "cases last week". See [[03.02 Lag and Rolling-Window Features]].
4. **Use the same delay in testing.** The backtest must be as blind as the live system: [[03.03 Data Leakage]].
5. **Save the download date** with every raw file, so you know which vintage you have.

## 5. Example
Today is the forecast day for week $t$. You want cases in week $t + 4$.

| Feature | Allowed if cases are 7 weeks late? |
|---|---|
| Cases in week $t - 1$ | ❌ Not published yet |
| Cases in week $t - 4$ | ❌ Not published yet |
| Cases in week $t - 7$ | ✅ Newest available |
| Cases in week $t - 8$ | ✅ |
| Rainfall in week $t - 1$ | ✅ Weather arrives fast |

Because weather arrives quickly and cases arrive slowly, **recent weather becomes more valuable** than it would be with instant case data. That is a point worth making in your report.

## 6. Revisions
Counts are not final when first published. Late notifications are added in later weeks, so a figure can grow. Two consequences:
- The **newest** weeks in any download are probably too low.
- A model trained on final numbers but fed first-published numbers sees lower values than it was trained on.

If you can, keep each week's download as a separate file. Later you can measure how much numbers change.

## 7. Two words that are easy to mix up
| Term | Meaning |
|---|---|
| **Nowcasting** | Estimating what is happening **now**, because current data is not published yet |
| **Forecasting** | Predicting what will happen **in the future** |

With a 7-week delay this project does both: it must first bridge the gap to today, then look ahead.

## 8. Common mistakes
- **Testing with data the live system would not have had.** The most common reason a forecasting project fails after deployment.
- **Assuming the delay is zero** because the historical file has every week.
- **Training on one source and running on another** without checking that their numbers agree.
- **Forgetting the delay can change.** Check it again before each phase.
- **Trusting the last few weeks of a fresh download** as final.

## 9. Exam and viva focus
- **Define** reporting delay and data vintage.
- **Real horizon = delay + lead time.** Be ready to work an example.
- **Nowcasting vs forecasting.**
- **Why does ignoring the delay overstate accuracy?** The model uses information nobody had at the time.
