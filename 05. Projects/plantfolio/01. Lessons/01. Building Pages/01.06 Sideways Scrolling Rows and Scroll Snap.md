# 01.06 · Sideways Scrolling Rows and Scroll Snap

> [!info] [[01.00 Building Pages|Lesson 1]] · Week 4 · Tasks COM-01, COM-02 · Priority 🟡 Useful
> **Builds on:** [[07.01 CSS Layout with Flexbox and Grid]] · [[01.02 Card Grids, Images and Sticky Bars]] · [[06.05 Media Queries and Breakpoints]]
> **Used for:** the "Plant lovers matching" row on Explore (P09) on a phone; the profile tabs on the Public Profile (P14, section 7); later the filter chips of the Exchange on a phone (wireframe p23).

## 1. Definitions
| Term | Meaning |
|---|---|
| **Overflow** | Content that is wider (or taller) than the box it sits in |
| **`overflow-x: auto`** | "If the content is too wide, let this box scroll sideways", and only this box |
| **Page-level sideways scroll** | The whole page is wider than the screen, so everything wobbles left and right. Always a bug on PlantFolio |
| **Scroll snap** | CSS that makes a scrolling box stop on a card's edge instead of halfway through one |
| **`scroll-snap-type`** | Set on the scrolling box: which direction snaps (`x`) and how strictly (`mandatory`) |
| **`scroll-snap-align`** | Set on each card: which edge lands on the snap line (`start`) |
| **`scroll-padding`** | Where the snap line is: how far in from the box's edge a card stops |
| **`overflow-wrap: anywhere`** | Lets one very long word break onto the next line instead of sticking out |

## 2. Why PlantFolio uses it
- Wireframe p16 puts three member cards side by side above the search results. On a 375 px phone three cards do not fit, and stacking them would push the plants a whole screen down.
- A sideways strip keeps them in one short row: the first card is fully visible and the next one **peeks in** at the right edge, which tells the user "swipe for more". App stores and shops use the same pattern.
- The design system's rule is **no horizontal scroll** on any page (CLAUDE.md, Testing). A strip is allowed because only the strip scrolls, never the page.
- It needs no JavaScript, which suits stage F.

## 3. How it works
```text
        the phone screen (375 px)
     |<-------------------------->|
     |  [ card 1 ]  [ card 2 ]    |  [ card 3 ]      <- the strip is wider than the screen
     |  ^                         |
     |  snap line, 16 px in       |  card 3 is reached by swiping; card 2 peeks in
```
1. The strip is a grid whose cards flow into **columns**, not rows (`grid-auto-flow: column`), so they line up side by side however many there are.
2. Each card has one fixed width, **240 px**, narrower than any phone screen (the smallest common phones are 320 px wide), so part of the next card always shows at the edge. On a 375 px phone about 107 px of card 2 peeks in.
3. `overflow-x: auto` turns the extra width into a scroll inside the strip. The page itself stays 375 px wide.
4. `scroll-snap-type: x mandatory` makes every swipe end with a card's start edge on the snap line.
5. From the tablet breakpoint up, the strip becomes a normal three-column row and stops scrolling.

## 4. Syntax
```css
.strip {
  display: grid;
  grid-auto-flow: column;              /* new cards make new columns, not new rows */
  grid-auto-columns: 240px;            /* every card the same width, narrower than the screen */
  gap: var(--space-12);
  overflow-x: auto;                    /* only this box scrolls sideways */
  scroll-snap-type: x mandatory;       /* stop on a card, never halfway */
  scroll-padding: 0 var(--space-16);   /* the snap line, 16 px in from the edge */
}

.strip > * {
  scroll-snap-align: start;            /* the card's left edge lands on the snap line */
}
```
| Value | Effect |
|---|---|
| `scroll-snap-type: x mandatory` | Always snaps after a swipe |
| `scroll-snap-type: x proximity` | Snaps only when the swipe ends close to a card |
| `scroll-snap-align: start / center / end` | Which edge of the card lines up |

## 5. Example: the people row on Explore
```css
/* public/assets/css/explore.css */
.people-row-list {
  display: grid;
  grid-auto-columns: 240px;                       /* the next card always peeks in */
  grid-auto-flow: column;
  gap: var(--space-12);
  margin: 0 calc(var(--space-16) * -1);           /* run to the screen edges ... */
  padding: var(--space-4) var(--space-16) var(--space-8);   /* ... but keep the first card in line */
  overflow-x: auto;
  overscroll-behavior-x: contain;                 /* a swipe at the end does not go "Back" in the browser */
  scroll-padding: 0 var(--space-16);
  scroll-snap-type: x mandatory;
  scrollbar-width: thin;
}

.people-row-list > * {
  scroll-snap-align: start;
}

@media (min-width: 768px) {                        /* all three fit: a plain row */
  .people-row-list {
    grid-auto-flow: row;
    grid-template-columns: repeat(3, minmax(0, 1fr));
    margin: 0;
    padding: var(--space-4) 0 0;
    overflow: visible;
  }
}
```
- **The negative margins** cancel the page's 16 px side padding, so the strip reaches the edges of the screen. The padding then puts the first card back in line with the heading above it. Total width = the screen, so the page does not grow.
- **`minmax(0, 1fr)`** on the desktop row lets a column be narrower than its content (a long username shortens with "…" instead of widening the page).

## 6. Keeping the rest of the page from scrolling sideways
A strip is the one place that may scroll. Everything else must fit, even with odd content:

| Cause | Fix used in PlantFolio |
|---|---|
| A box with `width: 100%` plus padding | `box-sizing: border-box` on everything (components.css, week 1) |
| A grid column that will not shrink below its content | `minmax(0, 1fr)` instead of `1fr` |
| A flex item with long text | `min-width: 0` on the item, plus `text-overflow: ellipsis` |
| **One very long word** someone typed, e.g. a search for 100 "z"s, printed in a heading | `overflow-wrap: anywhere` on the heading or its box |

**How to check it.** Open the page in a frame of the width you test (375 px). If the page's `document.documentElement.scrollWidth` is bigger than its `clientWidth`, something sticks out. Equal numbers mean no sideways scroll. In DevTools you can type both into the Console.

## 7. Bringing the chosen item into view without JavaScript
*Added in step 4.5 (Public Profile).* A row that scrolls has one weak spot: the item that matters can be off the screen. On the Public Profile the four tabs with their counts are wider than a phone, so on `user.php?u=kandy.jungle&tab=ratings` the lit **Ratings** tab sat beyond the right edge, and the page looked as if no tab was chosen.

The fix is the URL **fragment**, the `#…` part of an address ([[02.03 URL Structure and Domains]]). When a page opens at `…#tab-ratings`, the browser finds the element with `id="tab-ratings"` and scrolls it into view. It scrolls the page down to it, **and it also scrolls every box around it that can scroll**, so the tab row slides sideways until the tab shows. It moves only as far as needed: a tab that is already visible stays where it is.

```php
// public/user.php: every tab link ends with the id of the span inside that tab
$tab_url = fn ($key, array $more = []) => query_url('user.php', array_merge(
    ['u' => $member['username'], 'tab' => $key === 'collections' ? '' : $key],
    $more
)) . '#tab-' . $key;
```
```php
<a class="tab<?= $key === $tab ? ' is-active' : '' ?>" href="<?= e($tab_url($key)) ?>">
  <span class="profile-tab-inner" id="tab-<?= e($key) ?>"><?= e($item['label']) ?> <span class="tab-count"><?= e($item['count']) ?></span></span>
</a>
```
- **The `id` is on a span, not on the link.** When the target of a fragment can take keyboard focus (a link, a button), the browser focuses it, and the green focus ring appeared around the tab every time the page opened. A span cannot take focus, so the page only scrolls.
- **The span holds the label and the count.** With only the word inside, the browser scrolled just the word into view and the count stayed cut off at the edge.
- **`scroll-padding-top` on `html`** (layout.css, week 1) makes the browser stop below the sticky top bar instead of under it.
- **A smaller gap on phones** (16 px instead of the shared 24 px) lets the start of the next tab peek in, the same "there is more" signal as the people row's 240 px cards.

## 8. Common mistakes
- **`overflow-x: auto` on the page or `<body>`.** That hides the bug instead of fixing it, and breaks sticky headers. Scroll only the strip.
- **Cards exactly as wide as the screen.** Nothing peeks in, so nobody knows there is more. Make each card clearly narrower than the screen (PlantFolio: 240 px on a 375 px phone).
- **Expecting `minmax(240px, 80%)` to give 80% cards.** A grid column starts at its minimum and only grows toward its maximum when the strip has **spare room**. Two or three 240 px cards are already wider than a phone, so there is none, and every card stays 240 px; only a single card grows to 80%. Explore's first version had exactly this rule, and a pixel check of the screenshot showed 240 px cards. A plain `240px` says what the screen really shows.
- **Forgetting `scroll-snap-align` on the cards.** `scroll-snap-type` alone does nothing.
- **Negative margins without the matching padding.** The first card then touches the screen edge and no longer lines up with the heading.
- **Hiding the scroll bar completely** with `display: none` on `::-webkit-scrollbar`. Mouse users then cannot scroll the strip at all. A thin bar is enough.
- **Testing in a desktop window made narrow.** A headless browser cannot go below about 500 px; test at a true 375 px (an iframe or DevTools device mode).
- **Making a focusable element the target of a `#fragment`.** It receives focus when the page opens and shows its focus ring. Put the `id` on a span inside it.

- **What do `scroll-snap-type` and `scroll-snap-align` each do, and where does each go?**
