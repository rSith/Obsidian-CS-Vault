# 02.03 · Client-Side Form Validation

> [!info] [[02.00 Interactivity and Responsive Design|Lesson 2]] · Week 6 · Task CORE-08 (UI) · Priority 🔴 Core
> **Builds on:** [[00.05 HTML Forms]] · [[00.09 Styling Forms with CSS]] · [[07.02 JavaScript fetch and Promises]]
> **Used for:** inline errors on Sign up, Add Plant, Create Listing and Settings, and the live username check.

## 1. Definitions
> [!note] Validation
> **Validation** is checking that input obeys the rules before it is accepted: required fields are filled, an email looks like an email, a password is long enough.

| | **Client-side validation** | **Server-side validation** |
|---|---|---|
| Runs in | The browser | PHP |
| Purpose | Fast, friendly feedback | The actual protection |
| Can be bypassed | Yes, easily | No |
| Required | For good usability | **Always** |

## 2. Why it is used
Telling someone their password is too short the moment they leave the field is better than telling them after a page reload. But the browser belongs to the user: they can switch JavaScript off or send a request by hand. So the roadmap says *"the server re-checks in stage B"*. Client-side validation is for **people**; server-side validation is for **safety**: [[03.06 Form Handling - Validation, Redirects and Flash Messages]].

## 3. How it works: three layers
### Layer 1: HTML attributes
```html
<input id="email" name="email" type="email" required autocomplete="email">
<input id="username" name="username" required minlength="3" maxlength="20" pattern="[a-z0-9._]+">
<input id="password" name="password" type="password" required minlength="8" autocomplete="new-password">
```
| Attribute | Rule |
|---|---|
| `required` | Must not be empty |
| `type="email"`, `"url"`, `"number"`, `"date"` | Must have that format; phones show a matching keyboard |
| `minlength`, `maxlength` | Length of text |
| `min`, `max`, `step` | Range of a number or date |
| `pattern` | Must match a regular expression |

With these alone, the browser blocks the submit and shows its own message bubble. This layer works with JavaScript off.

### Layer 2: your own messages, placed beside the field
The built-in bubbles cannot be styled and vanish quickly. The **Constraint Validation API** lets a script read the browser's verdict and show the project's own `.field-error`.

| Member | Gives |
|---|---|
| `input.validity.valid` | `true` if every rule passes |
| `input.validity.valueMissing` | `required` failed |
| `input.validity.typeMismatch` | Wrong format for its `type` |
| `input.validity.tooShort` | Shorter than `minlength` |
| `input.validity.patternMismatch` | `pattern` failed |
| `form.noValidate = true` | Switches the bubbles off, so your messages take over |

### Layer 3: checks only the server can make
Is the username already taken? That needs a request: section 6.

## 4. Syntax: the markup for one field
```html
<div class="field">
  <label class="field-label" for="username">Username</label>
  <input class="input" id="username" name="username" required minlength="3" maxlength="20"
         pattern="[a-z0-9._]+" data-pattern-message="Use lowercase letters, numbers, dots and underscores."
         aria-describedby="username-error">
  <p class="field-error" id="username-error"></p>
</div>
```
- **`<label for>`** names the field for everyone, and makes the words clickable.
- **`aria-describedby`** ties the error text to the input, so a screen reader reads it with the field.
- The error element is always present and empty. The script fills it.

## 5. Example: the validation script
```js
function messageFor(input) {
  const validity = input.validity;

  if (validity.valueMissing) return 'This field is required.';
  if (validity.typeMismatch) return 'Enter a valid email address, like name@example.com.';
  if (validity.tooShort) return `Use at least ${input.minLength} characters.`;
  if (validity.patternMismatch) return input.dataset.patternMessage || 'Check the format.';
  return '';
}

function showError(input) {
  const error = document.getElementById(input.getAttribute('aria-describedby'));
  if (!error) return;

  const message = messageFor(input);
  error.textContent = message;
  input.setAttribute('aria-invalid', message ? 'true' : 'false');
}

document.querySelectorAll('form[data-validate]').forEach((form) => {
  form.noValidate = true;                         // set by script: without JavaScript the bubbles still work

  form.addEventListener('focusout', (event) => {  // "on blur": when the user leaves a field
    if (event.target.matches('input, select, textarea')) showError(event.target);
  });

  form.addEventListener('submit', (event) => {
    const fields = [...form.querySelectorAll('input, select, textarea')];
    fields.forEach(showError);

    const firstInvalid = fields.find((field) => !field.validity.valid);
    if (firstInvalid) {
      event.preventDefault();
      firstInvalid.focus();                       // take the user to the first problem
    }
  });
});
```
What it does, matching the roadmap: errors appear **on blur and on submit**, inline, and the submit is stopped only when something is wrong. The CSS already styles `[aria-invalid="true"]`, so setting that one attribute gives the red border **and** the screen-reader announcement.

## 6. The live username check
```js
function debounce(callback, delay) {
  let timer = null;
  return (...args) => {
    clearTimeout(timer);
    timer = setTimeout(() => callback(...args), delay);
  };
}

const usernameInput = document.querySelector('#username');
const usernameHint = document.querySelector('#username-hint');

const checkUsername = debounce(async () => {
  const username = usernameInput.value.trim();
  if (!usernameInput.validity.valid) return;      // do not ask the server about an invalid name

  const response = await fetch(`api/check-username.php?u=${encodeURIComponent(username)}`);
  if (!response.ok) return;                       // a failed check must never block sign-up
  const result = await response.json();

  usernameHint.textContent = result.available ? `@${username} is available.` : `@${username} is taken.`;
}, 400);

usernameInput.addEventListener('input', checkUsername);
```
**Debounce** waits until the user has stopped typing for 400 ms. Without it, typing `nimali.grows` sends twelve requests.

The endpoint in stage F checks a mock list:
```php
<?php
// public/api/check-username.php: stage F checks a mock list; stage B asks the database (CORE-08)
header('Content-Type: application/json');

$username = strtolower(trim((string) ($_GET['u'] ?? '')));
$taken = ['nimali.grows', 'aroid.amaya', 'kandy.jungle', 'dinesh.greens', 'ruwan.roots'];

$valid = preg_match('/^[a-z0-9._]{3,20}$/', $username) === 1;

echo json_encode([
    'valid'     => $valid,
    'available' => $valid && !in_array($username, $taken, true),
]);
```
> [!warning] "Available" is only a hint
> Between the check and the submit, someone else can take the name. The real guarantee is the `UNIQUE` rule on `users.username` in the database, and the registration code that handles its error.

## 7. Writing a good error message
| Weak | Better |
|---|---|
| "Invalid input" | "Enter a valid email address, like name@example.com." |
| "Error in password" | "Use at least 8 characters." |
| A red border only | A red border **and** a sentence |

Say what is wrong and how to fix it, next to the field, in words. Colour alone is not a message.

## 8. Common mistakes
- **Client-side checks only.** Anyone can post directly to the server.
- **Validating on every keystroke.** "Invalid email" after the first letter. Validate on blur and on submit.
- **Emptying the form when it fails.** The user must retype everything.
- **A submit button disabled until all is valid.** The user cannot find out what is missing.
- **Errors only at the top of the page,** far from their fields.
- **Colour alone** for errors.
- **`novalidate` written in the HTML.** Without JavaScript there is then no validation at all. Let the script set it.
- **Different rules in the browser and on the server.** The browser accepts what the server rejects, or the other way round.
- **An over-strict `pattern`,** such as rejecting valid emails or names with non-English letters.
- **No debounce** on a live check.
- **Blocking sign-up when the live check fails** to answer.

## 9. Exam and viva focus
- **Client-side vs server-side validation:** purpose of each, and why both are needed.
- **HTML5 validation attributes:** `required`, `type`, `pattern`, `minlength`, `min`, `max`.
- **Validation vs sanitisation vs escaping.**
- **What is a regular expression?** A pattern that describes a set of strings.
- **Why label every input?** Accessibility, and a larger click target.
- **What is debouncing?** Delaying a function until input has paused.
- **Viva:** "If I disable JavaScript, can I register with an empty email?" (In stage B: no, the server rejects it.) · "Why is `noValidate` set from JavaScript?" · "The username check says available; can registration still fail?"
