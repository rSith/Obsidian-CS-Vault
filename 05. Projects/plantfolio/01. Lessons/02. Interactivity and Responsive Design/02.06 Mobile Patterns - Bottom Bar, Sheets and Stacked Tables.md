# 02.06 · Mobile Patterns: Bottom Bar, Sheets and Stacked Tables

> [!info] [[02.00 Interactivity and Responsive Design|Lesson 2]] · Week 6 · Task COM-16 · Priority 🔴 Core
> **Builds on:** [[06.03 Mobile Web, One Web and Mobile First]] · [[06.05 Media Queries and Breakpoints]] · [[06.04 Making Pages Responsive]], which cover responsive design itself. This note covers the specific phone layouts in the wireframes (p23).
> **Used for:** the responsive pass on every page.

## 1. Definitions
| Term | Meaning |
|---|---|
| **Mobile first** | Write the base CSS for the smallest screen, then add rules for wider screens with `min-width` media queries |
| **Breakpoint** | A width at which the layout changes. Here: 768 px (tablet) and 1024 px (desktop). |
| **Touch target** | The area that responds to a finger. At least 44 × 44 px in this project. |
| **Bottom sheet** | A panel that slides up from the bottom edge of a phone screen |
| **Safe area** | The part of a phone screen not covered by rounded corners or the home indicator |

## 2. Why it is used
The brief asks for a **mobile-responsive** platform, and people photograph plants with phones. A wide layout simply squeezed onto a phone gives tiny buttons, tables that scroll sideways and a filter sidebar that fills the screen. The wireframes replace each with a pattern made for a thumb.

| Desktop | Phone |
|---|---|
| Top navigation | **Bottom bar:** Home, Garden, +, Exchange, Profile |
| Filter sidebar | Filters in a **bottom sheet** |
| My Exchanges table | **Stacked cards** |
| "List a plant" button in the header | A **floating** button |
| "Add plant" menu | A **+ sheet:** Add plant · Identify · Health check |
| Inner pages show the navigation | Inner pages **hide the bar** to give room |

## 3. How it works: mobile first
```css
/* Base: phones. One column, bottom bar visible. */
.filters { display: none; }

/* Tablet and up */
@media (min-width: 768px) {
  .filters { display: block; }
}

/* Desktop */
@media (min-width: 1024px) {
  .page-with-sidebar { display: grid; grid-template-columns: 260px 1fr; gap: var(--gutter); }
}
```
The phone layout is the default and needs **no media query**. Wider screens add to it. The breakpoints are typed as numbers because `var()` cannot be used in a media query: [[00.05 CSS Custom Properties and Design Tokens]].

## 4. Pattern: touch targets
```css
.btn, .chip, .bottom-bar a {
  min-height: 44px;
  min-width: 44px;
}

@media (min-width: 768px) {
  .btn-sm { min-height: 32px; }      /* a mouse does not need 44 px */
}
```
A finger is far less precise than a mouse pointer. Related rules already in the project:
- **Form inputs use 16 px text on phones.** Smaller text makes iOS Safari zoom in when the field is tapped.
- **Nothing depends on hover.** A phone has none. Anything shown on hover must also be reachable by a tap.

## 5. Pattern: a table that becomes cards
A five-column table cannot fit 375 px. On a phone each row becomes a small card, with the column name beside each value.

```html
<table class="stack-table">
  <thead>
    <tr><th>Member</th><th>Rating</th><th>Message</th><th>Status</th></tr>
  </thead>
  <tbody>
    <tr>
      <td data-label="Member">@aroid.amaya</td>
      <td data-label="Rating">4.8 (31)</td>
      <td data-label="Message">I have a snake plant pup to swap.</td>
      <td data-label="Status">New</td>
    </tr>
  </tbody>
</table>
```
```css
/* Phone: each row is a card */
.stack-table thead {
  position: absolute;                 /* visually hidden, still read by screen readers */
  width: 1px; height: 1px; overflow: hidden; clip-path: inset(50%);
}
.stack-table tr {
  display: block;
  margin-bottom: var(--space-12);
  padding: var(--space-12);
  border: 1px solid var(--color-line);
  border-radius: var(--radius-card);
}
.stack-table td {
  display: flex;
  justify-content: space-between;
  gap: var(--space-12);
  padding: var(--space-4) 0;
}
.stack-table td::before {
  content: attr(data-label);          /* prints the column name */
  font-weight: var(--weight-semibold);
  color: var(--color-muted);
}

/* Tablet and up: an ordinary table again */
@media (min-width: 768px) {
  .stack-table thead { position: static; width: auto; height: auto; clip-path: none; }
  .stack-table tr { display: table-row; border: 0; padding: 0; }
  .stack-table td { display: table-cell; padding: var(--space-12); }
  .stack-table td::before { content: none; }
}
```
`attr(data-label)` reads the attribute, so the HTML is written once and only the CSS changes between layouts. One caution: changing a table's `display` can make some screen readers stop announcing it as a table. Test it, and keep the labels meaningful.

## 6. Pattern: filters in a bottom sheet
On a phone the filter form is off-screen until asked for. On a tablet it is simply part of the page.

```css
.filter-sheet {
  position: fixed;
  inset: auto 0 0 0;
  max-height: 80dvh;
  overflow-y: auto;
  padding: var(--space-16);
  padding-bottom: calc(var(--space-16) + env(safe-area-inset-bottom));
  background: var(--color-white);
  border-radius: var(--radius-card) var(--radius-card) 0 0;
  transform: translateY(100%);              /* parked below the screen */
  transition: transform var(--transition-fast);
}
.filter-sheet.is-open { transform: translateY(0); }

@media (min-width: 768px) {
  .filter-sheet { position: static; max-height: none; transform: none; border-radius: 0; padding: 0; }
}
```
A "Filters" button toggles `.is-open`. Because it behaves like a modal on a phone, the same focus rules apply: move focus into it when it opens, return it on close, close on Esc: [[02.02 Tabs, Modals, Toasts and Focus]]. The same form, with the same field names, serves both layouts: [[02.04 URLSearchParams and Shareable Filter URLs]].

- **`dvh`** is the *dynamic* viewport height. It follows the phone's address bar as it shows and hides. Plain `vh` does not, and cuts content off.
- **`env(safe-area-inset-bottom)`** adds room for the home indicator on newer phones.

## 7. Pattern: the floating button and the bar
```css
.fab {
  position: fixed;
  right: var(--space-16);
  bottom: calc(72px + env(safe-area-inset-bottom));   /* sits above the bottom bar */
  min-height: 48px;
}

@media (min-width: 768px) {
  .fab { display: none; }                              /* the header has this action */
}
```
Inner pages (a form, a detail page) hide the bottom bar. One way is a variable the page sets before including the header, which the footer checks before printing the bar.

## 8. Testing on a real phone
`CLAUDE.md` asks for this before a page is called finished.
1. **DevTools device toolbar** (F12, then the phone icon) at 375 px for quick checks.
2. **A real phone** on the same Wi-Fi: open `http://<your computer's IP address>/plantfolio/public/`.

> [!note] Why the styles may be missing on the phone
> Every stylesheet link is built from `base_url` in `config/config.php`. If that says `http://localhost/…`, the phone looks for the files on *itself*. For a phone test, set `base_url` to the computer's network address. Windows Firewall must also allow Apache.

What to look for: horizontal scrolling, text too small to read, targets too close together, content hidden behind the bar, inputs that zoom the page.

## 9. Common mistakes
- **Desktop first, then "fixing" mobile** with a pile of `max-width` rules.
- **Horizontal scroll at 375 px.** One fixed-width element is enough to cause it.
- **Hiding content on mobile** instead of rearranging it. A phone user needs the same information.
- **Targets under 44 px,** or links packed tightly together.
- **`100vh` for full-height panels** on a phone.
- **A fixed bar covering the last row** of content.
- **Features that need hover.**
- **Testing only in DevTools.** It does not show real touch, the on-screen keyboard or the safe area.
- **A separate mobile page.** One page, one HTML, different CSS: [[06.03 Mobile Web, One Web and Mobile First]].
- **A sheet with no way to close it by keyboard.**
