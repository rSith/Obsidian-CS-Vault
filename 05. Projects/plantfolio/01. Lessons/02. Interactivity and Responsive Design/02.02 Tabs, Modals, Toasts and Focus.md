# 02.02 · Tabs, Modals, Toasts and Focus

> [!info] [[02.00 Interactivity and Responsive Design|Lesson 2]] · Week 5 · Tasks COM-12, CORE-19, CORE-20, CORE-23 · Priority 🔴 Core
> **Builds on:** [[09.07 Accessible Tab Widget]] (the full tab pattern) · [[07.03 DOM Manipulation and Events]] · [[09.05 ARIA Roles, Properties and States]]
> **Used for:** the tabs on P05, P09, P13 and P14; the modals S4, S5 and S6; the toast with Undo; the grid / list toggle.

## 1. Definitions
| Term | Meaning |
|---|---|
| **Tab panel** | Several sections in one place, one shown at a time |
| **Modal dialog** | A box that appears over the page and must be answered or closed before anything else can be used |
| **Scrim** (backdrop) | The dimmed layer behind a modal |
| **Toast** | A short message that appears, confirms something and disappears by itself |
| **Focus** | The element that keyboard input currently goes to |
| **Focus management** | Moving focus deliberately when the page changes, so keyboard users are not lost |

## 2. Why it is used
- **Tabs** keep a long page (a plant's Story, Care guide, Reminders, Photos) short.
- **Modals** keep the user in context for a small task: rate a trader, log a health update, confirm a delete.
- **Toasts** confirm an action without interrupting, and offer **Undo**, which is kinder than asking "Are you sure?" for every small action.
- **Focus management** is what separates a component that works with a mouse from one that works for everyone.

## 3. Tabs
The project starts with the simplest version, already in `components.css`: **a row of links; the current one gets `.is-active`.** Each tab is a normal link (for example `plant.php?id=42&tab=reminders`) and PHP shows the matching section. It works with no JavaScript.

Week 5 adds a shared script that switches panels without a reload. The pattern, in short:

| Element | Attributes |
|---|---|
| The row | `role="tablist"` |
| Each tab | `role="tab"`, `aria-selected="true"` or `"false"`, `aria-controls="panel-id"`, `tabindex="0"` for the selected one and `"-1"` for the others |
| Each panel | `role="tabpanel"`, `aria-labelledby="tab-id"`, `hidden` unless selected |

Keyboard: **Tab** enters the row, **arrow keys** move between tabs, **Tab** again moves into the panel. The whole pattern with code is in [[09.07 Accessible Tab Widget]]; it is not repeated here.

```js
function selectTab(tab) {
  const tablist = tab.closest('[role="tablist"]');
  tablist.querySelectorAll('[role="tab"]').forEach((other) => {
    const selected = other === tab;
    other.setAttribute('aria-selected', String(selected));
    other.tabIndex = selected ? 0 : -1;
    document.getElementById(other.getAttribute('aria-controls')).hidden = !selected;
  });
}
```

## 4. Modals with the `<dialog>` element
HTML has a built-in dialog. Opened with `showModal()`, the browser itself:
- puts it above everything, with a backdrop;
- makes the rest of the page unusable while it is open;
- keeps **Tab** inside it;
- closes it on **Esc**;
- returns focus to the element that had it before, when it closes.

Building those five behaviours by hand on a `div` is where most modal bugs come from.

```html
<button class="btn btn-danger" type="button" data-modal-open="delete-plant">Delete</button>

<dialog class="modal" id="delete-plant" aria-labelledby="delete-plant-title">
  <h2 id="delete-plant-title">Delete Monty?</h2>
  <p>This removes the plant, its story and its photos. It cannot be undone.</p>
  <form method="post" action="plant-delete.php">
    <button class="btn btn-secondary" type="button" data-modal-close>Cancel</button>
    <button class="btn btn-danger" type="submit">Delete Monty</button>
  </form>
</dialog>
```
```js
document.addEventListener('click', (event) => {
  const opener = event.target.closest('[data-modal-open]');
  if (opener) {
    document.getElementById(opener.dataset.modalOpen).showModal();
    return;
  }

  if (event.target.closest('[data-modal-close]')) {
    event.target.closest('dialog').close();
    return;
  }

  // A click on the backdrop arrives with the dialog itself as its target
  if (event.target instanceof HTMLDialogElement) {
    event.target.close();
  }
});
```
```css
.modal {
  padding: 0;                              /* so only the backdrop counts as "outside" */
  border: 0;
  border-radius: var(--radius-card);
  max-width: min(480px, calc(100vw - 32px));
}

.modal::backdrop {
  background: rgba(43, 43, 40, 0.5);       /* the scrim */
}
```
This covers the four ways to close that the roadmap lists: **×, Cancel, the scrim and Esc.**

Rules from the design system, visible in the example:
- **A destructive action is confirmed in a dialog that names the item:** "Delete Monty?", and the button says "Delete Monty", not "OK".
- **One primary button per area.**
- The dialog is named for screen readers by `aria-labelledby` pointing at its heading.
- In stage F the form does nothing. In stage B it is a real POST with a CSRF token.

## 5. Toasts with Undo
```html
<div class="toast" id="toast" role="status" hidden>
  <span data-toast-text></span>
  <button class="toast-undo" type="button" data-toast-undo hidden>Undo</button>
</div>
```
```js
let toastTimer = null;
let undoAction = null;

function hideToast() {
  document.getElementById('toast').hidden = true;
  undoAction = null;
}

function showToast(message, onUndo = null) {
  const toast = document.getElementById('toast');
  toast.querySelector('[data-toast-text]').textContent = message;
  toast.querySelector('[data-toast-undo]').hidden = onUndo === null;
  undoAction = onUndo;

  toast.hidden = false;
  clearTimeout(toastTimer);
  toastTimer = setTimeout(hideToast, 6000);
}

document.querySelector('[data-toast-undo]').addEventListener('click', () => {
  if (undoAction) undoAction();
  hideToast();
});

// showToast('Watered Monty · next on 7 Oct', () => restoreReminder(11));
```
- **`role="status"`** makes screen readers announce the new text politely, without moving focus. The element must already be in the page when the text changes.
- **`textContent`**, never `innerHTML`: the message contains a plant's name, which a user typed.
- **`clearTimeout`** stops an earlier timer from hiding a newer toast.
- Leave it visible long enough to read and reach the button. Six seconds is a reasonable start.

| Use a toast for | Do not use a toast for |
|---|---|
| "Saved", "Watered Monty" | An error the user must fix |
| An action that can be undone | Anything that needs a decision |

## 6. The grid / list toggle
Two buttons that switch My Garden between cards and a table:
```html
<div role="group" aria-label="View">
  <button type="button" data-view="grid" aria-pressed="true">Grid</button>
  <button type="button" data-view="list" aria-pressed="false">List</button>
</div>
```
`aria-pressed` tells a screen reader which is on, and the CSS styles `[aria-pressed="true"]`. The script flips the two values and switches which view has the `hidden` attribute.

## 7. Focus: four rules
1. **Opening** something moves focus **into** it.
2. **Closing** it returns focus to **what opened it**.
3. While a modal is open, focus **cannot leave** it.
4. Focus is **always visible** (`:focus-visible`).

`<dialog>` gives the first three. Check all four by using each component **with the keyboard only**.

## 8. Common mistakes
- **A `div` modal with no focus handling.** Tab walks through the page behind it.
- **A modal that cannot be closed with Esc,** or has no visible close button.
- **"Are you sure?" with OK and Cancel.** Name the item and the action.
- **Opening a modal from a modal.**
- **A toast that vanishes too fast,** or covers the bottom bar on a phone.
- **An error shown in a toast.** It disappears before it is read.
- **`innerHTML` for the message.**
- **Tabs built from `div`s with click handlers.** They cannot be reached with the keyboard.
- **Showing a panel with CSS only** and not updating `aria-selected`.
- **Confirmations everywhere.** For small, reversible actions use Undo.

## 9. Exam and viva focus
- **Modal vs non-modal dialog.**
- **ARIA roles for tabs:** `tablist`, `tab`, `tabpanel`; `aria-selected`, `aria-controls`.
- **What is a live region?** `role="status"` and `aria-live`: content that is announced when it changes.
- **Why is focus management needed?** Keyboard and screen-reader users must know where they are after the page changes.
- **Error prevention and recovery:** confirmation dialogs vs Undo. See [[05.08 UI Design Principles]].
- **The first rule of ARIA:** use a native element when one exists. See [[09.04 Introduction to ARIA and the Five Rules]].
