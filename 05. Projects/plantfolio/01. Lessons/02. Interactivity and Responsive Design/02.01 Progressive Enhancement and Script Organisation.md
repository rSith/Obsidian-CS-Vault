# 02.01 · Progressive Enhancement and Script Organisation

> [!info] [[02.00 Interactivity and Responsive Design|Lesson 2]] · Week 5 · Priority 🔴 Core
> **Builds on:** [[07.03 DOM Manipulation and Events]] · [[07.02 JavaScript fetch and Promises]]
> **Used for:** deciding what JavaScript is allowed to be responsible for, and how `app.js`, `forms.js` and `filters.js` are structured.

## 1. Definitions
> [!note] Progressive enhancement
> **Progressive enhancement** means building in layers. The page first works with HTML alone. CSS then makes it look right. JavaScript finally makes it more convenient. Each layer improves the one below and none is required for the basic task.

| Term | Meaning |
|---|---|
| **Graceful degradation** | The opposite direction: build the full experience, then try to keep it usable when something is missing |
| **Hook** | The attribute a script uses to find the elements it should act on |
| **`defer`** | A `<script>` attribute: download now, run after the HTML has been read |

## 2. Why it is used
`CLAUDE.md` states the approach: *pages are server-rendered; forms POST normally first; `fetch()` is added later only where the wireframes ask for no-reload actions.* The reasons:

- **Reliability.** A script that fails to load, or stops on an error, must not leave a member unable to log a health update.
- **Security stays on the server.** If the form works without JavaScript, the server has to validate and authorise every request anyway. Nothing depends on browser code that a user can switch off or change.
- **Accessibility.** Native links, buttons and forms work with keyboards and screen readers before any script runs.
- **The viva.** Each feature has a plain version you can explain, and an enhanced version built on it.

## 3. How it works: three layers of one feature
"Mark done" on a care reminder:

| Layer | What exists | Result |
|---|---|---|
| **HTML** (stage B) | A small `<form method="post">` around the button | Click → the page reloads → the reminder is done |
| **CSS** | The button styled as `.btn .btn-secondary` | Looks right |
| **JavaScript** | Intercepts the submit, sends it with `fetch`, shows a toast with Undo | No reload |

If the script fails, the form still submits the ordinary way.

```js
document.querySelectorAll('form[data-enhance="mark-done"]').forEach((form) => {
  form.addEventListener('submit', async (event) => {
    event.preventDefault();                              // stop the normal reload

    try {
      const response = await fetch(form.action, {
        method: 'POST',
        body: new FormData(form),                        // the same fields the form would send
        headers: { Accept: 'application/json' },
      });
      if (!response.ok) throw new Error(`Status ${response.status}`);

      const result = await response.json();
      showToast(result.message);
    } catch (error) {
      form.submit();                                     // fall back to the normal way
    }
  });
});
```
In stage F only the toast part exists, because nothing is saved yet.

## 4. Loading scripts
```html
<script src="assets/js/app.js" defer></script>
```
| Attribute | Download | Runs | Order kept |
|---|---|---|---|
| none | Blocks the page while downloading | Immediately | Yes |
| `async` | In parallel | As soon as it arrives, possibly before the HTML is complete | No |
| **`defer`** | In parallel | **After the HTML is read** | **Yes** |

With `defer`, every element already exists when the script starts, so `document.querySelector` finds what it is looking for. This is the project's rule.

## 5. Hooks: `data-*` attributes, not styling classes
```html
<button class="btn btn-danger" type="button" data-modal-open="delete-plant">Delete</button>
```
```js
const opener = event.target.closest('[data-modal-open]');
const dialogId = opener.dataset.modalOpen;               // "delete-plant"
```
- Classes say how something **looks**. `data-*` attributes say what a script should **do** with it.
- A designer can rename `.btn-danger` without breaking behaviour, and a developer can move the hook without changing the look.
- `data-modal-open` in HTML becomes `dataset.modalOpen` in JavaScript: the dashes turn into camelCase.

**State** is the exception. A class such as `.is-active`, or better an ARIA attribute such as `aria-selected="true"`, is set by the script and styled by the CSS.

## 6. No inline handlers
```html
<!-- Not in this project -->
<button onclick="deletePlant(42)">Delete</button>

<!-- Instead -->
<button type="button" data-action="delete" data-plant-id="42">Delete</button>
```
Inline handlers mix behaviour into the HTML, need global functions, and are blocked by a strict Content Security Policy. With event listeners, all behaviour is in the `.js` files.

## 7. Example: the shape of a script file
```js
// assets/js/app.js: tabs, modals, toasts, navigation

function initModals() {
  document.addEventListener('click', (event) => {
    const opener = event.target.closest('[data-modal-open]');
    if (opener) {
      document.getElementById(opener.dataset.modalOpen).showModal();
    }
  });
}

function initTabs() {
  // set up every element marked data-tabs
}

initModals();
initTabs();
```
- One `init…` function per feature; each finds its own hooks and does nothing if the page has none. The same file can then load on every page.
- **One listener on `document`** handles every opener on the page, including ones added later. This is event delegation: [[07.03 DOM Manipulation and Events]].
- Use `const` by default and `let` when a value changes. Never `var`.

> [!note] Three files share one global space
> Plain scripts all define their functions in the same global scope. Two files that both define `init()` overwrite each other. Give functions specific names (`initTabs`, `initValidation`), or load the files with `type="module"`, which gives each file its own scope and behaves like `defer`.

## 8. Common mistakes
- **A feature that exists only in JavaScript.** A "form" built from `div`s that only `fetch` can submit.
- **`<a href="#">` or a `div` as a button.** Use `<button type="button">` for actions and `<a>` for navigation.
- **Forgetting `type="button"`.** Inside a form, a `<button>` without a type **submits the form**.
- **Scripts without `defer`** in the `<head>`. `querySelector` returns `null`.
- **Hooking behaviour to styling classes.**
- **A listener on every row** instead of one delegated listener.
- **`console.log` left in.** The project's rule is to remove them.
- **Hiding content with JavaScript at load.** The page flashes. If something starts hidden, say so in the HTML (`hidden`) or the CSS.
- **Trusting anything decided in the browser.** A disabled button, a hidden field and a JavaScript check can all be bypassed.
- **Calling `preventDefault()` and then failing** before the request is sent. The user clicks and nothing happens. Fall back.

## 9. Exam and viva focus
- **Define progressive enhancement** and contrast it with graceful degradation.
- **The three layers of a web page:** structure (HTML), presentation (CSS), behaviour (JavaScript). **Separation of concerns.**
- **`defer` vs `async`.**
- **Unobtrusive JavaScript:** behaviour attached from script files, not written into the HTML.
- **What are `data-*` attributes?** Custom attributes for storing extra information on an element, read with `dataset`.
- **`let`, `const` and `var`.**
- **Why must validation and access checks be on the server?**
- **Viva:** "What happens on this page if JavaScript is disabled?" · "Why is there no `onclick` anywhere?" · "Why does the form still have an `action` if `fetch` sends it?"
