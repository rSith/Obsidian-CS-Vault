# 04.05 · Counts, Averages and Rating Rules in SQL

> [!info] [[04.00 Core Features|Lesson 4]] · Weeks 9–10 · Tasks CORE-27, COM-05, COM-12, COM-13 · Priority 🟡 Supporting
> **Parent concept:** [[06.02 SQL Joins, Aggregation and Indexes]], which explains joins, `GROUP BY` and aggregate functions. This note covers how PlantFolio uses them.
> **Used for:** the numbers on profiles, cards and the landing page, and the rules that keep ratings honest.

## 1. Definitions
| Term | Meaning |
|---|---|
| **Derived (calculated) value** | A value worked out from other data when it is needed, not stored |
| **Aggregate function** | A function that turns many rows into one value: `COUNT`, `AVG`, `SUM`, `MIN`, `MAX` |
| **Scalar subquery** | A small query inside another that returns exactly one value |
| **Rating breakdown** | How many 5-star, 4-star … 1-star ratings a member has |

## 2. Why it is used
The mock data marks five values on the user as *"not columns of `users`: stage B calculates these with `COUNT()` and `AVG()`"*: `plant_count`, `collection_count`, `swap_count`, `rating_avg`, `rating_count`. Listings carry `interest_count` and the owner's rating. The landing page shows live totals.

If these were stored, every new plant, rating or interest would have to update a counter somewhere else, and one missed update makes the number wrong for good. Calculating them from the real rows means they **cannot disagree** with the data.

## 3. How it works: scalar subqueries
```sql
SELECT u.id, u.username, u.full_name, u.bio, u.location, u.avatar, u.created_at,
       (SELECT COUNT(*) FROM plants p WHERE p.user_id = u.id)                AS plant_count,
       (SELECT COUNT(*) FROM collections c WHERE c.user_id = u.id)           AS collection_count,
       (SELECT COUNT(*) FROM user_ratings r WHERE r.rated_id = u.id)         AS rating_count,
       (SELECT ROUND(AVG(r.score), 1) FROM user_ratings r WHERE r.rated_id = u.id) AS rating_avg
FROM users u
WHERE u.username = :username;
```
Each bracket is its own small query, run for the one user, giving one value. The result row has exactly the keys of the mock `$current_user`.

For a **public** profile, count only what the visitor may see: `p.is_public = 1`.

## 4. The trap this avoids
It is tempting to join everything and count:

```sql
-- WRONG: the counts multiply each other
SELECT u.id, COUNT(p.id) AS plant_count, COUNT(r.id) AS rating_count
FROM users u
LEFT JOIN plants p ON p.user_id = u.id
LEFT JOIN user_ratings r ON r.rated_id = u.id
GROUP BY u.id;
```
A member with 18 plants and 23 ratings produces $18 \times 23 = 414$ joined rows, and **both counts come out as 414**. Two unrelated one-to-many joins multiply. The fixes: separate subqueries as above, or `COUNT(DISTINCT p.id)`.

## 5. Averages and "no ratings yet"
- `AVG()` over no rows returns **`NULL`**, not 0. A member with no ratings has `rating_avg = NULL` and `rating_count = 0`.
- The `rating` partial already handles it: it shows the stars only when `rating_count > 0` and otherwise prints "No ratings yet".
- Round in SQL (`ROUND(AVG(score), 1)`) or in PHP (`number_format`), not both.
- An average of 5.0 from one rating is not the same as 4.9 from 23. That is why the count is always shown beside it.

## 6. Example: the rating breakdown
```php
<?php
/** Number of ratings at each score, from 5 down to 1, including scores nobody gave. */
function get_rating_breakdown(int $user_id): array
{
    $stmt = db()->prepare(
        'SELECT score, COUNT(*) AS total
         FROM user_ratings
         WHERE rated_id = :user_id
         GROUP BY score'
    );
    $stmt->execute(['user_id' => $user_id]);
    $found = $stmt->fetchAll(PDO::FETCH_KEY_PAIR);      // [5 => 19, 4 => 3, 3 => 1]

    $breakdown = [];
    foreach ([5, 4, 3, 2, 1] as $score) {
        $breakdown[$score] = (int) ($found[$score] ?? 0);   // fill the gaps with 0
    }

    return $breakdown;
}
```
`GROUP BY` returns a row only for scores that exist. The bars on the profile need all five, so PHP fills the missing ones with 0.

## 7. Counts on a list of rows
The listing cards need each listing's interest count. One grouped subquery, joined in:

```sql
SELECT l.id, l.title, l.type, l.location, l.created_at,
       u.username, u.full_name, u.avatar,
       COALESCE(i.interest_count, 0) AS interest_count
FROM exchange_listings l
JOIN users u ON u.id = l.user_id
LEFT JOIN (
    SELECT listing_id, COUNT(*) AS interest_count
    FROM listing_interests
    WHERE status <> 'withdrawn'
    GROUP BY listing_id
) i ON i.listing_id = l.id
WHERE l.status = 'open'
ORDER BY l.created_at DESC;
```
- The subquery counts once per listing; the `LEFT JOIN` attaches the result.
- **`COALESCE(x, 0)`** replaces `NULL` (no interests) with 0.

## 8. The rules that make a rating trustworthy
A rating system is worthless if it can be gamed. The task COM-12 says *"one per person per exchange"*. The full set of rules, and where each is enforced:

| Rule | Enforced by |
|---|---|
| A score is a whole number from 1 to 5 | `CHECK (score BETWEEN 1 AND 5)` and PHP validation |
| One rating per person per exchange | **`UNIQUE (rater_id, listing_id)`** in the table plan |
| Nobody rates themselves | PHP: `rater_id !== rated_id` |
| Only the two people in the exchange may rate it | PHP: the listing is marked exchanged, and the rater is its owner or the member in `exchanged_with` |
| Only after the exchange happened | PHP: the listing's status |
| The rater is the logged-in user | `rater_id` comes from the session, never from the form |

```php
<?php
try {
    $stmt = db()->prepare('INSERT INTO user_ratings (rater_id, rated_id, listing_id, score, comment)
                           VALUES (:rater_id, :rated_id, :listing_id, :score, :comment)');
    $stmt->execute([
        'rater_id'   => $current_user['id'],
        'rated_id'   => $rated_id,
        'listing_id' => $listing_id,
        'score'      => $score,
        'comment'    => $comment,
    ]);
} catch (PDOException $error) {
    if ($error->getCode() !== '23000') {
        throw $error;
    }
    $errors['score'] = 'You have already rated this exchange.';     // the UNIQUE rule refused it
}
```
The database's `UNIQUE` rule is what truly prevents a second rating, even if two requests arrive at the same instant. PHP only translates its refusal into a friendly message.

The same pattern serves likes (COM-15): `UNIQUE (plant_id, user_id)` means a member can like a plant once.

## 9. The landing-page counts
"1,240 plants · 310 members · 85 swaps" on the landing page (CORE-27) are three `COUNT(*)` queries. Count only **public** plants. On a busy site such numbers would be cached; here they can be calculated on each visit.

## 10. Common mistakes
- **Two one-to-many joins and a `COUNT`.**
- **Treating `NULL` as 0** without `COALESCE`, or printing "★ (0)".
- **Stored counters** that drift from the truth.
- **Counting private plants** on a public profile.
- **`rater_id` or `rated_id` from a hidden field.**
- **No `UNIQUE` rule,** relying on "check if they already rated".
- **Allowing a rating before any exchange,** or from someone who was not part of it.
- **An average with no count beside it.**
- **`COUNT(column)` when `COUNT(*)` was meant.** `COUNT(column)` skips `NULL` values.
- **Selecting a column that is neither grouped nor aggregated.**
- **A query per row in a loop** (one count query for each of 12 cards). Use a join or a subquery so the page runs a fixed number of queries.
