# 04.03 · Dates, Reminders and Due Logic

> [!info] [[04.00 Core Features|Lesson 4]] · Week 9 · Tasks CORE-22, CORE-23, CORE-24 · Priority 🔴 Core
> **Builds on:** [[03.02 PDO and Prepared Statements]] · [[06.02 SQL Joins, Aggregation and Indexes]]
> **Used for:** the care reminders, the Dashboard's "Today's care", and Mark done with Undo.

## 1. Definitions
| Term | Meaning |
|---|---|
| **Recurring task** | Something that repeats at a fixed interval: water every 7 days |
| **`last_done`** | The date the task was last completed |
| **`interval_days`** | How many days between two completions |
| **`next_due`** | The date the task should next be done |
| **Overdue** | `next_due` is before today |
| **Time zone** | The offset that decides what "today" means |

## 2. Why it is used
Care reminders are one of the nine core features, and the Dashboard is built around them. The whole feature rests on one rule from `database/README.md`:

$$\text{next\_due} = \text{last\_done} + \text{interval\_days}$$

> *"Reminders are calculated from `next_due` — no background scheduler is needed for the Dashboard."*

Nothing runs at midnight to mark tasks as due. A reminder is "due" simply because its `next_due` date is today or earlier **at the moment someone looks**. That keeps the system small enough to explain completely.

## 3. How it works
| `next_due` compared with today | State | Shown as | Colour |
|---|---|---|---|
| Earlier | `overdue` | "Overdue 2 days" | Red |
| The same day | `due` | "Due today" | Terracotta |
| Tomorrow | `upcoming` | "Tomorrow" | |
| Later | `upcoming` | "In 3 days" | |

The helper `care_due()` already turns a `next_due` date into this state and text. It was written in stage F against mock dates and needs no change.

**Store the facts, work out the state.** The table holds dates. "Overdue" is never stored: it would be wrong by tomorrow.

## 4. One clock
"Today" must mean the same thing everywhere. Two clocks exist: PHP's and the database's.

- The helpers set PHP to **`Asia/Colombo`**, because XAMPP's default is another country's time zone (`Europe/Berlin` in this computer's `php.ini`).
- SQL functions such as `CURDATE()` use the **database server's** time zone, which may differ.

So let PHP decide the date and pass it into every query:
```php
<?php
$today = date('Y-m-d');          // one clock: PHP, in Asia/Colombo
```
Then a reminder cannot be "due" on the Dashboard and "upcoming" in a query during the hours when the two clocks disagree.

## 5. Syntax: date arithmetic
| Need | SQL |
|---|---|
| Add days | `DATE_ADD(last_done, INTERVAL interval_days DAY)` |
| Days between two dates | `DATEDIFF(next_due, :today)` |
| Today or earlier | `next_due <= :today` |
| This week | `next_due BETWEEN :today AND DATE_ADD(:today2, INTERVAL 7 DAY)` |

| Type | Holds | Use |
|---|---|---|
| `DATE` | A day | `last_done`, `next_due`, `acquired_on` |
| `DATETIME` | A day and time | `created_at`, `logged_at` |

Dates written `YYYY-MM-DD` sort correctly as text and are what MySQL returns.

## 6. Example: the Dashboard query
The mock array `$mock_reminders` defines the shape. The query returns it:

```php
<?php
/** Reminders that are due today or overdue, most overdue first. */
function get_due_reminders(int $user_id, string $today): array
{
    $stmt = db()->prepare(
        'SELECT r.id, r.plant_id, r.task, r.interval_days, r.last_done, r.next_due,
                p.nickname, p.photo, s.common_name
         FROM care_reminders r
         JOIN plants p ON p.id = r.plant_id
         JOIN plant_species s ON s.id = p.species_id
         WHERE p.user_id = :user_id AND r.next_due <= :today
         ORDER BY r.next_due ASC'
    );
    $stmt->execute(['user_id' => $user_id, 'today' => $today]);

    return $stmt->fetchAll();
}
```
The reminder has no `user_id` of its own. Ownership is reached **through the plant**: `p.user_id = :user_id`.

## 7. Example: Mark done
```php
<?php
/** Mark a reminder done today. Returns its previous dates for Undo, or null if it is not the user's. */
function mark_reminder_done(int $reminder_id, int $user_id, string $today): ?array
{
    $pdo = db();

    // 1. Load it as its owner, and keep the old dates
    $stmt = $pdo->prepare(
        'SELECT r.id, r.last_done, r.next_due, r.interval_days
         FROM care_reminders r JOIN plants p ON p.id = r.plant_id
         WHERE r.id = :id AND p.user_id = :user_id'
    );
    $stmt->execute(['id' => $reminder_id, 'user_id' => $user_id]);
    $before = $stmt->fetch();

    if ($before === false) {
        return null;
    }

    // 2. Apply the rule: next_due = last_done + interval_days
    $stmt = $pdo->prepare(
        'UPDATE care_reminders
         SET last_done = :today, next_due = DATE_ADD(:today2, INTERVAL interval_days DAY)
         WHERE id = :id'
    );
    $stmt->execute(['today' => $today, 'today2' => $today, 'id' => $reminder_id]);

    return $before;
}
```
For the toast "Watered Monty · next on 7 Oct — Undo":
- the **next date** for the message is `date('Y-m-d', strtotime($today . ' +' . $before['interval_days'] . ' days'))`, shown with `format_day()`;
- **Undo** writes `$before['last_done']` and `$before['next_due']` back, through the same owner check.

Where to keep `$before` until Undo is pressed is a design choice: in the session, or sent back in the JSON reply and returned by the Undo request. Either way the Undo request is a POST with a CSRF token and is checked for ownership again.

## 8. The soonest reminder for a plant card
Each plant card shows the hint of its **soonest** reminder. A plant can have several reminders, or none. One way to fetch exactly one per plant:

```sql
SELECT p.id, p.nickname, p.photo, p.health_status,
       r.task, r.interval_days, r.next_due
FROM plants p
LEFT JOIN care_reminders r
       ON r.id = (SELECT r2.id FROM care_reminders r2
                  WHERE r2.plant_id = p.id
                  ORDER BY r2.next_due ASC
                  LIMIT 1)
WHERE p.user_id = :user_id
ORDER BY p.nickname;
```
`LEFT JOIN` keeps plants with no reminder; their `next_due` is `NULL`, and the card partial already skips the hint in that case.

## 9. Decisions the rule leaves open
| Question | Options |
|---|---|
| A task done **late**: is the next one counted from today, or from when it was due? | From today (the rule as written). The plant was watered today, so it needs water again in 7 days. |
| The interval is edited | Recalculate `next_due` from `last_done` with the new interval |
| A new reminder | `last_done` = today, or the day it was really last done |
| A re-check after a diagnosis (ML-16) | A reminder 7 days ahead; decide what `task` value it uses |

Write the answers in the data dictionary so the code and the report agree.

## 10. Common mistakes
- **Storing "overdue" or "due today"** in a column.
- **Two clocks:** `date()` in PHP and `CURDATE()` in SQL, in different time zones.
- **Dates as text in another format** (`07/10/2026`). They do not sort, and is that 7 October or 10 July?
- **Comparing a `DATETIME` with a date** and missing rows from later the same day.
- **Off by one:** "in 1 day" where "Tomorrow" was meant; `<` where `<=` was meant.
- **An update with no owner check,** because the reminders table has no `user_id`. Join through the plant.
- **`INNER JOIN` to reminders** in the garden query. Plants without a reminder disappear.
- **Forgetting the rule in seed data.** Every seeded row must satisfy `next_due = last_done + interval_days`.
- **Fixed dates in the seed.** They are all overdue a month later.
- **A background job** added for something the query already does.
