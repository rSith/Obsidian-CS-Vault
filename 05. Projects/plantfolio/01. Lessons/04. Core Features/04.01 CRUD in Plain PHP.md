# 04.01 · CRUD in Plain PHP

> [!info] [[04.00 Core Features|Lesson 4]] · Weeks 9–10 · Tasks CORE-13, CORE-16, CORE-19, CORE-20, COM-06 · Priority 🔴 Core
> **Builds on:** [[03.02 PDO and Prepared Statements]] · [[03.06 Form Handling - Validation, Redirects and Flash Messages]] · [[03.07 Access Control and Ownership Checks]]
> **Used for:** collections, plants, health logs, reminders and listings.

## 1. Definition
> [!note] CRUD
> **CRUD** stands for **C**reate, **R**ead, **U**pdate, **D**elete: the four things an application does with stored data.

| Operation | SQL | HTTP method | In PlantFolio |
|---|---|---|---|
| **Create** | `INSERT` | POST | Add a plant, create a listing |
| **Read** | `SELECT` | GET | My Garden, a plant's profile |
| **Update** | `UPDATE` | POST | Edit a plant, rename a collection, mark a reminder done |
| **Delete** | `DELETE` | POST | Delete a plant, close a listing |

## 2. Why it is used
Almost every feature of the site is CRUD on one table, with rules about who may do it. Learn the pattern once on the simplest table (collections) and the rest is the same pattern with more columns.

## 3. How it works: the wiring recipe
The pages already exist. The roadmap's instruction for stage B: *"Replace one mock array at a time with a query function returning the same shape, and delete it from `mock-data.php` when done."*

```text
1. Write a function that runs the query and returns rows shaped like the mock array.
2. In the page, replace  $mock_plants  with a call to that function.
3. Reload. The page should look exactly as it did.
4. Delete the mock array.
5. Make the forms save. Run the Test Plan cases. Try wrong inputs.
```
Step 3 is the test of the contract described in [[00.07 Mock Data Shaped Like Database Rows]]. If the page changes, the query's column names or types differ from the mock.

## 4. Read
```php
<?php
/** A member's collections with the number of plants in each. */
function get_collections(int $user_id): array
{
    $stmt = db()->prepare(
        'SELECT c.id, c.name, c.is_public, COUNT(p.id) AS plant_count
         FROM collections c
         LEFT JOIN plants p ON p.collection_id = c.id
         WHERE c.user_id = :user_id
         GROUP BY c.id, c.name, c.is_public
         ORDER BY c.name'
    );
    $stmt->execute(['user_id' => $user_id]);

    return $stmt->fetchAll();
}
```
A `LEFT JOIN` keeps collections with no plants, with a count of 0. Aliases (`AS plant_count`) produce the exact keys the page reads.

## 5. Create
```php
<?php
if ($_SERVER['REQUEST_METHOD'] === 'POST') {
    csrf_verify();

    $name      = trim((string) ($_POST['name'] ?? ''));
    $is_public = isset($_POST['is_public']) ? 1 : 0;        // a checkbox is absent when unticked

    if ($name === '' || mb_strlen($name) > 60) {
        $errors['name'] = 'Give the collection a name of up to 60 characters.';
    }

    if (!$errors) {
        $stmt = db()->prepare('INSERT INTO collections (user_id, name, is_public)
                               VALUES (:user_id, :name, :is_public)');
        $stmt->execute([
            'user_id'   => $current_user['id'],             // from the session, never from the form
            'name'      => $name,
            'is_public' => $is_public,
        ]);

        flash_set('Collection "' . $name . '" created.');
        header('Location: ' . url('garden.php'), true, 303);
        exit;
    }
}
```

## 6. Update
```php
<?php
$stmt = db()->prepare('UPDATE collections SET name = :name, is_public = :is_public
                       WHERE id = :id AND user_id = :user_id');
$stmt->execute([
    'name'      => $name,
    'is_public' => $is_public,
    'id'        => $id,
    'user_id'   => $current_user['id'],
]);

if ($stmt->rowCount() === 0) {
    // Nothing matched (not theirs, or gone) OR nothing changed. Load the row to tell which.
}
```
Three rules:
- **List the columns you allow to change.** Never build the `SET` from whatever the request contains.
- **`AND user_id = :user_id`** in the `WHERE`.
- **`rowCount()` is 0 in two cases:** no matching row, and a matching row whose values were already the same. Do not treat 0 as an error without checking.

### One form for add and edit
`plant-form.php` serves both (wireframe P06). The presence of an ID decides:

| | Add | Edit |
|---|---|---|
| Address | `plant-form.php` | `plant-form.php?id=42` |
| On GET | Empty form | Form filled from the row, loaded **as its owner** |
| On POST | `INSERT` | `UPDATE … WHERE id = :id AND user_id = :user_id` |
| Validation | The same code | The same code |

## 7. Delete
```php
<?php
// Deleting a plant together with its photo files (CORE-20)
csrf_verify();

$id = filter_input(INPUT_POST, 'id', FILTER_VALIDATE_INT);
$plant = $id ? find_owned_plant($id, $current_user['id']) : null;
if ($plant === null) {
    not_found();
}

// 1. Remember which files belong to it
$stmt = db()->prepare('SELECT photo FROM health_logs WHERE plant_id = :id AND photo IS NOT NULL');
$stmt->execute(['id' => $id]);
$files = $stmt->fetchAll(PDO::FETCH_COLUMN);
if ($plant['photo'] !== null) {
    $files[] = $plant['photo'];
}

// 2. Delete the row. ON DELETE CASCADE removes its logs and reminders.
$stmt = db()->prepare('DELETE FROM plants WHERE id = :id AND user_id = :user_id');
$stmt->execute(['id' => $id, 'user_id' => $current_user['id']]);

// 3. Only then remove the files
foreach ($files as $file) {
    $path = config('upload_dir') . '/' . basename($file);     // basename: never leave the uploads folder
    if (is_file($path)) {
        unlink($path);
    }
}

flash_set($plant['nickname'] . ' was deleted.');
header('Location: ' . url('garden.php'), true, 303);
exit;
```
**Why database first, files second?** If the order were reversed and the delete query failed, the plant would remain with broken images. In this order the worst case is a leftover file nobody can reach, which is harmless.

The database removes child **rows** through `ON DELETE CASCADE` ([[03.01 MySQL Schema - Types, Keys and Foreign Key Rules]]). It knows nothing about **files**. PHP must remove those.

## 8. A checklist for every write
- [ ] POST only; `csrf_verify()` first
- [ ] `require_login()`; the user ID comes from the session
- [ ] Every value validated on the server
- [ ] A prepared statement, with named columns
- [ ] `AND user_id = :user_id` on update and delete
- [ ] Several related queries wrapped in a transaction
- [ ] Flash message, then redirect with `exit`
- [ ] Tested with a second account

## 9. Common mistakes
- **Wiring several pages at once.** When something breaks you cannot tell which change did it. One array at a time.
- **A query whose columns differ from the mock's keys.** The page prints warnings or blanks.
- **`SELECT *` with joins.** Two tables both have `id` and `name`; one overwrites the other in the row. Name and alias the columns.
- **`INNER JOIN` where `LEFT JOIN` is needed.** Collections with no plants, or plants with no reminder, vanish from the list.
- **Building the `SET` from `$_POST`.**
- **No owner condition.**
- **Deleting with a link.**
- **Leaving files on disk,** or deleting them before the row.
- **No transaction** around an insert that needs two tables.
- **A checkbox read with `$_POST['is_public']`** directly. An unticked box sends nothing.
- **Keeping the mock array "just in case".** The page then quietly falls back to fake data.

## 10. Exam and viva focus
- **Expand CRUD** and map each letter to SQL and to an HTTP method.
- **DML statements:** `INSERT`, `SELECT`, `UPDATE`, `DELETE`, with syntax.
- **`DELETE` vs `TRUNCATE` vs `DROP`:** remove chosen rows; remove all rows; remove the table.
- **Why must `UPDATE` and `DELETE` have a `WHERE`?**
- **What is a transaction, and when is one needed?**
- **Soft delete vs hard delete:** marking a row as deleted vs removing it.
- **Viva:** "Show me how a mock array became a query, and what changed in the page." (Nothing below the data line.) · "What happens to the photo file when a plant is deleted?" · "Why is the same file used for adding and editing a plant?"
