# 04.04 · Search, Filters and Pagination

> [!info] [[04.00 Core Features|Lesson 4]] · Week 10 · Tasks COM-01 – COM-04, CORE-15 · Priority 🔴 Core
> **Builds on:** [[01.03 Query Strings and GET Parameters in PHP]] · [[02.04 URLSearchParams and Shareable Filter URLs]] · [[03.02 PDO and Prepared Statements]]
> **Used for:** Explore, the Exchange marketplace and the My Garden filter bar.

## 1. Definitions
| Term | Meaning |
|---|---|
| **`LIKE`** | An SQL comparison that matches text against a pattern |
| **Wildcard** | A symbol standing for unknown characters: `%` any number, `_` exactly one |
| **Dynamic query** | A query whose `WHERE` is assembled from the filters that are actually set |
| **Pagination** | Showing results a page at a time |
| **`LIMIT` / `OFFSET`** | How many rows to return, and how many to skip first |

## 2. Why it is used
"Search and discovery" is one of the nine core features. The filters already produce a query string in stage F. Now the server must turn that string into a query, safely, and return twelve results at a time (COM-04).

This page is also the most likely place in the project for **SQL injection**, because it takes several user-chosen values and builds a query from them. The test in the roadmap is typing `' OR '1'='1` into the search box.

## 3. How it works: three parts of the query
```text
SELECT … FROM …
WHERE   <fixed rules>  AND  <one condition per active filter>     ← values through placeholders
ORDER BY <one of a few allowed orders>                            ← chosen from a whitelist
LIMIT 12 OFFSET <(page - 1) × 12>                                 ← integers
```
Each part is made safe in a different way, because a placeholder can stand only for a **value** ([[03.02 PDO and Prepared Statements]]).

## 4. Searching with `LIKE`
```php
<?php
$like = '%' . addcslashes($q, '%_\\') . '%';     // "pothos" → "%pothos%"
```
- The **wildcards go in the value**, not in the SQL. The SQL says `LIKE :q`.
- **`addcslashes($q, '%_\\')`** puts a backslash before `%`, `_` and `\` in what the user typed. Otherwise a search for `100%` means "100 followed by anything", and `_` matches any character.
- With a `utf8mb4_unicode_ci` collation, `LIKE` ignores upper and lower case: `Pothos` finds `pothos`.

| Pattern | Matches |
|---|---|
| `pothos%` | Starts with "pothos" |
| `%pothos` | Ends with "pothos" |
| `%pothos%` | Contains "pothos" |

## 5. Example: the marketplace query
```php
<?php
/** One page of open listings matching the filters, and the total number of matches. */
function search_listings(string $q, string $type, string $sort, int $page, int $per_page = 12): array
{
    // 1. Conditions: fixed rules first, then one per active filter
    $where  = ["l.status = 'open'"];
    $params = [];

    if ($q !== '') {
        $like = '%' . addcslashes($q, '%_\\') . '%';
        $where[] = '(l.title LIKE :q1 OR l.looking_for LIKE :q2)';
        $params['q1'] = $like;
        $params['q2'] = $like;                    // a named placeholder can be used only once
    }
    if (in_array($type, ['swap', 'free', 'either'], true)) {
        $where[] = 'l.type = :type';
        $params['type'] = $type;
    }
    $where_sql = implode(' AND ', $where);

    // 2. Order: only texts written here can reach the SQL
    $orders = ['newest' => 'l.created_at DESC', 'title' => 'l.title ASC'];
    $order_sql = $orders[$sort] ?? $orders['newest'];

    // 3. Total, for the page links
    $stmt = db()->prepare("SELECT COUNT(*) FROM exchange_listings l WHERE $where_sql");
    $stmt->execute($params);
    $total = (int) $stmt->fetchColumn();

    // 4. One page of rows
    $stmt = db()->prepare(
        "SELECT l.id, l.title, l.type, l.looking_for, l.location, l.photo, l.created_at,
                u.username, u.full_name, u.avatar
         FROM exchange_listings l
         JOIN users u ON u.id = l.user_id
         WHERE $where_sql
         ORDER BY $order_sql
         LIMIT :limit OFFSET :offset"
    );
    foreach ($params as $name => $value) {
        $stmt->bindValue(':' . $name, $value);
    }
    $stmt->bindValue(':limit', $per_page, PDO::PARAM_INT);
    $stmt->bindValue(':offset', ($page - 1) * $per_page, PDO::PARAM_INT);
    $stmt->execute();

    return ['rows' => $stmt->fetchAll(), 'total' => $total];
}
```
Why this is safe even though the SQL is built from pieces:
- `$where_sql` contains only **text written in the code** plus placeholder names. No user value is ever placed in it.
- `$order_sql` is one of two strings from the `$orders` array. An unknown `sort` falls back to the default.
- Every user value travels through a placeholder.

The rating and interest counts on the cards are added in [[04.05 Counts, Averages and Rating Rules in SQL]].

## 6. Pagination
$$\text{offset} = (\text{page} - 1) \times \text{per\_page} \qquad \text{pages} = \left\lceil \frac{\text{total}}{\text{per\_page}} \right\rceil$$

| Page | `LIMIT 12 OFFSET …` | Rows shown |
|---|---|---|
| 1 | 0 | 1–12 |
| 2 | 12 | 13–24 |
| 3 | 24 | 25–36 |

```php
<?php
$page = max(1, (int) filter_input(INPUT_GET, 'page', FILTER_VALIDATE_INT));

$result = search_listings($q, $type, $sort, $page);
$pages  = max(1, (int) ceil($result['total'] / 12));

/** The address of another page, keeping every current filter. */
function page_url(int $page): string
{
    $params = $_GET;
    $params['page'] = $page;

    return '?' . http_build_query($params);
}
?>
<nav aria-label="Pages">
  <?php if ($page > 1): ?>
    <a href="<?= e(page_url($page - 1)) ?>">Previous</a>
  <?php endif; ?>
  <span>Page <?= e($page) ?> of <?= e($pages) ?></span>
  <?php if ($page < $pages): ?>
    <a href="<?= e(page_url($page + 1)) ?>">Next</a>
  <?php endif; ?>
</nav>
```
- The page links **keep the other parameters**, so moving to page 2 does not lose the search.
- `ORDER BY` must be present and stable. Without it, the database may return rows in a different order on each request and the same listing appears on two pages.
- A request for a page beyond the last (`page=999`) should show the empty state, not an error.

## 7. Rules that are always in the `WHERE`
Filters are optional. These are not:

| Page | Fixed condition |
|---|---|
| Explore, plants | `p.is_public = 1`, and the plant's collection is public |
| Exchange | `l.status = 'open'` |
| My Garden | `p.user_id = :user_id` |

A search that forgets them leaks private plants through the results: [[03.07 Access Control and Ownership Checks]].

## 8. Searching plants and people
Explore has two tabs (COM-01, COM-02). A simple design: the same `q` runs two queries, one on plants (`nickname`, species names) and one on members (`username`, `full_name`), and each tab shows its count. A search starting with `@` can go straight to the People tab. Never search or display `email` or `phone`.

## 9. When `LIKE` is not enough
`LIKE '%word%'` reads every row, because an index cannot help when the pattern starts with a wildcard. For a few thousand rows that is fine. Larger sites use a **full-text index** (`MATCH … AGAINST`) or a search engine. Naming that in the report's future-work section shows you know the limit.

## 10. Common mistakes
- **A user value placed in the SQL string,** usually in `ORDER BY` or `LIMIT` "because placeholders don't work there".
- **Wildcards written in the SQL** (`LIKE '%:q%'`). The placeholder is then inside a string and is not replaced.
- **Not escaping `%` and `_`** in the user's text.
- **Reusing one named placeholder** for two columns.
- **Counting on a different `WHERE`** than the one that fetches rows. The page count is then wrong.
- **No `ORDER BY`** with `LIMIT`.
- **Fetching everything and slicing in PHP.** The database should return only one page.
- **Page links that drop the filters.**
- **A negative or zero page** producing a negative offset. Clamp it.
- **Forgetting the fixed privacy conditions.**
- **Returning columns the page must not show,** such as the owner's email, "because the join has them".
