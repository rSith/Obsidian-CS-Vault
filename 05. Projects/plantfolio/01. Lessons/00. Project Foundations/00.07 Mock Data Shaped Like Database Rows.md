# 00.07 · Mock Data Shaped Like Database Rows

> [!info] [[00.00 Project Foundations|Lesson 0]] · Week 1 · Module MOD-01 · Priority 🔴 Core
> **Builds on:** [[00.02 PHP Basics for Templates]] · [[06.01 Relational Schema Design and Normalisation]]
> **Used for:** `includes/mock-data.php`, the data source of every page during stage F.

## 1. Definitions
| Term | Meaning |
|---|---|
| **Mock data** | Invented data that stands in for the real source while the rest is being built |
| **Row** | One record of a database table: one plant, one listing |
| **Joined column** | A column that comes from a related table, added by a `JOIN` |
| **Calculated column** | A value worked out by the query, such as a count or an average |
| **Contract** | An agreement about the exact shape of data passed between two parts of a program |

## 2. Why it is used
PlantFolio is built **frontend first**: all 15 pages exist before the database does. Pages still need something to show. The trick that makes this safe is that each mock array has **exactly the shape of the row a future query will return**. Stage B then replaces where the data comes from, and the pages do not change.

| Without this rule | With it |
|---|---|
| Pages are redesigned when real data arrives | Only the data source is swapped |
| Field names are invented page by page | Field names are the real column names |
| The database is designed after the UI, to fit it | The table plan is agreed in weeks 1–2 and both sides follow it |

## 3. How it works
A database row arrives in PHP as an **associative array**: column name → value. So a mock row is written as one.

```php
// One row of `plants`, joined with its species, collection and soonest reminder
$plant = [
    'id' => 42, 'user_id' => 1, 'collection_id' => 1, 'species_id' => 1,   // plants
    'nickname' => 'Monty', 'photo' => 'mock/monty.svg',
    'acquired_on' => '2025-03-20', 'health_status' => 'thriving', 'is_public' => 1,

    'scientific_name' => 'Monstera deliciosa',       // from plant_species
    'common_name'     => 'Swiss cheese plant',
    'collection_name' => 'Living room',              // from collections
    'task' => 'water', 'interval_days' => 7,         // from care_reminders
    'next_due' => '2026-10-08',
];
```

Four rules keep it honest:

| Rule | Example | Why |
|---|---|---|
| **Real column names** from `database/README.md` | `health_status`, not `status` or `health` | The page reads by key |
| **Raw values, as the database stores them** | `'needs_attention'`, `'2026-10-08'`, `1` | Formatting is the page's job (`health_label()`, `time_ago()`) |
| **Joined and calculated columns are marked in comments** | `// from plant_species` | The comment is the plan for the future `JOIN` |
| **Include the awkward cases** | `'avatar' => null`, an overdue reminder, a private plant | The page must handle them before real data arrives |

## 4. Calculated columns
Some values are not stored anywhere. The mock user has:

```php
$current_user = [
    'id' => 1, 'username' => 'nimali.grows', 'full_name' => 'Nimali Perera',

    // Not columns of `users`: stage B calculates these with COUNT() and AVG() on other tables.
    'plant_count' => 18, 'collection_count' => 3, 'swap_count' => 12,
    'rating_avg' => 4.9, 'rating_count' => 23,
];
```
Storing a count in the `users` table would have to be kept in step with the plants table for ever. Calculating it in the query avoids that: [[04.05 Counts, Averages and Rating Rules in SQL]].

## 5. Dates that stay true
```php
function mock_date($days)
{
    return date('Y-m-d', strtotime($days . ' days'));
}

$reminder = ['task' => 'water', 'interval_days' => 5,
             'last_done' => mock_date(-7), 'next_due' => mock_date(-2)];
```
A fixed date such as `'2026-10-06'` would say "Overdue 2 days" on 8 October and "Overdue 40 days" on the day of the demo. `mock_date(-2)` is always two days ago. Each mock reminder also obeys the database rule `next_due = last_done + interval_days`: here $-7 + 5 = -2$.

## 6. Example: the swap in stage B
**Stage F**, in the page:
```php
require_once __DIR__ . '/../includes/mock-data.php';
$plants = $mock_plants;
```
**Stage B**, a function that returns the **same shape**:
```php
function get_plants_for_user(PDO $pdo, int $user_id): array
{
    $stmt = $pdo->prepare(
        'SELECT p.id, p.user_id, p.collection_id, p.species_id, p.nickname, p.photo,
                p.acquired_on, p.health_status, p.is_public,
                s.scientific_name, s.common_name,
                c.name AS collection_name
         FROM plants p
         JOIN plant_species s ON s.id = p.species_id
         LEFT JOIN collections c ON c.id = p.collection_id
         WHERE p.user_id = :user_id
         ORDER BY p.nickname'
    );
    $stmt->execute(['user_id' => $user_id]);

    return $stmt->fetchAll();
}

$plants = get_plants_for_user($pdo, $current_user['id']);
```
The loop and the `plant-card` partial below this line are untouched. `c.name AS collection_name` shows how a query produces the exact key the mock used. (The reminder columns are left out here to keep the example short.)

The roadmap's rule for stage B: replace **one mock array at a time**, and delete it from `mock-data.php` when it is done. The file shrinks to nothing by Gate 2. `seed.sql` is built from the same sample content, so the wired pages show the same Monty and Goldie as before.

## 7. Common mistakes
- **Invented keys.** A page reads `$plant['name']` and the column is `nickname`. Wiring then means editing every page.
- **Formatted values in the data:** `'due' => 'Overdue 2 days'`. The database cannot return that. Store the date; let `care_due()` produce the words.
- **Nested arrays** such as `'species' => ['name' => …]`. A SQL row is flat.
- **Only happy cases.** No plant without a reminder, no member without a photo, no empty list.
- **Fixed dates.**
- **Using a mock-only helper in a page.** `mock_date()` belongs in `mock-data.php` only, because that file is deleted later.
- **Designing the table plan after the pages.** The plan (tasks DES-06 to DES-08) is finished in weeks 1–2 for exactly this reason.
- **Assuming types match.** Check numbers and `null` when wiring; a decimal such as an average may arrive as a string.
