# 00.08 · Team Git Workflow and Pull Requests

> [!info] [[00.00 Project Foundations|Lesson 0]] · Week 1 · Task PLN-09 · Priority 🟡 Supporting
> **Builds on:** [[00.01 Git Branching and Commit Messages]], which explains branches, merges and commit messages. Also [[03. Self-Study/GitHub Foundations/What is Version Control|What is Version Control]] and [[03. Self-Study/GitHub Foundations/Introduction to GitHub|Introduction to GitHub]]. This note adds what a **team** needs.
> **Used for:** the rules in `CONTRIBUTING.md`.

## 1. Definitions
| Term | Meaning |
|---|---|
| **Remote** | The copy of the repository on GitHub, named `origin` |
| **Protected branch** | A branch GitHub refuses direct pushes to. Changes arrive only through a pull request. |
| **Pull request (PR)** | A request to merge one branch into another, with a page for discussion and review |
| **Code review** | Another person reads and runs the change before it is merged |
| **Tag** | A permanent name for one commit, such as `v1.0-core` |
| **Release** | A tag published on GitHub with notes and files attached |

## 2. Why it is used
Seven people share one repository. Without rules, one push can break the version everyone else is using, and nobody knows which copy is the working one. The workflow guarantees:
- **`main` always works** and can be shown in a demo at any time;
- **every change is seen by a second person** before it is merged;
- **every commit can be traced** to a task on the Task Sheet.

## 3. How it works: the branches
```text
main       protected. Always a working, demo-ready version. Updated only from develop.
 └─ develop   protected, default branch. Every finished module lands here first.
     ├─ feature/<module>-ui   stage F: the module's pages with mock data
     ├─ feature/<module>      stage B or M: the same module wired
     ├─ fix/<short-name>      bug fixes
     └─ docs/<short-name>     documentation only
```
Each module is reviewed **twice**: a **UI pull request** in stage F and a **wired pull request** later. For module MOD-04 that is `feature/garden-ui`, then `feature/garden`.

## 4. Syntax: the daily cycle
```bash
git checkout develop && git pull          # 1. start from the latest develop
git checkout -b feature/garden-ui         # 2. create your branch (once)

git add public/garden.php                 # 3. commit small, meaningful steps
git commit -m "feat(garden): add collection tabs with mock data (CORE-14)"

git push -u origin feature/garden-ui      # 4. first push; afterwards just: git push

git checkout develop && git pull          # 5. at least daily: bring in others' work
git checkout feature/garden-ui
git merge develop
```

### Commit message format
```text
type(scope): what changed (TASK-ID)
```
| type | when |
|---|---|
| `feat` | New feature or page |
| `fix` | Bug fix |
| `style` | CSS or layout only |
| `refactor` | Code change with no change in behaviour |
| `db` | Schema or seed changes |
| `docs` | README, comments, documentation |
| `test` | Test cases or evidence |
| `chore` | Setup, config, dependencies |

The task ID in brackets links the commit to the Task Sheet. Real examples from the project's history:
```text
style(scaffold): add design tokens for palette and health colours (CORE-04)
feat(scaffold): add plant card and listing card partials with mock data (CORE-05)
```

## 5. A pull request, step by step
1. Push the branch. On GitHub open a PR: **base `develop` ← compare `feature/…`**.
2. Fill in the template: summary, module and tasks, how it connects, how to test, screenshots at desktop and 375 px.
3. Assign the module's reviewer.
4. Update the Task Sheet.
5. The reviewer **pulls the branch and runs it**, works through the checklist, then approves or requests changes, within 3 days.
6. Fix requests with **new commits on the same branch**. The PR updates by itself.
7. Once approved, the leader merges with **Create a merge commit** and deletes the branch.

| Reviewer checks, UI PR | Reviewer checks, wired PR |
|---|---|
| Runs on a fresh pull (Apache only) | Runs with `schema.sql` and `seed.sql` re-imported |
| Matches the wireframe; uses shared components and tokens | Assigned Test Plan cases pass |
| Works at 375, 768, 1024 px; no console errors | Prepared statements, escaped output, CSRF, access checks |
| Output escaped, alt text, labels, visible focus | Readable, commented, follows the conventions |

## 6. Example: a merge conflict
You and a teammate both changed the same lines. `git merge develop` stops and marks the file:

```text
<<<<<<< HEAD
<h1>My Garden</h1>
=======
<h1>Your Garden</h1>
>>>>>>> develop
```
1. Open the file. Decide what the lines should be, and delete the three marker lines.
2. `git add` the file.
3. `git commit` to finish the merge.

Merging `develop` into your branch every day keeps conflicts small.

## 7. Releases
At the UI freeze and at each gate, the leader opens a PR **`main` ← `develop`** titled `Release: <milestone>`, which needs one approval. After merging:
```bash
git checkout main && git pull
git tag -a v1.0-core -m "Gate 2: coursework complete"
git push origin v1.0-core
```
| Tag | When |
|---|---|
| `v0.5-ui` | UI freeze, week 7 |
| `v0.8-gate1` | Gate 1, week 9 |
| `v1.0-core` | Gate 2, week 10 |
| `v1.0-ml` | Gate 3, week 14 |
| `v1.0` | Final release, week 16 |

A tag lets you return to exactly the version that was demonstrated, whatever happened afterwards.

## 8. Never commit
`config/config.php`, passwords or API keys, `venv/`, trained model files, datasets, user uploads. The `.gitignore` covers these. **If a secret is committed, it must be changed, not just deleted,** because Git keeps it in the history.

## 9. Common mistakes
- **Working on `develop` or `main`.** GitHub blocks the push, and the commits must then be moved.
- **One huge pull request.** Nobody can review 40 files properly. One module, one PR.
- **`git add .` without looking.** Run `git status` first.
- **Not pulling for a week,** then a large conflict.
- **Fixing review comments in a new branch.** Push to the same branch.
- **A commit message with no task ID.**
- **A reviewer who approves without running the code.**
- **`git push --force` on a shared branch.** It deletes other people's commits.
- **Merging your own pull request** with no review.
