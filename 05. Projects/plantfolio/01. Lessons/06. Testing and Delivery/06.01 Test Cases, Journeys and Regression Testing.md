# 06.01 · Test Cases, Journeys and Regression Testing

> [!info] [[06.00 Testing and Delivery|Lesson 6]] · From week 8, and weeks 15–16 · Tasks CORE-28, COM-17, ML-18, TST-03, TST-04, TST-10, TST-11 · Priority 🔴 Core
> **Builds on:** [[03.04 Testing WebApps and Best Practices]], which covers testing web applications in general. [[03.06 Unit Testing with pytest]] covers automated unit tests. This note covers how PlantFolio's own Test Plan is written and run.
> **Used for:** the Test Plan cases TC-001 – TC-058, the journeys A–D and the final regression.

## 1. Definitions
| Term | Meaning |
|---|---|
| **Test case** | One precise check: given this starting point and these steps, this result is expected |
| **Test plan** | The full list of test cases, with who runs them and when |
| **Positive test** | Correct input; the feature should work |
| **Negative test** | Wrong input; the feature should refuse it **properly** |
| **Boundary test** | Input exactly at, just below and just above a limit |
| **Journey** (end-to-end test) | A complete task a real user would do, across several pages |
| **Regression test** | Re-running earlier tests after a change, to confirm nothing that worked is now broken |
| **Smoke test** | A quick run of the most important paths: is it basically alive? |
| **Severity** | How serious a defect is: Critical, High, Medium, Low |

## 2. Why it is used
- **"It works on my machine, when I use it the way I meant"** is not evidence. A written case can be run by a teammate who does not know the code, and gives the same verdict each time.
- **The Definition of Done requires it:** a task is Done only when *"the assigned Test Plan cases pass and results are logged"*.
- **Negative tests are where the marks and the vulnerabilities are.** A login form that accepts the right password proves little. One that handles the sixth wrong password correctly proves the lockout exists.

## 3. How it works: the anatomy of a test case
| Field | Example |
|---|---|
| **ID** | TC-00X |
| **Title** | Login locks after five wrong passwords |
| **Task** | CORE-12 |
| **Preconditions** | A registered account `test.a`; not locked; logged out |
| **Steps** | 1. Open the login page. 2. Enter `test.a` and a wrong password. 3. Submit. 4. Repeat four more times. 5. Enter the **correct** password and submit. |
| **Test data** | Wrong: `wrong-password`. Correct: the seeded password. |
| **Expected result** | Attempts 1–5 show the same generic error. Attempt 6, although correct, is refused with the "too many attempts" message. |
| **Actual result** | *(filled in when run)* |
| **Status** | Pass / Fail / Blocked |

The numbering here is an illustration; the real IDs are in the Task Sheet. A case is good when **two people running it reach the same verdict**. "Check that login works" is not a test case.

## 4. Finding the cases: two techniques
### Equivalence partitioning
Group the possible inputs into classes that should behave alike, and test **one from each**. For a username of 3–20 characters: too short, valid, too long, containing a forbidden character, already taken.

### Boundary value analysis
Mistakes cluster at limits (`<` written where `<=` was meant). Test **on the limit and one step either side**.

| Rule | Just below | On the limit | Just above |
|---|---|---|---|
| Password at least 8 characters | 7 → refused | 8 → accepted | 9 → accepted |
| Upload at most 5 MB | 4.9 MB → accepted | 5.0 MB → accepted | 5.1 MB → refused |
| 12 listings per page | 12 results → 1 page | | 13 results → 2 pages |
| Lock after 5 failures | 4 → not locked | 5 → locked | |
| **Confidence High from 80 %** | 0.794 → "79 %", Medium | 0.795 → "80 %", High | |
| **Not sure below 60 %** | 0.594 → "59 %", Not sure | 0.595 → "60 %", Medium | |

The last two rows test a rule from the design system: the word is decided from the **rounded** percentage ([[05.07 Confidence Thresholds and Honest AI Results]]).

## 5. Example: a set of cases for one feature
Add a plant with a photo (CORE-16, CORE-17):

| Type | Case | Expected |
|---|---|---|
| Positive | Valid details, a 2 MB JPG | Saved; appears in My Garden; photo resized |
| Negative | Empty nickname | Inline error; nothing saved; other fields keep their values |
| Negative | A 9 MB photo | Refused with the size message |
| Negative | A `.pdf` renamed to `.jpg` | Refused: not a real image |
| Negative | Nickname `<script>alert(1)</script>` | Saved and shown **as text**; nothing runs |
| Negative | Submit with the CSRF field removed (DevTools) | Rejected with 403 |
| Negative | Logged out, open `plant-form.php` | Redirected to login |
| Negative | `plant-form.php?id=` another member's plant | Not found |
| Boundary | Nickname of exactly the maximum length, and one more | Accepted; refused |

The roadmap's standing list of wrong inputs gives a starting set for every module: *empty forms, wrong password, oversized or wrong-type files, `<script>` in text fields, `' OR '1'='1` in search, and another user's ID in the URL.*

## 6. Journeys
A journey strings features together the way a person would. The Figma prototype defines four:

| Journey | Path |
|---|---|
| **D · First visit** | Landing → sign up → empty Dashboard → add the first plant |
| **A · Add an unknown plant** | Photo → Plant Identifier → use the suggestion → save → the plant's profile |
| **B · Diagnose a sick plant** | Plant profile → Health Check → result → save to the story → re-check reminder |
| **C · Swap a plant** | Create a listing → another member expresses interest → contact revealed → mark exchanged → rate |

Journeys catch what separate cases miss: the page that works alone but receives the wrong data from the page before it. Journey C needs **two accounts** in two browsers.

The gate demonstrations are journeys too. Gate 1: *register → add plant with photo → log health → reminder appears on Dashboard → mark done.*

## 7. Regression testing
Fixing one thing can break another. After a fix:
1. Re-run the case that failed. It must now pass.
2. Re-run the **cases around it**: the same page, the same helper, the same table.
3. Run the **smoke set**: the four journeys.

At the end (TST-11) the whole Test Plan is run once more on the release candidate. Tags make this practical: you always know which version was tested ([[00.08 Team Git Workflow and Pull Requests]]).

## 8. Logging defects
A failed case becomes an entry in the Task Sheet's Issue Log.

| Field | Content |
|---|---|
| Title | "Private plant visible in Explore results" |
| Steps to reproduce | Exact steps, account and data |
| Expected / Actual | What should happen; what did |
| Severity | See below |
| Evidence | Screenshot, the address, the error text |
| Status | Open → Fixed → **Re-tested** → Closed |

| Severity | Meaning | Example |
|---|---|---|
| **Critical** | Data loss, a security hole, or the site unusable | Another member's plant can be deleted |
| **High** | A core feature fails with no workaround | Photos cannot be uploaded |
| **Medium** | A feature misbehaves; a workaround exists | The sort order resets on page 2 |
| **Low** | Cosmetic | A badge is misaligned at 375 px |

MS-5 requires **no open Critical or High issues**. If time runs short, the roadmap's rule decides: cut from Should and Could tasks, never from Must tasks or security.

## 9. Common mistakes
- **Only positive tests.**
- **Vague cases** with no exact steps or expected result.
- **The author testing their own module only.** A reviewer finds what the author cannot see.
- **Testing with one account.** Access-control faults are invisible.
- **Not resetting the data.** A case that needs an empty garden fails because the last run left plants. Use the seed's reset script.
- **Fixing a bug and not re-testing** the things near it.
- **"Fixed" marked without a re-test.**
- **Testing only at desktop width.**
- **Results kept in memory,** not logged. The report then has no evidence.
- **Changing the expected result to match what the code does.**
- **Leaving all testing to week 15.** Each wired pull request already runs its cases.

## 10. Exam and viva focus
- **Verification vs validation:** building the product right vs building the right product.
- **Levels of testing:** unit, integration, system, acceptance.
- **Black-box vs white-box testing:** from the outside by behaviour vs with knowledge of the code.
- **Equivalence partitioning and boundary value analysis,** with an example.
- **Regression testing:** what and why.
- **Functional vs non-functional testing:** what it does vs how well (performance, usability, security, accessibility).
- **Parts of a test case** and of a defect report.
- **Alpha vs beta testing;** user acceptance testing.
- **Viva:** "How do you know the lockout works?" · "Show me a negative test you ran and its result." · "After you fixed that bug, how did you check you had not broken anything else?"
