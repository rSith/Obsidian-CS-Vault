# 06.03 · Production Configuration and Release

> [!info] [[06.00 Testing and Delivery|Lesson 6]] · Week 16 · Tasks DEP-02, DEP-05, DEP-06, DEP-17, DEP-19 · Priority 🟡 Supporting
> **Builds on:** [[06.06 Environment Variables and Configuration]] · [[00.08 Team Git Workflow and Pull Requests]] · [[08.04 Cloud Deployment Basics]]
> **Used for:** the `production` setting, the fresh-install test, the `v1.0` release and the demo.

## 1. Definitions
| Term | Meaning |
|---|---|
| **Environment** | A place the software runs, with its own settings: development, production |
| **Development** | Your own computer. Errors are shown; data is fake. |
| **Production** | The version real users, or examiners, use. Errors are hidden; data is real. |
| **Release** | A specific, tested version made available, identified by a tag |
| **Fresh install** | Setting the project up on a clean machine using only its instructions |
| **Database dump** | A file containing a database's structure and data, for backup or transfer |

## 2. Why it is used
Settings that help while building are dangerous in a finished site. An error message that shows the developer a file path and an SQL query shows an attacker the same. And a project that runs only on its author's laptop cannot be marked: the examiner, or a teammate at the demo, must be able to run it.

## 3. How it works: one switch
`config/config.php` has `'app_env' => 'development'`. The code reads it and behaves differently:

```php
<?php
// Near the top of includes/helpers.php, after config() is defined

error_reporting(E_ALL);                              // always notice every problem

if (config('app_env') === 'production') {
    ini_set('display_errors', '0');                  // never show errors to visitors
    ini_set('log_errors', '1');                      // write them to the server's error log
} else {
    ini_set('display_errors', '1');                  // development: show them on the page
}

// Anything that is not caught ends here
set_exception_handler(function (Throwable $error) {
    error_log($error->getMessage() . ' in ' . $error->getFile() . ':' . $error->getLine());

    http_response_code(500);
    echo 'Something went wrong. Please try again.';   // production shows only this
});
```
The code is the same on every machine. Only the value in the ignored `config.php` differs: [[06.06 Environment Variables and Configuration]].

## 4. What changes for production
| Setting | Development | Production |
|---|---|---|
| `app_env` | `development` | `production` |
| PHP errors | On the page | Hidden, logged |
| `base_url` | `http://localhost/plantfolio/public` | The real address, with `https://` |
| Database user | `root`, no password (XAMPP default) | A dedicated user, strong password, rights to one database |
| Session cookie | | `Secure` flag on, with HTTPS |
| Web root | `htdocs`, with `.htaccess` locks | The server's document root set to `public/` itself |
| `styleguide.php`, test files | Present | Removed or protected |
| Seed data | Demo accounts | Demo accounts only if the site is a demo; never real passwords in a file |

## 5. The fresh-install test (DEP-06)
The README's "Run it locally" section is a promise. The test: **a teammate, on a computer that has never had the project, follows the README and nothing else.** Every question they ask is a missing line.

Steps the README must cover, including two that are easy to forget:
1. Install XAMPP (PHP 8+), Git and VS Code.
2. Clone into `htdocs`.
3. Copy `config/config.example.php` to `config/config.php`.
4. **Enable the GD extension** in `php.ini` (`extension=gd`) and restart Apache. Without it, photo uploads fail: [[04.02 Secure File Uploads in PHP]].
5. Start Apache and MySQL. Create the `plantfolio` database. Import `schema.sql`, then `seed.sql`.
6. Open the site. Log in with a **documented demo account**.
7. The ML service: create its environment, install the requirements, **download the model files** from the link in `ml-service/models/README.md`, and start it.
8. What to expect if the ML service is not running: the site still works.

## 6. Example: the release
```bash
# 1. A dump of the database for the release
mysqldump -u root plantfolio > plantfolio-v1.0.sql

# 2. After the release pull request (main ← develop) is approved and merged:
git checkout main && git pull
git tag -a v1.0 -m "Final release and submission"
git push origin v1.0
```
Then on GitHub, create a **release** from the tag and attach the SQL dump and the notebooks, as task DEP-19 describes. Database dumps are deliberately not committed (the `.gitignore` excludes them), so the release page is where they live.

| Tag | Milestone |
|---|---|
| `v0.5-ui` | UI freeze |
| `v0.8-gate1` | Gate 1 |
| `v1.0-core` | Gate 2, with a database dump |
| `v1.0-ml` | Gate 3 |
| `v1.0` | Submission |

A tag is fixed. Whatever happens to the code afterwards, `v1.0` is exactly what was submitted.

## 7. Hosting, if the site goes online
Deciding this is task DEP-01, and the roadmap says to settle it **by week 10, not week 15**.
- **The PHP site** runs on almost any shared PHP hosting: upload the files, point the domain at `public/`, create the database, import the dump, write the production `config.php`.
- **The ML service** is the hard part. It needs a host that runs Python with enough memory for TensorFlow, which ordinary PHP hosting does not offer. A realistic outcome is: the site hosted, the ML features demonstrated locally. Because of the fallback design, a hosted site without the ML service still works.
- A hosted site needs **HTTPS**.

## 8. The demo
| Risk on the day | Preparation |
|---|---|
| No internet in the room | The site runs locally. Fonts come from Google Fonts, so text falls back to the backup fonts in `variables.css`; check that it still looks acceptable. Icons are local files. |
| The ML service will not start | The fallback works; the **backup demo video** (DEP-17) shows the AI features |
| The data is in a mess from testing | Run the seed's reset script just before |
| "Today's care" is empty | Seed reminders are relative to today, so some are always due |
| A teammate presents a part they did not build | Rehearse twice (DEP-18); the weekly notes explain each part |

Presenting is covered in [[09.03 Presenting and Storytelling]], and the report in [[09.01 Technical and Scientific Writing]].

## 9. Common mistakes
- **Errors displayed in the submitted or hosted version.**
- **`config.php` committed** to make the install "easier".
- **A README nobody tested.**
- **A setup step that lives only in your memory:** the GD extension, the model download, the time zone.
- **No demo account,** or its password known to one person only.
- **`root` with no password** on a hosted database.
- **Tagging before the final regression,** then fixing a bug on top. The tag no longer matches what was tested.
- **Moving a tag** after pushing it.
- **`styleguide.php` left public.**
- **Model files or database dumps committed** to the repository.
- **A demo that depends on the room's Wi-Fi.**
- **Deciding about hosting in the last week.**
