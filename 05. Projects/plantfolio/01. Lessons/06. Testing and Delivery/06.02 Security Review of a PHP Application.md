# 06.02 · Security Review of a PHP Application

> [!info] [[06.00 Testing and Delivery|Lesson 6]] · Week 15, and on every wired pull request · Tasks DES-12, TST-02 · Priority 🔴 Core
> **Builds on:** [[13.01 Web Security and Major Threats]] · [[13.10 Best Practices for Securing a Website]] and the security notes of [[03.00 Database and Accounts|Lesson 3]]. Those explain each threat and defence. This note turns them into **one review you can carry out**.
> **Used for:** `docs/security-checklist.md` (DES-12) and the security review (TST-02).

## 1. Definitions
| Term | Meaning |
|---|---|
| **Security review** | A systematic check that each known threat has a working defence |
| **Vulnerability** | A weakness that can be exploited |
| **Threat** | Something that could exploit it |
| **Attack surface** | Every place where outside input enters: forms, URLs, uploads, cookies, API endpoints |
| **Defence in depth** | Several independent protections, so one failure is not fatal |
| **Least privilege** | Every user and program has only the access it needs |

## 2. Why it is used
`CLAUDE.md` says the security rules are checked *"on every change from stage B onward"*. A rule that is written down but never tested tends to have one page where it was forgotten. Attackers, and examiners, look for exactly that page. The review asks the same question everywhere: **is this defence present on every route, and can I prove it?**

## 3. How it works: two passes
1. **Read the code** for each rule. Searching finds the forgotten places quickly.
2. **Attack the running site** with the wrong inputs. This proves the defence actually works.

Use **two accounts** (A and B) and the browser's developer tools (F12), which let you edit a form's hidden fields and resend requests.

## 4. The checklist
| # | Threat | Defence in PlantFolio | How to test | Explained in |
|---|---|---|---|---|
| 1 | **SQL injection** | PDO prepared statements; emulation off; whitelists for sort order | `' OR '1'='1` and `'; DROP TABLE users; --` in search, login and every `?id=` | [[03.02 PDO and Prepared Statements]] · [[13.03 SQL Injection]] |
| 2 | **Cross-site scripting** | `e()` on every output; `textContent` in JavaScript | `<script>alert(1)</script>` and `"><img src=x onerror=alert(1)>` as nickname, bio, listing title, search text | [[00.04 Output Escaping in PHP]] · [[13.07 Cross-Site Scripting (XSS)]] |
| 3 | **CSRF** | A per-session token in every POST form, checked first | Delete the hidden token field in DevTools and submit; send a POST with `curl` and no token | [[03.05 CSRF Tokens]] |
| 4 | **Broken access control** | `require_login()`; `AND user_id = :user_id`; 404 for private items | As B, open and submit A's IDs in addresses and hidden fields; open private pages logged out | [[03.07 Access Control and Ownership Checks]] |
| 5 | **Weak password storage** | `password_hash()` / `password_verify()` | Look at `users.password_hash` in phpMyAdmin: it must start with `$2y$` or similar, never be readable | [[03.03 Password Hashing and Login Lockout]] |
| 6 | **Brute force** | One generic error; lock for 15 min after 5 failures | Five wrong passwords, then the right one | [[03.03 Password Hashing and Login Lockout]] |
| 7 | **Session attacks** | New session ID at login; `HttpOnly`, `SameSite`; logout destroys | Compare the cookie before and after login; after logout press Back and reload | [[03.04 PHP Sessions and Login State]] |
| 8 | **Malicious uploads** | `finfo` content check; 5 MB; random names; re-encoding; no execution in `uploads/` | A `.php` file renamed `.jpg`; a 20 MB file; then try to open an uploaded file's address as a script | [[04.02 Secure File Uploads in PHP]] |
| 9 | **Privacy leaks** | Contact details only after interest, only chosen fields; private plants hidden | View the **page source** of a listing before expressing interest; search for a private plant | [[01.04 Rendering States - Empty, Owner and Visitor Views]] |
| 10 | **Information leaks** | Errors hidden in production; no secrets in Git; protected folders | Cause an error and read the page; open `/includes/helpers.php` and `/config/config.php` in the browser | [[06.03 Production Configuration and Release]] |
| 11 | **Data changed by GET** | Every change is a POST | Search the code for links that delete, log out or mark done | [[01.03 Query Strings and GET Parameters in PHP]] |
| 12 | **The ML service** | Reached only by PHP, on `127.0.0.1`; replies validated | Stop Flask: the site must still work. Try to reach port 5000 from another device. | [[05.01 Calling the ML Service from PHP with cURL]] |

## 5. Example: searching the code
A text search across the project turns "I think we always do this" into a list to check. In VS Code, *Search in files* with a regular expression:

| Search for | Looking for |
|---|---|
| `<\?=\s*\$` | A value printed without `e()`. Each hit needs a reason. |
| `\$_(GET\|POST\|REQUEST)\[` inside the HTML part of a file | Input printed directly |
| `->query\(` | A query with no placeholders. Is any variable inside it? |
| `(SELECT\|UPDATE\|DELETE\|INSERT)[^;]*\$` | A variable placed in SQL text |
| `method="post"` | Every form. Does each one contain `csrf_field()`? |
| `UPDATE\|DELETE` | Every change. Does each one have the owner condition? |
| `innerHTML` | Data written as HTML in JavaScript |
| `header\('Location` | Is each one followed by `exit`? |

Then list every file in `public/` beside the Access column of the page table in `CLAUDE.md`: does each private page call `require_login()` near its top?

## 6. Beyond the twelve
Worth a line each in the report, whether or not they are implemented:
- **HTTPS** on any hosted version. Without it, passwords and session cookies cross the network readable.
- **Security headers:** `X-Frame-Options: DENY` stops the site being shown inside another page (clickjacking); a `Content-Security-Policy` limits which scripts may run.
- **The database account.** XAMPP's default is `root` with an empty password. On any shared or hosted server, a dedicated user with a strong password and rights to one database only.
- **Rate limiting** on sign-up, the username check and the ML endpoints.
- **Removing development pages:** `styleguide.php`, any `phpinfo()` test file.
- **Open redirects:** a `?next=` parameter must accept local paths only.
- **Denial of service** by large uploads or many requests: [[13.09 Denial of Service]].

Being able to say *"we did not implement X; here is the risk and what we would do"* is a stronger answer than silence.

## 7. Recording the review
| Field | Example |
|---|---|
| Rule | 4, access control |
| Where | `listing-form.php`, POST |
| Test | As B, submitted A's listing ID in the hidden field |
| Result | **Fail:** A's listing was updated |
| Severity | Critical |
| Fix and re-test | Owner condition added to the `UPDATE`; re-tested, now Not found |

A table of rules, tests and results, with failures and fixes included, is the evidence section of the report. A review that found nothing usually was not a review.

## 8. Common mistakes
- **Reviewing only the pages you remember.** Start from a list of **every** file in `public/` and `public/api/`.
- **Forgetting the JSON endpoints.** They need login, CSRF and ownership too.
- **Testing through the interface only.** The interface hides what the server must refuse. Edit the request.
- **One account.**
- **"We use prepared statements"** stated in the report, with one concatenated query still in the code.
- **Checking XSS in one field.** Every stored text that is ever displayed.
- **Security testing with errors visible** and not re-checking in production mode.
- **Fixing a finding and not re-testing.**
- **Treating the checklist as paperwork.** Each row is a real attempt.
- **Secrets in the repository's history.** Deleting the line is not enough; the credential must be changed.

- **Name common web vulnerabilities and one defence for each:** SQL injection, XSS, CSRF, broken access control, insecure file upload, weak authentication.
- **The CIA triad:** confidentiality, integrity, availability.
- **Defence in depth; least privilege; attack surface.**
- **OWASP Top 10:** a widely used list of the most serious web application risks.
- **Authentication vs authorisation.**
- **Validation, sanitisation and output encoding:** which stops what.
- **Why HTTPS?**
- **Penetration testing vs code review.**
