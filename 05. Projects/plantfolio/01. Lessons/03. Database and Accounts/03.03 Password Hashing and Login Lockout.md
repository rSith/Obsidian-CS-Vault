# 03.03 · Password Hashing and Login Lockout

> [!info] [[03.00 Database and Accounts|Lesson 3]] · Week 8 · Tasks CORE-07, CORE-09, CORE-12 · Priority 🔴 Core
> **Builds on:** [[10.07 Authentication in E-Commerce]] · [[13.02 Related Threat Terms]]
> **Used for:** registration, login and the 15-minute lock after 5 failed attempts.

## 1. Definitions
| Term | Meaning |
|---|---|
| **Hash function** | Turns any input into a fixed-length code. The same input always gives the same code. It cannot be reversed. |
| **Password hashing** | Storing the hash of a password, never the password |
| **Salt** | A random value mixed into each password before hashing, so two users with the same password get different hashes |
| **Cost** (work factor) | How slow the hashing is made, on purpose |
| **Brute-force attack** | Trying many passwords until one works |
| **Lockout** | Refusing further attempts for a while after repeated failures |

## 2. Why it is used
Databases get stolen: through a bug, a leaked backup, a lost laptop. If passwords are stored as typed, every member's password is exposed, and since people reuse passwords, so are their email and bank accounts. With hashing, the thief holds only codes that cannot be turned back into passwords.

| | **Hashing** | **Encryption** |
|---|---|---|
| Reversible | **No** | Yes, with the key |
| Used for | Passwords | Data that must be read again |

Passwords are **hashed**, not encrypted: the site never needs to know the password, only to check it.

## 3. How it works
```text
Register:   "MyPlants2026"  ──password_hash()──▶  "$2y$10$Qw8…"   stored in users.password_hash
Log in:     "MyPlants2026"  ──password_verify(typed, stored)──▶  true or false
```
PHP's `password_hash()`:
- generates a **random salt** for each password and stores it inside the result;
- uses an algorithm designed to be **slow** (bcrypt by default), so guessing billions of passwords is impractical;
- records the algorithm and cost in the result, so `password_verify()` knows how to check it.

**Why not MD5 or SHA-256?** They are built to be **fast**. A graphics card can try billions of guesses a second against them, and tables of precomputed hashes exist for common passwords. A slow, salted algorithm defeats both.

## 4. Syntax
```php
<?php
$hash = password_hash($password, PASSWORD_DEFAULT);     // on registration and password change

if (password_verify($password, $user['password_hash'])) {
    // correct
}

if (password_needs_rehash($user['password_hash'], PASSWORD_DEFAULT)) {
    // after a successful login: PHP's default got stronger, so store a fresh hash
}
```
- The column is `VARCHAR(255)`, with room for future algorithms.
- Never compare hashes yourself with `===`. `password_verify()` reads the salt from the stored hash and compares safely.

## 5. Example: login with a generic error and a lockout
A sketch of the logic. The `users` table plan already has `failed_logins` and `locked_until`.

```php
<?php
function attempt_login(string $email, string $password): array
{
    $pdo = db();
    $generic = 'Email or password is incorrect.';

    $stmt = $pdo->prepare('SELECT id, password_hash, failed_logins, locked_until FROM users WHERE email = :email');
    $stmt->execute(['email' => $email]);
    $user = $stmt->fetch();

    if ($user === false) {
        return ['ok' => false, 'error' => $generic];          // same message as a wrong password
    }

    if ($user['locked_until'] !== null && strtotime($user['locked_until']) > time()) {
        return ['ok' => false, 'error' => 'Too many attempts. Try again in a few minutes.'];
    }

    if (!password_verify($password, $user['password_hash'])) {
        $failures = $user['failed_logins'] + 1;
        $lock = $failures >= 5 ? date('Y-m-d H:i:s', time() + 15 * 60) : null;

        $stmt = $pdo->prepare('UPDATE users SET failed_logins = :failures, locked_until = :lock WHERE id = :id');
        $stmt->execute(['failures' => $failures, 'lock' => $lock, 'id' => $user['id']]);

        return ['ok' => false, 'error' => $generic];
    }

    // Success: clear the counter
    $stmt = $pdo->prepare('UPDATE users SET failed_logins = 0, locked_until = NULL WHERE id = :id');
    $stmt->execute(['id' => $user['id']]);

    return ['ok' => true, 'user_id' => (int) $user['id']];
}
```
After `ok`, the page starts the session: [[03.04 PHP Sessions and Login State]].

**One generic error.** "No account with that email" would tell an attacker which emails are registered. "Email or password is incorrect" tells them nothing. The same thinking applies to the sign-up and password-reset pages.

**The lockout.** Five wrong passwords lock the account for fifteen minutes. Guessing drops from thousands of tries a second to twenty an hour.

## 6. Registration
```php
<?php
$stmt = db()->prepare('INSERT INTO users (username, email, password_hash, full_name)
                       VALUES (:username, :email, :hash, :full_name)');
$stmt->execute([
    'username'  => $username,
    'email'     => $email,
    'hash'      => password_hash($password, PASSWORD_DEFAULT),
    'full_name' => $full_name,
]);
```
The plain password exists only in the request, for a moment. It is never stored, logged, emailed or printed back into the form.

## 7. Password rules for users
- **Length matters most.** A minimum of 8 characters; allow long passphrases.
- **Do not trim or alter a password.** A space is a valid character.
- **The strength meter on the sign-up page advises;** the server enforces only the minimum.
- **Never show whether the password or the email was the wrong part.**
- In production the site must use **HTTPS**, or the password travels readable across the network.

## 8. Common mistakes
- **Storing the password as typed,** or "encrypted" with a key kept beside it.
- **MD5 or SHA-1,** with or without a home-made salt.
- **A column too short for the hash.** `VARCHAR(50)` cuts it off and nobody can ever log in.
- **Comparing with `==`** instead of `password_verify()`.
- **Different messages** for unknown email and wrong password.
- **Hashing in JavaScript** before sending. The hash then *is* the password; it adds nothing.
- **Logging the request** including the password.
- **Seed data with plain passwords** in the hash column.
- **No lockout,** or one that never resets after a success.
- **A lockout that reveals account existence** by appearing only for real accounts. Decide the wording with care.
- **Emailing a forgotten password.** If the site can send it, it stored it. A reset link is the only correct design.

## 9. Exam and viva focus
- **Hashing vs encryption:** one-way vs reversible.
- **What is a salt, and what does it prevent?** Identical passwords giving identical hashes; precomputed (rainbow) tables.
- **Why must a password hash be slow?**
- **Name suitable algorithms:** bcrypt, Argon2. Unsuitable: MD5, SHA-1.
- **Brute-force and dictionary attacks,** and defences: lockout, rate limiting, strong passwords, multi-factor authentication.
- **Authentication factors:** something you know, have, are.
- **User enumeration:** learning which accounts exist from different responses.
- **Viva:** "If someone stole your database, what could they do with the `password_hash` column?" · "Why does a wrong email give the same message as a wrong password?" · "What happens on the sixth wrong attempt?"
