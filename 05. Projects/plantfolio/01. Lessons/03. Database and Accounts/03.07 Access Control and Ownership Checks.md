# 03.07 · Access Control and Ownership Checks

> [!info] [[03.00 Database and Accounts|Lesson 3]] · Weeks 8–10 · Tasks CORE-10, CORE-21, COM-09 · Priority 🔴 Core
> **Builds on:** [[03.04 PHP Sessions and Login State]] · [[01.04 Rendering States - Empty, Owner and Visitor Views]] · [[13.01 Web Security and Major Threats]]
> **Used for:** every page that shows private data and every action that changes data.

## 1. Definitions
| Term | Question it answers |
|---|---|
| **Authentication** | *Who are you?* Proved by logging in. |
| **Authorisation** (access control) | *Are you allowed to do this?* Decided on every request. |
| **Ownership check** | *Is this thing yours?* The most common authorisation rule here. |
| **IDOR** (insecure direct object reference) | The flaw where changing an ID in a request reaches someone else's data |
| **Least privilege** | Give each user only the access they need |

## 2. Why it is used
Logging in proves who someone is. It does not limit what they can reach. The addresses in PlantFolio contain IDs: `plant.php?id=42`, `plant-form.php?id=42`, a hidden `id` in every delete form. IDs are simple numbers, so anyone can change 42 to 43.

The rule in `CLAUDE.md`: *"check **ownership** before every edit or delete (try another user's ID in the URL)."* Broken access control is consistently one of the most common serious web vulnerabilities, because nothing looks wrong: the pages work, the queries are safe from injection, and the hole is only visible to someone who types a different number.

## 3. How it works
> [!important] The one rule
> **The user's identity comes from the session. Never from the request.** Every query that touches private data includes it.

```sql
-- Wrong: anyone who knows or guesses the ID can delete the plant
DELETE FROM plants WHERE id = :id;

-- Right: the row must also belong to the logged-in user
DELETE FROM plants WHERE id = :id AND user_id = :user_id;
```
`:user_id` is `$current_user['id']`, which `require_login()` loaded from the session. With the second query, plant 43 simply does not match for the wrong user: zero rows change.

## 4. Syntax: find-or-fail helpers
Every edit page starts by loading the thing **as its owner**.

```php
<?php
/** The plant with this id if it belongs to this user, otherwise null. */
function find_owned_plant(int $plant_id, int $user_id): ?array
{
    $stmt = db()->prepare('SELECT * FROM plants WHERE id = :id AND user_id = :user_id');
    $stmt->execute(['id' => $plant_id, 'user_id' => $user_id]);

    return $stmt->fetch() ?: null;
}

/** Answer 404 and stop. Used when something does not exist OR is not the visitor's to see. */
function not_found(): never
{
    http_response_code(404);
    $page_title = 'Not found';
    include __DIR__ . '/header.php';
    echo '<p>We could not find that page.</p>';
    include __DIR__ . '/footer.php';
    exit;
}
```
```php
<?php
// plant-form.php?id=42 (editing)
$current_user = require_login();

$id = filter_input(INPUT_GET, 'id', FILTER_VALIDATE_INT);
$plant = $id ? find_owned_plant($id, $current_user['id']) : null;

if ($plant === null) {
    not_found();
}
```

## 5. 404, not 403
| Status | Says | Tells an attacker |
|---|---|---|
| `403 Forbidden` | "This exists, but you may not see it" | That ID 43 is a real, private plant |
| `404 Not Found` | "There is nothing here" | Nothing |

`CLAUDE.md`: *"private plants return Not found to others."* Someone else's plant and a plant that does not exist give the **same** answer. The helper above does both with one query.

## 6. Example: three kinds of rule in PlantFolio
### A. Private to the owner (edit, delete, settings)
Always `AND user_id = :user_id`, on the `SELECT` that loads the form **and** on the `UPDATE` or `DELETE` that the form submits to. Checking only on the form page is not enough: the POST can be sent directly.

### B. Public to read, with exceptions (plant profile, collections)
```php
<?php
/** A plant that this viewer may see: public, or their own. $viewer_id is 0 for a logged-out visitor. */
function find_visible_plant(int $plant_id, int $viewer_id): ?array
{
    $stmt = db()->prepare('SELECT * FROM plants
                           WHERE id = :id AND (is_public = 1 OR user_id = :viewer_id)');
    $stmt->execute(['id' => $plant_id, 'viewer_id' => $viewer_id]);

    return $stmt->fetch() ?: null;
}
```
The rule is written **once, in a function**, and every page that shows a plant uses it. A list page (Explore) needs the same condition in its query, or private plants leak through search results.

### C. Revealed by an action (contact details on a listing)
```php
<?php
/** True if this member has an active interest in this listing. */
function has_expressed_interest(int $listing_id, int $user_id): bool
{
    $stmt = db()->prepare("SELECT 1 FROM listing_interests
                           WHERE listing_id = :listing_id AND user_id = :user_id AND status <> 'withdrawn'");
    $stmt->execute(['listing_id' => $listing_id, 'user_id' => $user_id]);

    return $stmt->fetchColumn() !== false;
}
```
Only if this is true does the page **query and print** the owner's contact details, and then only the fields the owner chose (`share_email`, `share_phone`). Before that, the details are not in the page at all: [[01.04 Rendering States - Empty, Owner and Visitor Views]].

## 7. Where the checks go
| Layer | Does | Is it security? |
|---|---|---|
| The interface hides Edit and Delete from visitors | Avoids offering what will be refused | No |
| The page that shows the edit form loads the row as its owner | Stops the form being opened | Partly |
| **The handler that performs the change includes the owner in its query** | Stops the change | **Yes. This one is essential.** |

## 8. How to test it
The roadmap lists this among the wrong inputs to try on every wired module:
1. Create two accounts, A and B. As A, add a plant and note its ID.
2. Log in as B.
3. Open `plant.php?id=<A's private plant>` → must be Not found.
4. Open `plant-form.php?id=<A's plant>` → must be Not found.
5. With the browser's developer tools, change the hidden `id` in one of B's own delete forms to A's ID and submit → A's plant must still exist.
6. Log out and repeat step 3 for a private plant.

## 9. Common mistakes
- **`WHERE id = :id` alone** on an update or delete.
- **Checking on the form page but not in the POST handler.**
- **Taking the user ID from a hidden field** (`<input type="hidden" name="user_id">`). The visitor controls it.
- **Believing a hidden button is protection.**
- **403 or "this is private"** for someone else's private item.
- **Protecting the detail page and forgetting the lists:** search results, the public profile, the marketplace, the JSON endpoints in `api/`.
- **Forgetting the `api/` endpoints.** A `fetch` endpoint needs login, CSRF and ownership exactly as a page does.
- **Unpredictable IDs treated as the defence.** Random IDs slow guessing; they do not replace the check.
- **Rules written separately on each page,** which then disagree. One function per rule.
- **Not testing with a second account.** With one account everything always works.
- **Uploaded files reachable by URL.** A private plant's photo in `public/uploads/` can still be opened by anyone who has its address. Random file names make the address unguessable; decide whether that is enough for the project.
