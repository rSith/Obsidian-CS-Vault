# 03.08 · Remember Me Tokens

> [!info] [[03.00 Database and Accounts|Lesson 3]] · Week 8 · Task CORE-09 · Priority 🟡 Useful
> **Builds on:** [[03.04 PHP Sessions and Login State]] · [[03.03 Password Hashing and Login Lockout]]
> **Used for:** the "Remember me" box on Log in (P02): `remember_me_set()`, `remember_me_log_in()` and `log_out()` in `includes/auth.php`, and the `remember_tokens` table.

## 1. Definitions
> [!note] Persistent login ("Remember me")
> Staying logged in on one browser for days, even after the browser is closed, without typing the password again.

> [!note] Selector-validator token
> A login token in two random parts kept in a cookie as `selector:validator`. The **selector** finds the row in the database (like a username). The **validator** proves the cookie is genuine (like a password), so the database keeps only a **hash** of it.

## 2. Why PlantFolio uses it
- Members check their plants every day; typing a password each time is a reason to stop using the site.
- A longer session cookie **does not work**: PHP deletes an idle session's file on the server after about 24 minutes (`session.gc_maxlifetime`). The browser would still send its cookie, but the server would have forgotten who it was. A separate token stored in the database survives that.
- Decided in the database design (DES-07, decision 5), which added the `remember_tokens` table.

## 3. How it works
```text
Log in with the box ticked
  selector  = 24 random hex      validator = 64 random hex
  database:  remember_tokens (user_id, selector, sha256(validator), expires_at = now + 30 days)
  browser:   cookie plantfolio_remember = "selector:validator"   (HttpOnly, SameSite=Lax, 30 days)

Days later, the session is gone but the cookie is not
  1. find the row by selector
  2. delete it (a token works once)
  3. hash_equals(row.token_hash, sha256(validator from cookie))  and not expired?
       yes → log_in(user_id) and give the browser a NEW selector:validator
       no  → delete the cookie; the member logs in normally

Log out
  delete this browser's row and both cookies
```

## 4. Syntax
```php
<?php
$selector  = bin2hex(random_bytes(12));      // 12 bytes → 24 hex characters (CHAR(24))
$validator = bin2hex(random_bytes(32));      // 32 bytes → 64 hex characters
$hash      = hash('sha256', $validator);     // 64 hex characters (CHAR(64))

setcookie('plantfolio_remember', $selector . ':' . $validator, [
    'expires'  => time() + 30 * 86400,
    'path'     => '/',
    'secure'   => !empty($_SERVER['HTTPS']),
    'httponly' => true,
    'samesite' => 'Lax',
]);

hash_equals($stored_hash, hash('sha256', $validator_from_cookie));   // constant-time comparison
```

## 5. Worked example in PlantFolio
`remember_me_log_in()` (called by `current_user()` when the session has no `user_id`):

```php
<?php
$cookie = $_COOKIE['plantfolio_remember'] ?? '';
if (!is_string($cookie) || !preg_match('/^([0-9a-f]{24}):([0-9a-f]{64})\z/', $cookie, $parts)) {
    return;                                              // no cookie, or not ours
}
[, $selector, $validator] = $parts;

$stmt = db()->prepare('SELECT id, user_id, token_hash, expires_at > NOW() AS valid
                       FROM remember_tokens WHERE selector = :selector');
$stmt->execute(['selector' => $selector]);
$token = $stmt->fetch();

if ($token) {                                            // used up either way
    db()->prepare('DELETE FROM remember_tokens WHERE id = :id')->execute(['id' => $token['id']]);
}
if (!$token || !$token['valid'] || !hash_equals($token['token_hash'], hash('sha256', $validator))) {
    remember_cookie('', time() - 3600);                  // delete the cookie
    return;
}

log_in($token['user_id']);                               // session_regenerate_id(true) inside
remember_me_set($token['user_id']);                      // a fresh token for next time
```

### Why each part is there
| Part | Defends against |
|---|---|
| Only `sha256(validator)` in the database | A leaked database dump: the hashes cannot be turned back into cookies |
| SHA-256 here, not `password_hash()` | The validator is 256 random bits, impossible to guess, so a fast hash is enough. Passwords are short and guessable, so they need slow bcrypt |
| A separate selector | Finding the row without comparing secrets in SQL (`WHERE token_hash = …` would leak timing) |
| `hash_equals()` | Timing attacks on the comparison |
| Deleted on every use, replaced by a new one | A stolen cookie that was already used is worthless. If the thief uses it first, the real member's next visit fails, which shows something is wrong |
| Wrong validator → the row is deleted | Someone guessing with a known selector gets one try, and the real cookie stops working too |
| `HttpOnly`, `SameSite=Lax`, `Secure` on HTTPS | The same cookie attacks as the session cookie: [[03.04 PHP Sessions and Login State]] |
| Deleted on logout | "Log out" on a shared computer must really log out |

## 6. Common mistakes
- **Storing the user id (or the password hash) in the cookie.** Anyone can edit a cookie: `user_id=1` would make them Nimali.
- **Storing the token itself in the database.** A database leak would then be a list of working logins.
- **One token forever.** Without rotation, a stolen cookie works for 30 days alongside the real one.
- **Forgetting logout.** Deleting the session but not the token logs the member straight back in on the next page.
- **Comparing with `===`.** Use `hash_equals()`.
- **Skipping `session_regenerate_id()`** when the token logs someone in: it is a login like any other.

## 7. Exam and viva focus
- **Why not just make the session cookie last 30 days?** The server deletes idle session data after about 24 minutes; the cookie would point at nothing.
- **What is stored in the browser, and what in the database?** Browser: `selector:validator`. Database: selector, SHA-256 of the validator, user id, expiry.
- **Why SHA-256 and not bcrypt for the validator?** It is long and random, so brute force is hopeless even against a fast hash; bcrypt is for short human passwords.
- **What happens if someone steals the cookie?** They can use it once, until the real member uses it (or the reverse); rotation and logout limit the damage. HTTPS and `HttpOnly` make stealing it hard in the first place.
