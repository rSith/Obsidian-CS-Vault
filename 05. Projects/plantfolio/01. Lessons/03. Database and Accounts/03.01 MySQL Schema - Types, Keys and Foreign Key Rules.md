# 03.01 · MySQL Schema: Types, Keys and Foreign Key Rules

> [!info] [[03.00 Database and Accounts|Lesson 3]] · Week 8 · Tasks CORE-01, CORE-02 · Priority 🔴 Core
> **Builds on:** [[06.01 Relational Schema Design and Normalisation]] (tables, keys, normal forms) and [[06.02 SQL Joins, Aggregation and Indexes]]. This note covers what those leave out: the MySQL-specific choices in `schema.sql`.
> **Used for:** `database/schema.sql` and `database/seed.sql`.

## 1. Definitions
| Term | Meaning |
|---|---|
| **DDL** | Data Definition Language: the SQL that creates structure (`CREATE TABLE`, `ALTER`, `DROP`) |
| **Storage engine** | The part of MySQL that stores a table's rows. PlantFolio uses **InnoDB**. |
| **Character set** | Which characters a text column can hold. PlantFolio uses **utf8mb4**. |
| **Collation** | The rules for comparing and sorting text in a character set |
| **Constraint** | A rule the database enforces on every row |
| **Referential action** | What happens to child rows when their parent is deleted: `ON DELETE …` |

## 2. Why it matters
The task CORE-01 asks for a schema that is *"InnoDB, utf8mb4, foreign keys, re-runnable"*. Each word is a decision:

| Word | Without it |
|---|---|
| **InnoDB** | No foreign keys and no transactions |
| **utf8mb4** | A bio with an emoji, or some Sinhala and Tamil text, is cut off or rejected |
| **Foreign keys** | A plant can point to a user who does not exist |
| **Re-runnable** | The file fails the second time, and nobody can rebuild the database from scratch |

A constraint in the database is the last line of defence. PHP validation can have a bug; a `NOT NULL` or `UNIQUE` rule cannot be skipped.

## 3. How it works: data types
| Type | Holds | Used for |
|---|---|---|
| `INT UNSIGNED AUTO_INCREMENT` | Whole numbers from 0, numbered automatically | `id` |
| `VARCHAR(n)` | Text up to `n` characters | `username`, `title`, `location` |
| `TEXT` | Long text | `bio`, `description`, `note` |
| `DATE` | A day: `2026-11-23` | `acquired_on`, `last_done`, `next_due` |
| `DATETIME` | A day and a time | `created_at`, `logged_at`, `locked_until` |
| `TINYINT(1)` | 0 or 1 | `is_public`, `share_email` |
| `DECIMAL(4,3)` | An exact decimal | `confidence` (0.000 to 1.000) |
| `ENUM('a','b')` | One value from a fixed list | `health_status`, listing `type` |

Rules of thumb: the **smallest type that fits**; `DATE` when the time of day does not matter; never store a date as text; `VARCHAR(255)` for a password hash, so a future algorithm fits.

## 4. InnoDB and utf8mb4
| | **InnoDB** | MyISAM (older) |
|---|---|---|
| Foreign keys | Yes | No |
| Transactions | Yes | No |
| Locking | One row | The whole table |

| | **utf8mb4** | `utf8` in MySQL |
|---|---|---|
| Bytes per character | Up to 4 | Up to 3 |
| Emoji and all scripts | Yes | No |

In MySQL the name `utf8` means an incomplete three-byte version. Always write `utf8mb4`, and use it in the PDO connection too: [[03.02 PDO and Prepared Statements]].

## 5. Constraints
| Constraint | Guarantees | Example |
|---|---|---|
| `PRIMARY KEY` | Each row has a unique identifier | `id` |
| `NOT NULL` | A value is always present | `username` |
| `UNIQUE` | No two rows share this value | `users.username`, `users.email`; `(rater_id, listing_id)` |
| `DEFAULT` | A value when none is given | `created_at DEFAULT CURRENT_TIMESTAMP` |
| `CHECK` | A condition holds | `score BETWEEN 1 AND 5` |
| `FOREIGN KEY` | The referenced row exists | `plants.user_id → users.id` |

A `UNIQUE` on **two columns together**, such as `(rater_id, listing_id)`, means "one rating per person per exchange": the database itself refuses a second one.

## 6. Foreign-key rules: what happens on delete
| Rule | When the parent is deleted | Use when |
|---|---|---|
| `ON DELETE CASCADE` | The child rows are deleted too | The child has no meaning alone: a plant's health logs |
| `ON DELETE SET NULL` | The child stays; its link becomes `NULL` | The child should survive: a plant whose collection is deleted |
| `ON DELETE RESTRICT` (default) | The delete is **refused** while children exist | Losing the child would be a mistake |

These are design decisions for the ERD (task DES-06), which must show the rule on every relationship. Examples of the questions to settle:
- Delete a **plant** → its health logs, reminders and photos go with it (`CASCADE`).
- Delete a **collection** → should its plants vanish? Almost certainly not (`SET NULL`).
- Delete a **user** → what happens to ratings they gave other people?

`SET NULL` needs the column to allow `NULL`. `CASCADE` is powerful: one delete can remove many rows, so decide each on purpose.

## 7. Example: three tables
A sketch that follows the table plan in `database/README.md`. The final columns come from the data dictionary (DES-08).

```sql
SET NAMES utf8mb4;
SET FOREIGN_KEY_CHECKS = 0;              -- allow dropping tables in any order
DROP TABLE IF EXISTS plants;
DROP TABLE IF EXISTS collections;
DROP TABLE IF EXISTS users;
SET FOREIGN_KEY_CHECKS = 1;

CREATE TABLE users (
    id            INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    username      VARCHAR(20)  NOT NULL,
    email         VARCHAR(255) NOT NULL,
    password_hash VARCHAR(255) NOT NULL,
    full_name     VARCHAR(100) NOT NULL,
    location      VARCHAR(100) NULL,
    failed_logins TINYINT UNSIGNED NOT NULL DEFAULT 0,
    locked_until  DATETIME NULL,
    created_at    DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    UNIQUE KEY uq_users_username (username),
    UNIQUE KEY uq_users_email (email)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

CREATE TABLE collections (
    id        INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    user_id   INT UNSIGNED NOT NULL,
    name      VARCHAR(60)  NOT NULL,
    is_public TINYINT(1)   NOT NULL DEFAULT 1,
    CONSTRAINT fk_collections_user FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

CREATE TABLE plants (
    id            INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    user_id       INT UNSIGNED NOT NULL,
    collection_id INT UNSIGNED NULL,
    nickname      VARCHAR(60)  NOT NULL,
    photo         VARCHAR(255) NULL,
    acquired_on   DATE NULL,
    health_status ENUM('thriving', 'stable', 'needs_attention', 'sick') NOT NULL DEFAULT 'stable',
    is_public     TINYINT(1) NOT NULL DEFAULT 1,
    CONSTRAINT fk_plants_user FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE,
    CONSTRAINT fk_plants_collection FOREIGN KEY (collection_id) REFERENCES collections(id) ON DELETE SET NULL,
    KEY idx_plants_health (health_status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```
- **Parents before children** when creating; children before parents when dropping.
- Naming constraints (`fk_plants_user`) makes error messages readable.
- InnoDB adds an index on a foreign-key column by itself if none exists.
- The four `health_status` values are exactly the ones used in the mock data, the CSS classes and the tokens.

## 8. Making it re-runnable, and the seed
- **`DROP TABLE IF EXISTS`** at the top, so running the file again starts clean.
- **`seed.sql`** inserts demo data in parent-first order. It is built from the mock data, so wired pages show the same Monty and Goldie.
- **Seed passwords must be hashes.** Generate each with `password_hash()` in PHP and paste the result. A plain-text password in the seed cannot be logged in with.
- Reminder dates in the seed should be **relative to today** (`CURDATE() - INTERVAL 2 DAY`), for the same reason as `mock_date()`.

```bash
mysql -u root plantfolio < database/schema.sql
mysql -u root plantfolio < database/seed.sql
```

## 9. Common mistakes
- **`utf8` instead of `utf8mb4`.**
- **MyISAM tables,** or no `ENGINE` and an old server default. Foreign keys are then silently ignored.
- **Creating a child table before its parent.**
- **A foreign-key column whose type differs from the key it points to** (`INT` vs `INT UNSIGNED`). The constraint cannot be created.
- **No `ON DELETE` rule decided.** Deleting a user then fails with a foreign-key error at the worst moment.
- **`CASCADE` everywhere without thought.**
- **Dates as `VARCHAR`.** Sorting and "due today" then break.
- **No `UNIQUE` on username and email,** relying on a PHP check alone. Two requests at the same instant both pass the check.
- **A schema that only runs once.**
- **Editing tables by hand in phpMyAdmin** and not updating `schema.sql`. The file and the real database drift apart, and a teammate's fresh install is broken.
- **A `CHECK` you assume is enforced.** MariaDB and MySQL 8 enforce it; MySQL 5.7 accepts the syntax and ignores it.

## 10. Exam and viva focus
- **DDL vs DML:** defining structure vs changing data (`INSERT`, `UPDATE`, `DELETE`, `SELECT`).
- **Name the constraint types** and what each guarantees.
- **Referential integrity** and the `ON DELETE` actions.
- **`CHAR` vs `VARCHAR`; `DATE` vs `DATETIME`; `DECIMAL` vs `FLOAT`.**
- **InnoDB vs MyISAM.**
- **What is a transaction? ACID:** atomicity, consistency, isolation, durability.
- **Why are constraints placed in the database when PHP already validates?**
- **Viva:** "What happens to a plant's health logs when I delete the plant, and where is that decided?" · "Why `utf8mb4`?" · "How would a teammate rebuild your database from nothing?"
